Module 3: Spring Core Framework, IoC Container, Bean Lifecycle & AOP

Spring Framework Container Internals AOP Proxy Pitfalls ⏱️ 55 min deep dive Target Roles: SDE-2, SDE-3, Spring Boot Lead, Backend Architect

1. Inversion of Control (IoC) & Dependency Injection (DI)

1.1 The Hollywood Principle: Inversion of Control

In traditional imperative programming, application code directly controls execution flow and resource lifecycles by invoking new OrderServiceImpl().

Inversion of Control (IoC) flips this responsibility (the "Hollywood Principle": "Don't call us, we'll call you"). The framework acts as the orchestrator: it instantiates objects, binds their dependencies, manages their complete lifecycles, and invokes application hooks when necessary.

1.2 Dependency Injection (DI) Pattern

Dependency Injection is the specific design pattern used by Spring to implement IoC. Instead of a component instantiating its collaborators or looking them up from a JNDI registry, collaborators are injected into the component at runtime by the IoC container.

1.3 What is a Spring Bean?

A Spring Bean is simply a plain Java object (POJO) that is instantiated, assembled, and managed by the Spring IoC container based on configuration metadata represented internally by BeanDefinition structures.

3. Component Scanning & Stereotype Annotations

3.1 Component Scanning Mechanics (ASM Bytecode Scanning)

When @ComponentScan(basePackages = "com.myapp") is declared, Spring does not load every .class file into the JVM using the ClassLoader (which would consume excessive Metaspace).

Instead, Spring uses the low-level ASM bytecode manipulation library via ClassPathScanningCandidateComponentProvider. It parses the raw compiled bytecode files on disk directly into an AST, checks if class annotations match @Component or its meta-annotations, and registers a BeanDefinition without initializing the class!

3.2 Stereotype Annotations Hierarchy

  • @Component: General-purpose stereotype annotation for any Spring-managed component.
  • @Service: Marks a service layer component containing core business transactions and logic. Semantically indicates a domain facade.
  • @Repository: Marks persistence/DAO components. Critical feature: Automatically applies Exception Translation via PersistenceExceptionTranslationPostProcessor, translating vendor-specific JDBC or Hibernate exceptions (e.g., SQLException, HibernateException) into Spring's unified, unchecked DataAccessException hierarchy!
  • @Controller / @RestController: Presentation tier handling HTTP requests in Spring MVC / REST endpoints.
  • @Configuration: Declares classes that define beans via @Bean methods. CGLIB Proxying: By default (proxyBeanMethods = true), Spring subclasses configuration classes with CGLIB to ensure direct calls between @Bean methods return the cached singleton instance instead of instantiating new objects.

5. Bean Scopes & The Prototype Injection Hazard

5.1 The 4 Primary Bean Scopes

  • singleton (Default): Exactly one shared instance per Spring IoC container. Stateless, thread-safe design is mandatory.
  • prototype: A new bean instance is created every single time the bean is requested from the container (via getBean() or injection). Critical Warning: Spring manages the initialization of prototype beans, but does NOT manage their destruction! The client code must clean up prototype resources manually.
  • request (Web-aware): One instance created per HTTP request lifecycle; discarded when the HTTP request completes.
  • session (Web-aware): One instance created per user HTTP session.

5.2 The Prototype-Injected-into-Singleton Hazard

When a prototype bean is injected into a singleton bean: 

@Component
@Scope("singleton")
public class OrderService {
    @Autowired
    private TokenGenerator tokenGenerator; // TokenGenerator is @Scope("prototype")!
}

Because the singleton OrderService is instantiated only once at startup, its dependencies are also injected only once! The prototype TokenGenerator is never re-created for subsequent requests, effectively turning it into a singleton and leaking user state!

Resolving Prototype Injection via ObjectProvider or @Lookup Java 
@Component
@Scope("singleton")
public class OrderService {
    @Autowired
    private ObjectProvider<TokenGenerator> tokenProvider; // Solution 1: ObjectProvider

    public void createOrder() {
        TokenGenerator token = tokenProvider.getObject(); // Returns a brand new prototype instance!
        token.process();
    }
}

// Solution 2: Scoped Proxy in the Prototype Definition:
@Component
@Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS)
public class TokenGenerator { ... }

7. Profiles, Properties & Environment Abstraction

  • @Profile("prod"): Restricts bean registration or configuration classes to specific active runtime profiles (activated via spring.profiles.active=prod).
  • @Value("${payment.timeout:5000}"): Injects individual property values from property files with optional default fallbacks.
  • @ConfigurationProperties(prefix = "payment"): Type-safe hierarchical binding of configuration trees into validated Java records/beans with Hibernate Validator support.
  • Environment Abstraction: Represents the current execution profile and external properties source hierarchy (Command Line Arguments $\rightarrow$ JVM System Properties $\rightarrow$ OS Environment Variables $\rightarrow$ Application Properties).

8. Aspect-Oriented Programming (AOP) & Proxy Internals

8.1 Core AOP Terminology

  • Aspect: A modularization of a cross-cutting concern (e.g. logging, transactions, security) defined with @Aspect.
  • Join Point: A specific execution point in the application (in Spring AOP, always a method execution).
  • Pointcut: A predicate expression matching join points: @Pointcut("execution(* com.myapp.service.*.*(..))").
  • Advice: Action taken at a join point:
    • @Before: Executes prior to the join point.
    • @AfterReturning: Executes after normal return without exceptions.
    • @AfterThrowing: Executes if method throws an exception.
    • @After: Executes finally regardless of outcome.
    • @Around: Most powerful advice; wraps the method invocation using ProceedingJoinPoint.proceed() to measure latency or modify arguments/return values.

8.2 Spring AOP Proxy Mechanics: JDK Dynamic vs. CGLIB

Spring AOP is proxy-based. When a bean is targeted by an aspect (or @Transactional, @Async, @Cacheable), the container does not return the raw target bean. It returns a dynamically generated Proxy wrapper:

  • JDK Dynamic Proxy: Used when the target class implements an interface. Creates dynamic proxies using native Java reflection (java.lang.reflect.Proxy).
  • CGLIB Proxy: Generates a runtime subclass of the target class using bytecode enhancement. Since Spring Boot 2.x+, CGLIB is the default proxying mechanism (spring.aop.proxy-target-class=true), eliminating class-casting issues.

9. Real-Time Production Issues & Post-Mortems

🚨 Incident 1: Silent @Transactional Failure via Internal Self-Invocation

Scenario: In an order checkout pipeline, a database query succeeded but subsequent ledger debits threw a NullPointerException. Database records were partially committed, violating ACID atomicity, even though the method had @Transactional!

🔍 Root Cause Analysis (RCA)

The developer invoked the transactional method internally from within the same class: 

@Service
public class OrderService {
    public void processOrder(Order order) {
        // ... some preliminary steps
        this.saveOrderWithTransaction(order); // CRITICAL BUG: Self-invocation via 'this'!
    }

    @Transactional // AOP aspect never intercepts this call!
    public void saveOrderWithTransaction(Order order) {
        orderRepo.save(order);
        ledgerRepo.debit(order.getAmount());
    }
}

Because Spring AOP works via proxies, when an external caller invokes orderService.processOrder(), it calls the outer proxy. However, inside processOrder(), calling this.saveOrderWithTransaction() bypasses the proxy and executes on the raw target object! The transaction interceptor was never triggered, leaving database auto-commit active.

💡 Production Resolution
  • Architectural Separation (Recommended): Move saveOrderWithTransaction() to a separate collaborator bean (e.g., OrderPersistenceService) so calls always pass through the Spring proxy.
  • Self-Injection: Inject the proxy into itself via @Lazy private OrderService self; and invoke self.saveOrderWithTransaction().
🚨 Incident 2: Circular Dependency Boot Failure via Constructor Injection

Scenario: A microservice failed to start in production with BeanCurrentlyInCreationException: Error creating bean with name 'orderService': Requested bean is currently in creation: Is there an unresolvable circular reference?

🔍 Root Cause Analysis (RCA)

OrderService required PaymentService in its constructor, while PaymentService required OrderService in its constructor. While Spring's 3-level cache (singletonFactories) can resolve circular references for setter or field injection, it is mathematically impossible to instantiate either bean via constructor injection because neither constructor can complete without the other instance already existing!

💡 Production Resolution
  • Refactor (Best Practice): Break the circular dependency by introducing a third mediating service (e.g., PaymentNotificationCoordinator) or an event-driven ApplicationEventPublisher.
  • Temporary Hotfix: Add @Lazy to one constructor parameter (e.g. public OrderService(@Lazy PaymentService payment)) so Spring injects a dynamic proxy instead of the real bean at startup.

11. Senior / Staff Technical Interview Q&A

🎯 Q1: How does Spring resolve circular dependencies using the Three-Level Cache?

Answer: In DefaultSingletonBeanRegistry, Spring maintains 3 maps:
1. singletonObjects (Level 1): Fully initialized beans ready for production.
2. earlySingletonObjects (Level 2): Raw instantiated objects exposed before property injection (often for early proxy resolution).
3. singletonFactories (Level 3): Holds ObjectFactory lambdas capable of generating early bean references or wrapping beans in AOP proxies if circular dependencies exist.
When Bean A is instantiated, its factory is placed in Level 3. While injecting Bean B, B looks for A; it finds A's factory in Level 3, moves A to Level 2, injects it into B, and finishes B. Then A completes and moves to Level 1.

🎯 Q2: Why will @Async or @Transactional fail silently if placed on a private method?

Answer: Spring AOP proxies operate by either subclassing the target (CGLIB) or implementing its interfaces (JDK dynamic proxy). A subclass cannot override a private method. When an external or internal caller invokes the method, the call bypasses the proxy entirely or cannot be overridden in the dynamic subclass, so the transaction interceptor or async executor advice is never invoked.

🎯 Q3: What is the purpose of proxyBeanMethods = true in @Configuration?

Answer: When proxyBeanMethods = true (the default), Spring enhances the @Configuration class with CGLIB at startup. If one @Bean method invokes another @Bean method directly in code (e.g. dataSource() called by transactionManager()), the CGLIB proxy intercepts the method call, checks the ApplicationContext cache, and returns the existing singleton bean rather than instantiating a second duplicate instance.
