Module 6: Spring Framework Core Masterclass

In-depth, practical coverage of every requested Spring Framework topic—from IoC and bean creation to scopes, configuration, profiles, and proxy-based AOP. Examples use modern constructor injection and Java configuration, with tough enterprise scenarios and interview-ready explanations.

Suggested study time: 2–3 hours · Examples target Spring Framework 6 / Spring Boot 3. Some scope and proxy behavior depends on application type and configuration.

1. IoC — Inversion of Control

Inversion of Control (IoC) means application code does not control every object’s creation and wiring. Instead, a framework/container creates managed objects, supplies their dependencies, and coordinates lifecycle callbacks. IoC is the broader principle; Dependency Injection is one common way Spring implements it.

Without IoC: OrderService -> new MySqlOrderRepository() -> new StripePaymentClient() With Spring IoC: ApplicationContext creates Repository + PaymentClient -> injects them into OrderService -> manages configured lifecycle and scopes
Tightly coupled versionJava
class OrderService {
    private final MySqlOrderRepository repository =
        new MySqlOrderRepository(); // hard-coded implementation
}
IoC-friendly versionJava
interface OrderRepository {
    void save(Order order);
}

@Service
class OrderService {
    private final OrderRepository repository;

    OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}

Spring can supply a configured repository implementation. The service depends on an abstraction rather than constructing a concrete dependency itself. This improves testability, replaceability, and centralized configuration.

Tough use case — multi-tenant payments: An order service must route payments to different providers by tenant and environment. Hard-coding new StripeClient() across business classes spreads provider logic everywhere. Inject a PaymentGateway interface and choose implementations through configuration or a routing service. IoC makes the object graph configurable; it does not automatically design the routing policy for you.

2. Dependency Injection (DI)

DI is the technique of supplying an object’s collaborators from outside instead of having the object construct or locate them. Spring resolves beans by type, qualifiers, primary preference, and other metadata during context creation.

ApplicationContext | resolves OrderRepository bean | resolves PaymentGateway bean v OrderService(repository, paymentGateway)
Constructor injection — preferred defaultJava
@Service
class CheckoutService {
    private final OrderRepository orders;
    private final PaymentGateway gateway;

    CheckoutService(OrderRepository orders, PaymentGateway gateway) {
        this.orders = orders;
        this.gateway = gateway;
    }
}

With a single constructor, Spring can use it without requiring @Autowired. If multiple candidates implement an interface, use @Qualifier, @Primary, or a deliberate collection/map injection strategy.

Resolve multiple implementations explicitlyJava
@Service("cardGateway")
class CardGateway implements PaymentGateway { /* ... */ }

@Service("bankGateway")
class BankGateway implements PaymentGateway { /* ... */ }

@Service
class PaymentRouter {
    private final PaymentGateway gateway;

    PaymentRouter(@Qualifier("bankGateway") PaymentGateway gateway) {
        this.gateway = gateway;
    }
}
DI is not service location: calling context.getBean(...) throughout business logic hides dependencies and couples code to Spring. Prefer declaring required collaborators in constructors.

3. Spring Bean

A Spring bean is an object instantiated, assembled, and managed by the Spring IoC container. Not every Java object is a Spring bean: an object created with new by application code is not automatically managed unless it is registered or otherwise handed into the container through a supported mechanism.

Ways to register beans

  • Classpath scanning: @Component and its stereotypes.
  • Explicit Java configuration: a method annotated with @Bean.
  • Framework auto-configuration: configuration classes register beans conditionally.
Bean registered using configurationJava
@Configuration
class PaymentConfiguration {
    @Bean
    PaymentGateway paymentGateway() {
        return new BankGateway(/* constructor args */);
    }
}

The bean name defaults to the factory-method name (paymentGateway here), unless explicitly configured. Bean definitions carry metadata such as type, scope, qualifiers, lazy behavior, and lifecycle callbacks.

Tough use case — third-party SDK: You cannot annotate a vendor SDK class with @Component. Register it with @Bean, configure credentials and timeouts from external properties, and inject the SDK wrapper into your services. Keep secrets out of source code.

4. ApplicationContext

ApplicationContext is Spring’s full-featured container interface. It builds on BeanFactory capabilities and adds facilities such as internationalization, event publication, resource loading, and integration with application infrastructure. In typical Spring Boot applications, the context is the central container used during startup.

During startup

  • Loads bean definitions
  • Processes configuration and scans
  • Creates eager singleton beans
  • Applies post-processors and proxies
  • Publishes lifecycle events

During runtime

  • Resolves managed dependencies
  • Provides configured beans
  • Publishes application events
  • Resolves messages and resources
Boot application context access — use sparinglyJava
@Component
class StartupReporter implements ApplicationRunner {
    private final ApplicationContext context;

    StartupReporter(ApplicationContext context) {
        this.context = context;
    }

    @Override
    public void run(ApplicationArguments args) {
        System.out.println("Bean count: " + context.getBeanDefinitionCount());
    }
}

Injecting the context is legitimate for infrastructure or dynamic integration cases, but business services should usually receive specific dependencies directly. A global context lookup can make dependencies invisible and unit tests harder.

5. BeanFactory

BeanFactory is the foundational IoC container contract for retrieving beans and managing their definitions. ApplicationContext extends it with broader application features. For ordinary Spring Boot application code, use the context and normal DI rather than manually using BeanFactory.

CapabilityBeanFactoryApplicationContext
Bean lookup and IoC basicsYesYes (inherits the contract)
Application eventsNot its core contractYes
MessageSource/i18n integrationNot its core contractYes
Typical roleFoundational container abstractionApplication-level container

Historically, BeanFactory is often described as more minimal and lazy in some default behaviors, while ApplicationContext eagerly creates non-lazy singleton beans during refresh. Avoid reducing the distinction to “one creates beans and the other does not”: both participate in bean creation and retrieval; their features and default container behavior differ.

6. Component Scanning

Component scanning discovers candidate classes annotated with component stereotypes in configured base packages and registers bean definitions. In Spring Boot, @SpringBootApplication includes component scanning rooted at the package containing the application class, covering its subpackages by default.

Recommended package layoutJava
com.example.orders
  OrdersApplication.java  // @SpringBootApplication
  controller/
  service/
  repository/
  config/
  client/

Place the application class at a root package above application components. If the class sits in com.example.orders.boot while services are in com.example.orders.service, default scanning may miss sibling packages. Set an explicit scan base only when the package design requires it.

Explicit scanning when neededJava
@SpringBootApplication(scanBasePackages = {
    "com.example.orders",
    "com.example.shared"
})
public class OrdersApplication { }
Tough use case — bean exists in IDE but app fails in production: a shared library component lives outside the application’s scan root, causing NoSuchBeanDefinitionException. Verify package roots, conditional configuration, active profiles, and whether the library exposes an auto-configuration. Avoid broad scanning of unrelated packages, which can create accidental bean collisions.

7. Bean Lifecycle

For a typical singleton bean, Spring first creates the instance, injects dependencies, runs awareness callbacks where applicable, applies BeanPostProcessors before initialization, invokes initialization callbacks, and then applies post-processors after initialization. A proxy may be returned instead of the raw target. On context shutdown, destruction callbacks are invoked for managed singleton beans.

Bean definition -> instantiate -> inject dependencies / populate properties -> aware callbacks (where applicable) -> BeanPostProcessor.beforeInitialization -> @PostConstruct -> InitializingBean.afterPropertiesSet() -> custom init method -> BeanPostProcessor.afterInitialization (proxy may be created) -> bean ready for use -> context shutdown -> @PreDestroy / DisposableBean / custom destroy
Initialization and destruction hooksJava
@Component
class SearchIndexClient {
    @PostConstruct
    void initialize() {
        // Validate config and prepare local resources.
    }

    @PreDestroy
    void close() {
        // Release owned resources gracefully.
    }
}

Use @PostConstruct from jakarta.annotation in modern Spring Boot 3. Initialization callbacks should not assume every other bean has completed all application-level startup work. For long-running startup tasks, consider ApplicationRunner, lifecycle interfaces, or explicit readiness coordination.

Prototype lifecycle caveat: Spring creates and initializes prototype beans but does not manage their full destruction lifecycle after handing them to the caller. If a prototype owns resources, the application must close them or use a different resource-management design.
Tough use case — startup traffic before warm-up: a bean’s constructor succeeds, but its cache is not yet warmed when requests arrive. Bean initialization is not the same as application readiness. Use explicit readiness/lifecycle coordination and ensure the readiness probe stays false until critical startup work is complete.

8. Bean Scope overview

Scope controls how many instances Spring creates and how long the container associates them with a context. Scope does not automatically make an object thread-safe.

ScopeInstance semanticsTypical contextRisk / note
singletonOne instance per bean definition per containerMost services and repositoriesShared across concurrent requests; avoid mutable request-specific fields.
prototypeNew instance each time requested from containerShort-lived stateful helperDestruction is not fully managed by Spring after handoff.
requestOne instance per HTTP requestWeb applicationNot available outside an active request unless appropriately proxied/contextualized.
sessionOne instance per HTTP sessionStateful web sessionCan retain memory for long periods; session concurrency matters.

Use @Scope("singleton"), @Scope("prototype"), @RequestScope, or @SessionScope where appropriate. Singleton is the default scope.

9. Singleton scope

A Spring singleton is one instance per bean definition in a particular IoC container—not necessarily one instance for the entire JVM. Multiple application contexts can each own their own singleton instance. The singleton bean is shared, so its design should normally be stateless or safely concurrent.

Safe stateless serviceJava
@Service
class TaxService {
    BigDecimal calculate(BigDecimal subtotal, BigDecimal rate) {
        return subtotal.multiply(rate);
    }
}
Dangerous mutable request stateJava
@Service
class DangerousCheckoutService {
    private String currentUserId; // shared by all request threads!

    void checkout(String userId) {
        this.currentUserId = userId;
        // Another request can overwrite this field before it is used.
    }
}
Tough use case — cross-customer invoice corruption: a singleton service stores the current invoice/customer in an instance field while two HTTP requests execute concurrently. Request A can observe request B’s value. Keep per-invocation state in local variables, method arguments, or an explicitly scoped/context-propagated mechanism.

10. Prototype scope

A prototype bean is created each time it is requested from the container. However, injecting a prototype directly into a singleton generally resolves the prototype once when the singleton is created; it does not automatically create a fresh prototype for every method call.

Prototype beanJava
@Component
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
class CsvImportJob {
    private final String jobId = UUID.randomUUID().toString();
    String jobId() { return jobId; }
}
Use ObjectProvider for repeated lookupJava
@Service
class ImportCoordinator {
    private final ObjectProvider<CsvImportJob> jobs;

    ImportCoordinator(ObjectProvider<CsvImportJob> jobs) {
        this.jobs = jobs;
    }

    CsvImportJob newJob() {
        return jobs.getObject(); // new prototype instance per lookup
    }
}

Other options include method injection or a scoped proxy depending on the use case. Be deliberate about who owns cleanup for any resources held by prototype instances.

11. Request scope

Request scope creates one bean instance per HTTP request. It is useful for request-local metadata, but request-scoped objects should not be treated as durable storage and should not be accessed from arbitrary background threads after the request ends.

Request-scoped request metadataJava
@Component
@RequestScope
class RequestMetadata {
    private String correlationId;
    public String getCorrelationId() { return correlationId; }
    public void setCorrelationId(String id) { this.correlationId = id; }
}

When a singleton needs a request-scoped dependency, Spring commonly uses a scoped proxy or a provider so the current request’s instance is resolved at use time. A raw request-scoped target cannot be safely used when there is no active web request.

Tough use case — async order processing: a controller reads request-scoped tenant metadata and submits a task to an executor. The worker runs after the HTTP request has completed, so the request scope may no longer be active. Copy required immutable values into the task command explicitly instead of passing a request-scoped bean to background work.

12. Session scope

Session scope creates one bean instance per HTTP session. It can hold session-level workflow state, but should be used sparingly in horizontally scaled services. Large session objects increase memory use, concurrent requests can mutate the same session state, and load-balanced deployments may need sticky sessions or distributed session storage.

Example session-scoped wizard stateJava
@Component
@SessionScope
class CheckoutWizardState {
    private String cartId;
    private int currentStep;

    public String getCartId() { return cartId; }
    public void setCartId(String id) { this.cartId = id; }
    public int getCurrentStep() { return currentStep; }
    public void setCurrentStep(int step) { this.currentStep = step; }
}
Security and scale: do not store passwords, payment secrets, or unbounded object graphs in session state. A session-scoped bean is not automatically thread-safe; multiple browser requests can overlap.

13. Constructor, Setter, and Field Injection

StyleAdvantagesTrade-offsRecommendation
ConstructorExplicit required dependencies, supports final fields, easy unit tests, exposes circular dependencies earlyLarge constructors can reveal too many responsibilitiesPreferred for required dependencies
SetterCan represent optional or reconfigurable dependencyObject may be temporarily incomplete; mutation is possibleUse selectively for optional dependencies
FieldConcise syntaxHidden dependencies, awkward plain unit tests, cannot use final fields normallyAvoid in application service code

13.1 Constructor injection

@Service
class ReportService {
    private final ReportRepository repository;

    ReportService(ReportRepository repository) {
        this.repository = repository;
    }
}

13.2 Setter injection

@Component
class NotificationService {
    private TemplateRenderer renderer;

    @Autowired
    void setRenderer(TemplateRenderer renderer) {
        this.renderer = renderer;
    }
}

13.3 Field injection

@Component
class LegacyReportService {
    @Autowired
    private ReportRepository repository;
}

Field injection can work, but a plain unit test cannot construct the class with all dependencies passed explicitly. Constructor injection makes the required object graph visible and easier to test.

Tough use case — circular dependency: OrderService constructor-injects InvoiceService, which constructor-injects OrderService. Spring cannot build either object because each requires the other first. Avoid the cycle by extracting a third collaborator, reversing an event/command dependency, or moving orchestration to a higher-level service. Do not use lazy injection as a reflexive band-aid.

14. @Component

@Component is the generic stereotype marking a class as a component candidate for scanning. Use it for components that do not fit a more specific architectural role.

@Component
class CurrencyFormatter {
    String format(BigDecimal amount, Currency currency) {
        return currency.getCurrencyCode() + " " + amount;
    }
}

Component scanning registers a bean definition; the annotation does not mean a new instance is created for every injection. Scope and lifecycle still apply.

15. @Service

@Service is a specialized component stereotype commonly used for business/application services. Its primary benefit is semantic clarity and architectural intent; it is still a Spring component and can be discovered by component scanning.

@Service
class RefundService {
    private final PaymentGateway gateway;
    private final RefundRepository refunds;

    RefundService(PaymentGateway gateway, RefundRepository refunds) {
        this.gateway = gateway;
        this.refunds = refunds;
    }

    Refund issue(RefundRequest request) {
        // Validate business rules, call gateway, persist refund state.
        return refunds.save(gateway.refund(request));
    }
}

Put business rules and orchestration here, not in controllers or repository implementations.

16. @Repository

@Repository marks a persistence/data-access component. With the appropriate Spring persistence exception-translation infrastructure, exceptions from supported persistence technologies can be translated into Spring’s consistent DataAccessException hierarchy.

@Repository
class JdbcOrderRepository {
    private final JdbcTemplate jdbc;

    JdbcOrderRepository(JdbcTemplate jdbc) {
        this.jdbc = jdbc;
    }

    Order findById(long id) {
        return jdbc.queryForObject(
            "select id, status from orders where id = ?",
            (rs, row) -> new Order(rs.getLong("id"), rs.getString("status")),
            id
        );
    }
}

Use parameterized queries, transaction boundaries appropriate to the operation, and indexes validated against real query plans. Never concatenate untrusted values into SQL.

17. @Controller

@Controller marks a Spring MVC web component. In classic MVC, handler methods often return view names. For a JSON response from a regular @Controller, use @ResponseBody on the method or class; @RestController combines @Controller and @ResponseBody.

@Controller
class AccountPageController {
    @GetMapping("/account")
    String accountPage(Model model) {
        model.addAttribute("title", "Account");
        return "account"; // resolves a view such as account.html/JSP
    }

    @GetMapping("/api/account/status")
    @ResponseBody
    AccountStatus status() {
        return new AccountStatus("ACTIVE");
    }
}

Controllers should translate HTTP input/output and delegate business behavior to services. Avoid embedding transaction workflows or direct SQL in controller methods.

18. @Configuration

@Configuration declares a class containing bean definitions and configuration methods. In standard full configuration mode, Spring enhances the class so calls between @Bean methods can be intercepted to preserve container-managed bean semantics. With proxyBeanMethods = false, methods are not intercepted; avoid direct calls between factory methods if you need container-managed references.

@Configuration(proxyBeanMethods = false)
class ClientConfiguration {
    @Bean
    Clock applicationClock() {
        return Clock.systemUTC();
    }

    @Bean
    RetryPolicy retryPolicy() {
        return new RetryPolicy(3, Duration.ofMillis(200));
    }
}

Use configuration classes to define infrastructure and third-party objects; keep them small and focused.

19. @Bean

@Bean marks a method whose returned object is registered in the application context. It is especially useful for third-party classes, factory APIs, and explicit wiring. The method name is the default bean name.

@Configuration(proxyBeanMethods = false)
class HttpClientConfiguration {
    @Bean
    HttpClient paymentHttpClient() {
        return HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(2))
            .followRedirects(HttpClient.Redirect.NEVER)
            .build();
    }
}

For production clients, configure request timeouts too, handle retries carefully, and avoid logging credentials. A connection timeout alone does not guarantee a total request deadline.

20. Profiles

Profiles conditionally activate bean definitions and configuration for an environment or deployment mode. Common examples are dev, test, and prod. Profiles are not a secure secret-management system and should not be used to bake production credentials into source control.

@Configuration
class PaymentProviderConfiguration {
    @Bean
    @Profile("dev")
    PaymentGateway sandboxGateway() {
        return new SandboxPaymentGateway();
    }

    @Bean
    @Profile("prod")
    PaymentGateway productionGateway(PaymentProperties properties) {
        return new RealPaymentGateway(properties);
    }
}
# application.yml
spring:
  profiles:
    active: dev

# Override when deploying:
# java -jar app.jar --spring.profiles.active=prod
Tough use case — production accidentally uses sandbox: multiple profile-specific beans or a hard-coded active profile can select the wrong payment provider. Validate the active profile and provider configuration at startup, fail fast if required production settings are missing, and expose safe non-secret configuration indicators to internal diagnostics.

21. Properties

Spring configuration can come from application.properties, YAML, environment variables, JVM system properties, command-line arguments, and other property sources. Higher-precedence sources can override lower-precedence values. Use external configuration for environment-specific values; never commit production secrets.

application.propertiesProperties
payment.gateway.base-url=https://sandbox.example.invalid
payment.gateway.connect-timeout=2s
payment.gateway.read-timeout=3s
payment.gateway.max-attempts=2

Type-safe configuration with @ConfigurationProperties

@ConfigurationProperties(prefix = "payment.gateway")
@Validated
public record PaymentProperties(
    @NotNull URI baseUrl,
    @NotNull Duration connectTimeout,
    @NotNull Duration readTimeout,
    @Min(1) @Max(3) int maxAttempts
) {}

Enable binding with @ConfigurationPropertiesScan or @EnableConfigurationProperties(PaymentProperties.class). Use Bean Validation where applicable. Type-safe configuration improves discoverability and validation compared with scattering raw string lookups throughout services.

22. Environment

Environment exposes active/default profiles and the property-source abstraction. It is useful in infrastructure code for conditional decisions and diagnostics, but injecting it into every service just to read settings can hide dependencies. Prefer a focused @ConfigurationProperties object for related settings.

@Component
class StartupConfigurationCheck implements ApplicationRunner {
    private final Environment environment;

    StartupConfigurationCheck(Environment environment) {
        this.environment = environment;
    }

    @Override
    public void run(ApplicationArguments args) {
        log.info("Active profiles: {}",
            Arrays.toString(environment.getActiveProfiles()));

        String region = environment.getProperty("app.region", "local");
        validateSupportedRegion(region);
    }
}

Never log all environment properties in production: they may include secrets. Log only explicitly safe values, and ensure missing mandatory configuration causes a clear startup failure.

23. AOP — Aspect-Oriented Programming

Aspect-Oriented Programming modularizes cross-cutting concerns that otherwise get repeated across many methods, such as timing, audit metadata, transaction boundaries, and authorization checks. Spring AOP is primarily proxy-based: calls made through a Spring proxy can trigger advice around the target method.

Caller | v Spring AOP proxy |-- before / around advice v Target bean method | v after / after-returning / after-throwing advice

Use AOP for behavior that genuinely applies across a set of join points. Avoid hiding core business rules in broad aspects where execution flow becomes difficult to understand.

24. Aspect

An aspect groups pointcut definitions and advice. In Spring, an aspect is commonly a class annotated with @Aspect and registered as a bean, often via @Component. Add the appropriate Spring AOP dependency, such as spring-boot-starter-aop, when using Spring Boot.

@Aspect
@Component
class ServiceTimingAspect {
    private static final Logger log =
        LoggerFactory.getLogger(ServiceTimingAspect.class);

    @Around("execution(public * com.example.orders.service..*(..))")
    Object timeServiceCall(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.nanoTime();
        try {
            return joinPoint.proceed();
        } finally {
            long elapsedMs = (System.nanoTime() - start) / 1_000_000;
            log.debug("{} completed in {} ms",
                joinPoint.getSignature().toShortString(), elapsedMs);
        }
    }
}

For high-volume systems, consider metrics instrumentation rather than logging every invocation. Never log raw method arguments indiscriminately; they may contain tokens, personal data, or payment details.

25. Pointcut

A pointcut selects which join points should be advised. Spring AOP supports method-execution pointcuts and annotation-based selection, among others. Narrow pointcuts are easier to reason about and safer to deploy than broad package-wide expressions.

// Select public methods in the service package and its subpackages:
@Pointcut("execution(public * com.example.orders.service..*(..))")
void applicationServiceMethods() {}

// Select methods carrying a custom annotation:
@Pointcut("@annotation(com.example.orders.aop.Audited)")
void auditedMethods() {}

Use explicit package boundaries or custom annotations such as @Audited for targeted cross-cutting behavior. Verify pointcuts with tests because an expression that matches too broadly can affect latency and behavior across the service.

26. Advice

Advice is the action run at a selected join point. Common Spring AOP advice types are:

AdviceWhen it runsExample use
@BeforeBefore target methodLightweight validation or contextual logging.
@AfterReturningAfter normal returnRecord successful operation metadata.
@AfterThrowingWhen target throwsRecord failure metrics; exception still propagates unless separately handled.
@AfterAfter completion, success or failureCleanup that must run in either outcome.
@AroundWraps target invocationTiming, retries when appropriate, or controlled invocation.
@Aspect
@Component
class AuditAspect {
    @AfterReturning(
        pointcut = "@annotation(com.example.orders.aop.Audited)",
        returning = "result"
    )
    void auditSuccess(JoinPoint jp, Object result) {
        // Persist safe audit metadata; don't log sensitive result objects.
    }

    @AfterThrowing(
        pointcut = "@annotation(com.example.orders.aop.Audited)",
        throwing = "error"
    )
    void auditFailure(JoinPoint jp, Throwable error) {
        // Record failure type and operation identity.
    }
}
Around advice responsibility: call proceed() exactly as intended. Omitting it skips the target; calling it multiple times repeats the operation. Retrying non-idempotent payments or order creation from generic advice can create duplicate side effects.

27. Proxy

A proxy is an object that intercepts calls and delegates to a target, optionally applying advice. Spring AOP commonly uses JDK dynamic proxies when proxying interfaces and CGLIB subclass proxies when class-based proxying is needed. Exact selection can depend on configuration and framework version.

Proxy typeTypical mechanismConstraint
JDK dynamic proxyImplements one or more interfacesConsumers generally interact through proxied interfaces.
CGLIB proxySubclass of target classCannot subclass final classes; final methods cannot be overridden for interception.

27.1 Self-invocation trap

@Service
class BillingService {
    public void bill() {
        this.writeAudit(); // direct self-call bypasses proxy interception
    }

    @Transactional
    public void writeAudit() {
        // Expected transaction advice may not run on this call.
    }
}

In proxy-based AOP, an external call enters through the proxy. A call through this inside the target normally bypasses that proxy, so annotations such as @Transactional may not apply to self-invocation. Move the advised operation to another bean or redesign the boundary rather than relying on a self-injected proxy workaround.

Tough use case — missing transaction: an engineer adds @Transactional to an internal helper method, calls it from another method on the same object, and assumes the transaction starts. Production partial writes occur because proxy advice was bypassed. Confirm calls cross the Spring proxy and test rollback behavior against the actual transaction manager.

27.2 AOP boundaries and limitations

  • Spring proxy AOP advises method executions invoked through the proxy; it is not full AspectJ weaving.
  • Private methods and self-invocation are common traps for proxy-based interception.
  • Proxying can affect concrete-type assumptions and injection expectations.
  • Keep aspects narrow, observable, and covered by integration tests.

28. End-to-end enterprise use case

Consider an order-processing service that calls a payment provider, writes to a database, and emits audit records. A robust Spring design separates the responsibilities:

HTTP Controller | v OrderService (@Service) -----> PaymentGateway interface | | v v OrderRepository (@Repository) configured SDK @Bean | v Database ApplicationContext wires dependencies Profiles/properties choose environment-specific endpoint AOP records timing/audit metadata around selected service methods
  • IoC/DI: the service receives repository and gateway collaborators through its constructor.
  • Beans/configuration: the SDK client is registered through @Bean and configured from validated properties.
  • Profiles: dev uses a sandbox provider; prod uses the real provider, with startup validation.
  • Scopes: stateless service beans remain singleton; request metadata is request-scoped only when needed and is not passed into background tasks.
  • Lifecycle: clients initialize and close resources using supported lifecycle hooks.
  • AOP: narrowly scoped timing/audit advice records safe metadata without hiding transaction or payment logic.
Architecture warning: AOP logging is not a substitute for business audit guarantees. For financial events, persist audit/outbox records transactionally and deliver them reliably; an aspect that logs to a separate destination can fail independently of the business transaction.

29. Interview questions and fast revision

Q1. IoC vs DI?

IoC is the broader principle of delegating control to a framework/container. DI is a technique that supplies dependencies from outside an object.

Q2. BeanFactory vs ApplicationContext?

ApplicationContext extends BeanFactory and adds application-level capabilities such as events, message resolution, and resource integration.

Q3. What is a Spring bean?

An object whose creation, wiring, and lifecycle are managed by the Spring container.

Q4. Why constructor injection?

It makes required dependencies explicit, supports final fields, improves unit testing, and reveals dependency cycles early.

Q5. Are @Component, @Service, @Repository, and @Controller interchangeable?

They are component stereotypes with different architectural meaning. @Repository also participates in persistence exception translation when the relevant infrastructure is active; @Controller is a web-layer stereotype.

Q6. Singleton scope means one object per JVM?

No. It means one instance per bean definition per Spring container.

Q7. Injecting prototype into singleton: what happens?

Usually one prototype is resolved when the singleton is created. Use ObjectProvider or another lookup mechanism for a new instance on each request.

Q8. Why does ThreadLocal/request scope cause problems in async tasks?

Execution may continue after the request context ends or on a different thread. Pass required context explicitly or use supported propagation mechanisms.

Q9. @Configuration vs @Component with @Bean methods?

Full @Configuration can be enhanced to intercept inter-bean method calls; a lite configuration class or proxyBeanMethods=false does not provide the same interception semantics.

Q10. @Bean vs @Component?

@Component marks a class for scanning. @Bean registers the object returned by a factory method, useful for third-party types and explicit construction.

Q11. How are profiles different from properties?

Properties provide configuration values; profiles activate selected bean definitions/configuration for an environment or mode.

Q12. What is a pointcut vs advice?

A pointcut selects join points; advice defines the action to run at those join points.

Q13. What is an aspect?

A module that groups cross-cutting behavior, typically pointcuts and advice.

Q14. Why might @Transactional not work on a method?

Possible causes include self-invocation bypassing the proxy, visibility/proxy constraints, missing transaction infrastructure, or a mismatch between exception/rollback expectations and configuration.

Q15. What is the proxy doing?

It intercepts calls crossing the proxy boundary so Spring can apply advice such as transactions, security, caching, or custom aspects.

Design rules

  • Constructor-inject required dependencies.
  • Keep singleton services stateless.
  • Use configuration properties for related settings.
  • Use profiles for conditional configuration—not secrets.
  • Use providers for repeated prototype lookup.

Debugging rules

  • For missing beans, inspect scan roots and conditions.
  • For scope errors, inspect proxy/provider behavior.
  • For missing advice, inspect proxy crossing and pointcuts.
