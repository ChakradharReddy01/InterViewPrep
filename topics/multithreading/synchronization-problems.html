Synchronization Problems Masterclass

Learn to distinguish deadlock, starvation, livelock, race conditions, and thread contention. Each problem has a different symptom, root cause, diagnostic approach, and fix. This guide connects the concepts to Java code and production debugging.

Suggested study time: 45–60 minutes · Java 17 examples · Includes diagrams, diagnostic commands, prevention patterns, and interview Q&A.

1. Race condition

A race condition occurs when the correctness of a result depends on the timing or interleaving of concurrent operations. A common example is two threads incrementing the same non-atomic variable: both read the old value, both calculate the same next value, and one update overwrites the other.

Initial count = 10 Thread A: read 10 ── add 1 ── write 11 Thread B: read 10 ── add 1 ── write 11 Expected result after two increments: 12 Actual result in this interleaving: 11 (lost update)
Incorrect shared counterJava
class UnsafeCounter {
    private int count;

    void increment() {
        count++; // read + add + write: not atomic
    }

    int get() {
        return count;
    }
}

1.1 Why count++ is not atomic

Conceptually, count++ involves reading the field, computing a new value, and writing it back. The JVM may interleave these steps with another thread. Marking the field volatile makes reads and writes visible but does not turn the compound increment into one atomic operation.

Three common safe alternativesJava
// Option A: mutual exclusion
class SynchronizedCounter {
    private int count;
    synchronized void increment() { count++; }
    synchronized int get() { return count; }
}

// Option B: atomic read-modify-write
AtomicInteger atomic = new AtomicInteger();
atomic.incrementAndGet();

// Option C: high-contention statistics counter
LongAdder adder = new LongAdder();
adder.increment();
long observed = adder.sum();

Use synchronized/locks when several pieces of state must change together. Use atomic variables for simple atomic state transitions. LongAdder is often suitable for high-contention statistics, but its sum is not a transactional snapshot while updates are happening.

1.2 Visibility vs atomicity vs ordering

ConceptQuestion answeredExample
AtomicityCan another thread observe a partially completed operation?AtomicInteger.incrementAndGet() is atomic.
VisibilityWhen one thread writes, when can another see the write?A volatile write happens-before a subsequent read of that field.
OrderingCan operations be observed in an unexpected order?Synchronization and volatile establish specified happens-before relationships.
Interview trap: volatile int count; count++; is still a race. Volatile does not make read-modify-write sequences atomic.

2. Deadlock

A deadlock occurs when a group of threads waits forever because each thread is waiting for a resource held by another thread in that group. The threads cannot make progress because the required locks will not be released until the waiting threads proceed.

Thread A owns Lock 1 Thread B owns Lock 2 | | v v waits for Lock 2 <-----------------> waits for Lock 1 A cannot proceed until B releases Lock 2. B cannot proceed until A releases Lock 1.

2.1 The four Coffman conditions

These four conditions must all hold for a classic resource deadlock:

  1. Mutual exclusion: at least one resource cannot be shared simultaneously.
  2. Hold and wait: a thread holds one resource while waiting for another.
  3. No preemption: resources cannot simply be taken away; the holder releases them.
  4. Circular wait: there is a cycle in which each thread waits for a resource held by the next.

2.2 Reproducing the lock-ordering bug

Dangerous pattern — do not run in a production processJava
Object accountA = new Object();
Object accountB = new Object();

Thread t1 = new Thread(() -> {
    synchronized (accountA) {
        sleepBriefly();
        synchronized (accountB) {
            System.out.println("A then B");
        }
    }
});

Thread t2 = new Thread(() -> {
    synchronized (accountB) {
        sleepBriefly();
        synchronized (accountA) {
            System.out.println("B then A");
        }
    }
});

t1.start();
t2.start(); // Both can wait forever if each acquired its first lock.

2.3 Prevention: global lock ordering

When a workflow must lock multiple accounts/resources, assign a stable ordering (for example, account ID) and always acquire locks in that order, regardless of argument order.

Lock resources in deterministic orderJava
void transfer(Account from, Account to, BigDecimal amount) {
    if (from == to) {
        return; // or handle self-transfer according to domain rules
    }

    Account first = from.id().compareTo(to.id()) < 0 ? from : to;
    Account second = first == from ? to : from;

    synchronized (first) {
        synchronized (second) {
            from.debit(amount);
            to.credit(amount);
        }
    }
}

Other strategies include avoiding nested locks, reducing the number of shared resources, using a single lock for a small invariant, or using timed tryLock with a carefully designed release-and-retry strategy. Timeouts detect or limit indefinite waiting; they do not automatically make a business operation correct.

Production pattern: payment requests freeze and request latency climbs. A thread dump reveals one group of request threads waiting for account locks in opposite orders. Fix the acquisition order, add deadlock diagnostics, and test reverse-direction transfers under concurrency.

3. Starvation

Starvation occurs when a thread is continually denied the CPU, a lock, a connection, or another required resource while other threads keep making progress. Unlike deadlock, the system may still be doing useful work; the problem is that one or more threads repeatedly lose access.

3.1 Common causes

  • Unfair lock acquisition: newly arriving threads repeatedly acquire a lock before older waiters.
  • Long critical sections: a thread holds a shared lock for too long, leaving others waiting.
  • Priority imbalance: higher-priority runnable threads can dominate lower-priority work in some environments; Java thread priority is only a scheduling hint and is not portable fairness control.
  • Thread-pool starvation: all workers block on tasks that require the same exhausted pool to make progress.
  • Resource-pool starvation: a subset of requests monopolizes database connections or permits.

3.2 Example: tasks starved in a constrained pool

Pool has 4 workers worker 1: parent task waits for child task worker 2: parent task waits for child task worker 3: parent task waits for child task worker 4: parent task waits for child task queue: child 1, child 2, child 3, child 4 All workers are occupied by waiting parents. No worker can execute the queued children.

This is commonly called thread-pool starvation and can become a starvation deadlock. Avoid blocking on child tasks submitted to the same small pool; use asynchronous composition, separate pools by workload, or redesign dependencies.

3.3 Mitigation

  • Use fair locks only where fairness matters: new ReentrantLock(true) can reduce barging, often with throughput trade-offs. Fairness is not a universal guarantee of end-to-end business fairness.
  • Keep critical sections short; do not perform network calls or blocking I/O while holding application locks.
  • Use bounded work queues, sensible timeouts, and separate pools for unrelated workloads.
  • Track wait time per task/request, not just average throughput.
Important: making a lock fair can reduce one source of starvation, but it cannot fix a thread that is waiting on the wrong resource, a dependency cycle, or an overloaded downstream system.

4. Livelock

Livelock occurs when threads remain active and repeatedly react to one another, but their actions prevent forward progress. Unlike a deadlock, the threads are not simply frozen waiting for locks; they keep running, retrying, yielding, or changing state.

Thread A: detects conflict -> backs off Thread B: detects conflict -> backs off Both retry at nearly the same time Both collide again Both back off and retry forever CPU activity continues, business progress does not.

4.1 Real-world analogy

Two people meet in a narrow hallway. Both step left to be polite; both then step right; both repeat the same reaction and never pass. In software, coordinated retries can create the same pattern.

4.2 Prevention: bounded retries and randomized backoff

Retry with exponential backoff and jitterJava
boolean executeWithRetry() throws InterruptedException {
    int maxAttempts = 5;

    for (int attempt = 0; attempt < maxAttempts; attempt++) {
        if (tryPerformOperation()) {
            return true;
        }

        long capMillis = Math.min(1_000L, 50L << attempt);
        long delayMillis = ThreadLocalRandom.current()
                .nextLong(capMillis + 1);

        Thread.sleep(delayMillis);
    }

    return false; // report a controlled failure or schedule a later retry
}

Jitter spreads retries over time so competing workers are less likely to collide again simultaneously. Always use a retry limit, an overall deadline, and an idempotency strategy where the operation may have partially succeeded. Restore interruption or propagate InterruptedException; do not swallow cancellation signals.

Production pattern: several application replicas retry a distributed lock every fixed 50 ms. They wake together, collide together, and make no progress. Exponential backoff with random jitter, a bounded deadline, and clear lock ownership/lease semantics help break the synchronized retry cycle.

5. Thread contention

Thread contention happens when multiple threads compete for the same limited resource—often a monitor or lock. Contention is not automatically a correctness bug; it becomes a performance problem when waiting consumes significant time, throughput falls, or tail latency grows.

Many request threads | | | | | v v v v v +-------------------+ | One shared lock | <-- one thread enters +-------------------+ | | | | v v v v waiting / parked threads Result: serialized work despite many request threads.

5.1 Symptoms and measurements

  • Throughput stops increasing as thread count increases.
  • p95/p99 latency rises while many threads are BLOCKED, WAITING, or parked.
  • CPU can be high under spin/retry contention, or low when most threads are blocked. CPU alone does not diagnose contention.
  • Profiles show time in lock acquisition, monitor entry, condition waits, or a hot synchronized method.

5.2 Common sources

  • One global lock around unrelated data.
  • Long synchronized blocks that include logging, serialization, database calls, or HTTP requests.
  • High-frequency writes to a shared counter or cache entry.
  • Too many threads competing for a small database connection pool or semaphore.
  • Excessive retries that amplify load during a dependency slowdown.

5.3 Reduce contention

Shorten the critical section

Compute and validate outside the lock where safe. Keep only the invariant-preserving state change inside.

Reduce shared state

Use immutable data, thread confinement, or local accumulation when possible.

Partition work

Lock striping or partitioned data can let independent keys proceed concurrently.

Choose suitable primitives

Use atomic variables for simple state, read/write locks for suitable read-heavy access, and concurrent collections for shared structures.

Bad: slow I/O while holding a lockJava
synchronized (cacheLock) {
    CacheEntry entry = cache.get(key);
    RemoteService.refresh(entry); // slow network call blocks every lock user
    cache.put(key, entry);
}
Better: snapshot under lock, perform I/O outside, then validate/updateJava pattern
CacheEntry snapshot;
long version;

synchronized (cacheLock) {
    snapshot = cache.get(key).copy();
    version = cache.versionOf(key);
}

CacheEntry refreshed = remoteService.refresh(snapshot); // no shared lock held

synchronized (cacheLock) {
    if (cache.versionOf(key) == version) {
        cache.put(key, refreshed);
    } else {
        // Another writer changed the entry: reconcile or retry.
    }
}

This optimistic pattern is illustrative: the version check and update must be atomic with respect to competing writers, and the copied state must be safe to use outside the lock. Real code may use a per-key lock, a versioned value, or a database compare-and-set.

6. Production diagnosis toolkit

6.1 Capture and inspect thread dumps

CommandsShell / JVM
# Identify the JVM process
jcmd -l

# Capture a thread dump (replace PID)
jcmd <PID> Thread.print

# Alternative on supported JDK installations
jstack -l <PID>

Capture several thread dumps a few seconds apart. A single dump is a snapshot; repeated dumps help distinguish a persistent deadlock from a transient slow operation or repeated contention. Protect dumps because they may contain class names, request details, and other operational information.

6.2 Programmatic deadlock detection

ThreadMXBeanJava
import java.lang.management.ManagementFactory;
import java.lang.management.ThreadInfo;
import java.lang.management.ThreadMXBean;

ThreadMXBean bean = ManagementFactory.getThreadMXBean();
long[] ids = bean.findDeadlockedThreads();

if (ids != null) {
    ThreadInfo[] info = bean.getThreadInfo(ids, true, true);
    for (ThreadInfo thread : info) {
        System.err.println(thread);
    }
}

findDeadlockedThreads() can detect cycles involving object monitors and ownable synchronizers on supported JVMs. This is a diagnostic aid, not a substitute for capturing thread dumps and investigating the application-level lock order.

6.3 What to look for

SymptomLikely directionNext step
Explicit “Found one Java-level deadlock” reportDeadlockMap each thread's held lock and requested lock; break the cycle.
One thread waits much longer than peersStarvation or unfair accessMeasure wait duration, fairness, pool saturation, and dependency limits.
High CPU with repeated retries, little progressLivelock or spin/retry loopInspect retry cadence, collision patterns, backoff, and idempotency.
Many threads blocked at the same monitorContentionFind the lock owner and shorten or partition the critical section.

8. Interview questions and answer outlines

Q1. What are the four Coffman conditions?

Mutual exclusion, hold and wait, no preemption, and circular wait. A classic deadlock requires all four; prevention strategies aim to break at least one.

Q2. Why doesn't volatile fix count++?

Volatile provides visibility and ordering guarantees for field access, but increment is a compound read-modify-write operation. Use an atomic type or synchronization.

Q3. Deadlock vs starvation?

In deadlock, a cycle of waiting prevents the involved threads from progressing. In starvation, other work may continue while one thread repeatedly fails to obtain CPU or a resource.

Q4. Deadlock vs livelock?

Deadlocked threads wait without progress. Livelocked threads keep executing or retrying, but their interactions prevent useful progress.

Q5. Is contention always a bug?

No. Some contention is expected when sharing a resource. It becomes a performance concern when wait time reduces throughput or violates latency goals.

Q6. How does global lock ordering prevent deadlock?

If every thread acquires locks in the same strict order, the circular-wait cycle cannot form for those locks.

Q7. Can fair locks eliminate starvation?

They can reduce starvation caused by unfair lock acquisition, but they cannot solve starvation caused by thread-pool exhaustion, downstream limits, scheduling, or dependency cycles. Fairness may reduce throughput.

Q8. How do you mitigate livelock?

Use randomized exponential backoff, bounded retries, deadlines, and a coordination strategy that prevents all contenders from retrying in lockstep.

Q9. How would you diagnose a production deadlock?

Capture thread dumps with jcmd or jstack, identify each thread's held and requested locks, check the JVM deadlock report, then trace the lock order back to the code path.

Q10. How do you reduce lock contention?

Shorten critical sections, move I/O outside locks where safe, reduce shared mutable state, partition data, and use atomic or concurrent data structures when their semantics fit.

Q11. What is thread-pool starvation deadlock?

All workers are occupied by tasks waiting for child tasks queued in the same pool. No worker remains to execute the children. Avoid blocking task dependency cycles.

Q12. Why should retries use jitter?

Identical fixed delays cause contenders to wake simultaneously and collide again. Randomized delays spread retries over time and reduce synchronized collisions.
