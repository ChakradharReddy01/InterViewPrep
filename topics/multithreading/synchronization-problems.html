Module 2: Synchronization Hazards: Deadlock, Starvation & Livelock

Concurrency Hazards Senior Systems Production Outages & RCA ⏱️ 45 min deep dive Target Roles: SDE-2, SDE-3, Principal Architect

1. Deadlock & The 4 Coffman Conditions

1.1 What is a Deadlock?

A Deadlock occurs when two or more threads are permanently blocked, each waiting for a lock held by another thread in the group. 

[ Thread 1 ] ---holds Lock A---> waiting for Lock B ---+
      ^                                                |
      |                                                v
      +--- waiting for Lock A <---holds Lock B--- [ Thread 2 ]

1.2 The 4 Coffman Conditions

A deadlock can occur only if all four of the following conditions hold simultaneously:

  1. Mutual Exclusion: At least one resource must be held in a non-shareable mode.
  2. Hold and Wait: A thread must hold at least one resource while waiting to acquire additional resources held by other threads.
  3. No Preemption: Resources cannot be forcefully taken away from a thread; they can only be released voluntarily by the holding thread.
  4. Circular Wait: A closed chain of threads exists such that each thread holds at least one resource needed by the next thread in the chain.

1.3 Preventing Deadlocks: Global Resource Ordering

The most reliable enterprise strategy to eliminate deadlocks is to break the Circular Wait condition by enforcing a strict global lock acquisition order:

Deadlock-Free Fund Transfer with Resource Ordering Java 
public void transferMoney(Account fromAccount, Account toAccount, BigDecimal amount) {
    // 1. Enforce a deterministic global locking order based on account ID:
    Account firstLock = fromAccount.getId().compareTo(toAccount.getId()) < 0 ? fromAccount : toAccount;
    Account secondLock = fromAccount.getId().compareTo(toAccount.getId()) < 0 ? toAccount : fromAccount;

    // 2. Always acquire locks in identical global order across all threads:
    synchronized (firstLock) {
        synchronized (secondLock) {
            fromAccount.debit(amount);
            toAccount.credit(amount);
        }
    }
}

2. Thread Starvation & Livelock

2.1 Thread Starvation

Starvation occurs when a runnable thread is perpetually denied CPU time-slices or lock acquisition because "greedy" threads or higher-priority threads consistently monopolize the resources.

  • Causes: Thread priority abuse (Thread.setPriority()), non-fair locking mechanisms where new threads "barge in" ahead of waiting threads, or long-running critical sections.
  • Solutions: Use fair synchronization primitives (e.g., new ReentrantLock(true)) and standard priority levels.

2.2 Livelock

Unlike deadlock (where threads are parked and frozen), in a Livelock, threads are actively executing and burning CPU, but constantly reacting to each other's state changes in a way that prevents any forward progress!

Real-world analogy: Two polite people trying to pass each other in a narrow hallway, simultaneously stepping to the left, then simultaneously stepping to the right, over and over again without ever walking past.

Resolving Livelock with Exponential Backoff + Random Jitter Java 
// Preventing livelock during transaction retry collisions:
public void executeWithJitterRetry() {
    int attempts = 0;
    while (attempts < MAX_RETRIES) {
        if (tryAcquireResources()) {
            performWork();
            return;
        }
        attempts++;
        // Random jitter breaks synchronized collision loops:
        long sleepMs = (long) (Math.pow(2, attempts) * 100) + ThreadLocalRandom.current().nextInt(50);
        Thread.sleep(sleepMs);
    }
}

3. Thread Contention & Performance Degradation

Thread Contention occurs when multiple threads attempt to access a synchronized monitor or lock at the same instant.

  • Symptoms: CPU utilization spikes, application throughput drops, and threads spend >90% of their lifecycle parked in BLOCKED or WAITING.
  • Solutions:
    1. Reduce Lock Hold Time: Move I/O, validations, and computation completely outside the synchronized block.
    2. Lock Striping: Instead of locking an entire structure, lock independent partitions (as demonstrated by ConcurrentHashMap).
    3. Read/Write Splitting: Replace mutual exclusion with ReentrantReadWriteLock or StampedLock.
    4. Lock-Free Alternatives: Migrate to atomic variables (AtomicLong, LongAdder).

4. Real-Time Production Issues & Post-Mortems

🚨 Incident 1: Cross-Account Deadlock Freezing All Payment Gateways

Scenario: A peer-to-peer mobile payments platform froze during high-traffic evening hours. Thread dumps revealed over 180 Tomcat worker threads in BLOCKED state, resulting in complete outage.

🔍 Root Cause Analysis (RCA)

The transfer method locked accounts in the order they were passed in arguments: synchronized(from) { synchronized(to) { ... } }.

User 1 transferred $10 from Account A to Account B (Thread 1 locked A, waiting for B). Simultaneously, User 2 transferred $5 from Account B to Account A (Thread 2 locked B, waiting for A). A circular wait was formed, deadlocking both worker threads. Subsequent transfers involving Account A or B also deadlocked, triggering a cascading thread freeze.

💡 Production Resolution

Implemented strict Account ID ordering before acquiring locks, mathematically eliminating circular wait dependencies.

🚨 Incident 2: High-CPU Livelock in Distributed Lock Lease Negotiation

Scenario: A scheduled reconciliation job spiked CPU to 100% across all Kubernetes pods. No database records were updated, yet all pods remained in tight loops.

🔍 Root Cause Analysis (RCA)

When a pod failed to acquire a distributed lock, it released its partial resources and immediately slept for an identical fixed interval of 50ms. All 10 pods woke up on the exact same millisecond, re-attempted the lock, collided again, and released again in an infinite livelock cycle.

💡 Production Resolution

Injected exponential backoff with randomized jitter into the retry loop to desynchronize thread wakeups.

6. Senior / Staff Technical Interview Q&A

🎯 Q1: How can tryLock() prevent deadlocks?

Answer: ReentrantLock.tryLock() attempts to acquire a lock without blocking indefinitely. If a thread acquires Lock A but fails to acquire Lock B within a specified timeout (e.g. lockB.tryLock(500, TimeUnit.MILLISECONDS)), the thread can voluntarily release Lock A, back off, and retry later. This breaks the Hold and Wait condition, preventing permanent deadlocks.

🎯 Q2: What is the fundamental difference between a Deadlock and a Livelock?

Answer: In a Deadlock, threads are blocked in the BLOCKED or WAITING state, consuming 0% CPU while permanently waiting for locks held by each other. In a Livelock, threads are actively running in the RUNNABLE state, consuming high CPU cycles while continuously modifying their state in response to other threads without making any forward business progress.
