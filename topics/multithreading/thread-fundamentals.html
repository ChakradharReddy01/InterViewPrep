Module 2: Thread Fundamentals, OS Scheduling & Future Architecture

Multithreading OS & JVM Internals Production Incidents ⏱️ 45 min deep dive Target Roles: SDE-2, SDE-3, Systems / Backend Architect

1. Operating System Mechanics: Process vs. Thread

1.1 Process Architecture

An OS Process is an execution container providing isolated resources (private virtual memory address space, page tables, file descriptors, security credentials, and environment variables).

  • Memory Isolation: Processes cannot access each other's memory directly. If Process A crashes due to a segmentation fault, Process B is completely unaffected.
  • Inter-Process Communication (IPC): Sharing data between processes requires heavy OS-mediated mechanisms such as Unix Domain Sockets, Pipes, Shared Memory segments (POSIX), or TCP loopbacks.
  • Process Control Block (PCB): The OS kernel maintains a heavy data structure tracking registers, page tables, and I/O status.

1.2 Thread Architecture (Lightweight Process)

A Thread is the smallest schedulable unit of CPU execution within a process.

  • Shared Resources: All threads within the same JVM process share the exact same Heap Memory, Metaspace, and File Descriptors.
  • Per-Thread Private Resources: Each thread maintains its own private JVM Stack (for local variables and method invocation frames), Program Counter (PC) Register, and CPU register state.
  • Thread Control Block (TCB): Maintained by the kernel to record thread ID, CPU affinity, priority, and scheduling state.

1.3 The Real Cost of Context Switching

When a CPU core switches from executing Thread 1 to Thread 2:

  1. Direct Overhead: The CPU traps into kernel mode, saves Thread 1's hardware register state (PC, stack pointer, general-purpose registers) into its TCB, and loads Thread 2's registers.
  2. Indirect Cache Invalidation Overhead (The Big Killer): The hardware CPU L1/L2 data and instruction caches become "cold". The new thread experiences massive cache misses, forcing the CPU pipeline to stall while waiting for main RAM memory fetches. Having too many platform threads (e.g. 5,000+) causes thrashing, where the CPU spends more time swapping thread contexts than running application logic!

2. Thread Lifecycle & The 6 JVM Thread States

While the underlying OS kernel typically has 3 primary states (Ready, Running, Waiting), the Java Virtual Machine defines exactly 6 states in the java.lang.Thread.State enum:

                                 |  Thread.start()
                                 v
                         +---------------+
                         |   RUNNABLE    | <-- (Ready in OS queue or executing on CPU)
                         +---------------+
                            /    |    \
       acquire monitor lock/     |     \  Thread.sleep(t) / Object.wait(t) /
                          /      |      \ LockSupport.parkNanos()
                         v       |       v

                         \       |       /

                           \     |     /

2.1 Exhaustive Breakdown of Each State

JVM State Underlying Cause / Trigger Consuming CPU? How to Exit the State
NEW Thread t = new Thread() has been instantiated, but t.start() has not yet been invoked. No Calling start()
RUNNABLE Actively executing instructions on a CPU core OR waiting in the OS run-queue for a CPU time-slice. YES Preemption, yielding, entering lock/I/O wait, or method completion
BLOCKED Waiting specifically to acquire an intrinsic object monitor lock inside a synchronized block or method. No (OS parked) The holding thread exits the synchronized block and releases the monitor
WAITING Waiting indefinitely for another thread to perform a specific action. Triggered by Object.wait(), Thread.join(), or LockSupport.park() (e.g. waiting on a ReentrantLock). No (OS parked) Another thread calls notify(), notifyAll(), or LockSupport.unpark(t)
TIMED_WAITING Waiting for a specified duration. Triggered by Thread.sleep(ms), Object.wait(ms), Thread.join(ms), or LockSupport.parkNanos(). No (OS timer) Specified time elapses, or notification / interrupt is received
TERMINATED The thread's run() method completed normally or threw an unhandled runtime exception. No Thread is dead; cannot be restarted via start() (throws IllegalThreadStateException)
⚠️ Senior Distinction: BLOCKED vs. WAITING

In thread dumps, engineers often confuse BLOCKED and WAITING:
- BLOCKED applies strictly to intrinsic Java monitors (synchronized). A thread is blocked trying to cross a lock boundary.
- WAITING occurs when a thread has already acquired a lock, but voluntarily surrendered it (via wait()) or is waiting on a higher-level JUC synchronization primitive (like ReentrantLock, CountDownLatch, or CompletableFuture).

3. Thread Creation Mechanisms: Thread vs. Runnable vs. Callable & Future

3.1 Mechanism 1: Extending java.lang.Thread

public class WorkerThread extends Thread {
    @Override
    public void run() {
        System.out.println("Executing on: " + Thread.currentThread().getName());
    }
}
// Launching:
new WorkerThread().start(); // Calls native JVM start0()

Architectural Limitation: Java does not support multiple class inheritance. If a class extends Thread, it cannot extend any other domain class. Furthermore, it tightly couples the unit of work (the task) to the execution mechanism (the thread).

3.2 Mechanism 2: Implementing java.lang.Runnable

@FunctionalInterface
public interface Runnable {
    void run();
}

// Decoupled task:
Runnable task = () -> System.out.println("Running task: " + Thread.currentThread().getName());
new Thread(task).start();

Pros: Clean separation of concerns. Can be submitted to thread pools (ExecutorService).
Cons: run() returns void (cannot return a computation result) and cannot throw checked exceptions.

3.3 Mechanism 3: Implementing Callable<V>

@FunctionalInterface
public interface Callable<V> {
    V call() throws Exception;
}

Introduced in Java 5 to solve the limitations of Runnable: it is parameterized to return a computed value $V$ and is permitted to throw checked exceptions.

3.4 The Future<V> Interface & FutureTask<V>

A Future<V> represents the pending result of an asynchronous computation:

Executing Callable with Future Java 
ExecutorService executor = Executors.newFixedThreadPool(4);

Callable<OrderSummary> task = () -> {
    // Simulate external inventory check
    return inventoryClient.fetchStock("SKU-991");
};

Future<OrderSummary> future = executor.submit(task);

// Non-blocking status check:
if (!future.isDone()) {
    System.out.println("Inventory check still calculating...");
}

try {
    // CRITICAL: Always use timed get() in production to prevent thread hanging!
    OrderSummary summary = future.get(3, TimeUnit.SECONDS);
    System.out.println("Result received: " + summary);
} catch (TimeoutException e) {
    future.cancel(true); // Interrupt the running thread
    logger.warn("Inventory check timed out after 3 seconds");
} catch (ExecutionException e) {
    logger.error("Callable threw an exception: ", e.getCause());
}

4. Real-Time Production Issues & Post-Mortems

🚨 Incident 1: "OutOfMemoryError: unable to create new native thread" Outage

Scenario: A payment notification service handling 4,000 webhooks/sec suddenly crashed with java.lang.OutOfMemoryError: unable to create new native thread. The JVM had 12GB of free heap, yet the entire process crashed and Linux prevented SSH access.

🔍 Root Cause Analysis (RCA)

A junior engineer handled incoming webhook alerts by writing: new Thread(() -> sendWebhook(payload)).start();. Under peak traffic, over 15,000 threads were spawned in 3 seconds. Each platform thread allocated a 1MB virtual stack and required a kernel PID in the OS process table.

The system hit the Linux user process limit defined in /etc/security/limits.conf (nproc = 4096). When the JVM requested the OS to spawn thread #4097, the OS kernel refused the clone() system call with error EAGAIN, crashing the JVM.

💡 Production Resolution
  • Zero Manual Thread Instantiation: Strictly banned new Thread() in SonarQube rules.
  • Bounded Thread Pools: Replaced with a tuned ThreadPoolExecutor using a bounded ArrayBlockingQueue and an explicit rejection policy (CallerRunsPolicy or metric-monitored AbortPolicy).
  • OS Limit Adjustment: Tuned Linux OS limits: ulimit -u 65535 in the Docker/systemd service configuration.
🚨 Incident 2: Total Tomcat Thread Starvation via Untimed Future.get()

Scenario: An e-commerce search service's p99 latency jumped from 25ms to infinity. Tomcat's max thread pool (200 threads) became 100% occupied. All incoming HTTP requests were queued and rejected with 504 Gateway Timeouts.

🔍 Root Cause Analysis (RCA)

To fetch pricing, the controller called: Future<Price> future = pricingExecutor.submit(pricingTask); Price p = future.get(); // BLOCKS INDEFINITELY!.

A downstream pricing vendor suffered a network partition and failed to respond. Because future.get() was invoked without a timeout, Tomcat worker threads remained parked in WAITING indefinitely waiting for a notification that never arrived. Within 20 seconds, all 200 Tomcat worker threads were trapped in future.get(), paralyzing the application.

💡 Production Resolution

Mandated timeouts on every blocking operation across the codebase:

// PRODUCTION RULE: Never use untimed future.get()
Price p = future.get(500, TimeUnit.MILLISECONDS);

6. Senior / Staff Technical Interview Q&A

🎯 Q1: What happens if you call run() instead of start() on a Thread?

Answer: Calling run() executes the method synchronously on the current calling thread, behaving like any standard Java method call. No new OS thread or stack frame is created. Calling start() invokes the native method start0(), which requests the OS kernel to spawn a new native thread with its own call stack and invokes run() asynchronously on that new thread.

🎯 Q2: Can a terminated thread be restarted by calling start() again?

Answer: No. Once a thread reaches the TERMINATED state, its native OS thread context has been deallocated. Calling start() again throws IllegalThreadStateException. The JVM explicitly checks if (threadStatus != 0) throw new IllegalThreadStateException(); at the very beginning of Thread.start().

🎯 Q3: What is the internal difference between Thread.sleep() and Object.wait()?

Answer: 1. Lock Retention: Thread.sleep() puts the current thread into TIMED_WAITING but retains all monitor locks it currently holds. In contrast, Object.wait() releases the monitor lock of the object it is called upon, allowing other waiting threads to acquire the lock.
2. Monitor Requirement: Object.wait() must be called from within a synchronized block on that specific object; otherwise, it throws IllegalMonitorStateException. Thread.sleep() can be called from anywhere.

🎯 Q4: How does future.cancel(true) actually interrupt a running thread?

Answer: If passed true, cancel() calls Thread.interrupt() on the worker thread executing the task. It does not forcefully kill the thread. It sets the thread's interrupt status flag. If the thread is currently blocked in an interruptible method (such as sleep(), wait(), or socket I/O), an InterruptedException is thrown. If the thread is executing pure CPU calculations, it will continue running unless the code explicitly checks Thread.currentThread().isInterrupted() and exits voluntarily.
