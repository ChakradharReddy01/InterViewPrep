Threads, Lifecycle, Runnable, Callable & Future

A beginner-friendly but technically deep guide to how Java work runs concurrently, how to retrieve results, and how to diagnose common production failures. Learn the idea, see the code, then practise explaining it in interviews.

OS + JVM internalsJava code examplesVisual explanationsProduction incidentsInterview-ready answers
The big picture: A process is a running program with resources. A thread is an execution path inside that process. Runnable describes work, Callable describes work that returns a value, and Future represents a result that may become available later.

1. Process vs Thread

Imagine a restaurant. The process is the restaurant: building, kitchen, equipment, and inventory. Threads are the workers doing tasks inside it. Workers share the restaurant's kitchen and equipment, but each worker has their own immediate task and working notes.

Process

  • An instance of a running program.
  • Has its own virtual address space and OS-managed resources.
  • Usually isolated from other processes for safety.
  • Processes communicate through mechanisms such as sockets, pipes, or shared memory.

Thread

  • An execution path within a process.
  • Threads in one JVM share heap objects, class metadata, and many process resources.
  • Each thread has its own stack, program counter, and execution state.
  • Shared mutable objects require coordination to avoid race conditions.
ONE JAVA PROCESS / JVM ┌─────────────────────────────────────────────────────────────┐ │ Shared heap: Customer, Order, cache, arrays, shared objects │ │ Shared class metadata, open process resources │ │ │ │ Thread A Thread B Thread C │ │ own stack own stack own stack │ │ local variables local variables local variables │ │ call frames call frames call frames │ └─────────────────────────────────────────────────────────────┘ Shared objects are useful — but concurrent mutation can race.

Real example: order processing

A Spring Boot service receives an order. One thread handles the HTTP request while another task checks inventory. Both may reference the same Order object. If both mutate its state without a clear ownership rule or synchronization, one update may overwrite another.

Interview distinction: A process is a resource/isolation boundary; a thread is an execution unit. Thread communication through shared memory is efficient, but shared mutable state creates concurrency hazards. Threads are not automatically faster: CPU work is limited by available cores, and excessive threads add scheduling and memory overhead.

2. Thread lifecycle: the journey of a thread

A Java thread moves through a defined set of JVM states. These states describe what the JVM knows about the thread; they are not a one-to-one copy of every operating-system scheduler state.

new Thread(task) │ ▼ [ NEW ] │ start() ▼ [ RUNNABLE ] ───── run() completes / uncaught failure ───► [ TERMINATED ] │ │ │ │ │ └── sleep(timeout), wait(timeout), join(timeout), parkNanos │ │ ▼ │ │ [ TIMED_WAITING ] │ │ │ timeout / notify / interrupt │ │ ▼ │ └── wait(), join(), park ─► [ WAITING ] ────────────┐ │ │ wake / unpark └── waits to enter synchronized monitor ─► [ BLOCKED ] │ lock acquired ────────────────┴──► RUNNABLE

Important: RUNNABLE includes both ready-to-run and currently-running from the JVM's perspective. You cannot infer that a RUNNABLE thread is actively consuming CPU just from that state alone.

BLOCKED vs WAITING — common interview trap

BLOCKED

The thread is trying to enter a synchronized region but another thread owns that monitor.

synchronized (lock) {
    // Thread B may be BLOCKED here
}

WAITING

The thread is waiting for a condition/action, for example after calling wait() or waiting for another thread using join().

synchronized (lock) {
    lock.wait(); // releases this monitor
}
Do not confuse sleep() with wait(): sleep() does not release monitors the thread holds. wait() must be called while owning that object's monitor and releases that monitor while waiting. Always test a condition in a loop around wait() because wake-ups can be spurious and conditions can change.

Observe states with code

Thread worker = new Thread(() -> {
    try {
        Thread.sleep(500);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt(); // restore interrupt signal
    }
}, "demo-worker");

System.out.println(worker.getState()); // NEW
worker.start();
System.out.println(worker.getState()); // often RUNNABLE; timing-dependent
worker.join();
System.out.println(worker.getState()); // TERMINATED

State observations are snapshots and can change immediately. Do not write correctness logic that depends on a sampled getState() value.

4. Creating a thread: Thread class

There are two related but different actions: defining the work and deciding how it executes. Extending Thread combines them in one class. It is valid, but less flexible for most application code.

class ReportThread extends Thread {
    @Override
    public void run() {
        System.out.println("Creating report on " + Thread.currentThread().getName());
    }
}

public class Main {
    public static void main(String[] args) {
        ReportThread t = new ReportThread();
        t.start(); // asks JVM to start concurrent execution
    }
}

start()

Starts a new thread of execution; the JVM invokes run() on that new execution path.

run()

A normal method call. Calling it directly runs the method on the current thread and does not start a new thread.

Why not extend Thread for every task? Java allows a class to extend only one class, and extending Thread couples business work to its execution mechanism. Prefer a Runnable or Callable submitted to an executor for most backend tasks.

5. Runnable: describe work without returning a result

Runnable is a functional interface with void run(). It represents an action that can be executed later. It does not return a value and its method signature cannot declare checked exceptions.

Runnable sendEmail = () -> {
    System.out.println("Sending receipt on " + Thread.currentThread().getName());
};

Thread t = new Thread(sendEmail, "receipt-worker");
t.start();

Prefer task + executor for backend services

import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class ReceiptService {
    public static void main(String[] args) {
        ExecutorService pool = Executors.newFixedThreadPool(4);
        try {
            pool.submit(() -> System.out.println("Send receipt"));
        } finally {
            pool.shutdown(); // orderly shutdown; production apps manage lifecycle centrally
        }
    }
}

The task is reusable and independent of whether it runs on a fresh thread or a pool worker. In a server, avoid creating a new thread per request without limits; use a deliberately sized executor or framework-managed execution model.

Use Runnable when: you need to perform an action, do not need a return value, and want to separate the task from the thread/executor that runs it.

6. Callable: work that returns a result

Callable<V> has a call() method that returns a value of type V and may throw checked exceptions. It is useful when background work produces a result that another part of the program will need.

import java.util.concurrent.Callable;

Callable<Integer> calculateInvoiceTotal = () -> {
    int subtotal = 1200;
    int tax = 180;
    return subtotal + tax;
};

Unlike a plain Runnable, a Callable is typically submitted to an ExecutorService, which returns a Future<V>.

7. Future: a handle to a result that may arrive later

A Future<V> represents the result of an asynchronous computation. You can check completion, wait for the result, cancel the task, or check cancellation. A Future is not the result itself; it is a handle for observing and controlling the computation.

Request thread Executor worker │ │ │ submit(Callable) │ ├──────────────────────────────►│ execute call() │◄──────── Future<V> ──────────┤ │ │ │ do other work │ compute / call remote service │ │ │ future.get(timeout) │ result or exception ├──────────────────────────────►│ │◄──────── value / error ───────┤

Complete Java example with timeout and cleanup

import java.util.concurrent.*;

public class FutureExample {
    public static void main(String[] args) {
        ExecutorService pool = Executors.newFixedThreadPool(2);
        Future<String> future = pool.submit(() -> {
            // Simulate an inventory lookup
            Thread.sleep(150);
            return "SKU-42 is in stock";
        });

        try {
            String result = future.get(500, TimeUnit.MILLISECONDS);
            System.out.println(result);
        } catch (TimeoutException e) {
            future.cancel(true); // requests interruption; task must cooperate
            System.err.println("Inventory lookup exceeded its deadline");
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt(); // preserve cancellation signal
            System.err.println("Caller was interrupted");
        } catch (ExecutionException e) {
            Throwable cause = e.getCause();
            System.err.println("Task failed: " + cause);
        } finally {
            pool.shutdown();
        }
    }
}

FutureTask

FutureTask<V> implements both Runnable and Future<V>. This lets it wrap a Callable and be executed by a Thread or executor while also exposing the result.

FutureTask<Integer> task = new FutureTask<>(() -> 20 * 3);
new Thread(task, "calculation-worker").start();
try {
    System.out.println(task.get()); // 60
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
} catch (ExecutionException e) {
    throw new RuntimeException(e.getCause());
}
Subtle point: Future.get(timeout) timing out does not guarantee the remote service stopped working. Cancellation usually requests interruption. Code should respond to interrupts, and HTTP/database clients should also have connection/read/request timeouts.

9. Real-world workflow: checking inventory during checkout

Suppose a checkout service checks inventory from another service. The task is independent, so it can run on a bounded executor. The request thread still needs an explicit deadline and a fallback/error strategy.

Customer checkout request │ ▼ Checkout service │ submit(Callable<Stock>) ▼ Bounded executor ─────► Inventory API │ │ │ Future<Stock> │ response / failure ▼ ▼ get(deadline) ◄──────── result │ ┌────┴────┐ ▼ ▼ in stock timeout/error │ │ confirm fail safely, retry only when safe, order or return a clear unavailable response
ExecutorService inventoryPool = new ThreadPoolExecutor(
    8, 16,
    30, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(200),
    new ThreadPoolExecutor.CallerRunsPolicy()
);

Future<Boolean> stockFuture = inventoryPool.submit(
    () -> inventoryClient.isAvailable("SKU-42")
);

try {
    boolean available = stockFuture.get(400, TimeUnit.MILLISECONDS);
    if (!available) {
        // Return a business response: item unavailable
    }
} catch (TimeoutException e) {
    stockFuture.cancel(true);
    // Return a controlled timeout/fallback response
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    // Stop waiting and propagate cancellation appropriately
} catch (ExecutionException e) {
    // Log correlation ID and root cause; map to a safe API response
}

This is an illustrative executor configuration, not a universal production setting. Pool size, queue capacity, and rejection behavior must be selected from measured workload, downstream limits, and latency objectives. Also configure a timeout in the inventory HTTP client itself.

10. Production issues, root causes, and fixes

Incident A — “Unable to create new native thread”

Symptom: A service creates a thread for every incoming webhook. During a traffic spike, native thread creation fails even though Java heap appears to have free space.

Root cause: Unbounded thread creation consumes native memory for stacks and OS thread/process resources. Heap space and native-thread capacity are different resource pools.

Fix: Use a bounded executor, bounded queue, explicit rejection/backpressure policy, and metrics for active threads, queue depth, rejected tasks, and task latency. Tune OS limits only after understanding the resource usage; raising limits alone does not fix unbounded concurrency.

Incident B — request pool starved by untimed Future.get()

Symptom: HTTP latency climbs; all server request threads are waiting for a downstream service that is stalled.

Root cause: future.get() has no timeout. Many requests remain blocked while holding request-processing capacity.

Fix: Use a deadline-aware timeout, configure the downstream client's own timeouts, limit concurrent calls, propagate cancellation, and monitor p95/p99 latency. A timeout is not a magic kill switch for the remote work.

Incident C — cancelled task keeps consuming CPU

Symptom: future.cancel(true) returns, but CPU usage remains high.

Root cause: The task performs a long CPU loop and never checks the interrupt flag. Interrupt requests cancellation; it does not forcibly terminate arbitrary Java code.

while (!Thread.currentThread().isInterrupted()) {
    doOneSmallUnitOfWork();
}

Fix: Make long-running tasks interruption-aware. When catching InterruptedException, usually restore the flag with Thread.currentThread().interrupt() and exit or propagate cancellation.

Incident D — task exceptions are silently missed

Symptom: Background work fails, but the API or logs show no clear error.

Root cause: The code submits a task and never inspects the Future. Exceptions from submitted tasks are captured and are typically observed when calling get() (or through a suitable completion/error-handling mechanism).

Fix: Observe completion and failure; log the root cause and correlation ID; expose task failures through metrics/alerts. For tasks with no result, still define an error-handling strategy.

Incident E — overload hidden by a huge queue

Symptom: The service stays up but requests become very slow and memory grows.

Root cause: A large/unbounded queue accepts work faster than workers can finish it, causing queue delay and retained request data.

Fix: Bound the queue, reject or apply backpressure, set end-to-end deadlines, and tune concurrency to the downstream system's capacity. More threads are not always the solution.

11. Production debugging toolkit

When a service is slow, distinguish CPU saturation, lock contention, queue buildup, and downstream blocking instead of guessing.

# Linux: view per-thread CPU usage for a Java process
top -H -p <JAVA_PID>

# Capture a JVM thread dump (JDK tools)
jcmd <JAVA_PID> Thread.print > threads.txt

# Count OS threads associated with the process on Linux
ls -1 /proc/<JAVA_PID>/task | wc -l

# Inspect process resource limits
ulimit -u

12. Thumb rules to remember

  • Use start(), not run(), when you intend to start a separate thread.
  • Do not restart a Thread object. Create a new task/thread instead.
  • Prefer Runnable/Callable over extending Thread to keep business logic separate from execution.
  • Runnable = action; Callable = result-bearing computation.
  • Future = handle for the outcome, not the outcome itself.
  • Put deadlines around blocking waits. Also configure timeouts on network/database clients.
  • Cancellation is cooperative. Interrupt-aware code must respond to the signal.
  • Use bounded concurrency and queues. Unbounded thread creation or queues turn overload into an outage.
  • Restore interruption if you catch InterruptedException and cannot propagate it: Thread.currentThread().interrupt().
  • Do not rely on getState() for synchronization. It is only a snapshot.

13. Interview Q&A — answer with definition, contrast, and example

Try answering aloud before opening each answer. Strong answers explain what it is, why it matters, and one practical caveat.

Q1. What is the difference between a process and a thread?

A process is a running program with its own virtual address space and OS resources. A thread is an execution path within a process. Threads in one process share heap objects and many resources but have their own stacks and execution state. Sharing makes communication efficient, but shared mutable state can create race conditions.

Q2. What are the six Java thread states?

NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, and TERMINATED. Mention that JVM RUNNABLE covers ready-to-run and running, and that these are JVM states rather than a complete mapping of OS states.

Q3. What happens when run() is called instead of start()?

run() is an ordinary method call and executes on the caller's thread. start() arranges for the JVM to start a new thread of execution and invoke its run method. A Thread instance can only be started once.

Q4. Why prefer Runnable over extending Thread?

Runnable separates the task from its execution mechanism, preserves the option to extend another class, and can be submitted to executors. Extending Thread is useful for specialised cases but couples task logic and thread lifecycle.

Q5. Runnable vs Callable?

Runnable's run() returns void and cannot declare checked exceptions. Callable's call() returns a value and can throw checked exceptions. Submitting a Callable to an ExecutorService yields a typed Future for its outcome.

Q6. What is Future?

Future represents a pending or completed asynchronous computation. It provides methods to retrieve the result, check completion, and request cancellation. Calling untimed get() may block indefinitely, so request paths generally need a deadline.

Q7. Does future.cancel(true) kill the worker thread?

No. It requests cancellation and may interrupt the worker. Interrupt is cooperative: interruptible operations may throw InterruptedException, while CPU loops must check the interrupt flag and exit themselves. Configure downstream timeouts too.

Q8. What is the difference between BLOCKED and WAITING?

BLOCKED means waiting to acquire an intrinsic monitor for a synchronized section. WAITING means waiting for another action, such as notify, another thread finishing, or an unpark. In a thread dump, identify the stack and lock owner before choosing a fix.

Q9. Why is an unbounded thread-per-request model risky?

Each platform thread consumes native resources and scheduling overhead. A traffic spike can exhaust OS thread limits or native memory. Use bounded concurrency, bounded queues, backpressure/rejection, metrics, and carefully tuned timeouts.

Q10. How would you investigate high latency caused by concurrency?

Check latency percentiles, CPU, thread count, executor active count and queue depth, rejection counts, and downstream timings. Capture a thread dump and look for repeated stacks in locks, Future.get, or network calls. Confirm the root cause with metrics before changing pool sizes.

Q11. What is FutureTask?

FutureTask implements both Runnable and Future. It wraps a Callable or Runnable, can be executed by a Thread or executor, and exposes completion/result/cancellation through the Future API.

Q12. Can a RUNNABLE thread be waiting for CPU?

Yes. Java's RUNNABLE state includes threads that are ready but not currently scheduled as well as threads executing on a CPU. Use OS/JVM profiling and thread dumps together for diagnosis.
