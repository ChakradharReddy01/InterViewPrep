Synchronization, Intrinsic Locks, volatile, Atomic Variables & CAS

Learn how multiple threads safely update shared data, why apparently simple code fails under load, and how to choose the right concurrency tool. Explanations start with everyday analogies, then build toward Java implementation details and interview-ready answers.

Core question

What if two threads touch the same mutable data at the same time?

Goal

Correct results, visibility, predictable behavior, and acceptable performance.

Golden idea

Protect the whole operation that must behave as one logical action—not just one line.

1. Race Condition

Kid-friendly idea: Two people see one last cookie. Both check that it exists, both decide they can take it, and both act. The final result violates the rule “only one cookie can be taken.” A race condition happens when a program's correctness depends on the unpredictable timing of threads.

Why count++ is not one indivisible action

Incrementing a shared integer is a read → calculate → write sequence. Two threads can read the same old value and overwrite each other's update. This is called a lost update.

Initial count = 10 Thread A Thread B -------- -------- read count -> 10 read count -> 10 calculate 10 + 1 -> 11 calculate 10 + 1 -> 11 write count = 11 write count = 11 Expected: 12 Actual: 11 (one update lost)
Broken exampleJava
class UnsafeCounter {
    private int count = 0;

    void increment() {
        count++; // not atomic; multiple threads can lose updates
    }

    int getCount() {
        return count;
    }
}

Even if each line looks simple, the operation as a whole is not thread-safe. The same pattern appears in inventory counts, wallet balances, seat reservations, and request counters.

Check-then-act race

if (stock >= quantity) {   // check
    stock -= quantity;     // act
}

Two orders can both observe stock = 1 and both sell the last item. Protect the check and the update together, or make the database perform a conditional atomic update.

Interview phrase: “A race condition is a correctness bug caused by unsafely interleaved concurrent operations on shared state. I first identify the shared mutable state, then identify the non-atomic invariant, and finally protect that invariant with a lock, an atomic operation, or a database transaction/constraint as appropriate.”

2. Critical Section

A critical section is the smallest logical region that reads or changes shared state and must obey a concurrency rule. A lock protects entry to that region.

Good critical section

Check available inventory and decrement it under one synchronization boundary.

synchronized (inventoryLock) {
    if (stock >= quantity) {
        stock -= quantity;
    }
}

Dangerous critical section

Locking only the decrement leaves the check exposed to races.

if (stock >= quantity) {
    synchronized (inventoryLock) {
        stock -= quantity;
    }
}

Three classic correctness goals

  • Mutual exclusion: no two threads execute the protected critical section at the same time for the same lock.
  • Progress: if the lock is free and threads are trying to enter, the system should be able to let one proceed.
  • Bounded waiting: ideally, a waiting thread should not be postponed forever. Java intrinsic monitors do not promise strict fairness, so starvation is still possible in some workloads.
Thumb rule: Lock the complete invariant (the check + decision + update), but keep the critical section short. Avoid network calls, database calls, sleeps, or expensive work while holding a lock unless there is a very deliberate reason.

3. synchronized Method vs. Block

synchronized provides mutual exclusion and a happens-before visibility guarantee. When one thread exits a synchronized region and another later acquires the same monitor, writes made before unlock become visible to the acquiring thread.

Instance synchronized method

public synchronized void deposit(long amount) {
    balance += amount;
}

Locks this. Two calls on the same object serialize; calls on two different account objects can run concurrently.

Synchronized block

private final Object lock = new Object();

public void deposit(long amount) {
    validate(amount); // outside lock
    synchronized (lock) {
        balance += amount;
    }
}

Locks the chosen object and lets you narrow the protected region. A private final lock avoids exposing the lock to unrelated code.

Static synchronized method

public static synchronized void refreshGlobalConfig() {
    // guarded by MyService.class monitor
}

A static synchronized method locks the Class object, e.g. MyService.class, not an instance's this. It therefore does not automatically exclude an instance synchronized method.

Important behavior

  • Locks are reentrant: a thread holding a monitor can acquire that same monitor again.
  • If a synchronized method throws an exception, the monitor is still released as the method exits.
  • synchronized is not a distributed lock. It coordinates threads inside one JVM only.
  • Calling Thread.sleep() inside a synchronized block does not release the monitor.
Common bug: Synchronizing on a public object, a string literal, or an object other code can also lock may create accidental contention or deadlocks. Prefer a private final lock when a dedicated lock is needed.

4. Intrinsic Lock

Every Java object can be used as a monitor lock. This built-in locking mechanism is called an intrinsic lock (or monitor lock). A synchronized instance method uses the current object's lock; a synchronized block uses the exact object in parentheses.

Object accountA Object accountB +------------------+ +------------------+ | monitor A | | monitor B | | balance = 100 | | balance = 500 | +------------------+ +------------------+ Thread 1 locks A Thread 2 locks B | | +---- can run concurrently -------+ Two threads locking the SAME object must coordinate.

Reentrancy example

class ReportService {
    public synchronized void generate() {
        writeHeader(); // same thread can re-enter this object's monitor
    }

    private synchronized void writeHeader() {
        System.out.println("Header");
    }
}

Reentrancy prevents a thread from deadlocking itself when a synchronized method calls another synchronized method using the same monitor. It does not prevent deadlocks involving two different locks.

Deadlock example

// Thread A: holds lock1, waits for lock2
// Thread B: holds lock2, waits for lock1

Mitigate deadlocks by acquiring multiple locks in a consistent global order, minimizing nested locks, and using time-bounded lock acquisition with explicit recovery when appropriate.

5. Monitor: Entry Set, Wait Set, wait / notify

A monitor combines a lock with coordination support. Think of a meeting room: one person owns the room; others queue to enter. A person inside can wait for a condition, release the room, and later compete to enter again.

+----------------------+ | ENTRY SET | | threads waiting for | | synchronized monitor | +-----------+----------+ | monitor becomes available v +----------------------+ | OWNER THREAD | | runs critical code | +-----------+----------+ | calls obj.wait() | releases this monitor v +----------------------+ | WAIT SET | | waiting for notify, | | timeout or interrupt | +----------------------+
  • wait() must be called while owning that same object's monitor; it releases that monitor and suspends the thread.
  • notify() wakes one arbitrary waiter; it does not hand over the lock immediately. The awakened thread must re-acquire the monitor.
  • notifyAll() wakes all waiters; they compete to re-acquire the monitor and should re-check their conditions.
  • Use while, not if, around wait() because wakeups can be spurious and conditions may no longer be true when the thread resumes.
class OneSlotBuffer {
    private String value;
    private boolean full;

    public synchronized void put(String item) throws InterruptedException {
        while (full) {
            wait(); // releases this object's monitor
        }
        value = item;
        full = true;
        notifyAll();
    }

    public synchronized String take() throws InterruptedException {
        while (!full) {
            wait();
        }
        String result = value;
        value = null;
        full = false;
        notifyAll();
        return result;
    }
}

For most production producer-consumer code, prefer higher-level utilities such as BlockingQueue, Semaphore, or Condition over manually coordinating wait/notify.

Correction to a common myth: “Always use notifyAll()” is a useful safe default for many condition patterns, not a universal law. Use notify() only when the design proves waking one waiter is correct; otherwise, notifyAll() avoids waking the wrong category of waiter and leaving the system stuck.

6. volatile: Visibility and Ordering, Not Compound Atomicity

Kid-friendly analogy: A shared whiteboard is useful only if everyone sees the latest writing. volatile gives a visibility and ordering guarantee for one variable. It does not make a multi-step update indivisible.

class Worker {
    private volatile boolean running = true;

    void stop() {
        running = false;
    }

    void work() {
        while (running) {
            doSmallUnitOfWork();
        }
    }

    private void doSmallUnitOfWork() {
        // short work; real code should also define interruption/shutdown behavior
    }
}

A write to a volatile field happens-before a subsequent read of that same field. The JVM and hardware implement the Java Memory Model's guarantees using the mechanisms appropriate to the platform; don't assume this literally means every access reads or writes RAM.

Why volatile doesn't fix count++

private volatile int count = 0;

void increment() {
    count++; // still a read-modify-write race
}

Two threads can both read 7, both compute 8, and both write 8. Visibility is not the same as mutual exclusion or atomicity.

Good use cases

  • Independent stop/running flag.
  • Publishing an immutable configuration reference.
  • State where one write and one read are sufficient and no compound invariant exists.

Not sufficient for

  • count++ or balance -= amount.
  • Check-then-act logic.
  • Keeping several variables consistent as one unit.

7. Atomic Variables

Classes such as AtomicInteger, AtomicLong, and AtomicReference provide atomic operations on a single value, often implemented with compare-and-set primitives and memory-ordering support.

import java.util.concurrent.atomic.AtomicInteger;

class SafeCounter {
    private final AtomicInteger count = new AtomicInteger();

    void increment() {
        count.incrementAndGet();
    }

    int value() {
        return count.get();
    }
}

This prevents lost updates for the counter. It does not automatically make a multi-field operation atomic—for example, decrementing inventory and inserting an order still needs a broader consistency strategy.

AtomicReference: atomic state replacement

record Config(String endpoint, int timeoutMs) {}

AtomicReference config =
    new AtomicReference<>(new Config("https://api.example", 500));

void updateTimeout(int newTimeout) {
    config.updateAndGet(old ->
        new Config(old.endpoint(), newTimeout));
}

AtomicLong vs. LongAdder

ToolBest fitTrade-off
AtomicLongExact atomic value; sequence numbers or coordination decisions.Heavy contention can cause repeated CAS retries.
LongAdderHigh-contention statistics such as request counts.sum() is not a single atomic snapshot while updates are happening; don't use it for strict business invariants.
synchronizedProtecting multiple related fields or a compound invariant.Contending threads may block; lock scope matters.
Thumb rule: Use atomics for simple state transitions on one value. Use a lock when multiple variables must change together. Use LongAdder for high-throughput statistics, not for an account balance or inventory truth.

8. CAS: Compare-And-Set / Compare-And-Swap

CAS means: “Change the value to the new value only if it is still the value I observed.” The comparison and conditional update happen atomically. If another thread changed it first, the operation fails and the caller may retry.

Observed current value = 5 Expected value = 5, new value = 6 CAS(5 -> 6) | +-- current still 5? -- YES --> update to 6, success | +-- current is 7? ----- NO ---> no update, failure; re-read/retry
import java.util.concurrent.atomic.AtomicInteger;

AtomicInteger stock = new AtomicInteger(10);

boolean reserveOne() {
    while (true) {
        int current = stock.get();
        if (current <= 0) {
            return false;
        }
        if (stock.compareAndSet(current, current - 1)) {
            return true;
        }
        // Someone changed stock; re-read and retry.
    }
}

CAS is optimistic: a thread attempts an update without acquiring a traditional monitor lock. Under contention, retries may burn CPU, so lock-free does not automatically mean faster or fairer.

The ABA problem

A thread reads A; another thread changes A → B → A; the first thread sees A again and CAS succeeds even though the state changed in between. For reference-based algorithms where history matters, use a version/stamp such as AtomicStampedReference or redesign the state representation.

AtomicStampedReference head =
    new AtomicStampedReference<>(initialNode, 0);

int[] stampHolder = new int[1];
Node oldHead = head.get(stampHolder);
int oldStamp = stampHolder[0];

boolean updated = head.compareAndSet(
    oldHead, newHead, oldStamp, oldStamp + 1
);

CAS and atomic classes are often implemented with CPU/JVM primitives (e.g. compare-exchange instructions or VarHandle operations), but exact implementation details vary by JVM and processor.

9. Real Production Incidents: Symptoms, Root Cause, Fix

Incident A — Duplicate or oversold inventory

Two request threads both read stock = 1 and both pass the check. The service oversells because the check and decrement were separate operations.

Fix: For in-memory state, protect the entire check-and-decrement with one lock or CAS loop. For a multi-instance service, use a database conditional update (for example, update only where stock is sufficient), transaction/locking, and idempotency where needed. A JVM monitor cannot coordinate separate service instances.

Incident B — High CPU from a contended atomic counter

A global AtomicLong is updated on every request by hundreds of threads. Under high contention, CAS retries and cache-coherence traffic reduce throughput.

Fix: For telemetry counters, evaluate LongAdder, per-thread metrics, or metrics aggregation. Benchmark under realistic contention; don't replace atomics blindly.

Incident C — Application hangs due to lock contention

A synchronized method performs a slow remote API call while holding the monitor. Other requests queue behind it and latency climbs.

Fix: Keep only shared-state mutation under the lock; perform slow I/O outside it when correctness allows. Use thread dumps and Java Flight Recorder to locate monitor contention.

Incident D — Stale shutdown flag

A worker loops on a non-volatile boolean that another thread changes. Without a proper happens-before relationship, the worker may not observe the update promptly—or at all under the Java Memory Model.

Fix: Use volatile, an atomic variable, or interruption / structured task cancellation. Design shutdown so blocking operations can also be unblocked.

Production diagnostics

# Find JVM threads blocked waiting to enter a monitor
jcmd  Thread.print -l

# Capture a JFR recording with lock/monitor events (JDK options vary)
jcmd  JFR.start name=locks settings=profile duration=30s filename=locks.jfr

# On Linux, inspect per-thread CPU
top -H -p

A thread dump is a snapshot: correlate repeated dumps and metrics rather than diagnosing from a single line. JFR settings and command options can vary by JDK version.

10. Thumb Rules to Memorize

Choose synchronized when…

  • A compound invariant must be protected.
  • Several fields must be read/updated consistently.
  • You want simple, lexical lock management.

Choose volatile when…

  • You need visibility for a single independent state flag/reference.
  • Operations do not depend on read-modify-write atomicity.
  • You can explain the happens-before relationship.

Choose atomics/CAS when…

  • A single value needs an atomic transition.
  • The retry logic is correct and bounded enough for expected contention.
  • Lock-free behavior is useful, not just fashionable.

Production safety

  • Do not hold locks across slow I/O unnecessarily.
  • Never assume a JVM lock coordinates multiple machines.
  • Measure contention; optimize based on evidence.
One-line memory trick: synchronized = mutual exclusion + visibility; volatile = visibility + ordering for that field; Atomic* = atomic operations on a value; CAS = update only if the observed value is still current.

11. Interview Questions & Model Answers

Q1. What is a race condition?

It is when the correctness of a program depends on how concurrent operations interleave. For example, two threads incrementing a shared integer can both read the same value and overwrite each other's update. I would protect the full operation with synchronization or use an atomic operation if it is a single-value update.

Q2. What is a critical section?

The code region that accesses shared mutable state and must obey a concurrency invariant. I keep it as small as possible while ensuring the entire check-and-update sequence is protected.

Q3. What is the difference between a synchronized method and block?

An instance synchronized method locks this for the whole method. A synchronized block locks the specific object expression for only the enclosed region. Blocks allow a smaller critical section and a private lock object.

Q4. What is the difference between intrinsic lock and monitor?

The intrinsic lock is Java's built-in locking mechanism associated with an object. The monitor is the coordination mechanism around that lock, including ownership and wait-set behavior used by wait/notify.

Q5. Does volatile make count++ thread-safe?

No. It guarantees visibility and ordering for volatile accesses, but count++ is a compound read-modify-write operation. Use AtomicInteger for a counter or synchronization if the operation belongs to a larger invariant.

Q6. What is CAS and why can it be useful?

Compare-and-set atomically updates a value only if it matches an expected value. It supports optimistic lock-free algorithms, but retries under contention can consume CPU and algorithms must account for issues such as ABA.

Q7. Is an atomic variable always better than synchronized?

No. Atomics are excellent for single-value operations. Synchronization is often clearer and more appropriate when multiple values or steps must remain consistent. Performance depends on contention and workload.

Q8. Why use while around wait()?

Threads can wake spuriously, and another thread may change the condition before the awakened thread reacquires the monitor. The condition must be checked again after every wakeup.

Q9. Can synchronized protect data across two service instances?

No. It coordinates threads that share the same monitor in one JVM. Cross-instance consistency needs a shared coordination mechanism such as a database transaction/conditional update, a distributed lock when justified, or an architecture that avoids shared mutable state.

Q10. How would you debug monitor contention in production?

I would correlate latency and CPU metrics, capture repeated thread dumps with lock information, inspect which threads own and wait for monitors, and use JFR to profile contention and lock hold times. Then I'd reduce lock scope or redesign the shared state and verify with load tests.

Interview answer structure

Definition → Simple example → What goes wrong → Java solution → Trade-off → Production use case

Example: “For a request counter, AtomicLong makes increments atomic. If it is only telemetry and there is heavy contention, I would consider LongAdder. If the counter controls a financial invariant, I would not treat it as just a metric; I would protect the business operation and persist the invariant in a transactional shared store.”
