Module 2: Synchronization, Monitors, Volatile & Hardware CAS

Multithreading Hardware & JMM Lock-Free Concurrency ⏱️ 50 min deep dive Target Roles: SDE-2, SDE-3, Concurrency / Performance Specialist

1. Race Conditions & Critical Sections

1.1 What is a Race Condition?

A Race Condition occurs when the correctness of a program depends on the relative timing, interleaving, or execution order of multiple concurrent threads accessing shared mutable state.

  • Read-Modify-Write: When an operation consists of multiple non-atomic steps (e.g., count++: 1. read count, 2. add 1, 3. write back). If two threads execute step 1 simultaneously with count = 5, both compute 6, resulting in a lost update.
  • Check-Then-Act: When a thread observes a condition (e.g., if (balance >= amount)) and acts on it (e.g., balance -= amount). If another thread mutates balance between the check and the act, invalid state or negative balances result.

1.2 Critical Section & Mutual Exclusion

A Critical Section is a segment of code that accesses shared mutable resources and must not be executed concurrently by more than one thread. To maintain thread safety, the system must guarantee three properties:

  1. Mutual Exclusion: Only one thread can execute in the critical section at any given instant.
  2. Progress: If no thread is executing in the critical section and some threads wish to enter, only those threads can participate in deciding who enters next.
  3. Bounded Waiting: There must be a limit on the number of times other threads can enter the critical section after a thread has requested entry (preventing thread starvation).

2. Synchronized Methods, Blocks & Monitor Mechanics

2.1 Synchronized Method vs. Synchronized Block

  • Synchronized Instance Method: Locks the entire method body using the object's instance monitor (this). 
    public synchronized void updateBalance(long amount) {
    this.balance += amount;
}
  • Synchronized Static Method: Locks the java.lang.Class object in Metaspace/Heap (Account.class). It does not block non-static synchronized methods on instances of the same class!
  • Synchronized Block (Fine-Grained): Restricts locking strictly to the critical lines of code and allows locking on private dedicated lock objects, reducing contention and preventing external callers from deadlocking on this: 
    private final Object lock = new Object(); // Private final lock prevents external hijacking

public void processTransaction(Transaction tx) {
    validate(tx); // Unsynchronized validation outside critical section!
    
    synchronized (lock) {
        this.balance += tx.amount(); // Strictly bounded critical section
    }
    
    sendNotification(tx); // Unsynchronized I/O outside critical section
}

2.2 Intrinsic Locks & Reentrancy

Every object in Java has an Intrinsic Lock stored in its 64-bit Mark Word header.

Reentrancy Guarantee: Java intrinsic locks are completely reentrant. If a thread that already holds a lock attempts to acquire it again (e.g., a synchronized method recursively calling another synchronized method on the same object), the JVM allows it immediately without deadlocking itself. Internally, the JVM associates an acquisition counter with the lock:

  • When the thread acquires the lock, the counter increments to 1 and records the thread ID.
  • Each reentrant entry increments the counter (2, 3...).
  • Each exit decrements the counter. The lock is only released to other threads when the counter reaches 0.

2.3 Monitor Mechanics: Entry Set vs. Wait Set

The JVM implements object synchronization using Monitors based on the Mesa monitor architecture: 

                             +----------------------------+
                             |   ENTRY SET (Blocked)      |
                             | Threads waiting to acquire |
                             | lock on synchronized block |
                             +-------------+--------------+
                                           |
                              acquires lock|
                                           v
                             +----------------------------+
                             |       OWNER THREAD         |
                             |  Active in Critical Section|
                             +-------------+--------------+
                                           |
                               Object.wait() releases lock
                                           v
                             +----------------------------+
                             |    WAIT SET (Waiting)      |
                             | Threads waiting for        |
                             | notify() / notifyAll()     |
                             +----------------------------+
  • Entry Set: When Thread A holds the monitor, other threads trying to enter are placed into the Entry Set and transitioned to the BLOCKED state.
  • Wait Set: When the owner thread calls wait(), it voluntarily releases the monitor and moves to the Wait Set in the WAITING state.
  • notify() vs. notifyAll(): notify() moves a single arbitrary thread from the Wait Set to the Entry Set. If that thread cannot proceed, the system deadlocks. Always use notifyAll() in enterprise code to wake all waiting threads, allowing them to re-check their condition loops.

3. The volatile Keyword & Hardware Memory Semantics

3.1 CPU Caches & The MESI Protocol

Modern multi-core processors maintain private L1/L2 caches per core. When Thread 1 on Core 0 writes flag = true, the update initially lives inside Core 0's write buffer and L1 cache. Unless a hardware memory barrier is emitted, Core 1 executing Thread 2 may continue reading flag = false indefinitely from its own stale L1 cache!

3.2 Memory Barriers & The Happens-Before Relationship

Declaring a variable volatile instructs the JVM and compiler to enforce strict memory ordering:

  • Visibility: Every write to a volatile variable is immediately flushed to shared L3 cache / RAM. Every read from a volatile variable is loaded directly from coherent main memory, bypassing stale registers.
  • Instruction Reordering Prevention: The JVM emits hardware memory barriers (such as mfence or lock prefixed instructions on x86) around volatile variables:
    • StoreStore barrier before volatile write (ensures previous normal writes are visible first).
    • StoreLoad barrier after volatile write (ensures the write is visible before subsequent reads).
    • LoadLoad and LoadStore barriers after volatile reads.
  • Happens-Before Rule: A write to a volatile variable happens-before every subsequent read of that same volatile variable.
⚠️ Why volatile DOES NOT Guarantee Atomicity

volatile guarantees visibility and ordering, but zero mutual exclusion or atomicity. Compound operations like count++ or flag = !flag consist of 3 distinct bytecode instructions. Two threads can execute the read simultaneously, resulting in lost updates even if count is volatile!

4. Atomic Variables & Hardware Compare-And-Swap (CAS)

4.1 The Compare-And-Swap (CAS) Hardware Primitive

CAS is a CPU instruction (CMPXCHG on x86) that performs an atomic read-modify-write in a single processor cycle: 

boolean compareAndSwap(int expectedValue, int newValue) {
    // Executed atomically at the hardware CPU bus/cache level:
    if (this.currentValue == expectedValue) {
        this.currentValue = newValue;
        return true;  // CAS Succeeded!
    }
    return false;     // CAS Failed, value was changed by another thread!
}

4.2 Atomic Variables (java.util.concurrent.atomic)

Classes like AtomicInteger, AtomicLong, and AtomicReference implement lock-free concurrency using CAS and volatile memory pointers:

Lock-Free Optimistic Loop (AtomicInteger.incrementAndGet) Java 
// Under the hood in java.lang.invoke.VarHandle / Unsafe:
public final int getAndAddInt(Object o, long offset, int delta) {
    int v;
    do {
        v = getIntVolatile(o, offset); // 1. Read current volatile value
    } while (!weakCompareAndSetInt(o, offset, v, v + delta)); // 2. Optimistic CAS retry loop!
    return v;
}

4.3 The ABA Problem & AtomicStampedReference

In a lock-free algorithm, Thread 1 reads value $A$. Before Thread 1 performs its CAS, Thread 2 changes the value from $A \rightarrow B$, and then changes it back from $B \rightarrow A$.

Thread 1's CAS compares current value $A$ with expected value $A$, assumes nothing changed, and succeeds! While harmless for simple integers, in lock-free linked data structures (like concurrent stacks or free lists), this causes severe node reuse and memory pointer corruption.

Solving ABA with Version Stamps Java 
// Stores object reference AND an integer version stamp
AtomicStampedReference<Node> atomicRef = new AtomicStampedReference<>(initialNode, 0);

int currentStamp = atomicRef.getStamp();
Node currentNode = atomicRef.getReference();

// CAS verifies BOTH reference AND version stamp match:
boolean success = atomicRef.compareAndSet(
    currentNode, newNode, currentStamp, currentStamp + 1
);

4.4 AtomicLong vs. LongAdder Under Extreme Concurrency

When 200 threads simultaneously invoke atomicLong.incrementAndGet() under high throughput (e.g. 100,000 req/sec), all 200 threads continuously fail their CAS loops, hammering the same memory address and causing CPU cache-line bouncing.

Java 8 introduced LongAdder (extending Striped64):

  • Maintains an array of cells (Cell[]) striped across CPU cores.
  • When contention is detected, different threads update different cells independently without blocking each other.
  • Calling sum() accumulates the cells together, providing orders of magnitude higher write throughput than AtomicLong!

5. Real-Time Production Issues & Post-Mortems

🚨 Incident 1: Over-Draft Race Condition in Multi-Node Digital Wallet

Scenario: During a gaming tournament withdrawal rush, a customer with $100 in their wallet issued 5 rapid-fire withdrawal requests of $100 each. All 5 requests succeeded, leaving the platform with a $400 deficit.

🔍 Root Cause Analysis (RCA)

The withdrawal service implemented balance checking using non-atomic logic: 

// BROKEN CODE:
if (wallet.getBalance() >= amount) { // Step 1: Check
    wallet.debit(amount);            // Step 2: Act
}

Under high concurrency, 5 threads read getBalance() == 100 simultaneously before any thread executed debit(). Even though debit() had internal synchronization, the check-then-act boundary was unprotected.

💡 Production Resolution

Replaced with an atomic state transition using database pessimistic locking or compare-and-swap balance updates:

// OPTIMISTIC CAS PATTERN:
public void withdraw(long amount) {
    while (true) {
        long current = balance.get();
        if (current < amount) {
            throw new InsufficientFundsException();
        }
        if (balance.compareAndSet(current, current - amount)) {
            return; // Atomically debited!
        }
        // CAS failed due to concurrent withdrawal, retry loop immediately
    }
}
🚨 Incident 2: High CPU Spikes via Spin Contention on AtomicInteger in Metrics Engine

Scenario: A microservice handling 80,000 requests/sec observed CPU utilization climbing to 95% on 64-core AWS instances, with application throughput degrading drastically.

🔍 Root Cause Analysis (RCA)

The telemetry library tracked global request counts using a single shared AtomicLong. Across 64 CPU cores, hundreds of threads executed incrementAndGet() simultaneously. Because 63 out of 64 threads failed their CAS on every clock cycle, the CPU cores entered tight spin-retry loops, generating millions of invalidation messages across the hardware CPU interconnect bus.

💡 Production Resolution

Replaced AtomicLong with LongAdder for high-throughput metrics and throughput counters:

// High-concurrency throughput counter:
private final LongAdder requestCounter = new LongAdder();

public void onRequest() {
    requestCounter.increment(); // Lock-free striped increment, zero bus contention!
}

7. Senior / Staff Technical Interview Q&A

🎯 Q1: Why is volatile not sufficient to make a singleton instance thread-safe on its own?

Answer: volatile only provides visibility and prevents instruction reordering during initialization; it does not provide mutual exclusion. If two threads check if (instance == null) concurrently without a synchronized block, both threads can enter the initialization block simultaneously and instantiate two separate singleton objects. Mutual exclusion via synchronized combined with volatile (Double-Checked Locking) is required to ensure exactly one instance is created.

🎯 Q2: What is Lock Inflation / Lock Escalation in the HotSpot JVM?

Answer: HotSpot optimizes synchronized blocks dynamically through three tiers:
1. Biased Lock: Optimized for single-thread lock access; writes thread ID to Mark Word without CAS.
2. Lightweight Lock: When multiple threads access the lock without overlapping contention, threads use atomic CAS to exchange the object's Mark Word with a displaced mark word on their stack frame (zero OS kernel transitions).
3. Heavyweight Lock: When true concurrent contention occurs and CAS fails repeatedly, the lock inflates into an OS Mutex monitor. Contending threads are parked in the OS wait queue, incurring kernel context switches.

🎯 Q3: When should you prefer synchronized/ReentrantLock over Atomic/CAS operations?

Answer: Under low to moderate contention, CAS and Atomic variables are significantly faster because they avoid kernel context switches and thread parking. However, under heavy contention with complex multi-variable state mutations, CAS loops enter continuous CPU-spinning failure, consuming 100% CPU. In those scenarios, blocking locks (ReentrantLock) are superior because they park contending threads, freeing the CPU cores for the thread currently holding the lock to finish its critical section quickly.

🎯 Q4: Why must wait() and notify() always be called inside a while loop rather than an if statement?

Answer: Due to Spurious Wakeups and race conditions. A waiting thread can wake up without any thread calling notify() (spurious wakeup allowed by POSIX thread specifications). Furthermore, if notifyAll() is called, multiple threads wake up, but only one can consume the condition; by the time the second thread re-acquires the lock, the condition may no longer hold true. Checking the condition in a while (!condition) wait(); loop ensures the predicate is re-evaluated before proceeding.
