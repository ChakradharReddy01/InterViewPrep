Concurrent Collections Lock-Free CAS High-Throughput Queues ⏱️ 45 min deep dive Target Roles: SDE-2, SDE-3, Distributed Systems Engineer

1. ConcurrentHashMap: The High-Throughput Standard

1.1 Architecture & Lock-Free Reads

ConcurrentHashMap achieves multi-core scalability without coarse synchronized blocks:

  • Lock-Free Reads (get()): Uses volatile field references (volatile Node<K,V> next; and volatile V val;). A reader never acquires a lock, guaranteeing non-blocking reads even during concurrent writes.
  • Fine-Grained Writes (put()):
    1. If the bucket is empty, it uses atomic CAS (compareAndSetObject) to insert the head node with zero locking.
    2. If the bucket already contains nodes, it acquires a synchronized lock only on the first node (bin head) of that specific bucket. Other buckets remain completely unobstructed!
    3. If a bucket length reaches 8, it converts to a Red-Black TreeBin to protect against Hash-DoS attacks.
Atomic Compound Operations in ConcurrentHashMap Java 
ConcurrentHashMap<String, AtomicLong> counters = new ConcurrentHashMap<>();

// computeIfAbsent: Atomic check-and-insert guaranteed by bin-head monitor lock
counters.computeIfAbsent("API_USERS", k -> new AtomicLong(0)).incrementAndGet();

// merge: Atomic accumulation without race conditions
ConcurrentHashMap<String, Integer> inventory = new ConcurrentHashMap<>();
inventory.merge("ITEM_101", 5, Integer::sum);

2. CopyOnWriteArrayList: Read-Mostly Snapshot Semantics

2.1 How CopyOnWriteArrayList Works

Maintains an internal volatile array pointer: private transient volatile Object[] array;.

  • Lock-Free Reads ($O(1)$): Reads access the current snapshot array directly without locks or synchronization. Perfect for high-frequency reads (e.g. event listeners, observer patterns, configuration caches).
  • Expensive Writes ($O(N)$): Every single modification (add, set, remove) acquires a ReentrantLock, creates a brand new copy of the underlying array using Arrays.copyOf(), mutates the clone, and resets the volatile pointer.
  • Snapshot Iterators: The iterator takes a snapshot of the array at the moment of instantiation. It never throws ConcurrentModificationException and ignores modifications made after iteration begins.
⚠️ The Write-Heavy Anti-Pattern

Never use CopyOnWriteArrayList in write-heavy services! Inserting 10,000 items creates 10,000 array copies on the heap, triggering catastrophic GC allocation storms and freezing application threads.

3. BlockingQueues: ArrayBlockingQueue vs. LinkedBlockingQueue

3.1 ArrayBlockingQueue vs. LinkedBlockingQueue Deep Contrast

Feature ArrayBlockingQueue LinkedBlockingQueue
Backing Structure Fixed circular array (Ring buffer) Singly-linked chain of Node objects
Capacity Strictly bounded at initialization Optionally bounded (default Integer.MAX_VALUE)
Locking Architecture Single Lock (ReentrantLock shared by both producers and consumers) Two Independent Locks (putLock for producers and takeLock for consumers)
Throughput Lower under high producer-consumer concurrency due to lock contention Significantly higher because producers and consumers do not contend for the same lock
GC Allocation Zero object allocation per item (pre-allocated array) Allocates a Node wrapper object for every enqueued item
Two-Lock Architecture in LinkedBlockingQueue Java Internals 
// Under the hood in java.util.concurrent.LinkedBlockingQueue:
private final ReentrantLock takeLock = new ReentrantLock(); // Consumers lock here
private final Condition notEmpty = takeLock.newCondition();

private final ReentrantLock putLock = new ReentrantLock();  // Producers lock here
private final Condition notFull = putLock.newCondition();

private final AtomicInteger count = new AtomicInteger();    // Atomic cross-lock size counter

3.2 ConcurrentLinkedQueue (Lock-Free FIFO)

An unbounded, thread-safe FIFO queue based on the Michael & Scott lock-free queue algorithm. Uses pure atomic CAS on head and tail node pointers without ever blocking or parking threads.

4. Real-Time Production Issues & Post-Mortems

🚨 Incident 1: 15-Second Stop-The-World GC Storm via CopyOnWriteArrayList

Scenario: A real-time IoT gateway buffering sensor telemetry saw JVM Old Gen surge to 100%, causing consecutive 15-second GC pauses that caused network connection timeouts.

🔍 Root Cause Analysis (RCA)

Developers used CopyOnWriteArrayList as an in-memory buffer receiving 12,000 sensor readings per second. With 50,000 readings already stored, each incoming list.add(reading) allocated a fresh 50,001-element array on the heap. In 1 second, the service allocated over 5GB of short-lived arrays, overwhelming the Young Generation and flooding Old Gen.

💡 Production Resolution

Replaced with a bounded ArrayBlockingQueue<SensorReading> with zero node-allocation overhead, and drained elements in batches using drainTo().

🚨 Incident 2: High Producer-Consumer Lock Thrashing on ArrayBlockingQueue

Scenario: A high-frequency order placement pipeline hosted on a 32-core server capped at only 15,000 orders/sec. CPU profiling showed 75% of CPU time spent in ReentrantLock.lock().

🔍 Root Cause Analysis (RCA)

The messaging bridge used ArrayBlockingQueue. Because ArrayBlockingQueue shares a single lock for both put() and take(), 16 producer threads and 16 consumer threads constantly blocked each other on the same monitor.

💡 Production Resolution

Switched to LinkedBlockingQueue(50000) with separate putLock and takeLock, doubling throughput to 42,000 orders/sec.

5. Senior / Staff Technical Interview Q&A

🎯 Q1: Why does ConcurrentHashMap size() not simply lock the table to count elements?

Answer: Locking the table would destroy read and write concurrency. Instead, ConcurrentHashMap uses the striping technique of LongAdder: it maintains a baseCount and an array of CounterCell objects. When threads update the map, they update different counter cells via CAS. Calling size() sums baseCount plus all CounterCell values in a lock-free pass.

🎯 Q2: Can an iterator of CopyOnWriteArrayList reflect elements added after the iterator was created?

Answer: No. The iterator maintains a reference to the exact array instance that was active at the moment iterator() was called. When subsequent writes occur, the list creates a new array and points its internal reference to it, while the iterator continues traversing the immutable old array snapshot.
