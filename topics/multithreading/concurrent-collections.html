Concurrent Collections Masterclass

Understand which concurrent data structure to choose, how its concurrency strategy works, what consistency guarantees it provides, and what can go wrong in production. Includes Java examples, architecture diagrams, performance trade-offs, and interview questions.

Suggested study time: 45–60 minutes · Java 17 compatible · Focus on choosing the right collection for the access pattern.

1. Why concurrent collections exist

Ordinary collections such as HashMap, ArrayList, and LinkedList are not designed to make concurrent mutation safe by themselves. If multiple threads read and modify them without a suitable coordination strategy, the application can observe lost updates, inconsistent state, exceptions, or corrupted assumptions about the data.

Multiple producer / request threads | | | v v v +-------------------------+ | Concurrent data structure| | locks / CAS / snapshots | +-------------------------+ | | | v v v safe coordination according to the collection's documented contract

“Thread-safe” does not mean every multi-step business operation is automatically atomic. A collection can make individual methods safe while a sequence of separate calls remains racy.

Unsafe check-then-act on an ordinary mapJava
Map<String, Integer> counts = new HashMap<>();

// If multiple threads run this concurrently, both operations race.
if (!counts.containsKey("login")) {
    counts.put("login", 1);
}
Atomic operation using ConcurrentHashMapJava
ConcurrentHashMap<String, Integer> counts = new ConcurrentHashMap<>();
counts.putIfAbsent("login", 1);

// For an atomic counter update:
counts.merge("login", 1, Integer::sum);
Decision rule: start with the access pattern. Is it a map, list, or queue? Are reads far more frequent than writes? Must consumers wait for work? Is the queue bounded? Do you need atomic compound operations or just thread-safe individual calls?

2. ConcurrentHashMap

ConcurrentHashMap<K,V> is a thread-safe map designed for concurrent access. It usually scales much better than synchronizing every operation on one shared map lock. It does not permit null keys or values, which avoids ambiguity between “no mapping” and a mapping whose value is null.

2.1 How it works conceptually

hash(key) -> table bucket | +---------+----------+ | | empty bin occupied bin | | CAS insert coordinate updates at bin level | concurrent reads generally avoid locking the whole map

In modern Java implementations, reads generally use volatile/atomic visibility and do not acquire a global map lock. Updates use CAS where possible and coordinate at the relevant bin when needed. Under heavy collisions, a bin may be treeified to reduce lookup degradation. Exact implementation details are JDK-version-specific; do not assume the old Java 7 segmented-lock architecture applies to Java 8+.

2.2 Safe atomic updates

Per-key countersJava
ConcurrentHashMap<String, LongAdder> hits = new ConcurrentHashMap<>();

void recordHit(String endpoint) {
    hits.computeIfAbsent(endpoint, key -> new LongAdder())
        .increment();
}

long hitCount(String endpoint) {
    LongAdder counter = hits.get(endpoint);
    return counter == null ? 0L : counter.sum();
}

computeIfAbsent safely establishes a mapping for the key; LongAdder is often preferable to AtomicLong for highly contended statistics counters. Its sum() is not a globally atomic snapshot during concurrent updates, so use it for statistics rather than a strict transactional balance.

2.3 Useful methods and their guarantees

MethodUseImportant detail
putIfAbsent(k,v)Initialize only if missing.The map operation is atomic for that key.
computeIfAbsent(k, fn)Calculate and install a value if absent.Keep the mapping function short and avoid recursively modifying the same map.
compute(k, fn)Atomically compute a mapping for a key.Returning null removes the mapping or leaves it absent.
merge(k, v, fn)Combine a new value with the current mapping.Useful for per-key accumulation.
put(k,v)Insert or replace a mapping.Thread-safe single operation; not a multi-key transaction.

2.4 Iteration and size

Iterators are weakly consistent: they do not throw ConcurrentModificationException simply because another thread updates the map, and they may reflect some concurrent changes but do not promise a frozen point-in-time snapshot. Aggregate methods such as size() are useful for monitoring and control flow, but during concurrent mutation their values can change immediately and should not be used as a strict synchronization condition.

Common bug: if (map.get(key) == null) map.put(key, value) is a check-then-act race. Use putIfAbsent or an appropriate compute operation. Also remember that atomic map methods do not make mutation of a mutable object stored as the value automatically thread-safe.

2.5 Real-world use cases

  • In-memory metadata and configuration lookups with concurrent updates.
  • Per-key metrics and counters, often with LongAdder.
  • Deduplication markers and idempotency caches, provided expiration and durability are handled separately.

3. CopyOnWriteArrayList

CopyOnWriteArrayList is designed for workloads where iteration and reads are frequent but mutations are relatively rare. On a write, it creates a fresh backing array with the modification applied and publishes that new array. Existing readers can continue using the old array safely.

Current array: [listener A, listener B] | reader iterator keeps snapshot reference | writer adds listener C v New array: [listener A, listener B, listener C] Existing iterator still sees A, B. A newly created iterator sees A, B, C.

3.1 Complexity and behavior

OperationTypical costBehavior
get(index)O(1)Reads the current array without locking.
IterationO(n)Uses a snapshot captured when the iterator was created.
add/remove/setO(n) copying plus lock costPublishes a new array after mutation.

Snapshot iterators do not throw ConcurrentModificationException due to concurrent modifications, but they do not see later changes. Iterator mutation methods such as remove() are unsupported.

Event listener registryJava
final class EventBus {
    private final CopyOnWriteArrayList<Consumer<String>> listeners =
            new CopyOnWriteArrayList<>();

    void subscribe(Consumer<String> listener) {
        listeners.add(listener);
    }

    void publish(String event) {
        for (Consumer<String> listener : listeners) {
            listener.accept(event);
        }
    }
}

This works well when subscriptions change occasionally and events are published often. Consider how listener exceptions should be isolated: one failing listener should not accidentally prevent all later listeners from receiving the event unless that is the intended contract.

Production failure: allocation storm. A telemetry service stores tens of thousands of frequently arriving events in a CopyOnWriteArrayList. Every addition copies the entire array, producing huge allocation and garbage-collection pressure. Use a queue or purpose-built buffer for write-heavy ingestion; reserve copy-on-write collections for small, read-mostly registries.

3.2 When to choose it

  • Event listeners or observer registrations.
  • Small routing tables or configuration lists with infrequent updates.
  • Cases where stable snapshot iteration is more valuable than cheap writes.

4. BlockingQueue: producer-consumer coordination

BlockingQueue<E> defines queue operations that can wait when necessary. A producer can wait for capacity when the queue is full; a consumer can wait for an element when it is empty. This supports producer-consumer systems without manually writing a wait/notify protocol.

Producer threads Consumer threads | ^ v | put(item) --> [ BlockingQueue ] --> take() | | empty: take waits full: put waits (bounded queues)

4.1 The four operation styles

Operation styleInsertRemoveMeaning
Throws on failureadd(e)remove()Throws when full/empty.
Special valueoffer(e)poll()Returns false/null immediately if it cannot proceed.
Waitsput(e)take()Waits until space/item is available; interruptible.
Timed waitoffer(e, time, unit)poll(time, unit)Waits up to a limit, then returns false/null.

Blocking operations are interruptible. Code should handle InterruptedException appropriately, commonly by restoring the interrupt flag when it cannot propagate the exception.

Bounded producer-consumer patternJava
BlockingQueue<String> queue = new ArrayBlockingQueue<>(500);

// Producer: waits for capacity instead of allocating unlimited pending work.
void publish(String message) throws InterruptedException {
    queue.put(message);
}

// Consumer: waits until work becomes available.
void consumeLoop() throws InterruptedException {
    while (!Thread.currentThread().isInterrupted()) {
        String message = queue.take();
        process(message);
    }
}

4.2 Backpressure and boundedness

A bounded queue caps the number of queued elements. When producers outpace consumers, they must wait, time out, reject, or apply another domain-specific policy. This is a form of backpressure. An unbounded queue can absorb a burst but may accumulate work until memory is exhausted if the rate mismatch persists.

Poison pill caveat: a sentinel object is sometimes used to stop consumers, but it must be coordinated with the number of consumers and queue capacity. Do not use null as a sentinel: blocking queues generally prohibit null elements.

5. ArrayBlockingQueue

ArrayBlockingQueue is a bounded FIFO queue backed by a fixed-size circular array. Its capacity is chosen at construction and does not grow. It is useful when predictable queue capacity and memory bounds matter.

Fixed circular buffer, capacity = 5 head -> [A] [B] [C] [ ] [ ] <- tail take() advances head put() writes at tail When full: put waits / offer fails or times out.
Bounded queue with explicit admission behaviorJava
ArrayBlockingQueue<Task> queue = new ArrayBlockingQueue<>(1000);

boolean accepted = queue.offer(task);
if (!accepted) {
    // Decide explicitly: reject request, retry later, or persist elsewhere.
    metrics.incrementQueueFull();
}

By default, producer and consumer operations coordinate through a shared lock, which can become a contention point under high concurrency. The constructor has a fairness option: new ArrayBlockingQueue<>(capacity, true) favors waiting threads in FIFO order, typically at some throughput cost. Fairness does not mean tasks themselves are processed in every desired business order when multiple consumers run.

Strengths and trade-offs

  • Strength: strict capacity and no per-element linked-node allocation.
  • Trade-off: one shared lock can create contention between producers and consumers.
  • Choose it when: you need a predictable bounded buffer and simple FIFO semantics.

6. LinkedBlockingQueue

LinkedBlockingQueue is a FIFO queue backed by linked nodes. It can be bounded using a capacity argument or effectively unbounded when created with the no-argument constructor (capacity defaults to Integer.MAX_VALUE).

Producer side Consumer side putLock + notFull takeLock + notEmpty | | v v [head] -> [node] -> [node] -> [tail] shared count coordinates capacity / emptiness

Its implementation separates producer-side and consumer-side locking, with an atomic count used to coordinate the queue state. This can permit more producer/consumer overlap than a single-lock design in some workloads, but it allocates a node per enqueued item and performance depends on contention and workload.

Bound it explicitlyJava
// Prefer an explicit capacity when backlog must be limited.
BlockingQueue<Job> jobs = new LinkedBlockingQueue<>(2000);

if (!jobs.offer(job)) {
    // Queue is full: apply the application's overload policy.
    handleOverload(job);
}
Production failure: unbounded backlog. A service uses new LinkedBlockingQueue<>() while its downstream database slows down. Producers keep adding jobs; heap usage and task age rise until the service becomes unhealthy. Set a capacity based on acceptable waiting time and memory, and define what happens when it fills.

ArrayBlockingQueue vs LinkedBlockingQueue

DimensionArrayBlockingQueueLinkedBlockingQueue
StorageFixed circular arrayLinked nodes
CapacityAlways boundedBounded if configured; otherwise effectively unbounded
Per-element allocationNo new queue node per elementAllocates node objects
LockingShared lock for producers and consumersSeparate put/take locks coordinated by count
Typical choiceSimple, predictable bounded bufferPotentially useful when producer/consumer concurrency benefits from split locks

Neither is always faster. Benchmark using realistic producer counts, consumer counts, element sizes, capacity, and JVM settings.

7. ConcurrentLinkedQueue

ConcurrentLinkedQueue is an unbounded, thread-safe, non-blocking FIFO queue. It is designed for concurrent enqueue/dequeue without blocking producers and consumers on a queue lock. Modern implementations use atomic compare-and-set operations to coordinate head/tail and node links.

Producer A ----\ Producer B -----+--> CAS-based concurrent FIFO --> poll() Producer C ----/ | no capacity limit no waiting for item/space

7.1 Non-blocking does not mean free

When a thread cannot complete a CAS because another thread changed the structure, it retries. This avoids blocking on a lock but still consumes CPU under contention. “Lock-free” describes progress properties of the algorithm; it does not mean every operation finishes in a fixed number of steps or that contention disappears.

Non-blocking poll loopJava
ConcurrentLinkedQueue<String> queue = new ConcurrentLinkedQueue<>();

queue.offer("job-1");
queue.offer("job-2");

String item;
while ((item = queue.poll()) != null) {
    process(item);
}

poll() returns immediately with null if the queue is empty. It does not wait for work. Use a BlockingQueue when consumers should sleep until an item arrives.

7.2 Important trade-offs

  • Unbounded: it does not provide a built-in capacity limit or producer backpressure.
  • Non-blocking: useful when callers should not wait for queue operations.
  • Memory: queued nodes remain reachable until removed and reclaimed.
  • Size: obtaining size() requires traversal and may be inaccurate by the time it is used under concurrent changes; avoid using it as a capacity guard.
Choose ConcurrentLinkedQueue when you need concurrent FIFO enqueue/dequeue and non-blocking empty behavior. Choose a BlockingQueue when waiting and/or bounded capacity is part of the desired producer-consumer contract.

Q1. Why is ConcurrentHashMap preferred over Collections.synchronizedMap?

It is designed for concurrent access with finer-grained coordination and non-global-lock reads in typical modern implementations. A synchronized wrapper serializes access through one monitor and generally requires external synchronization for safe compound iteration.

Q2. Is ConcurrentHashMap fully lock-free?

No. Reads generally avoid locking, and some updates use CAS, but updates to occupied bins may use synchronization. It is a concurrent scalable map, not a guarantee that every operation is lock-free.

Q3. Why does ConcurrentHashMap reject null keys and values?

It avoids ambiguity between an absent mapping and a mapping whose value is null, which is especially important when retrieval happens concurrently.

Q4. What is a snapshot iterator?

CopyOnWriteArrayList iterators traverse the array version captured at iterator creation. They do not see subsequent writes and do not throw ConcurrentModificationException because of those writes.

Q5. Why not use CopyOnWriteArrayList for an event buffer?

Each mutation copies the backing array, so frequent writes to a large list create O(n) copying and substantial allocation/GC pressure.

Q6. Difference between put, offer, and add on a BlockingQueue?

Put waits for capacity; offer returns false immediately when it cannot insert; add throws an exception when insertion is not possible. Timed offer waits up to a specified duration.

Q7. ArrayBlockingQueue vs LinkedBlockingQueue?

ArrayBlockingQueue uses a fixed circular array and a shared lock. LinkedBlockingQueue uses linked nodes, can be explicitly bounded, and separates producer and consumer locks. Actual throughput depends on workload.

Q8. Is LinkedBlockingQueue always bounded?

No. Its no-argument constructor uses an effective capacity of Integer.MAX_VALUE. Specify a capacity when a backlog limit is required.

Q9. BlockingQueue vs ConcurrentLinkedQueue?

BlockingQueue supports waiting/timed operations and may impose capacity. ConcurrentLinkedQueue is non-blocking and unbounded; poll returns null immediately when empty.

Q10. Can thread-safe collections make a business workflow atomic?

Not automatically. Thread safety of individual calls does not make a multi-call check-then-act sequence atomic. Use atomic collection methods or a wider synchronization/transaction strategy.

Q11. How do you prevent an unbounded queue from exhausting memory?

Choose a bounded queue or a bounded admission policy, monitor queue depth and age, and define backpressure, rejection, persistence, or retry behavior.

Q12. Does lock-free mean there is no contention?

No. CAS retries can increase under contention, and lock-free algorithms can still consume CPU and have variable per-thread completion time.

Thumb rules

Do

  • Use atomic map methods for compound per-key updates.
  • Choose copy-on-write only for read-mostly collections.
  • Bound queues when memory and latency must be controlled.
  • Monitor queue depth, rejection, task age, and consumer throughput.

Avoid

  • Assuming thread-safe means every multi-step workflow is atomic.
  • Using a queue's size() as a concurrency guard.
  • Using an unbounded queue to hide sustained overload.
  • Choosing a collection based only on a benchmark from a different workload.
