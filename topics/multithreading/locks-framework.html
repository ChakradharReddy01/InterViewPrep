Locks Framework AQS Internals Optimistic Locking ⏱️ 45 min deep dive Target Roles: SDE-2, SDE-3, Senior Concurrency Engineer

1. ReentrantLock Architecture & AQS Internals

1.1 What is ReentrantLock?

ReentrantLock is a mutual exclusion lock implementing the Lock interface. Unlike intrinsic synchronized locks, it provides:

  • Timed Lock Acquisition: tryLock(timeout, unit) avoids indefinite blocking and deadlocks.
  • Interruptible Lock Acquisition: lockInterruptibly() allows a waiting thread to be cancelled via Thread.interrupt().
  • Fairness Policies: Optional FIFO fair queueing (new ReentrantLock(true)) to prevent thread starvation.
  • Multiple Wait Conditions: Associated with multiple independent Condition objects (e.g. notFull, notEmpty).
Canonical ReentrantLock Pattern Java 
private final ReentrantLock lock = new ReentrantLock();

public void performOperation() {
    lock.lock(); // Never put lock() inside the try block!
    try {
        // Critical section logic
    } finally {
        lock.unlock(); // Always release in finally to prevent permanent lock leaks!
    }
}

1.2 Under the Hood: AbstractQueuedSynchronizer (AQS)

ReentrantLock delegates its synchronization to an internal helper class that extends AbstractQueuedSynchronizer (AQS).

  • Volatile State: A single 32-bit volatile integer (private volatile int state;). In ReentrantLock, state == 0 means unlocked; state > 0 represents the reentrant hold count.
  • FIFO Node Queue: A doubly-linked CLH lock queue where blocked threads are queued as Node objects and parked using LockSupport.park().
  • Fair vs. Non-Fair:
    • Non-Fair (Default): When a thread invokes lock(), it immediately attempts an atomic CAS on the state without checking if other threads are waiting in the queue. Gives dramatically higher throughput due to CPU cache warmth.
    • Fair: Checks hasQueuedPredecessors() first. If threads are already waiting, the newcomer is appended to the tail of the queue. Lower throughput due to frequent thread parking.

2. ReentrantReadWriteLock (Read-Heavy Concurrency)

2.1 The Shared Read / Exclusive Write Paradigm

Standard mutual exclusion locks do not scale for Read-Heavy workloads where 99% of requests only read data without mutating it. ReentrantReadWriteLock splits locking into two complementary locks:

  • Read Lock (Shared): Multiple threads can acquire the read lock concurrently as long as no thread holds or is waiting for the write lock.
  • Write Lock (Exclusive): Only one thread can hold the write lock. While held, all read and write attempts are blocked.
Production ReadWriteLock Cache Pattern Java 
public class HighThroughputCache<K, V> {
    private final Map<K, V> store = new HashMap<>();
    private final ReentrantReadWriteLock rwLock = new ReentrantReadWriteLock();
    private final Lock readLock = rwLock.readLock();
    private final Lock writeLock = rwLock.writeLock();

    public V get(K key) {
        readLock.lock();
        try {
            return store.get(key); // Unlimited concurrent readers!
        } finally {
            readLock.unlock();
        }
    }

    public void put(K key, V value) {
        writeLock.lock();
        try {
            store.put(key, value); // Mutual exclusion
        } finally {
            writeLock.unlock();
        }
    }
}
⚠️ The Write Starvation & Upgrading Gotcha

1. Write Starvation: Under continuous streams of concurrent readers, writer threads can be starved indefinitely because new readers keep arriving and acquiring shared locks.
2. No Lock Upgrades: A thread holding a Read lock cannot upgrade to a Write lock (calling writeLock.lock() while holding readLock results in an immediate deadlock). However, Lock Downgrading (Write lock $\rightarrow$ Read lock $\rightarrow$ release Write lock) is fully supported.

3. StampedLock (Optimistic Read Locks - Java 8)

3.1 Why StampedLock Was Introduced

StampedLock overcomes the write starvation of ReentrantReadWriteLock by introducing a third mode: Optimistic Read.

An optimistic read does not acquire a lock at all! It simply returns a 64-bit numerical stamp (version token). The reader reads values into local variables, and then verifies whether a writer intervened by calling validate(stamp). If no writer acquired the lock, the read succeeded with zero cache line invalidation and zero synchronization overhead!

Optimistic Read Pattern in StampedLock Java 
public class Point {
    private double x, y;
    private final StampedLock sl = new StampedLock();

    public double distanceFromOrigin() {
        // 1. Try an Optimistic Read (Does NOT acquire a lock!)
        long stamp = sl.tryOptimisticRead();
        double currentX = x;
        double currentY = y;

        // 2. Validate if a writer mutated state while we read
        if (!sl.validate(stamp)) {
            // Optimistic read failed! Fall back to a fully pessimistic Read Lock:
            stamp = sl.readLock();
            try {
                currentX = x;
                currentY = y;
            } finally {
                sl.unlockRead(stamp);
            }
        }
        return Math.sqrt(currentX * currentX + currentY * currentY);
    }

    public void move(double deltaX, double deltaY) {
        long stamp = sl.writeLock(); // Exclusive write lock
        try {
            x += deltaX;
            y += deltaY;
        } finally {
            sl.unlockWrite(stamp);
        }
    }
}
🚨 StampedLock Architectural Warning: NOT Reentrant!

Unlike ReentrantLock, StampedLock is NOT REENTRANT! If a thread holding a write lock attempts to acquire the write lock again, it will deadlock itself immediately!

4. Condition (Multiple Wait-Sets per Lock)

In intrinsic synchronization, every object has exactly one wait set (wait(), notify()). Condition replaces monitor methods with await(), signal(), and signalAll(), bound directly to a Lock instance.

This allows creating multiple distinct wait sets for different predicates (e.g., waiting for buffer to not be full vs. waiting for buffer to not be empty).

Production Bounded Buffer (Producer-Consumer with Condition) Java 
public class BoundedBuffer<T> {
    private final Object[] items = new Object[100];
    private int putptr, takeptr, count;

    private final Lock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition(); // Wait-set for Producers
    private final Condition notEmpty = lock.newCondition(); // Wait-set for Consumers

    public void put(T x) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length) {
                notFull.await(); // Producers sleep here when buffer is full
            }
            items[putptr] = x;
            if (++putptr == items.length) putptr = 0;
            count++;
            notEmpty.signal(); // Wakes up only waiting CONSUMERS!
        } finally {
            lock.unlock();
        }
    }

    @SuppressWarnings("unchecked")
    public T take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0) {
                notEmpty.await(); // Consumers sleep here when buffer is empty
            }
            T x = (T) items[takeptr];
            if (++takeptr == items.length) takeptr = 0;
            count--;
            notFull.signal(); // Wakes up only waiting PRODUCERS!
            return x;
        } finally {
            lock.unlock();
        }
    }
}

5. Real-Time Production Issues & Post-Mortems

🚨 Incident 1: Write Starvation Outage in Stock Price Broadcast Engine

Scenario: During a market opening surge, an order matching engine's price updates lagged by 45 seconds. The writer thread updating market ticks was completely frozen, while read queries for stock quotes continued returning stale data.

🔍 Root Cause Analysis (RCA)

The market feed cache used a non-fair ReentrantReadWriteLock. Under 100,000 requests/sec, thousands of reader threads continuously acquired and released the shared read lock. Because at least one reader held the read lock at any given microsecond, the writer thread waiting for the exclusive write lock was starved and never granted access.

💡 Production Resolution
  • Migrated to StampedLock: Replaced ReentrantReadWriteLock with StampedLock's optimistic reads. Writers immediately acquire the write lock without waiting for optimistic readers.
  • Alternative: If using ReentrantReadWriteLock, instantiate with fairness enabled (new ReentrantReadWriteLock(true)) to prevent reader barge-in when a writer is queued.
🚨 Incident 2: Permanent Thread Lockup via Missing finally Block on ReentrantLock

Scenario: After throwing a runtime IllegalArgumentException in a payment processing service, all subsequent transactions hung indefinitely. Kubernetes readiness probes failed, causing cascading container restarts.

🔍 Root Cause Analysis (RCA)

An engineer called lock.lock() and placed lock.unlock() at the end of the method body without a try-finally block. When an unexpected exception was thrown midway through the method, execution aborted and unlock() was never called. The lock remained permanently held by the dead thread, blocking all future threads forever.

💡 Production Resolution

Enforced SonarQube rule: Every call to Lock.lock() must be immediately followed by a try-finally block with Lock.unlock() in the finally clause.

6. Senior / Staff Technical Interview Q&A

🎯 Q1: Why should lock.lock() be called OUTSIDE the try block?

Answer: If lock.lock() is placed inside the try block, and an unchecked exception occurs during the lock acquisition (e.g. Error, OutOfMemoryError), the flow jumps straight to the finally block and invokes lock.unlock(). Attempting to unlock a lock that was never successfully acquired by the current thread throws an IllegalMonitorStateException, which masks the real underlying error and corrupts state.

🎯 Q2: Can a thread holding a Read Lock in ReentrantReadWriteLock upgrade to a Write Lock?

Answer: No. Attempting to acquire a write lock while currently holding a read lock results in an immediate deadlock. To acquire a write lock, all read locks must first be completely released. However, a thread holding a Write lock can acquire a Read lock and then release the Write lock (known as Lock Downgrading).

🎯 Q3: How does StampedLock achieve higher performance than ReentrantReadWriteLock?

Answer: ReentrantReadWriteLock requires modifying shared memory state (incrementing the read lock counter in AQS via atomic CAS) on every single read operation. Across multiple CPU cores, this causes heavy cache line invalidation. StampedLock's optimistic read does not mutate any memory state or execute any CAS—it simply reads a volatile stamp and executes memory barriers. As long as writes are infrequent, reads operate at raw hardware memory speed.
