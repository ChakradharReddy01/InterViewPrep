Advanced Java Locks: ReentrantLock, ReentrantReadWriteLock, StampedLock & Condition

Understand the lock tools beyond synchronized: when each lock helps, how to use it safely, what can go wrong in production, and how to explain the trade-offs in an interview. The explanations begin with simple analogies and then move into implementation details.

ReentrantLock

One owner at a time, with timeouts, interruptible acquisition, and optional fairness.

ReadWriteLock

Many readers may coexist; writers need exclusive access.

StampedLock + Condition

Optimistic reads for selected workloads; separate condition queues for coordination.

1. ReentrantLock

Kid-friendly analogy: Imagine a room with one key. Only the person holding the key may enter. When finished, they must return the key. ReentrantLock is an explicit lock that your code acquires and releases.

It implements java.util.concurrent.locks.Lock and is useful when you need capabilities that intrinsic synchronized does not directly expose: timed acquisition, interruptible waiting, optional fairness, and multiple Condition queues.

Basic safe pattern

import java.util.concurrent.locks.ReentrantLock;

class Inventory {
    private final ReentrantLock lock = new ReentrantLock();
    private int stock = 10;

    boolean reserveOne() {
        lock.lock();
        try {
            if (stock == 0) {
                return false;
            }
            stock--;
            return true;
        } finally {
            lock.unlock(); // always release in finally
        }
    }
}
Critical rule: acquire the lock before entering the try, then unlock in finally. If code throws after acquiring the lock, finally still releases it. Never call unlock() unless the current thread successfully acquired that lock.

Useful acquisition choices

MethodBehaviorUse case
lock()Waits until acquired; not interruptible while waiting.Ordinary critical sections where waiting is acceptable.
lockInterruptibly()Allows a waiting thread to stop waiting when interrupted.Cancelable tasks and responsive shutdown.
tryLock()Returns immediately with success/failure.Optional work or avoiding indefinite waiting.
tryLock(timeout, unit)Waits up to a time limit, then returns false.Bounded lock wait with fallback/error response.

Timeout example

boolean updateWithDeadline() throws InterruptedException {
    if (!lock.tryLock(200, java.util.concurrent.TimeUnit.MILLISECONDS)) {
        return false; // report busy / retry later / degrade safely
    }
    try {
        updateSharedState();
        return true;
    } finally {
        lock.unlock();
    }
}

Timeouts bound the time spent waiting for this lock; they do not automatically bound work performed after the lock is acquired. A caller should define what a timeout means operationally—retry, return a busy response, or use a fallback.

Fair vs. non-fair

  • Non-fair (default): a new thread may acquire the lock ahead of queued waiters. Often gives higher throughput but does not promise first-come-first-served behavior.
  • Fair: queued waiters are favored in approximate arrival order, reducing some starvation risks but often lowering throughput.
ReentrantLock fairLock = new ReentrantLock(true);

Reentrancy

The same thread can acquire the same ReentrantLock multiple times. It must release it the same number of times before another thread can acquire it.

lock.lock();
try {
    nestedOperation(); // may acquire the same lock again
} finally {
    lock.unlock();
}

void nestedOperation() {
    lock.lock();
    try {
        // reentrant acquisition succeeds for the owning thread
    } finally {
        lock.unlock();
    }
}
Use it when: you need interruptible or timed lock acquisition, fairness configuration, or multiple condition queues. If you only need straightforward mutual exclusion, synchronized may be simpler.

2. ReentrantReadWriteLock

Kid-friendly analogy: In a library, many people can read the same book at once, but someone editing the master copy needs the room to themselves. A read-write lock models this pattern.

  • Read lock: multiple threads can hold it together, provided no writer owns the lock and acquisition policy allows them through.
  • Write lock: exclusive; while held, no other reader or writer can enter the protected region.
Reader A ---- READ LOCK ----\ Reader B ---- READ LOCK -----+---- can read concurrently Reader C ---- READ LOCK ----/ Writer ---- WRITE LOCK ---- exclusive access blocks readers and other writers

Example: in-memory configuration cache

import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantReadWriteLock;

class ConfigCache {
    private final Map data = new HashMap<>();
    private final ReentrantReadWriteLock rw = new ReentrantReadWriteLock();
    private final Lock readLock = rw.readLock();
    private final Lock writeLock = rw.writeLock();

    String get(String key) {
        readLock.lock();
        try {
            return data.get(key);
        } finally {
            readLock.unlock();
        }
    }

    void put(String key, String value) {
        writeLock.lock();
        try {
            data.put(key, value);
        } finally {
            writeLock.unlock();
        }
    }
}

This example protects the HashMap because it is not safe for concurrent mutation. The lock only protects accesses that use the same lock; returning a mutable object from the map may still expose state that callers can modify without protection.

Fairness, starvation, upgrade and downgrade

  • The default policy is non-fair. Under some access patterns, writers can wait a long time. Construct with new ReentrantReadWriteLock(true) if fairness is more important than peak throughput, then measure the impact.
  • Do not attempt a read-to-write upgrade by holding the read lock and then blocking on the write lock. The read lock prevents a writer from acquiring exclusive access, so this pattern can deadlock.
  • Downgrading is possible: acquire the write lock, acquire the read lock while still holding the write lock, then release the write lock. This lets the thread keep read protection after updating.
Lock read = rw.readLock();
Lock write = rw.writeLock();

write.lock();
try {
    refreshCache();
    read.lock(); // downgrade: acquire read before releasing write
} finally {
    write.unlock();
}
try {
    useFreshCacheUnderReadLock();
} finally {
    read.unlock();
}
Thumb rule: Read-write locks are not automatically faster. They add coordination overhead. Consider them when reads are frequent, the protected read work is substantial, writes are relatively rare, and profiling shows a normal mutex is a bottleneck.

3. StampedLock

Kid-friendly analogy: Instead of asking permission to read immediately, you take a quick look and note a version stamp. After reading, you check whether anyone changed the data while you were looking. If a writer did change it, throw away the result and read safely under a lock.

StampedLock provides write locks, read locks, and optimistic reads. An optimistic read does not hold a read lock. It returns a stamp that can later be validated. This can help read-mostly workloads when reads are short and writers are infrequent.

Correct optimistic read pattern

import java.util.concurrent.locks.StampedLock;

class Point {
    private double x;
    private double y;
    private final StampedLock lock = new StampedLock();

    double distanceFromOrigin() {
        long stamp = lock.tryOptimisticRead();
        double currentX = x;
        double currentY = y;

        if (!lock.validate(stamp)) {
            stamp = lock.readLock();
            try {
                currentX = x;
                currentY = y;
            } finally {
                lock.unlockRead(stamp);
            }
        }
        return Math.hypot(currentX, currentY);
    }

    void move(double newX, double newY) {
        long stamp = lock.writeLock();
        try {
            x = newX;
            y = newY;
        } finally {
            lock.unlockWrite(stamp);
        }
    }
}

The reader copies the fields to local variables, validates the stamp, and falls back to a read lock if a write overlapped. Validation must happen before the read result is trusted. Keep the optimistic read region simple; do not use unvalidated data to make irreversible decisions.

StampedLock rules that matter

  • Not reentrant: a thread must not recursively acquire a lock mode it already holds as if it were reentrant; designs that do this can deadlock.
  • Lock methods return a stamp token. Pass the correct token to the corresponding unlock method.
  • It does not implement the Lock interface in the same way as ReentrantLock; its API is stamp-based.
  • Optimistic reads can fail validation. Always implement a safe fallback.
  • It is more complex than a read-write lock; use it only when measurement shows the optimistic-read pattern is beneficial.
Safety warning: Optimistic reads are not “read anything without protection.” The fields and object graph must be designed so that reading during a concurrent write is safe enough to validate and retry. Avoid dereferencing mutable structures in a way that can break before validation.

4. Condition

Kid-friendly analogy: In a classroom, one queue waits for seats to become free, while another queue waits for students to arrive. A Condition lets threads wait for different conditions associated with the same lock.

A Condition is created by calling newCondition() on a Lock. It provides await(), signal(), and signalAll(), which correspond conceptually to object monitor waiting and notification—but can support multiple distinct wait queues per lock.

Bounded buffer: producer and consumer

import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

class BoundedBuffer {
    private final Object[] items = new Object[100];
    private int putIndex, takeIndex, count;

    private final Lock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    public void put(T item) throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == items.length) {
                notFull.await();
            }
            items[putIndex] = item;
            putIndex = (putIndex + 1) % items.length;
            count++;
            notEmpty.signal(); // a consumer may proceed
        } finally {
            lock.unlock();
        }
    }

    @SuppressWarnings("unchecked")
    public T take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == 0) {
                notEmpty.await();
            }
            T item = (T) items[takeIndex];
            items[takeIndex] = null;
            takeIndex = (takeIndex + 1) % items.length;
            count--;
            notFull.signal(); // a producer may proceed
            return item;
        } finally {
            lock.unlock();
        }
    }
}

How it works visually

Producer Shared buffer Consumer -------- ------------- -------- if buffer full: notFull.await() -----------> waits in notFull queue put item ---------------------> count increases notEmpty.signal() -----------------------------------------------> wakes consumer take item <------------------------------------------------------- count decreases notFull.signal() <------------- wakes producer if one is waiting
  • Call await() while holding the associated lock. It releases the lock while waiting and reacquires it before returning.
  • Use a while loop, not if, to re-check the condition after wakeup.
  • Always unlock in finally.
  • Choose signal() when one waiting thread is enough and the condition design is clear; use signalAll() when multiple waiters may now proceed or when signaling one waiter could leave the system stuck.
  • If await() throws InterruptedException, it is usually best to propagate it or restore the interrupt flag if you catch it and cannot propagate it.
Production shortcut: For a standard producer-consumer queue, prefer BlockingQueue unless you need custom coordination. It already handles waiting, signaling, capacity, and many edge cases.

6. Production Issues and Solutions

Incident A — Lock leak after an exception

Symptom: requests begin hanging after a validation exception; threads pile up waiting for one lock.

Cause: code acquired a ReentrantLock but called unlock() only at the end of the method. An exception skipped the unlock.

Solution: always use try/finally; enforce the pattern in review and static analysis.

Incident B — Writer waits behind continuous readers

Symptom: cache refresh or configuration updates are delayed while reads keep succeeding.

Cause: lock policy and workload allow long reader activity or reader traffic delays a writer.

Solution: measure lock wait times; consider fair ReentrantReadWriteLock, shorter read critical sections, immutable snapshot replacement, or a carefully validated StampedLock optimistic-read design. No lock is a universal fix.

Incident C — Deadlock from attempted lock upgrade

Symptom: a thread holds a read lock and waits forever for the write lock.

Cause: the thread's own read hold prevents the exclusive write lock from being acquired.

Solution: release read lock, acquire write lock, then re-check the condition before modifying. Or redesign the operation; avoid assuming upgrade is atomic.

Incident D — Incorrect optimistic read

Symptom: intermittent inconsistent calculations or exceptions under concurrent writes.

Cause: code trusted fields read optimistically before validating the stamp, or traversed mutable structures unsafely.

Solution: copy only safe-to-read fields into locals, validate before using the result, and fall back to a real read lock on failure.

Incident E — Wrong wait queue signaled

Symptom: producers and consumers stop making progress even though a condition may now be true.

Cause: a single generic wait queue or incorrect signaling wakes a thread whose predicate is still false.

Solution: use distinct conditions such as notFull and notEmpty, loop around await(), and signal the waiter category that can make progress.

Diagnostics checklist

  • Capture multiple thread dumps and identify lock owners and waiters.
  • Measure lock wait duration, hold duration, queue depth, throughput, and request latency.
  • Use Java Flight Recorder to inspect monitor/park events where available.
  • Load-test with realistic reader/writer ratios before choosing a lock implementation.
  • Never assume that a JVM lock protects shared data across multiple JVMs or containers.

7. Thumb Rules to Memorize

ReentrantLock

  • Every successful acquisition needs a matching unlock.
  • Unlock in finally.
  • Use timed or interruptible acquisition when waiting must be bounded or cancellable.

ReentrantReadWriteLock

  • Use only when reads dominate and contention makes it worthwhile.
  • Read-to-write upgrade is not supported as a simple blocking operation.
  • Write-to-read downgrade is possible in the right order.

StampedLock

  • Optimistic reads must be validated.
  • Use the exact stamp to unlock.
  • It is not reentrant; keep the design simple.

Condition

  • Call await() while holding its associated lock.
  • Check the predicate in a while loop.
  • Use separate Conditions for separate predicates when helpful.
Memory trick: ReentrantLock = control; ReadWriteLock = shared readers / exclusive writer; StampedLock = stamp + validate; Condition = wait for a specific condition.

8. Interview Questions with Model Answers

Q1. Why use ReentrantLock instead of synchronized?

Both provide mutual exclusion. I choose ReentrantLock when I need timed acquisition, interruptible waiting, an optional fairness policy, or multiple Condition queues. Otherwise, synchronized is often simpler and releases its monitor automatically at scope exit.

Q2. Why must unlock be in finally?

Any exception or early return after acquiring a lock could skip ordinary cleanup code. A finally block guarantees release on normal and exceptional exits, preventing lock leaks and indefinite blocking.

Q3. What is the difference between fair and non-fair ReentrantLock?

A fair lock favors queued waiters and can reduce starvation risk, but may reduce throughput. A non-fair lock lets a new arrival acquire ahead of queued threads, often improving throughput but offering no strict arrival-order guarantee.

Q4. When does ReentrantReadWriteLock help?

It can help when shared state is read frequently, writes are relatively rare, and the protected read operation is large enough that allowing concurrent readers offsets the coordination cost. I would benchmark it rather than assume it is faster.

Q5. Why is read-to-write lock upgrade dangerous?

A writer needs exclusive access, but the current thread's read hold prevents that exclusivity. Blocking on the write lock while retaining the read lock can deadlock. Release the read lock, acquire write, and re-check the predicate.

Q6. How does StampedLock optimistic reading work?

The reader gets an optimistic stamp, copies the relevant fields, and validates the stamp. If a writer intervened, validation fails and the reader repeats the read under a real read lock. It can reduce reader coordination in read-mostly workloads, but is more complex and not reentrant.

Q7. What is a Condition and why have multiple Conditions?

A Condition is a wait queue associated with a Lock. It allows threads to wait for predicates such as “buffer not full” and “buffer not empty” separately, so a producer can signal a consumer rather than waking an unrelated producer.

Q8. Why use while instead of if around await?

A wakeup does not prove the condition is true. Wakeups may be spurious, and another thread may consume the available resource before the awakened thread reacquires the lock. The predicate must be re-checked in a loop.

Q9. Are these locks distributed locks?

No. They coordinate threads inside the same JVM process. For shared state across application instances, use an appropriate shared-system mechanism such as database constraints/transactions or a distributed coordination service where justified.

Q10. How do you decide which lock is fastest?

I would identify the invariant and workload first, then measure contention and throughput under representative read/write ratios. Correctness and maintainability come first; optimistic or read-write locks should be chosen only when their trade-offs fit the workload.
