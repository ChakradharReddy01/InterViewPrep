Redis Architecture

What Redis is

Redis is an in-memory data-structure server that exposes commands over a network protocol. It stores values under keys, but values can be strings, hashes, lists, sets, sorted sets, streams, and other supported types. It is commonly used for caching, counters, sessions, rate limits, leaderboards, coordination, and event processing.

Java / Spring Boot application | | Redis protocol (TCP; commonly RESP) v +-----------------------------------+ | Redis server / primary | | Keyspace + data structures | | Command execution | | Expiration + eviction | | Optional persistence | +----------------+------------------+ | replication / cluster / \ v v Replica node Other shard nodes

Key-value model

SET user:42:name "Asha"
GET user:42:name
# "Asha"

HSET user:42 name "Asha" city "Bengaluru"
HGET user:42 name
# "Asha"

Execution and performance

Redis command execution is largely single-threaded for many core data operations, which avoids many concurrent mutation races within a command. Modern Redis can use I/O threads for some networking work and has additional background activities; do not generalize this to “Redis uses only one thread for everything.” Large or computationally expensive commands can still block command processing and create latency spikes.

Important operational concepts

  • Keyspace: the set of keys in a Redis database.
  • Data type: determines which commands are valid for a key.
  • Logical database: selected with SELECT in deployments that support multiple logical DBs; Redis Cluster supports only database 0.
  • Persistence: optional RDB snapshots and/or AOF logging, depending on configuration.
  • Replication: copies data from a primary to replicas, generally asynchronously.
  • Cluster: distributes keys across shards and supports resharding/failover.
Design rule: keep keys bounded, use suitable data structures, avoid unexpectedly large blocking operations, monitor memory and latency, and decide explicitly whether each dataset is disposable cache data or data that requires durable recovery.

1. String

Definition

Redis String is a binary-safe value type. It can store text, serialized JSON, bytes, numbers represented as strings, and counters. It is often used for simple cache entries, tokens, flags, counters, and distributed-lock values.

Commands

SET product:100:name "Mechanical Keyboard"
GET product:100:name
SET session:abc "serialized-session" EX 1800
INCR page:views
INCRBY wallet:balance 500
MSET feature:a "on" feature:b "off"
MGET feature:a feature:b

Visual example

Key Value product:100:name → "Mechanical Keyboard" page:views → "12501" session:abc → serialized session (TTL 1800s)

Atomic increments

INCR and INCRBY atomically update integer-valued strings at the command level, making them useful for counters and some rate-limit implementations. They do not create a complete business transaction across Redis and another database.

Expiration on writes

SET key value normally replaces the value and clears an existing TTL unless an expiration is supplied again. Use SET key value EX 60 or supported conditional options when you want the TTL applied with the value write.

Common mistakes

  • Storing a huge object as one string when field-level updates are needed.
  • Assuming a counter update and SQL database update are atomic together.
  • Overwriting a key and unintentionally removing its previous expiration.
  • Using unbounded key names or embedding sensitive data without access controls.

2. Hash

Definition

A Redis Hash stores field-value pairs under one Redis key. It is useful for compact object-like records when individual fields need to be read or updated.

HSET user:42 name "Asha" city "Bengaluru" plan "premium"
HGET user:42 name
HGETALL user:42
HINCRBY user:42 loginCount 1
HDEL user:42 plan
Redis key: user:42 +---------------------------+ | name → "Asha" | | city → "Bengaluru" | | plan → "premium" | | loginCount → "12" | +---------------------------+

Why use a Hash?

  • Read or update selected fields without replacing a full serialized object.
  • Use commands such as HINCRBY for atomic field increments.
  • Organize related fields under a predictable key.

Hash versus JSON string

HashSerialized JSON String
Field-level commands such as HGET/HSET.Often fetch and deserialize the entire JSON value.
Simple scalar fields.Naturally represents nested structures.
Field updates are convenient.Application controls serialization and schema.

Redis Hash is not automatically a relational table or a schema-enforced object. Plan key naming, field evolution, and object size. TTL normally applies to the entire hash key; field-level expiration capabilities depend on Redis version and should not be assumed on older deployments.

3. List

Definition

A Redis List is an ordered sequence of values. It supports pushes and pops at either end, making it useful for simple queues, recent-item lists, and bounded activity histories.

LPUSH jobs "job-3" "job-2" "job-1"
LRANGE jobs 0 -1
RPOP jobs
RPUSH recent:users "u1"
LTRIM recent:users 0 99
BLPOP simple-queue 5
LPUSH jobs job-3 job-2 job-1 LEFT RIGHT | | v v [job-1] ⇄ [job-2] ⇄ [job-3] RPOP → removes job-3 (rightmost item)

List as a queue

Producer pushes jobs and a consumer pops them. Blocking pops wait for work instead of repeatedly polling. However, a simple pop removes the item immediately; if the consumer crashes after popping, the item can be lost.

Safer queue handling

For reliable work queues, consider Redis Streams consumer groups, or an explicit processing/acknowledgment pattern. Redis Lists also support reliable-list patterns using move commands, but recovery and visibility-timeout behavior must be designed carefully.

Complexity and pitfalls

End operations are efficient; operations such as indexing or removing arbitrary elements can cost more. Use LTRIM to bound history lists and avoid unlimited growth.

4. Set

Definition

A Redis Set is an unordered collection of unique string members. It is useful for membership tests, deduplication, tags, and set algebra.

SADD product:100:tags "wireless" "keyboard" "office"
SISMEMBER product:100:tags "wireless"
SMEMBERS product:100:tags
SREM product:100:tags "office"
SINTER team:backend team:oncall
SUNION campaign:a campaign:b
Set: product:100:tags { "wireless", "keyboard", "office" } SADD ... "wireless" again → cardinality stays unchanged (member is unique)

Useful operations

  • SISMEMBER: test membership.
  • SADD: add unique members.
  • SINTER: find members common to sets.
  • SUNION: combine members.
  • SDIFF: find members present in one set but not another.

Set order is not guaranteed. Avoid returning a huge SMEMBERS result on a hot path; use scanning patterns where suitable and keep collection sizes controlled.

5. Sorted Set (ZSET)

Definition

A Sorted Set stores unique members associated with numeric scores. Redis orders members by score, with lexicographic ordering used to break score ties. It is useful for leaderboards, ranking, scheduled tasks, and time-based indexes.

ZADD leaderboard 1200 "player:alice"
ZADD leaderboard 980 "player:bob"
ZADD leaderboard 1500 "player:chen"
ZREVRANGE leaderboard 0 9 WITHSCORES
ZRANK leaderboard "player:bob"
ZINCRBY leaderboard 50 "player:bob"
ZRANGEBYSCORE scheduled:jobs -inf 1760000000
Leaderboard (score descending) 1. player:chen 1500 2. player:alice 1200 3. player:bob 1030 ← after ZINCRBY 50 Member uniqueness: one member has one current score per sorted set.

Use cases

  • Top-N leaderboard and player rank.
  • Scheduled work ordered by due-time score.
  • Recent events indexed by timestamp.
  • Priority queue-like ordering.

Scores are IEEE-754 double precision numbers, so integers are exactly representable only within the safe precision range. For high-resolution timestamps or composite ordering, choose a representation that preserves the needed precision. A Sorted Set is not by itself a durable job scheduler; handle claims, retries, crashes, and duplicate work explicitly.

6. TTL (Time To Live)

Definition

TTL is the remaining lifetime before a key expires. It is commonly used for cache freshness, sessions, temporary tokens, locks, and short-lived deduplication records.

SET cache:product:100 '{"name":"Keyboard"}' EX 300
TTL cache:product:100
PTTL cache:product:100
EXPIRE cache:product:100 60
PERSIST cache:product:100
t = 0s t = 100s t = 300s SET EX 300 → TTL ≈ 200s → key expires | v GET → nil

TTL command results

  • Non-negative value: remaining seconds (or milliseconds for PTTL).
  • -1: key exists but has no expiration.
  • -2: key does not exist.

Important behaviors

  • Expiration is attached to the key, not ordinarily each field in a hash or member in a set.
  • Replacing a value with commands such as ordinary SET may clear the TTL unless the command also sets/retains expiration as supported.
  • TTL is not a promise of deletion at an exact wall-clock millisecond.
  • For caches, TTL is a freshness policy—not a substitute for explicit invalidation where correctness requires it.

7. Expiration

TTL vs expiration

TTL is the remaining-time measurement; expiration is the mechanism/policy that marks a key to expire at a deadline or after a duration.

How Redis expires keys

Redis uses a combination of passive expiration (when a key is accessed and found expired) and active expiration (periodically sampling expiring keys and removing expired ones). Therefore, an expired key is treated as absent, but physical cleanup need not occur at the exact deadline.

Key has expiry timestamp | +--> command accesses key after expiry | → treated as absent (passive) | +--> periodic expiration work → expired keys sampled/removed (active)

Commands

EXPIRE session:abc 1800
EXPIREAT promotion:active 1760000000
PEXPIRE token:abc 30000
SET otp:123456 "used" EX 300

Expiration design

  • Use shorter TTLs for rapidly changing data and longer TTLs for stable reference data, based on business freshness requirements.
  • Add random TTL jitter to many similar keys to avoid synchronized expirations.
  • Refresh TTL deliberately for sliding sessions; fixed TTL and sliding TTL have different security and lifecycle semantics.
  • Do not rely on key expiration alone to perform business cleanup actions.

8. Cache Aside (Lazy Loading)

Definition

The application checks Redis first. On a cache miss, it reads the system-of-record database, puts the result in Redis, and returns it. The application controls cache population and invalidation.

Request | v Redis GET key | +---- HIT ----> return cached value | +---- MISS | v Read database | v Populate Redis with TTL | v Return value

Java-style example

Product getProduct(long id) {
    String key = "product:" + id;
    Product cached = redis.get(key);
    if (cached != null) return cached;

    Product product = repository.findById(id)
        .orElseThrow();

    redis.set(key, serialize(product), Duration.ofMinutes(5));
    return product;
}

This is pseudocode; production code must handle serialization, cache errors, null/not-found results, and concurrent misses.

Write path

A common pattern is: update the database transactionally, then invalidate the corresponding cache key after the database commit. Deleting the key often avoids serving an old cached value indefinitely. Invalidation timing and concurrent requests can still create races.

Advantages and drawbacks

  • Simple and widely applicable.
  • Only accessed data is cached.
  • Cache failure can fall back to the database if capacity allows.
  • Misses add latency and database load.
  • Hot keys can trigger stampedes.
  • Invalidation and stale-read races require explicit policy.

9. Write Through

Definition

In a write-through design, a write is propagated through the cache layer to the underlying data store before the operation is reported successful. The intended effect is to keep cache and backing data aligned on the write path.

Application | v Write-through layer | | v v Redis cache Primary database \ / completion after defined writes

Example workflow

  1. Application requests an update to product 100.
  2. Write-through component updates the authoritative store.
  3. It updates or refreshes the Redis representation according to the chosen protocol.
  4. The request completes according to the system's defined success conditions.

Benefits

  • Frequently accessed updated values may already be cached.
  • Centralized write logic can reduce stale-cache windows.

Trade-offs

  • Write latency increases because cache and backing-store work is coupled.
  • A partial failure can still occur unless a transaction/protocol handles it.
  • Cache entries may be written for data that is rarely read.
Important: Redis and a relational database generally do not share one atomic transaction. “Write-through” is a cache strategy, not a guarantee that two separate stores commit atomically. Define failure recovery and invalidation behavior.

10. Write Behind (Write Back)

Definition

Write-behind accepts a write into the cache layer first and persists it to the backing database asynchronously later.

Application | v Redis / write-behind buffer | immediate acknowledgment (by design) | +---- async worker / durable queue ----> Database

Example

A high-volume counter or telemetry pipeline may aggregate updates in memory and periodically flush batches to a database. This can reduce database write load, but only if the durability contract allows buffering and delayed persistence.

Benefits

  • Lower write latency for the caller.
  • Batching can reduce backing-store overhead.
  • Multiple updates may be coalesced.

Risks

  • Recent writes can be lost if acknowledged data is not durably recoverable and Redis fails.
  • Database lag can grow without bounds.
  • Flush failures, duplicate flushes, and ordering must be handled.
  • Reads from the database can lag behind accepted cache writes.
Do not casually use write-behind for financial balances or critical orders. A plain Redis write followed by an in-memory background task is not a durable write-behind system. Use a durable queue/log, retryable delivery, idempotent database writes, and monitoring if the use case requires this model.

11. Cache Eviction

Definition

Eviction is the policy Redis uses to decide what keys to remove when memory use reaches the configured maximum. Expiration and eviction are different: expiration removes keys whose TTL has elapsed; eviction removes keys to manage memory under the configured policy.

Common maxmemory policies

PolicyBehaviorTypical consideration
noevictionDoes not evict keys; memory-growing writes may fail at the limit.Useful when silently removing keys is unacceptable, but callers must handle write errors.
allkeys-lruEvicts keys approximating least recently used across all keys.General cache workload with recency locality.
allkeys-lfuEvicts keys approximating least frequently used across all keys.Workloads where repeated access frequency predicts future demand.
volatile-lruEvicts LRU keys among keys with expiration set.Only TTL-bearing keys are candidates.
volatile-lfuLFU-style eviction among expiring keys.Only TTL-bearing keys are candidates.
volatile-ttlPrefers expiring keys with shorter remaining TTL.TTL-based prioritization, not a pure popularity strategy.
volatile-random / allkeys-randomRandom eligible key selection.Useful only for workloads where random eviction is acceptable.

Exact policy availability and details can vary by Redis version. Check the deployed version's documentation and configuration.

Choosing a policy

  • For a pure cache, an all-keys LRU/LFU policy is often a starting point.
  • For mixed cache and critical data, separating instances or workloads is usually safer than relying on one eviction policy to protect everything.
  • Set memory headroom for replication buffers, client buffers, fragmentation, and persistence activity.
  • Monitor memory, evictions, rejected writes, hit ratio, and latency.

12. Distributed Lock

Purpose

A distributed lock coordinates workers across processes or machines so that only one holder should perform a protected operation at a time. Redis can implement a lease-based lock, but correctness depends on acquisition, expiration, ownership, and failure handling.

Basic acquisition

SET lock:invoice:123 random-owner-token NX PX 10000

NX means create only if the key does not exist; PX 10000 sets a 10-second lease. The owner token must be unique for each acquisition attempt.

Worker A: SET lock NX PX 10000 → OK Worker B: SET lock NX PX 10000 → nil Worker A does protected work Worker A releases only if token still matches

Safe release

-- Lua script: compare-and-delete atomically
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end

Do not blindly DEL the lock key. The lease may have expired and another worker may have acquired the same key; the original worker must not delete the new owner's lock.

Important limitations

  • A process can pause longer than the lease, then resume and continue its protected operation after another worker has acquired the lock.
  • Redis failover/replication behavior can complicate lock guarantees.
  • Use fencing tokens or downstream version checks when stale holders must be prevented from modifying protected resources.
  • Keep critical sections bounded; renew leases only with a safe ownership check.
  • For high-stakes coordination, evaluate whether a consensus-backed coordination system or database-level concurrency control is more appropriate.
Critical: a Redis lock alone does not prove that only one worker can ever perform a side effect under all pauses, partitions, and failovers. The protected resource should reject stale owners when strict correctness is required.

13. Pub/Sub

Definition

Redis Pub/Sub lets publishers send messages to channels, and currently subscribed clients receive them. It is a lightweight, real-time broadcast mechanism.

Publisher A ---- publish("price-updates", event) | v Redis channel / \\ v v Subscriber B Subscriber C
PUBLISH price-updates '{"productId":100,"price":99.5}'
SUBSCRIBE price-updates
PSUBSCRIBE price-*

Characteristics

  • Messages are delivered to active subscribers, subject to connection and delivery behavior.
  • Messages are not stored as a durable backlog for clients that were disconnected.
  • There is no consumer-group acknowledgment/replay mechanism comparable to Streams.
  • It is useful for live notifications, ephemeral signals, and cache-invalidation hints when missed messages can be recovered.
Do not use Pub/Sub as a durable job queue. If a disconnected subscriber must later process every event, use Redis Streams or a durable message broker with the needed persistence and acknowledgment semantics.

14. Redis Streams

Definition

Redis Streams is an append-oriented log data structure. Entries have IDs and fields, can be read by consumers, and support consumer groups with pending-entry tracking and acknowledgment.

XADD orders * orderId 123 status CREATED | v Redis Stream: orders | Consumer Group / \\ v v consumer-A consumer-B | XACK after processing

Commands

XADD orders * orderId 123 status CREATED
XRANGE orders - +
XGROUP CREATE orders order-workers $ MKSTREAM
XREADGROUP GROUP order-workers worker-1
  COUNT 10 BLOCK 5000 STREAMS orders >
XACK orders order-workers 1710000000000-0
XPENDING orders order-workers
XAUTOCLAIM orders order-workers worker-2 60000 0-0 COUNT 10

Line breaks are for readability; enter commands according to your Redis client/shell. A real consumer must use the actual IDs returned by Redis and handle empty reads, pending entries, and errors.

Consumer group lifecycle

  1. Producer appends an entry.
  2. A consumer group distributes new entries among its consumers.
  3. Delivered-but-unacknowledged entries are tracked in the Pending Entries List.
  4. Consumer performs the business operation.
  5. Consumer acknowledges with XACK after successful processing.
  6. Recovery logic inspects pending entries and reclaims work from failed consumers.

Streams vs Pub/Sub

Pub/SubStreams
Live broadcast to active subscribers.Stored entries that can be read later within retention.
No built-in replay backlog.Supports IDs, replay/range reads, and consumer groups.
No per-message acknowledgment.Consumer groups track pending messages and support acknowledgment.
Good for ephemeral notifications.Good for recoverable event processing, within Redis durability limits.

Production considerations

Define retention/trimming, consumer lag alerts, pending-entry recovery, idempotent processing, ordering requirements, and persistence. Streams are more recoverable than Pub/Sub but are not automatically equivalent to a fully managed durable event platform.

15. Persistence

What persistence means

Redis persistence saves data to storage so it can be restored after a process restart. Redis is often used as a disposable cache, but it can also hold data whose recovery matters. The required recovery-point objective (RPO) and recovery-time objective (RTO) should determine the configuration.

RDB snapshots

Point-in-time snapshots written to an RDB file.

Typical trade-off: compact backups and fast restoration, but recent writes after the last snapshot may be lost.

AOF log

Records write operations in an append-only log that can be replayed.

Typical trade-off: potentially smaller loss window depending on fsync policy, but larger files and rewrite/restore overhead.

RDB + AOF

Redis can be configured to use both. They solve related but different recovery needs. Persistence is not a replacement for backups, replication, disaster recovery, or a database designed to be the authoritative store for critical business data.

Questions to answer before production

  • How much recent data may be lost on process/host failure?
  • How long may recovery take?
  • Where are backups stored and how are restores tested?
  • Can disk saturation or persistence forks affect latency?
  • Is Redis data authoritative or rebuildable from a database/event log?

16. RDB (Redis Database Snapshot)

Definition

RDB produces point-in-time snapshots of the dataset in a compact binary file. Depending on configuration and command, Redis can create snapshots periodically or on demand.

Redis in-memory dataset | snapshot trigger | v background save process | v dump.rdb file | v restore at startup

Example configuration

save 900 1
save 300 10
save 60 10000

These example rules request snapshots when at least the stated number of changes occur within each interval. Actual configuration syntax and defaults depend on Redis version/distribution; inspect the running server configuration.

Advantages

  • Compact representation and often efficient restore.
  • Convenient for backups and moving snapshots.
  • Can limit disk-write overhead compared with logging every operation.

Disadvantages

  • Changes since the last successful snapshot may be lost.
  • Background save can consume CPU and memory; copy-on-write can increase memory pressure.
  • Snapshot frequency affects RPO, I/O, and resource use.

Test actual restore procedures and verify snapshot freshness. A file existing on disk does not prove it is recent, complete, or restorable.

17. AOF (Append Only File)

Definition

AOF records write operations in a log that Redis can replay during recovery. It can reduce the recovery gap relative to periodic snapshots, depending on fsync policy and storage behavior.

Client write command | v Redis executes command | v Append operation to AOF | fsync policy | v Durable log (subject to OS/storage guarantees)

Fsync policies

PolicyTrade-off
appendfsync alwaysRequests synchronization for each write operation; potentially higher write latency.
appendfsync everysecCommon balance between performance and durability; a crash may lose roughly the latest second of writes under normal assumptions.
appendfsync noLets the operating system decide when to flush; can improve throughput but may widen the loss window.

These are practical expectations, not absolute guarantees under every hardware, kernel, or storage failure.

AOF rewrite

As the log grows, Redis can rewrite it into a more compact sequence representing the current dataset. AOF rewrite is not simply deleting old bytes; Redis constructs a compact representation while preserving ongoing writes.

RDB vs AOF

RDBAOF
Snapshot of dataset at a point in time.Replayable log of write operations.
Often compact and fast to restore.Can provide a smaller loss window based on fsync policy.
May lose writes since last snapshot.May need more disk and replay time; rewrite is needed.

18. Replication

Definition

Redis replication copies data from a primary to one or more replicas. Replicas can serve selected read workloads and support failover systems, but replication is generally asynchronous.

Application writes | v +-------------+ | Primary | +------+------+ | replication stream / \\ v v +-----------+ +-----------+ | Replica 1 | | Replica 2 | +-----------+ +-----------+

Benefits

  • Replica copies can support failover orchestration.
  • Read traffic can be distributed where stale reads are acceptable.
  • Multiple copies can improve availability planning.

Important limitations

  • Asynchronous replication means a primary can acknowledge a write before replicas receive it.
  • If the primary fails before replication, a failover may lose recently acknowledged writes.
  • Replica reads may be stale.
  • Replication does not by itself create a backup; deletions and corrupt writes can propagate.
  • Failover orchestration, monitoring, and recovery are still required.

Sentinel and Cluster

Redis Sentinel monitors non-clustered primary/replica deployments and can coordinate failover. Redis Cluster shards data and has its own replica/failover behavior. They are different deployment modes; Sentinel is not the manager for Redis Cluster.

Consistency note: replication improves availability and can provide copies, but it is not a guarantee of strong consistency or zero data loss.

19. Redis Cluster

Why cluster?

Redis Cluster distributes the keyspace across multiple primary shards and supports replica-based failover. It helps scale data capacity and throughput beyond one primary, with operational and multi-key constraints.

Client / Cluster-aware Redis client | key hash → slot | +-------+--------+---------+ | | | v v v Shard A Shard B Shard C slots range slots slots Primary Primary Primary | | | Replica Replica Replica

Hash slots

Redis Cluster has 16,384 hash slots. A key is mapped to a slot, and each primary owns a range/set of slots. The client follows redirections such as MOVED and may handle ASK during slot migration.

Hash tags for related keys

SET cart:{user42}:items "..."
SET cart:{user42}:total "..."

The substring inside braces is used for hash-slot calculation when present, so keys with the same hash tag can be placed in the same slot. This can enable supported multi-key operations and Lua scripts that require keys in one slot.

Limitations

  • Multi-key commands and transactions generally require relevant keys to be in the same slot.
  • Some administrative and database features differ from standalone Redis.
  • Resharding, replica health, and slot balance require monitoring.
  • A single hot key remains on one shard and can become a bottleneck.
  • Failover can lose writes that had not replicated.

Cluster vs Sentinel

Redis ClusterRedis Sentinel
Shards keyspace across primaries and supports replica failover.Monitors a non-clustered primary/replica setup and coordinates failover.
For horizontal data partitioning and availability.For availability/failover without cluster sharding.
Requires cluster-aware clients and slot routing.Clients discover the current primary through Sentinel-aware integration.

20. Cache Consistency

What consistency means here

Cache consistency concerns whether the value returned by Redis matches the latest authoritative state to the degree the application requires. A cache can be stale because writes, invalidations, events, and replicas do not update simultaneously.

Common write-and-invalidate flow

1. Update product in database 2. Commit database transaction 3. Delete Redis key product:100 4. Next reader misses cache 5. Reader loads new DB value and repopulates Redis

Why invalidation races happen

Reader A: cache miss → reads old DB value Writer B: updates DB → deletes cache key Reader A: writes old value into cache Later reads see stale value until expiry/next invalidation

Deleting the key after the database commit is common, but it does not eliminate every race. Stronger requirements may need versioned values, compare-and-set logic, event ordering, or reading from the authoritative store after a write.

Strategies

  • TTL: bounds staleness approximately; does not guarantee immediate freshness.
  • Invalidate on write: delete affected cache entries after a committed database update.
  • Update cache on write: can reduce misses but needs careful ordering/failure handling.
  • Versioning: associate values with versions to prevent older data overwriting newer data.
  • Outbox/event invalidation: reliably publish invalidation/update events after the DB commit, while still handling duplicate and delayed events.
  • Read-your-writes: route the caller to authoritative data or use a version/session strategy when needed.
Design decision: define the freshness requirement per data type. A product description may tolerate seconds of staleness; an available balance, access-control decision, or inventory reservation may require a stricter authoritative path.

21. Cache Stampede (Thundering Herd)

Definition

A cache stampede occurs when a popular key expires or is evicted and many requests simultaneously miss the cache, causing a burst of duplicate database or downstream work.

Popular key expires | v 1,000 concurrent requests → Redis MISS | +----> DB query +----> DB query +----> DB query +----> hundreds more queries | v database overload

Mitigation 1: request coalescing / single-flight

Within an application instance, allow one request to load a missing key while other requests await its result. This reduces duplicate loads locally, but multiple service instances may still each load the same key.

Mitigation 2: distributed lock

Use a short-lived lock for cache regeneration when cross-instance coordination is required. Set a bounded wait, unique owner token, safe compare-and-delete release, and a fallback policy. Locks must not become a new bottleneck or correctness hazard.

Mitigation 3: TTL jitter

baseTTL = 300 seconds
actualTTL = baseTTL + random(0..60 seconds)

Randomized expiration spreads load across time. It is most useful when many keys are populated together.

Mitigation 4: stale-while-revalidate

Keep a stale-but-acceptable value available for a short grace period while one worker refreshes it in the background. This reduces latency and load, but only works when serving stale data is safe for that business domain.

Mitigation 5: pre-warming and rate controls

  • Refresh known hot keys before expiration.
  • Limit concurrent database loads and apply backpressure.
  • Use negative caching for safe not-found results to avoid repeated misses.
  • Monitor cache misses, hot keys, database query volume, and refresh latency.
Do not confuse: a cache stampede is many concurrent misses for the same or popular keys; cache penetration is repeated requests for keys that do not exist; cache avalanche is a broad surge of expirations or cache failure affecting many keys.

End-to-End Example: Product Cache in a Java Service

Operational checklist

  • Choose a cache key format and version it when serialized schemas change.
  • Set explicit TTLs and use jitter for synchronized workloads.
  • Decide behavior if Redis is unavailable: fail open to DB only if the DB can handle the load.
  • Use timeouts and connection pools in the Redis client.
  • Set a memory limit and appropriate eviction policy.
  • Protect Redis with authentication, TLS where needed, network isolation, and least-privilege access.
  • Measure cache hit ratio alongside database load; a high hit ratio alone does not prove correctness.
  • Test restarts, failover, persistence restore, and stale-cache races.

Production Failure Scenarios

Scenario 1 — Redis is unavailable

Problem: Every cache miss falls through to the database and traffic overwhelms it.

Response: Use bounded timeouts, circuit breaking where appropriate, concurrency limits, load shedding, and database protection. Do not let every request create unlimited fallback work.

Scenario 2 — Cache key expires under heavy traffic

Problem: Hundreds of requests execute the same expensive SQL query.

Response: Use single-flight/request coalescing, TTL jitter, pre-warming, stale-while-revalidate when safe, or a bounded refresh lock.

Scenario 3 — A cache write fails after a database update

Problem: Old cache data remains visible.

Response: Prefer post-commit invalidation, use a durable outbox/event when reliable propagation is required, monitor invalidation failures, and define a TTL-based upper bound for tolerated staleness.

Scenario 4 — Redis primary fails after acknowledging a write

Problem: An asynchronous replica may not have received the latest write before promotion.

Response: Understand replication and failover guarantees, use persistence/backup where appropriate, and do not store irreplaceable business truth only in Redis unless its durability model satisfies the requirements.

Scenario 5 — Memory reaches maxmemory

Problem: Keys are evicted unexpectedly or writes begin failing.

Response: Inspect memory and key growth, tune policy and TTLs, bound collections, reserve headroom, and separate disposable cache data from durable/critical workloads.

Senior Java Backend Interview Q&A

1. Is Redis only a cache?

No. Redis provides data structures, atomic commands, Pub/Sub, Streams, replication, persistence options, and cluster sharding. Whether it is used as a cache, coordination store, or data store depends on durability and correctness requirements.

2. What is the difference between TTL and expiration?

Expiration is the key's lifetime policy. TTL reports the remaining time before the key expires. Redis uses passive and active expiration, so cleanup is not guaranteed at the exact deadline.

3. Cache Aside vs Write Through vs Write Behind?

Cache Aside lets the application load on a miss and manage invalidation. Write Through propagates writes through a cache layer to the backing store before success is reported according to its protocol. Write Behind acknowledges before asynchronous persistence and therefore needs durable buffering, retries, idempotency, and explicit data-loss analysis.

4. RDB vs AOF?

RDB stores point-in-time snapshots. AOF records write operations for replay and has durability behavior influenced by its fsync policy. Both have trade-offs in recovery time, disk use, write latency, and recovery-point objective.

5. Redis replication vs Redis Cluster?

Replication copies a primary's data to replicas. Cluster partitions keys among multiple primaries and can use replicas for failover. Replication alone does not shard the keyspace, and Cluster is not managed by Sentinel.

6. How do you implement a safer Redis distributed lock?

Acquire with SET key unique-token NX PX lease. Release atomically only if the stored token matches. Handle lease expiry, process pauses, failover, and stale holders; use fencing tokens or downstream version checks if strict exclusion is required.

7. Pub/Sub vs Streams?

Pub/Sub delivers live messages to active subscribers and has no durable backlog or acknowledgment. Streams store entries and provide IDs, replay/range reads, consumer groups, pending tracking, and acknowledgments, subject to retention and persistence settings.

8. How do you prevent a cache stampede?

Use request coalescing, bounded refresh locks, TTL jitter, pre-warming, stale-while-revalidate when safe, negative caching where appropriate, and database concurrency limits.

9. Is Redis strongly consistent across replicas?

Ordinary primary-replica replication is generally asynchronous, so replica reads can be stale and failover can lose recent writes that were not replicated. Do not assume strong consistency or zero data loss.

10. Why is a Redis cache key invalidation race possible?

A reader can load an old database value, a writer can commit and delete the cache key, and then the reader can write the old value back into Redis. Versioning, coordinated loading, durable invalidation events, or authoritative reads may be needed for stricter requirements.

11. What is the difference between eviction and expiration?

Expiration removes keys whose TTL has elapsed. Eviction removes eligible keys to manage memory when maxmemory limits are reached. A key without a TTL can still be evicted under an allkeys policy.

12. Can Redis be the system of record for orders or balances?

Only if the chosen Redis deployment, persistence, replication, backup, recovery, and operational guarantees meet the business requirements. For many enterprise applications, a transactional database remains authoritative and Redis is a cache or specialized supporting store.
