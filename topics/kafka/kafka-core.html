1. Kafka architecture

Apache Kafka is a distributed event-streaming platform. Producers write records to topics; Kafka stores them in partitioned logs, replicates them across brokers, and lets consumer groups read at their own pace.

Order ServiceOrderCreated
→
Kafkaorders topic
→
Inventoryreserve stock
+
Analyticsmeasure sales

Different group IDs independently consume the same retained stream. One consumer group's progress does not remove records for other groups.

Kafka is a log

Records are appended to partition logs and assigned offsets. Consumers track progress with offsets; reading a record does not ordinarily delete it.

Why distributed?

Partitions spread load; replicas improve fault tolerance; consumers can scale processing. Durability and availability still depend on configuration and operational health.

Real-time example: when an order is placed, the Order Service emits OrderCreated. Inventory, payment, notification, and analytics services independently react. If analytics is down, it can resume later from its committed offset as long as the event remains within retention.

2. Broker, topic, partition

Broker

A Kafka server storing partitions and handling produce/fetch requests. A cluster comprises multiple brokers identified by broker IDs.

Topic

A named logical event stream, such as orders, payments, or shipment-events. Topic config includes retention and replication-related settings.

Partition

An ordered log within a topic. Offsets are local to a partition. Partitions distribute data and are the unit assigned to consumers in a group.

Example: topic orders with two partitions

PartitionOffset 0Offset 1Offset 2
P0Order AOrder COrder E
P1Order BOrder DOrder F

Offset 2 in P0 is unrelated to offset 2 in P1. Kafka does not promise a total order across partitions.

How partition selection works

  • Keyed record: a partitioner typically hashes the key. Using orderId keeps events for one order on the same partition under stable routing/configuration.
  • No key: the client partitioner distributes records according to its configured/default strategy; behavior can vary by client version.
  • Explicit partition: possible, but couples producer logic to the partition layout.
Production concern: adding partitions can change key-to-partition mapping for new records. If strict per-entity ordering matters, plan partition expansion and migration rather than assuming the sequence will remain on the same partition.

3. Replication, leader, follower

Each partition can have replicas on different brokers. The leader serves normal produce traffic; followers fetch and replicate the leader's log. If a leader fails, Kafka elects an eligible replica according to cluster state and configuration.

Broker 1P0 Leader
→
Broker 2P0 Follower
→
Broker 3P0 Follower
  • Replication factor (RF): total configured replicas per partition. RF=3 commonly means one leader and two followers.
  • ISR: in-sync replicas currently sufficiently caught up under Kafka's replication rules.
  • min.insync.replicas: with acks=all, minimum ISR size required to accept a write.
  • Unclean leader election: can improve availability but may elect a stale replica and lose records that existed only on the previous leader.
RF=3 does not automatically mean every write is acknowledged by all three replicas. Actual behavior depends on acks, ISR state, and min.insync.replicas.

Production scenario: RF=3, minimum ISR=2, and acks=all. If only one eligible ISR replica remains, Kafka may reject writes with a not-enough-replicas error. This sacrifices write availability to preserve the configured durability requirement.

Java producer example

Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG,
          StringSerializer.class.getName());
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG,
          StringSerializer.class.getName());
props.put(ProducerConfig.ACKS_CONFIG, "all");
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);

try (KafkaProducer<String, String> producer = new KafkaProducer<>(props)) {
    ProducerRecord<String, String> event =
        new ProducerRecord<>("orders", "O-481",
                              "{\"type\":\"OrderCreated\"}");
    producer.send(event, (metadata, error) -> {
        if (error != null) {
            // Log event ID, classify error, and trigger recovery/alerting.
            error.printStackTrace();
        } else {
            System.out.printf("partition=%d offset=%d%n",
                metadata.partition(), metadata.offset());
        }
    });
}

5. Producer acknowledgement and acks

acks=0

Producer does not wait for a broker acknowledgement. Lowest acknowledgement latency, but it cannot reliably know whether the broker received the record.

acks=1

Leader acknowledges after writing locally. If it fails before followers replicate the record, a failover can lose that record.

acks=all

Leader waits for the current ISR according to Kafka's replication protocol. Combine with a suitable RF and min.insync.replicas.

# Example starting point; validate against your Kafka version/SLO
replication.factor=3
min.insync.replicas=2

# Producer
acks=all
enable.idempotence=true

“All” means all replicas currently in the ISR, not every configured replica regardless of health. If ISR drops below the minimum, Kafka can reject writes rather than silently weaken the intended durability.

6. Producer retries and idempotent producer

Network failures can create an ambiguous outcome: the broker persists a record but the acknowledgement is lost. A retry may duplicate the append unless producer idempotence handles the retry within its supported protocol scope.

Producersends record
→
Brokerpersists
×
Networkack lost
↻
Retryambiguous
  • enable.idempotence=true uses producer IDs and sequence numbers to deduplicate retried batches from that producer session.
  • It does not deduplicate every new application-level send, nor does it make an external database/payment call exactly-once.
  • Modern clients may enable idempotence by default, depending on version and configuration. Check the effective client settings.
  • Use a stable business event ID and idempotent downstream handlers where duplicate business effects would be harmful.

Transient vs permanent errors

Transient

Temporary network issues, leader movement, throttling. Retry with bounded delivery timeout and monitor retry rates.

Permanent

Authorization failure, invalid topic, serialization bug, oversized record. Retrying blindly will not repair the cause.

Production issue: a payment event is sent, but the application times out and constructs a brand-new send. Kafka's producer idempotence may not deduplicate that new logical send. Carry a unique event ID and make the consumer's payment operation idempotent.

7. Ordering

Kafka preserves append order within each partition. It does not guarantee a total order across partitions.

Per-order ordering

Use orderId as the key so events for one order generally route to one partition.

OrderCreated
PaymentAuthorized
OrderShipped

Global order

A single partition provides one partition-wide sequence but limits parallelism. Most domains need ordering per entity, account, or aggregate rather than for every event in the system.

Apparent reordering causes: different keys land in different partitions; handlers complete concurrently; producer settings/client versions undermine the expected sequence; partition count or key strategy changes; downstream merges streams without sequence checks.

Use a key based on the aggregate that needs sequencing. Add an aggregate version/sequence number when consumers must detect gaps. If a failed event blocks later state transitions, defer later records or implement sequence-aware reconciliation.

8. Consumer and consumer group

Consumers poll Kafka and process assigned partitions. Members with the same group ID share partition assignments; a partition is assigned to at most one active member of that group at a time in the standard group model. Different group IDs consume independently.

TopicP0 P1 P2 P3
→
Group AC1:P0,P1 · C2:P2,P3
Same topicretained log
→
Group BAnalytics consumers
  • 4 partitions and 2 consumers: each may receive 2 partitions.
  • 4 partitions and 4 consumers: each may receive one partition.
  • 4 partitions and 6 consumers: at least 2 are idle for that topic while assignment is stable.
  • Partition count caps consumer-group parallelism for that topic.

Spring Kafka listener illustration

@KafkaListener(topics = "orders", groupId = "inventory-service")
public void onOrder(String payload) {
    // Validate the event and apply an idempotent business update.
    inventoryService.handle(payload);
}

Actual commit behavior depends on Spring Kafka container settings, listener type, error handler, and acknowledgement mode. Verify the configured commit boundary rather than assuming every listener return means the expected offset is committed immediately.

9. Offset, consumer commit, auto commit, manual commit

An offset identifies a record's position within one partition. The committed offset is the group's resume position. Conventionally, after processing record offset 41, commit 42—the next offset to consume.

Offset 40processed
→
Offset 41processed
→
Commit 42resume here
→
Offset 42next

Auto commit

With enable.auto.commit=true, the client periodically commits offsets according to its configured interval. The commit may not align with successful completion of each business operation.

Loss risk: if offsets are committed before processing completes and the app crashes, the group may resume after records whose work never completed.
Duplicate risk: if processing succeeds but the app crashes before commit, records are replayed and side effects may repeat.

Manual commit

Manual commit lets the app/framework coordinate offset advancement with processing success. In concurrent processing, commit only the highest contiguous range completed for each partition; do not commit past an earlier unfinished record.

consumer.subscribe(List.of("orders"));
while (running) {
    ConsumerRecords<String, String> records =
        consumer.poll(Duration.ofMillis(500));
    for (ConsumerRecord<String, String> r : records) {
        processIdempotently(r.value());
    }
    // Commit after the batch's processing contract is satisfied.
    consumer.commitSync();
}
Manual commit is not automatically exactly-once. If a database write succeeds and the process crashes before the Kafka offset commit, replay can repeat the write. Use idempotency, an inbox/dedup table, or Kafka transactions for supported Kafka-to-Kafka workflows.

10. Rebalancing

Rebalancing redistributes partition assignments when group membership, subscriptions, or topic metadata changes. It can temporarily interrupt processing.

Common triggers

  • Consumer deployment/autoscaling.
  • Crashes or missed heartbeats.
  • Poll loop blocked too long.
  • Partition/topic changes.
  • Subscription changes.

Mitigations

  • Keep poll loop responsive.
  • Tune max.poll.interval.ms to measured processing time.
  • Gracefully shut down consumers.
  • Use cooperative assignment where appropriate.
  • Monitor rebalance count and duration.

Incident: endless rebalances

A consumer polls records and then waits several minutes for a slow API. It does not poll within max.poll.interval.ms, so the group reassigns its partitions. Another consumer may process the same records while the original is still working.

Solution: bound processing time and batch size, fix the slow dependency, maintain safe commit boundaries, and make side effects idempotent. Increasing the timeout alone can hide the underlying capacity issue.

11. Consumer lag

Consumer lag measures how far a group's progress trails the partition log end. Tools may express it as offset difference, record count, or estimated time; know the metric definition.

Lag rising steadily

Input exceeds processing capacity or work is blocked. Check handler duration, DB/API latency, errors, and retries.

Lag spikes

Traffic bursts, deployments, rebalances, or temporary dependency failures. Correlate timestamps.

One partition lags

Hot key, uneven payload sizes, skewed work, or partition-specific dependency behavior.

Commands to start diagnosis

kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 \
  --describe --group inventory-service

kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --describe --topic orders
  1. Inspect lag by partition and group.
  2. Compare input rate with processing rate.
  3. Inspect rebalance rate, handler duration, retry rate, and commit failures.
  4. Check database pool saturation, lock waits, external API latency, GC, CPU, and network.
  5. Scale only if partitions are available and downstream capacity can handle it.
More consumers do not help if all partitions are already assigned or if the database is saturated. Extra instances may increase contention and worsen the incident.

For consume-transform-produce, Kafka transactions can atomically publish output records and commit consumed offsets. Downstream consumers using isolation.level=read_committed avoid reading aborted transactional records.

// Conceptual transaction flow; API details depend on client version.
producer.initTransactions();
producer.beginTransaction();
try {
    producer.send(outputRecord);
    producer.sendOffsetsToTransaction(offsets, consumerGroupMetadata);
    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();
    throw e;
}
Kafka cannot undo an email, database commit, or payment gateway call because a Kafka transaction aborts. For database-to-Kafka dual writes, consider the transactional outbox pattern.

13. Retry topic and DLQ

A retry topic provides another attempt, often after backoff. A dead-letter topic (DLQ) quarantines records that cannot be processed under the defined retry policy or are permanently invalid.

Main topicorders
→
Consumerprocess
→
Retry topicbounded backoff
→
DLQquarantine

Transient failure

DB connection timeout, HTTP 503, rate limit. Retry with bounded exponential backoff and jitter.

Permanent failure

Invalid schema, missing required field, deterministic bad payload. Avoid endless retries; route to DLQ with diagnostic metadata.

Preserve in DLQ

  • Original topic, partition, offset, key, event ID, timestamp.
  • Correlation/trace ID, schema version, consumer/service version.
  • Error class, safe message, attempt count, first/last failure time.
  • Redact secrets/PII and define access and retention policies.
Ordering trap: if a failed record is sent to a retry topic and later records continue, per-key order may break. If later events depend on it, pause/defer the partition or use sequence-aware recovery.

DLQ operations

  1. Alert on DLQ rate and oldest-record age.
  2. Group failures by cause/schema version.
  3. Fix root cause before replay.
  4. Replay through a controlled process with idempotent consumers.
  5. Audit replay ownership and outcome.

15. Kafka Streams

Kafka Streams is a Java library for transformations, filters, joins, aggregations, windowed operations, and stateful stream processing. Local state stores can be backed by Kafka changelog topics for recovery.

StreamsBuilder builder = new StreamsBuilder();
KStream<String, OrderEvent> orders =
    builder.stream("orders", Consumed.with(Serdes.String(), orderSerde));

orders.filter((key, event) -> event != null && event.orderId() != null)
      .groupByKey(Grouped.with(Serdes.String(), orderSerde))
      .count()
      .toStream()
      .to("order-counts", Produced.with(Serdes.String(), Serdes.Long()));

Illustrative code; imports, serde definitions, domain classes, and configuration are omitted. Choose the key and aggregation based on the business metric, not merely because the code compiles.

Event time vs processing time

Event time is when an event happened; processing time is when the app handles it. Late events and window grace periods affect aggregate correctness.

State stores / changelogs

State supports joins and aggregations. Changelog topics restore state after task migration/restart; monitor disk and restore time.

Repartitioning

Changing the key for an operation may require repartitioning, adding network, storage, and latency costs.

Exactly-once

Kafka Streams can use Kafka transactions for supported processing semantics; external side effects need their own consistency design.

The database + Kafka dual-write problem

If a service commits its database change and crashes before publishing, downstream systems miss the event. If it publishes first and the database transaction rolls back, consumers see an event for a change that did not commit.

One DB transactionupdate row + outbox row
→
Outbox relay / CDCpublish event
→
Kafkaconsumers

The transactional outbox writes the business change and event intent in one database transaction. A relay or CDC tool publishes the outbox row. Publishing may repeat, so consumers should be idempotent. An inbox/deduplication table keyed by event ID is one common option.

  • Use immutable event facts and clear event ownership.
  • Include event ID, event type, occurred-at time, producer, correlation ID, and schema version as appropriate.
  • Do not assume cross-topic ordering or one distributed transaction across all services.
  • Define compensating actions for multi-service workflows that partially succeed (saga pattern).

Monitoring essentials

Broker

Offline/under-replicated partitions, ISR changes, disk, network, request latency, metadata health.

Producer

Send rate, retries, error rate, delivery latency, buffer availability, batch size, compression ratio.

Consumer

Lag by partition, processing time, commit errors, rebalances, retry/DLQ rate, downstream latency.

Capacity planning

  • Estimate peak/average records per second, payload bytes, and growth.
  • Account for RF when estimating disk and network use.
  • Choose partition count from parallelism and load tests, not an arbitrary huge number.
  • Set retention from replay/recovery requirements, compliance, and cost.
  • Test broker loss, slow dependencies, consumer restart, schema mismatch, and DLQ replay.

18. Interview questions and answers

1. Is Kafka a queue or pub/sub?
Both patterns are possible: members in one group share partitions (queue-like); separate group IDs independently consume the retained stream (pub/sub-like).
2. Topic vs partition?
Topic is a named logical stream; partition is an ordered log inside it and the basic unit of distribution and group assignment.
3. Does Kafka guarantee order?
Within a partition, yes; across partitions, no total order. Key by the entity whose sequence matters.
4. What does acks=all mean?
The leader waits for the current ISR according to the protocol; min.insync.replicas enforces the required minimum. It does not necessarily mean every configured replica.
5. Why RF=3 is not enough for durability?
The write acknowledgement policy, ISR state, and min.insync.replicas determine which replicas need to acknowledge.
6. What does producer idempotence solve?
It prevents duplicate appends caused by supported retries using producer IDs/sequence numbers. It does not deduplicate arbitrary new sends or external effects.
7. Why can a consumer process a record twice?
The side effect may succeed but the offset commit may not; restart replays the record. Use stable event IDs and idempotent processing.
8. What does committed offset N mean?
The next record to consume is conventionally N. After processing record N-1, commit N.
9. What causes rebalances?
Membership or subscription changes, missed heartbeats/poll interval, or topic/partition changes. Rebalances interrupt progress and can expose duplicate-processing windows.
10. How do you handle poison messages?
Bound transient retries with backoff; send permanent failures to a DLQ with original location, event ID, schema, and error metadata; define controlled replay.
11. Retry topic vs DLQ?
Retry topic supports another attempt; DLQ quarantines records after policy or for permanent failure. Both require monitoring and replay procedures.
12. Is Kafka exactly-once end-to-end?
Kafka transactions cover supported Kafka workflows, not arbitrary external databases, email, or payment gateways.
13. How do you diagnose lag?
Inspect lag per partition, input/processing rate, rebalance and handler latency, retry/error rate, and downstream dependency health.
14. Why use Schema Registry and Avro?
They formalize event structure and evolution. Compatibility checks help independent deployments, but semantic contract tests are still necessary.
15. What is transactional outbox?
Store the business update and event intent in one DB transaction, then publish the outbox via relay/CDC. Consumers still need idempotency because publication may repeat.
16. Can more consumers solve lag?
Only if partitions are available and the bottleneck is parallelizable. More consumers cannot split one partition within a group and can overload downstream services.
17. What is Kafka Streams?
A Java library for continuous stream transformations, joins, windows, aggregations, and stateful processing using local state stores and Kafka changelogs.
