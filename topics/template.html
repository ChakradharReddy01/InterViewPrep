[Sample Topic] Database Connection Pooling & Thread Starvation

Production Incident Advanced ⏱️ 15 min read Target Roles: SDE-2, SDE-3, Staff / Tech Lead

1. Under-the-Hood Mechanisms & Architectural Flow

When building scalable backend microservices, establishing physical TCP connections to a relational database involves a 3-way TCP handshake, TLS negotiation, authentication, and session initialization. Doing this per-request degrades throughput and exhausts server sockets. Connection poolers (such as HikariCP) maintain an active pool of warmed-up connections.

Internally, pools utilize a lock-free or specialized concurrent data structure (e.g., HikariCP's FastList and thread-local caches via ConcurrentBag) to hand off pooled connections to waiting worker threads within nanoseconds.

2. Production-Grade Configuration & Code Pattern

Here is an optimized production configuration with proper leak detection and pool sizing based on PostgreSQL/MySQL IO concurrency:

application.yml (Production HikariCP Config) YAML 
spring:
  datasource:
    hikari:
      pool-name: OrdersDbPool
      maximum-pool-size: 30
      minimum-idle: 10
      idle-timeout: 300000
      connection-timeout: 20000 # Max 20s wait before failing fast
      max-lifetime: 1800000     # 30 mins, slightly below database wait_timeout
      leak-detection-threshold: 5000 # Warn if connection borrowed > 5s
      auto-commit: true

3. Real-Time Production Issue & Post-Mortem

🚨 Production Incident: Sudden HTTP 504 Gateway Timeouts During Flash Sale

Symptoms: During a peak sale event, the Order Service p99 latency spiked from 45ms to >15,000ms. CPU utilization remained abnormally low (<20%), yet Kubernetes readiness probes failed, triggering cascading pod restarts.

🔍 Root Cause Analysis (RCA)

Root Cause: A newly shipped feature invoked an un-indexed reporting query inside an open @Transactional block. The query locked a connection for 12 seconds. As traffic surged, all 30 connections in the Hikari pool were held by slow transactions. Subsequent worker threads blocked on getConnection() until their 30-second timeouts expired, exhausting the Tomcat thread pool.

💡 Production Resolution & Hardening Steps
  • Immediate Hotfix: Raised HikariCP pool leak detection to leak-detection-threshold: 3000 to identify offending queries in Datadog/Splunk logs. Added read replicas for long-running reporting queries.
  • Architectural Separation: Refactored the code to fetch data and call external APIs outside the database transaction, strictly shrinking transaction boundaries.
  • Circuit Breaker: Configured Resilience4j circuit breakers on database operations to fail fast when connection acquisition latency surpasses 500ms.

4. Production Diagnostic & Triage Commands

When investigating pool exhaustion or thread starvation on live production nodes:

# 1. Capture thread dump to inspect threads blocked on HikariCP getConnection
jcmd <PID> Thread.print | grep -A 10 "com.zaxxer.hikari.pool.HikariPool.getConnection"

# 2. Check active database connections and state in PostgreSQL
SELECT pid, query_start, state, query 
FROM pg_stat_activity 
WHERE state != 'idle' 
ORDER BY query_start ASC;

# 3. Check TCP socket state between app and database host
netstat -an | grep 5432 | awk '{print $6}' | sort | uniq -c

5. Senior Interview Questions & Answers

🎯 Q: Why shouldn't you simply set maximumPoolSize to a very large number (e.g. 500)?

Answer: Increasing the pool beyond CPU/disk saturation creates severe context switching overhead on the database server. PostgreSQL and MySQL process queries concurrently; each query requires memory, disk I/O, and CPU time. According to queuing theory and the formula pool size = (core_count * 2) + effective_spindle_count, smaller pools keep the database CPU caches warm, preventing thrashing and disk head contention, which yields significantly higher sustained throughput than large pools.
