Module 1: OOP Principles & Core Java Keywords Internals

Core Java Advanced Architecture Concurrency & JMM ⏱️ 40 min deep dive Target Roles: SDE-2, SDE-3, Backend Tech Lead

While every engineer knows the textbook definitions of Object-Oriented Programming (OOP), senior technical interviews test how polymorphism maps to the JVM's Virtual Method Table (vtable) and dynamic method dispatch, why Composition over Inheritance prevents the Fragile Base Class problem, and how Java keywords (volatile, synchronized, final, transient) interact directly with CPU caches, memory barriers, and the Java Memory Model (JMM).

1. OOP Core Mechanics: Classes, Objects & The 4 Pillars

1.1 Class vs. Object: Runtime Metaspace vs. Heap Allocation

A Class is a blueprint containing type descriptors, method bytecode, annotations, and vtables stored in off-heap Metaspace. An Object is a physical instance dynamically allocated on the Heap with an 8-byte aligned memory footprint (Mark Word + Klass Word + Instance Data + Padding).

1.2 Encapsulation (Data Hiding & Invariant Protection)

Encapsulation is not just about making fields private and generating getters/setters. True enterprise encapsulation ensures that an object maintains strict internal business invariants that outside callers cannot bypass or corrupt.

Defensive Copying & Invariant Protection Java 
public final class MoneyAccount {
    private final String accountId;
    private long balanceCents; // Immutable representation in minor currency units

    public MoneyAccount(String accountId, long initialDeposit) {
        if (initialDeposit < 0) {
            throw new IllegalArgumentException("Initial balance cannot be negative");
        }
        this.accountId = Objects.requireNonNull(accountId);
        this.balanceCents = initialDeposit;
    }

    public synchronized void debit(long amountCents) {
        if (amountCents <= 0 || amountCents > this.balanceCents) {
            throw new IllegalStateException("Insufficient funds or invalid debit amount");
        }
        this.balanceCents -= amountCents;
    }

    public synchronized long getBalanceCents() {
        return this.balanceCents;
    }
}

1.3 Inheritance vs. Composition (IS-A vs. HAS-A)

  • Inheritance (IS-A): Reuses code via subclassing (class Dog extends Animal). Tightly couples the child to the parent's internal state. Violating the Liskov Substitution Principle (LSP) causes the Fragile Base Class problem, where modifying a parent method breaks subclasses.
  • Composition (HAS-A): Assembles functionality by holding references to other classes (class OrderService { private final PaymentProcessor processor; }). Allows runtime swapping of behaviors, cleaner unit testing via mocks, and avoids tight class hierarchies.
  • Aggregation: A specialized form of HAS-A representing a "weak" relationship where the child can exist independently of the parent (e.g., a Department HAS-A Teacher; if the department closes, the teacher still exists).
  • Association: The most general structural relationship where two objects interact (1-to-1, 1-to-many, many-to-many).

1.4 Abstraction: Interface vs. Abstract Class

Dimension Interface Abstract Class
Multiple Inheritance A class can implement unlimited interfaces. Single inheritance only (extends one class).
State & Fields Only public static final constants (no instance state). Can hold full instance state (fields, constructors, mutables).
Method Capabilities Abstract methods, default methods (Java 8), static methods, and private helper methods (Java 9). Abstract methods, concrete methods, protected/package-private methods.
Design Intent Defines a contract or capability ("what" it can do, e.g., Comparable, Serializable). Provides a shared identity and partial skeleton implementation (Template Method Pattern).

2. Polymorphism & Dynamic Method Dispatch Internals

2.1 Method Overloading vs. Overriding

  • Method Overloading (Compile-Time / Static Polymorphism): Same method name, different parameter signature in the same class. Resolved at compile time based on parameter static reference types.
  • Method Overriding (Runtime / Dynamic Polymorphism): Subclass provides a specific implementation of a method declared in its parent. Must share same name, parameter types, and have a covariant return type (can return a subclass of the parent's return type). Access level cannot be reduced, and checked exceptions cannot be broader than the parent's.

2.2 Under the Hood: Dynamic Method Dispatch & Virtual Method Table (vtable)

When Java executes an overridden method like animal.makeSound(), how does the JVM know which subclass method to invoke at runtime without expensive string lookups?

  1. Every class loaded in Metaspace has an internal structure called the vtable (Virtual Method Table).
  2. The vtable is an array of direct pointers to the executable machine code or bytecode of every virtual method. Subclasses inherit the parent's vtable structure.
  3. When a subclass overrides a method, its vtable slot at index K is overwritten with the address of the subclass's method implementation.
  4. At runtime, the bytecode instruction invokevirtual simply reads the object's Klass pointer from its header, navigates to the vtable at predetermined offset K, and executes the jump in $O(1)$ constant time.
Bytecode Invocations Comparison:
- invokevirtual:   Standard polymorphic instance methods resolved via vtable.
- invokeinterface: Interface method calls resolved via itable (Interface Table).
- invokespecial:   Constructors (<init>), private methods, and super calls (bypasses vtable).
- invokestatic:    Static methods resolved at compile-time (no object receiver).
- invokedynamic:   Bootstrapped dynamic call sites for lambdas and dynamic languages.

3. Java Keywords: Internals, JMM & Memory Semantics

3.1 static

Associated with the class rather than any object instance.

  • Static Fields: In Java 8+, static variables reside on the Heap inside the java.lang.Class instance (moved out of PermGen).
  • Static Initializer Block (<clinit>): Generated by javac to execute static field initialization. Executed exactly once during class initialization, protected by an internal JVM class-initialization lock (thread-safe by specification).
  • Static Nested Class: Does not hold an implicit reference to the enclosing class instance, eliminating the risk of accidental memory leaks.

3.2 final & Immutability Guarantees

  • Final Variable: Can be initialized only once. For reference types, the reference pointer is immutable, but the internal state of the referenced object is still mutable unless designed defensively.
  • Final Method: Cannot be overridden. Allows the JIT compiler to perform aggressive method inlining (bypassing vtable lookups entirely).
  • Final Class: Cannot be extended (e.g., java.lang.String, java.lang.Integer).
  • JMM Final Field Freeze Action: Under the Java Memory Model, once an object's constructor finishes initializing a final field, the JMM issues a memory barrier ("freeze action"). This guarantees that any thread reading a reference to that object will immediately observe the properly initialized final field without explicit synchronization.

3.3 this and super

  • this represents the current object instance reference. Inside constructor chaining, this(...) invokes an overloaded constructor on the same class and must be the first statement.
  • super references the immediate parent class. In constructors, super(...) invokes the parent constructor. In bytecode, calling super.method() emits an invokespecial instruction to bypass polymorphic dynamic dispatch.

3.4 transient (Serialization Exclusion)

Indicates that a field should not be serialized when the object is converted into a byte stream using Java's native ObjectOutputStream. 

public class UserSession implements Serializable {
    private static final long serialVersionUID = 1L;
    private String username;
    
    // Critical: Do NOT persist passwords or security tokens across networks
    private transient String rawPassword;
    private transient Socket activeSocket; // Non-serializable system resources
}

3.5 volatile (Hardware Memory Barriers & Visibility)

In modern multi-core architectures, each CPU core has private L1/L2 caches. When Thread A writes to a regular variable, the update may stay trapped in Core 1's store buffer or L1 cache, invisible to Thread B executing on Core 2.

Marking a field volatile guarantees:

  • Visibility: Writes to a volatile variable are immediately flushed to main memory (L3 / RAM). Reads always bypass CPU registers/L1 cache and read directly from coherent memory.
  • Ordering (Happens-Before Relationship): The JVM instructs the compiler and CPU not to reorder read/write instructions around a volatile variable by injecting Memory Barriers (LoadLoad, LoadStore, StoreStore, StoreLoad / mfence or lock prefix on x86).
  • Non-Atomicity: volatile does NOT make compound operations (like count++) thread-safe! count++ consists of 3 distinct opcodes: read, increment, and write. Two threads can interleave, losing updates. Use AtomicInteger or VarHandle instead.

3.6 synchronized (Monitor Mechanics & Lock Escalation)

Every Java object can act as an intrinsic lock (monitor). In bytecode, a synchronized block is delineated by monitorenter and monitorexit opcodes.

HotSpot optimizes intrinsic locks through Lock Escalation / Inflation: 

[Biased Lock] ----------(Contention by another thread)----------> 
  [Lightweight / Thin Lock (CAS on thread stack)] ------(Busy spin failure)------> 
    [Heavyweight Lock (OS Mutex / Thread Park)]
  • Biased Locking: (Deprecated/disabled in modern JDKs) Assumes a single thread accesses the lock repeatedly; sets thread ID directly in the Mark Word with zero CAS overhead.
  • Lightweight Lock: When multiple threads access the lock without overlapping contention, each thread uses atomic Compare-And-Swap (CAS) to copy the object's Mark Word into a Displaced Mark Word on its execution stack. No OS-level kernel context switch.
  • Heavyweight Lock: When true contention occurs (CAS fails repeatedly), the lock inflates into a full OS monitor. Threads that fail to acquire the lock are placed in the kernel's wait queue and parked (blocked), incurring expensive user-to-kernel context switches.

3.7 native

Specifies that a method is implemented in platform-native code (C, C++, Assembly) and linked dynamically through JNI. Examples include System.currentTimeMillis() and Thread.currentThread().

3.8 strictfp

Forces floating-point calculations (float and double) to adhere strictly to the IEEE 754 standard across different CPU architectures, preventing platform-specific extended exponent precision drift. Starting in Java 17, strict floating-point semantics became standard by default, rendering the keyword obsolete.

4. Real-Time Production Issues & Post-Mortems

🚨 Incident 1: Double-Checked Locking Bug Due to Missing volatile

Scenario: Under high concurrency in an e-commerce checkout engine, a Singleton cache initialization caused random NullPointerException crashes on 0.01% of requests, even though the singleton check was preceded by a synchronized block.

🔍 Root Cause Analysis (RCA)

The code implemented Double-Checked Locking without declaring the singleton reference volatile: 

// BROKEN CODE:
public class CacheManager {
    private static CacheManager instance; // MISSING volatile!

    public static CacheManager getInstance() {
        if (instance == null) {
            synchronized (CacheManager.class) {
                if (instance == null) {
                    instance = new CacheManager(); // Reordering occurs here!
                }
            }
        }
        return instance;
    }
}

Instantiating an object via new CacheManager() compiles to 3 steps: 1. memory = allocate(); 2. ctor(memory); 3. instance = memory;. Without volatile, the JIT compiler and CPU reordered step 3 before step 2. Thread A assigned the non-null memory address to instance before the constructor finished running. Thread B arrived, observed instance != null, bypassed the lock, and accessed an uninitialized object, triggering NPEs!

💡 Production Resolution

Declaring private static volatile CacheManager instance; prevents instruction reordering by placing a StoreStore barrier before the assignment. Alternatively, use the Initialization-on-demand Holder idiom which leverages JVM class initialization guarantees:

public class CacheManager {
    private CacheManager() {}

    private static class Holder {
        static final CacheManager INSTANCE = new CacheManager();
    }

    public static CacheManager getInstance() {
        return Holder.INSTANCE; // Lazy, thread-safe, zero lock overhead
    }
}
🚨 Incident 2: Session Clustering Outage via Missing transient on Spring Beans

Scenario: During a Kubernetes rolling upgrade, user sessions replicated across Redis/Hazelcast nodes threw java.io.NotSerializableException: org.springframework.web.client.RestTemplate, causing thousands of active customer shopping carts to be wiped out.

🔍 Root Cause Analysis (RCA)

A junior engineer injected an autowired Spring service bean directly into an HttpSession attribute object: 

public class ShoppingCart implements Serializable {
    private List<CartItem> items;
    private PaymentService paymentService; // Non-serializable bean holding socket pools!
}

When the node cordoned during the upgrade, the distributed session manager attempted to serialize the ShoppingCart graph into Redis. Because PaymentService holds non-serializable HTTP connections, the entire serialization pipeline aborted.

💡 Production Resolution

Marked all non-stateful service handles as transient, or better, refactored data-transfer objects (DTOs) so they never hold references to service layer components:

public class ShoppingCart implements Serializable {
    private static final long serialVersionUID = 1L;
    private List<CartItem> items;
    private transient PaymentService paymentService; // Excluded from serialization
}

6. Senior / Staff Technical Interview Q&A

🎯 Q1: Why does a synchronized static method not block a synchronized non-static method on the same class?

Answer: They synchronize on completely different monitor objects. A synchronized static method acquires the lock on the java.lang.Class object instance residing in the Heap/Metaspace (MyClass.class). A synchronized non-static method acquires the monitor of the specific instance (this). Since the lock targets are distinct physical objects in memory, two threads can execute them simultaneously without blocking each other.

🎯 Q2: Can you override a static method in Java? Why or why not?

Answer: No, static methods cannot be overridden; they can only be hidden. Method overriding relies on dynamic method dispatch via the virtual method table (vtable) and the invokevirtual opcode, which checks the runtime object type in the heap. Static methods are invoked via invokestatic, which is bound statically at compile time based purely on the reference variable's declared type, not the runtime object instance.

🎯 Q3: Does marking a 64-bit long or double as volatile have special memory semantics?

Answer: Yes! In the Java Language Specification (JLS §17.7), writes to non-volatile 64-bit long and double values are treated as two separate 32-bit writes on 32-bit JVMs or specific hardware architectures. If multiple threads write concurrently without synchronization, a reader thread can observe a "torn read"—the higher 32 bits from one write and the lower 32 bits from another. Marking a long or double as volatile guarantees atomic 64-bit reads and writes even on 32-bit hardware.

🎯 Q4: Explain the Fragile Base Class problem and how Composition solves it.

Answer: The Fragile Base Class problem arises when a subclass inherits implementation details from a parent. If the parent class later modifies an internal method (e.g. changing addAll() to internally call add()), and the subclass had overridden both add() and addAll(), the subclass can silently produce duplicate counts or infinite recursion without any compiler warnings. Composition solves this by delegating to a private instance of the component rather than inheriting from it, preserving loose coupling and clean encapsulation boundaries.
