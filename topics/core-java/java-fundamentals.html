Module 1: Core Java — Deep Fundamentals & JVM Internals

Core Java Production Internals ⏱️ 35 min deep dive Target Roles: SDE-2, SDE-3, Lead Backend Engineer, Architect

Understanding Java at a senior engineering level requires moving past basic syntax and mastering how code executes on physical hardware through the JVM virtualization layer. This module covers the JVM execution pipeline, classloading mechanics, memory layout down to the byte level (Mark Word, Klass Pointer, Compressed OOPs), generational garbage collection, and reference types, complete with real-time production post-mortems and battle-tested triage commands.

1. JDK, JRE, and JVM Architectural Hierarchy

Java's execution boundary is split into three concentric architectural tiers: 

+---------------------------------------------------------------------------------+
| Java Development Kit (JDK)                                                      |
|   - Development Tools: javac, jcmd, jstack, jmap, jconsole, jshell, jar, javadoc|
| +-----------------------------------------------------------------------------+ |
| | Java Runtime Environment (JRE)                                              | |
| |   - Standard Java Class Libraries (rt.jar / java.base module)               | |
| |   - Supporting configuration files and security policies                    | |
| | +-------------------------------------------------------------------------+ | |
| | | Java Virtual Machine (JVM)                                              | | |
| | |   - ClassLoader Subsystem                                               | | |
| | |   - Execution Engine: JIT Compiler (C1/C2), Bytecode Interpreter, GC   | | |
| | |   - Runtime Data Areas: PC Register, Stack, Heap, Metaspace, Native Stk | | |
| | +-------------------------------------------------------------------------+ | |
| +-----------------------------------------------------------------------------+ |
+---------------------------------------------------------------------------------+

1.1 Java Virtual Machine (JVM)

The JVM is an abstract computing machine that has an instruction set and manipulates memory at runtime. It is platform-dependent: while Java bytecode (.class) is platform-independent, each operating system (Linux x86_64, macOS ARM64, Windows x64) has a tailored JVM implementation (HotSpot, OpenJ9, GraalVM) that translates platform-neutral bytecode into concrete machine instructions.

1.2 Java Runtime Environment (JRE)

The runtime implementation containing the minimal set of libraries (the Java Standard Class Library like java.lang, java.util, java.io) and configuration required to execute a pre-compiled Java program. Starting with Java 9 (Project Jigsaw), the monolithic JRE was superseded by modular runtime images constructed via jlink.

1.3 Java Development Kit (JDK)

The full-featured software development package containing the JRE plus compilers (javac), debuggers (jdb), profilers and diagnostics utilities (jcmd, jstack, jstat, jmap).

2. JVM Architecture, Java Compilation & Bytecode

2.1 Java Compilation Process

Java utilizes a two-stage compilation pipeline:

  1. Ahead-of-Time Static Compilation: javac parses .java source files into syntax trees (AST), enforces typing rules, and compiles them into platform-independent bytecode stored in .class files. No machine code is generated at this stage.
  2. Dynamic Just-In-Time (JIT) Execution: When launched, the JVM's interpreter executes bytecode immediately line-by-line without waiting for compilation. Simultaneously, execution counters monitor method invocations and loop iterations ("hot spots"). Hot code is compiled into native machine code by Tiered Compilers:
    • C1 (Client Compiler): Fast compilation with light optimizations for quick startup.
    • C2 (Server Compiler / Opto): Deep global optimizations (method inlining, loop unrolling, escape analysis, lock coarsening/elision) for maximum steady-state throughput.

2.2 What is Bytecode?

Bytecode is the instruction set of the Java Virtual Machine. Each opcode is 1 byte long (hence the name), allowing up to 256 instructions (such as aload_0, invokevirtual, getfield, ireturn).

Decompiling Bytecode with javap -c -v CLI 
// Java Source:
public int calculateSum(int a, int b) {
    int result = a + b;
    return result;
}

// Disassembled Bytecode via 'javap -c -p MyClass':
public int calculateSum(int, int);
  Code:
     0: iload_1         // Push local variable 1 (a) onto operand stack
     1: iload_2         // Push local variable 2 (b) onto operand stack
     2: iadd            // Pop top two ints, add them, push sum back onto operand stack
     3: istore_3        // Pop sum from operand stack, store in local variable 3 (result)
     4: iload_3         // Push local variable 3 onto operand stack
     5: ireturn         // Return int from operand stack

3. ClassLoader Subsystem & Loading Mechanics

The JVM does not load all classes into memory at startup. Classes are located, loaded, linked, and initialized dynamically on first active use (e.g., executing new, calling a static method, accessing a static field, or reflection).

3.1 The 3-Phase Lifecycle of a Class

  1. Loading: Reads binary byte stream of a class by name, creates a java.lang.Class instance in memory, and constructs runtime data structures in Metaspace.
  2. Linking:
    • Verification: Validates binary structure against JVM specifications (magic number 0xCAFEBABE, stack map tables, no operand stack overflows).
    • Preparation: Allocates static memory for static fields and assigns default zero values (e.g., int = 0, reference = null), NOT user-defined initial values.
    • Resolution: Replaces symbolic references in the constant pool with direct memory references.
  3. Initialization: Executes static initializers and static variable assignments (compiled into the class-level <clinit> method) in thread-safe order.

3.2 ClassLoader Hierarchy & Delegation Model

Java adheres to the Parent Delegation Model: when a ClassLoader receives a request to load a class, it delegates the search to its parent before attempting to locate it itself. 

+-------------------------------------------------------------+
| 1. Bootstrap ClassLoader                                    |
|    - Written in native C/C++                                |
|    - Loads core JDK classes: java.base, java.lang.*         |
|    - Represented as 'null' in Java code                     |
+------------------------------^------------------------------+
                               | delegates to parent
+------------------------------+------------------------------+
| 2. Platform ClassLoader (formerly Extension ClassLoader)    |
|    - Loads platform and extended APIs (java.sql, etc.)       |
+------------------------------^------------------------------+
                               | delegates to parent
+------------------------------+------------------------------+
| 3. Application (System) ClassLoader                         |
|    - Loads classes found on application classpath / module  |
+------------------------------^------------------------------+
                               | delegates to parent
+------------------------------+------------------------------+
| 4. Custom / Plugin ClassLoaders                             |
|    - OSGi, Tomcat WebappClassLoader (Child-First override)  |
+-------------------------------------------------------------+
  • Bootstrap ClassLoader: The root ClassLoader. Loads platform core runtime modules. If you execute String.class.getClassLoader(), it returns null because Bootstrap is implemented in native C++ in HotSpot.
  • Platform ClassLoader (Java 9+ / previously Extension): Loads standard Java extensions and platform modules that are not part of java.base.
  • Application ClassLoader: Loads application-specific classes defined on the environment classpath (-cp or --class-path).
⚠️ Delegation Model Violations in Production

Frameworks like Tomcat and OSGi intentionally invert this delegation model ("Child-First" or "Parent-Last"). A web application container tries to load bundled dependencies from WEB-INF/lib first before asking the parent server ClassLoader, allowing different deployed WARs to use conflicting versions of libraries (e.g. Jackson 2.12 vs 2.15).

4. Complete JVM Runtime Data Areas

The JVM splits its memory into thread-shared and thread-isolated regions: 

+---------------------------------------------------------------------------------------+
|                               JVM RUNTIME DATA AREAS                                  |
+---------------------------------------------------------------------------------------+
|  THREAD-SHARED (Shared by all threads)                                                |
|  +------------------------------------+  +-----------------------------------------+  |
|  | HEAP MEMORY                        |  | METASPACE (Off-Heap Native Memory)      |  |
|  | - Young Gen (Eden, S0, S1)         |  | - Klass structures & vtables            |  |
|  | - Old / Tenured Generation         |  | - Constant Pool & Method Bytecode       |  |
|  | - String Intern Pool (Java 7+)     |  | - Annotations & Field definitions       |  |
|  +------------------------------------+  +-----------------------------------------+  |
+---------------------------------------------------------------------------------------+
|  PER-THREAD PRIVATE (Created per thread lifecycle)                                    |
|  +----------------------+ +--------------------------+ +---------------------------+  |
|  | PROGRAM COUNTER (PC) | | JVM STACK                | | NATIVE METHOD STACK       |  |
|  | - Address of current | | - Stack Frames           | | - C/C++ frame execution   |  |
|  |   executing opcode   | |   [Local Vars, Ops, Data]| | - JNI invocations         |  |
|  +----------------------+ +--------------------------+ +---------------------------+  |
+---------------------------------------------------------------------------------------+

4.1 Program Counter (PC) Register

Each thread has its own PC Register. It holds the memory address of the JVM instruction currently being executed by that thread. If the thread is executing a native method, the PC register's value is undefined. It requires minimal memory and never throws an OutOfMemoryError.

4.2 JVM Stack & Stack Frames

Every thread receives a dedicated call stack allocated via -Xss (default typically 1MB on 64-bit JVMs). Each method call pushes a new Stack Frame onto the stack, and returning pops it off. A Stack Frame consists of:

  • Local Variable Array (LVA): 0-indexed table storing method parameters and local variables. Types long and double consume two consecutive slots (64 bits). For instance methods, slot 0 is always reserved for this.
  • Operand Stack: A pushdown LIFO stack used as a workspace for intermediate calculation results and parameter passing to invoked opcodes.
  • Frame Data (Dynamic Linking & Normal/Abrupt Return): References to the runtime constant pool to support dynamic linking and exception dispatch tables.

4.3 Native Method Stack

Allocated per thread to handle execution of native methods written in C, C++, or assembly invoked via the Java Native Interface (JNI).

4.4 Heap Memory

The shared memory region where all Java class instances and arrays reside. Managed entirely by the Garbage Collector. Modern JVM heaps utilize a generational layout:

  • Young Generation:
    • Eden Space: Initial destination for freshly instantiated objects. Uses Thread Local Allocation Buffers (TLABs) to allow lock-free allocations via bump-the-pointer.
    • Survivor Spaces (S0 & S1): Two alternating spaces. One is always active ("From"), and the other is empty ("To"). Surviving objects flip between them, incrementing their aging counter (tenuring threshold, default 15).
  • Old (Tenured) Generation: Holds long-lived objects promoted from Survivor spaces after exceeding the tenuring threshold or large objects allocated directly via Humongous allocation rules.

4.5 Method Area vs. Metaspace

The Method Area is a logical specification defined in the JVM specification. In JDK 7 and earlier, it was implemented inside heap memory known as PermGen (Permanent Generation), which had a contiguous fixed size boundary (-XX:MaxPermSize) leading to frequent java.lang.OutOfMemoryError: PermGen space crashes.

In JDK 8+, PermGen was completely eliminated and replaced with Metaspace:

  • Metaspace is allocated directly from native operating system memory (off-heap).
  • By default, Metaspace dynamically expands up to available physical system memory unless capped with -XX:MaxMetaspaceSize.
  • Holds metadata, runtime constant pool, method bytecode, annotations, method tables (vtables), and JIT-compiled code metadata.

5. Object Creation Lifecycle & Deep Memory Layout

5.1 The 5-Step Object Creation Pipeline

  1. Class Loading Check: When encountering the new opcode, the JVM inspects the constant pool to verify if the class has been loaded. If not, the ClassLoader subsystem loads it.
  2. Memory Allocation: The JVM calculates exact byte requirements and carves out memory from the Heap:
    • Bump-the-Pointer: If memory is compact (e.g. Serial/Parallel/G1 after compacting), a pointer advances by the object size. Done via lock-free thread-local TLABs.
    • Free List: If memory is fragmented (e.g., CMS), a linked list of free blocks is searched.
  3. Zero Initialization: Allocated memory (excluding object headers) is zeroed out to default primitive values, ensuring fields have deterministic defaults before constructor execution.
  4. Setting Object Header: Writes the Mark Word and Klass Word into the object's header.
  5. Constructor Invocation (<init>): Executes instance initialization blocks and constructor code to populate developer-assigned values.

5.2 Deep Object Memory Layout in 64-bit JVM

Every Java object on the heap is padded to a multiple of 8 bytes (alignment requirement of 64-bit CPU architecture). 

+--------------------------------------------------------------------------------+
|                             JAVA OBJECT IN MEMORY                              |
+--------------------------------------------------------------------------------+
| 1. OBJECT HEADER (12 or 16 Bytes)                                              |
|    +-------------------------------------------------------------------------+ |
|    | Mark Word (64 bits / 8 Bytes):                                          | |
|    |   - HashCode (31 bits)                                                  | |
|    |   - GC Generational Age (4 bits: max value 15)                          | |
|    |   - Biased Lock Flag (1 bit)                                            | |
|    |   - Lock State Bits (2 bits: 01=Normal, 00=Thin/Light, 10=Fat, 11=Marked)| |
|    +-------------------------------------------------------------------------+ |
|    | Klass Pointer (32 bits / 4 Bytes with +UseCompressedClassPointers)      | |
|    | (Points to the class metadata in Metaspace)                             | |
|    +-------------------------------------------------------------------------+ |
| 2. INSTANCE DATA                                                               |
|    - Primitive fields (boolean=1B, byte=1B, char=2B, short=2B, int/float=4B, |
|      long/double=8B) and references (4B compressed / 8B uncompressed)        |
+--------------------------------------------------------------------------------+
| 3. PADDING (0 to 7 Bytes)                                                      |
|    - Rounds total object byte size up to the nearest multiple of 8.            |
+--------------------------------------------------------------------------------+

5.3 Compressed OOPs (-XX:+UseCompressedOops)

On a 64-bit architecture, pointers natively require 8 bytes (64 bits), which drastically reduces CPU L1/L2 cache efficiency compared to 32-bit systems. Compressed Ordinary Object Pointers (Compressed OOPs) represent memory addresses as 32-bit integers by taking advantage of 8-byte object alignment.

Since all objects start at addresses divisible by 8, the last 3 bits of every memory pointer are always 000. The JVM drops the lowest 3 zero bits when storing pointers, effectively shifting bits to address up to: 

2^32 * 8 bytes = 4 GB * 8 = 32 GB of Heap space using 32-bit pointers!
⚠️ The 32 GB Heap Boundary Pitfall in Production

If you configure -Xmx32g or larger (e.g., -Xmx33g), Compressed OOPs can no longer map the heap with 32 bits and automatically disables. All pointers expand from 4 bytes to 8 bytes. A 33 GB heap frequently holds fewer actual objects than a 31 GB heap due to pointer bloat!

6. Garbage Collection Architecture & Collectors

6.1 The Weak Generational Hypothesis

JVM Garbage Collection is founded on two empirical observations:

  • Most objects become unreachable shortly after allocation (high infant mortality in Eden).
  • Objects that survive multiple GC cycles tend to live for a long duration.

6.2 Types of GC Pauses

  • Minor GC (Young GC): Collects dead objects from Eden and moves survivors to Survivor spaces. Fast, but incurs brief Stop-The-World (STW) pauses.
  • Major GC vs Full GC: Major GC cleans Old Gen; Full GC stops all application threads and cleans both Young, Old, and Metaspace, causing severe latency degradation.

6.3 Modern Production Garbage Collectors

Collector Target Use Case Pause Profile Algorithm
G1 GC (Default in Java 9+) Large heaps (4GB - 64GB), mixed throughput & latency Predictable target pause times (e.g., -XX:MaxGCPauseMillis=200) Region-based partitioning (2048 equal regions), incremental concurrent marking
ZGC (Scalable Low-Latency) Heaps from 16MB to 16TB, mission-critical latency Sub-millisecond pause times (<1ms STW) Colored pointers, load barriers, fully concurrent phase executions
Parallel GC Batch processing, offline ETL jobs Longer throughput-oriented STW pauses Multi-threaded stop-the-world copy and mark-compact

7. Java Reference Types: Strong, Soft, Weak, Phantom

Java provides four strengths of object reachability located in java.lang.ref: 

+-----------------------------------------------------------------------------------------+
| REFERENCE STRENGTH ORDER:                                                               |
| Strong References > Soft References > Weak References > Phantom References              |
+-----------------------------------------------------------------------------------------+

7.1 Strong Reference

Standard assignment in Java: User user = new User();. As long as a strong reference chain connects an object to a GC Root (e.g., local stack variable, static field, active thread), the GC will never collect it, choosing to throw OutOfMemoryError instead.

7.2 Soft Reference (SoftReference<T>)

An object referenced solely by a SoftReference survives normal GC cycles and is collected only when the JVM is under imminent memory pressure just before throwing an OOM. 

// Ideal for memory-sensitive caches:
SoftReference<byte[]> cacheData = new SoftReference<>(new byte[1024 * 1024 * 50]); // 50MB
byte[] data = cacheData.get();
if (data == null) {
    // Re-load data from database if GC cleared it under memory pressure
}

7.3 Weak Reference (WeakReference<T>)

Objects referenced solely by a WeakReference are reclaimed during the very next Garbage Collection cycle, regardless of available memory. Primarily used in WeakHashMap and canonical mappings where you don't want the lookup cache to prevent GC collection of the key.

7.4 Phantom Reference (PhantomReference<T>)

Calling phantomRef.get() always returns null. Its sole purpose is to track when an object has been finalized and reclaimed from memory by enqueueing it onto a ReferenceQueue. Used as a safe, high-performance replacement for dangerous finalize() methods (e.g., freeing off-heap DirectByteBuffers in Netty).

8. Real-Time Production Incidents & Post-Mortems

🚨 Incident 1: OutOfMemoryError: Metaspace Exhaustion During Blue-Green Deployments

Scenario: A Spring Boot payment service deployed on Kubernetes suffered cascading pod crashes every 48 hours with java.lang.OutOfMemoryError: Metaspace. Pod restarts temporarily solved it, but memory climbed steadily.

🔍 Root Cause Analysis (RCA)

The application utilized runtime dynamic proxy generation (via CGLIB / Hibernate / Reflection) inside an internally created custom ClassLoader for multi-tenant plugin isolation. The custom ClassLoader instances were held in static maps by a third-party metrics library. Because the ClassLoader itself was never unreferenced, none of the dynamically generated classes could be unloaded from Metaspace. Over hundreds of deployments and tenant reloads, Metaspace exceeded its -XX:MaxMetaspaceSize=256m threshold.

💡 Production Resolution
  • Configured Metaspace flags: -XX:MetaspaceSize=256M -XX:MaxMetaspaceSize=512M.
  • Enabled class unloading logging: -Xlog:class+unload=info to audit which classes were failing to unload.
  • Purged the static ClassLoader reference from the metrics registry upon tenant shutdown hook.
🚨 Incident 2: Silent ThreadLocal Leak in Tomcat / Jetty Worker Pools

Scenario: Heap usage in an enterprise authentication proxy grew linearly over 7 days until Old Gen reached 98% and caused continuous 15-second Stop-The-World Full GC pauses.

🔍 Root Cause Analysis (RCA)

Developers placed user authentication contexts inside a ThreadLocal<SecurityContext> inside a servlet filter. Because container threads (Tomcat worker threads) are pooled and never die, the thread's internal threadLocals table maintained a reference. While ThreadLocalMap.Entry extends WeakReference<ThreadLocal<?>>, the value (the SecurityContext holding large JWT token trees and user objects) remains strongly referenced until the worker thread executes again and performs table cleanups or until remove() is explicitly called.

💡 Production Resolution

Mandated a strict try-finally block in all servlet filters and interceptors:

public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) 
        throws IOException, ServletException {
    try {
        SecurityContextHolder.set(extractContext(request));
        chain.doFilter(request, response);
    } finally {
        SecurityContextHolder.remove(); // CRITICAL: Always clean up to prevent pool contamination
    }
}

10. Senior/Staff Technical Interview Questions & Answers

🎯 Q1: Why was PermGen replaced by Metaspace in Java 8?

Answer: PermGen had a contiguous fixed size set at startup (-XX:MaxPermSize). Calculating the exact size required for dynamic class generation (Spring proxies, CGLIB, Groovy) was notoriously difficult, causing frequent fatal OutOfMemoryError: PermGen errors. Metaspace moves class metadata to off-heap native memory that expands dynamically with OS memory, isolates class metadata from garbage collection pauses, and simplifies garbage collector implementations.

🎯 Q2: Can an object be allocated directly on the Stack instead of the Heap?

Answer: Yes, via Escape Analysis performed by the JIT compiler (C2). If the compiler proves that an object instantiated inside a method never "escapes" outside the method scope (i.e., not returned, not assigned to a field or global variable, not passed to an escaping method), the JVM can perform Scalar Replacement: it decomposes the object into its constituent primitive variables and allocates them directly in the method's Stack Frame local variable array, completely bypassing heap allocation and GC overhead.

🎯 Q3: Explain why setting -Xmx32g can cause worse performance than -Xmx31g.

Answer: With heaps under ~32GB, the JVM enables Compressed OOPs (-XX:+UseCompressedOops), representing object references as 32-bit integers by shifting 3 zero bits due to 8-byte alignment. Once the heap crosses the 32GB threshold, 32-bit references can no longer index all memory addresses, forcing the JVM to fall back to uncompressed 64-bit pointers. References jump from 4 bytes to 8 bytes, causing a 20-30% memory bloat, lower CPU cache density, and increased GC pressure.

🎯 Q4: How does a PhantomReference differ from WeakReference and finalize()?

Answer: finalize() was deprecated because it allowed resurrecting dead objects, had unpredictable execution timing, and caused GC stalls. WeakReference.get() returns the object until it is collected. In contrast, PhantomReference.get() always returns null to prevent object resurrection. An object's PhantomReference is placed on its registered ReferenceQueue only after the object has been completely reclaimed from physical memory, making it the safest mechanism for cleanup of native off-heap memory (e.g. via Java 9+ Cleaner).
