1. Records (Java 14 - 16 LTS): Immutability & Serialization Safety

1.1 What is a Record?

A Record is a transparent, shallowly immutable carrier for data. Declaring a record automatically synthesizes a private final field for each component, a public canonical constructor, component getter methods (named identically to the components, e.g. id() instead of getId()), and deterministic equals(), hashCode(), and toString() methods.

Modern Record with Compact Constructor Java 
public record OrderItem(String sku, int quantity, double unitPrice) {
    // Compact Constructor: Used for validation & normalization without field re-assignment
    public OrderItem {
        Objects.requireNonNull(sku, "SKU must not be null");
        if (quantity <= 0) {
            throw new IllegalArgumentException("Quantity must be positive: " + quantity);
        }
        if (unitPrice < 0.0) {
            throw new IllegalArgumentException("Price cannot be negative");
        }
        sku = sku.toUpperCase().trim(); // Field assignment happens automatically at the end!
    }

    // Custom helper method
    public double totalCost() {
        return quantity * unitPrice;
    }
}

1.2 Architectural Constraints & Serialization Security

  • Inheritance Restrictions: Every record implicitly extends java.lang.Record and is implicitly final. It cannot extend any other class, but it can implement interfaces.
  • Immutability Guarantee: All component fields are private final. Instance fields cannot be added outside the header; only static fields are permitted.
  • Serialization Superiority: Traditional Java serialization is notoriously insecure because it bypasses constructors, instantiating objects by reflection and injecting byte streams directly into memory. Records fix this vulnerability: during deserialization, the JVM must invoke the canonical constructor, ensuring invariant validations can never be bypassed!

2. Sealed Classes & Interfaces (Java 15 - 17 LTS)

2.1 Exhaustive Domain Modeling & The permits Clause

Historically, Java provided only two extremes for inheritance: open to everyone (public) or closed to everyone (final). Sealed Classes allow an author to explicitly declare which classes or interfaces are permitted to extend or implement them.

Algebraic Data Types with Sealed Interfaces Java 
// Top of the hierarchy: permits ONLY these three concrete records
public sealed interface PaymentMethod 
    permits CreditCardPayment, UpiPayment, CryptoPayment {}

public record CreditCardPayment(String cardNumber, String cvv, String expiry) implements PaymentMethod {}
public record UpiPayment(String upiId, String bankRef) implements PaymentMethod {}
public record CryptoPayment(String walletAddress, String transactionHash) implements PaymentMethod {}

2.2 Constraints on Permitted Subclasses

Every permitted subclass must directly extend the sealed class and specify exactly one of three modifiers:

  • final: Cannot be extended any further (e.g. records are implicitly final).
  • sealed: Continues the restricted inheritance hierarchy with its own permits list.
  • non-sealed: Re-opens the hierarchy to arbitrary subclasses.

3. Pattern Matching & Switch Expressions (Java 14 - 21 LTS)

3.1 Pattern Matching for instanceof (Java 16)

Eliminates redundant casting boilerplate and prevents ClassCastException:

// Old Boilerplate:
if (obj instanceof Order) {
    Order o = (Order) obj; // Manual casting
    System.out.println(o.getOrderId());
}

// Modern Pattern Matching for instanceof:
if (obj instanceof Order o && o.totalAmount() > 1000) {
    System.out.println("High value order: " + o.orderId()); // 'o' is scoped to this block
}

3.2 Switch Expressions & yield (Java 14)

Switch statements were upgraded into expressions that return values, using arrow syntax (->) to eliminate fall-through bugs without needing break statements: 

int httpStatus = 200;
String message = switch (httpStatus) {
    case 200, 201 -> "Success";
    case 400, 404 -> "Client Error";
    case 500, 502, 503 -> {
        logger.error("Internal server failure observed: {}", httpStatus);
        yield "Server Error"; // 'yield' returns a value from a multi-line block
    }
    default -> "Unknown Status";
};

3.3 Pattern Matching for switch & Guarded Patterns (Java 21)

Combines Sealed Classes and Pattern Matching to deliver Compiler-Enforced Exhaustiveness. Because the compiler knows all permitted subtypes of a sealed hierarchy, no default branch is needed:

Pattern Matching with 'when' Guards Java 
public String processPayment(PaymentMethod method) {
    return switch (method) {
        case CreditCardPayment cc when cc.cardNumber().startsWith("4") -> 
            "Processing Visa Card: " + cc.cardNumber();
        case CreditCardPayment cc -> 
            "Processing Standard Card: " + cc.cardNumber();
        case UpiPayment upi -> 
            "Triggering UPI notification to: " + upi.upiId();
        case CryptoPayment crypto -> 
            "Verifying block confirmations for: " + crypto.walletAddress();
        case null -> "No payment method supplied"; // Direct null handling in switch!
        // No 'default' branch needed! Adding a new permitted subtype causes a compile-time error.
    };
}

3.4 Record Deconstruction Patterns (Java 21)

// Deconstructs internal record components directly in the pattern:
if (method instanceof CreditCardPayment(String card, String cvv, String exp)) {
    System.out.println("Extracted Card number directly: " + card);
}

4. Text Blocks & Local Variable Type Inference (var)

4.1 Text Blocks (Java 15 LTS)

Multi-line string literals initiated by """ followed by a newline. Solves the issue of escaping JSON, SQL queries, and HTML:

Text Block Indentation Mechanics Java 
String query = """
               SELECT order_id, customer_id, total_price
               FROM orders
               WHERE status = 'SHIPPED'
               ORDER BY created_at DESC
               """;
  • Incidental vs. Essential Whitespace: The compiler automatically computes the common whitespace prefix of all lines and strips it away. The position of the closing """ dictates indentation.
  • Escape sequences: \ at the end of a line suppresses the newline character; \s preserves an explicit single whitespace.

4.2 Local Variable Type Inference: var (Java 10)

var enables the compiler to infer the static type of a local variable from its initializer at compile-time. It is NOT dynamic typing (like JavaScript or Python); the resulting variable is strictly and statically typed.

Where var IS Allowed Where var is FORBIDDEN
Local variables with explicit initializers (var count = 10;) Class member instance or static fields
Loop indices (for (var item : list)) Method parameters (e.g. void execute(var x))
Resource declarations in try-with-resources Method return types
Lambda formal parameters (e.g., (@NonNull var x) -> ...) Variables without immediate initializers or initialized to null

5. Virtual Threads & Project Loom (Java 21 LTS)

5.1 The Concurrency Paradigm Shift

Traditional Java threads (Platform Threads) are thin wrappers around physical Operating System (OS) kernel threads. They operate on a strict $1:1$ mapping:

  • Each platform thread consumes ~1MB of memory for its native call stack.
  • An OS can rarely handle more than 5,000 to 10,000 active threads before memory exhaustion and kernel context-switching overhead crashes the server.
  • In classic "thread-per-request" microservices, threads spend 95% of their lifecycle blocked waiting for database queries, Redis responses, or downstream microservices.

5.2 Virtual Threads Architecture: $M:N$ Scheduling

Virtual Threads (Project Loom) decouple Java threads from OS threads. They are lightweight, user-mode threads managed entirely by the JVM: 

+-------------------------------------------------------------------------------------+
| VIRTUAL THREADS (Millions of lightweight tasks, ~few hundred bytes each)           |
|  [ VT 1 ]  [ VT 2 ]  [ VT 3 ]  [ VT 4 ]  [ VT 5 ] ... [ VT 1,000,000 ]               |
+-------------------------------------------------------------------------------------+
                               | (Mounted / Unmounted dynamically)
                               v
+-------------------------------------------------------------------------------------+
| CARRIER THREADS (Standard Platform Threads in ForkJoinPool, pool size = CPU cores)  |
|  [ Carrier-1 ]          [ Carrier-2 ]          [ Carrier-3 ]          [ Carrier-4 ] |
+-------------------------------------------------------------------------------------+
                               | (1:1 OS Thread mapping)
                               v
+-------------------------------------------------------------------------------------+
| OS KERNEL THREADS                                                                   |
+-------------------------------------------------------------------------------------+

5.3 How Virtual Threads Mount and Unmount

  1. When a Virtual Thread executes CPU instructions, it is mounted onto a physical Carrier Thread.
  2. When the Virtual Thread performs a blocking I/O operation (e.g., Socket.read(), Thread.sleep(), JDBC query, HTTP call):
    • The JVM intercepts the call and saves the virtual thread's stack frames into the Java Heap (Continuation).
    • The virtual thread is unmounted from the Carrier Thread.
    • The Carrier Thread is now completely free to execute thousands of other virtual threads!
  3. When the OS signals that the network packet or database response has arrived, the virtual thread is re-queued and mounted onto any available Carrier Thread to resume execution seamlessly.
Executing 100,000 Virtual Threads with Zero Overhead Java 
// New Executor Service in Java 21: creates an ephemeral Virtual Thread per task
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 100_000).forEach(i -> {
        executor.submit(() -> {
            // Blocking I/O does NOT block the OS thread!
            Thread.sleep(Duration.ofSeconds(1));
            return "Task " + i + " completed";
        });
    });
} // Executor automatically waits for all tasks to complete upon close()
⚠️ The Virtual Thread Pinning Gotcha (Thread Pinning)

A Virtual Thread becomes pinned to its Carrier Thread (meaning it cannot be unmounted during blocking I/O) in two critical situations:

1. When executing a blocking operation inside a synchronized block or method.
2. When executing a blocking call inside a native method or foreign function call.

If a pinned virtual thread blocks on I/O, the underlying physical Carrier Thread is also blocked. If all carrier threads become pinned, the entire JVM stalls!
Fix: Replace legacy synchronized blocks guarding blocking I/O with java.util.concurrent.locks.ReentrantLock.

6. Real-Time Production Issues & Post-Mortems

🚨 Incident 1: Total Carrier Thread Starvation Due to Synchronized JDBC Driver Pinning

Scenario: A fintech payment gateway migrated from Java 17 to Java 21 and switched Tomcat to use Executors.newVirtualThreadPerTaskExecutor(). Under moderate load (2,000 req/sec), throughput collapsed, p99 latency spiked from 30ms to 45,000ms, and CPU dropped to near 0%.

🔍 Root Cause Analysis (RCA)

The service used an outdated database connection pool / JDBC driver where connection acquisition and statement execution wrapped socket calls in synchronized(this) { ... socket.read(); } blocks.

Because of synchronized, every virtual thread executing a SQL query pinned its carrier thread. The JVM's carrier pool (defaulting to 8 carrier threads on an 8-core CPU) became completely pinned and blocked on socket I/O. As thousands of incoming HTTP virtual threads queued up, zero carrier threads were available to schedule them, freezing the application.

💡 Production Resolution
  • Diagnosed via JVM Flag: Enabled pinning detection: -Djdk.tracePinnedThreads=full to output the exact stack traces causing thread pinning.
  • Driver Upgrade: Upgraded the JDBC driver and connection pool (HikariCP 5.1+) which replaced all internal synchronized locks with ReentrantLock.
🚨 Incident 2: Heap OOM from ThreadLocal Pooling Anti-Pattern in Virtual Threads

Scenario: An enterprise logging interceptor maintained a ThreadLocal<byte[]> buffer of 2MB to serialize JSON logs. With platform threads (200 threads), heap usage was 400MB. When migrated to virtual threads under a spike of 50,000 concurrent requests, the JVM crashed with java.lang.OutOfMemoryError: Java heap space.

🔍 Root Cause Analysis (RCA)

In traditional architectures, platform threads are pooled and reused (e.g. 200 threads). When using virtual threads, threads are ephemeral—you create a new virtual thread per request. 50,000 concurrent virtual threads each allocating a 2MB ThreadLocal buffer consumed $50,000 \times 2\text{MB} = 100\text{GB}$ of heap memory!

💡 Production Resolution
  • Rule: Never pool Virtual Threads! They are meant to be created and discarded.
  • Replacement: Migrated from heavy ThreadLocal instances to Scoped Values (JEP 446 / Java 21 preview), which allow immutable, lightweight data sharing across threads without retaining heap buffers.

8. Senior / Staff Technical Interview Q&A

🎯 Q1: Should you pool Virtual Threads like Platform Threads?

Answer: Absolutely not. Pooling threads was an architectural workaround created solely because platform threads are expensive OS resources ($1\text{MB}$ stack, kernel context switching). Virtual threads, by contrast, are cheap Java objects allocated on the heap (costing a few hundred bytes) that are collected by the GC when finished. Pooling virtual threads wastes memory, prevents carrier unmounting, and breaks thread-per-request concurrency models.

🎯 Q2: Do Virtual Threads make CPU-bound tasks (e.g. video rendering or cryptography) faster?

Answer: No. Virtual threads provide massive throughput improvements only for I/O-bound tasks (database queries, network requests, disk I/O) where threads spend significant time waiting. For CPU-bound tasks, the physical CPU cores are already saturated at 100%; virtual threads cannot create more compute capacity and introduce slight scheduling overhead compared to a fixed pool sized to available CPU cores.

🎯 Q3: Why is deserialization of Records considered fundamentally safer than normal classes?

Answer: In standard classes, Java serialization bypasses constructors completely, initializing memory reflectively and assigning values to fields directly from the stream. This allows malicious byte streams to inject corrupted invariants or bypass security validations. With Records, the JVM serialization protocol mandates that deserialization must invoke the canonical constructor, guaranteeing that all parameter checks and invariant validations run on deserialized objects.

🎯 Q4: Explain the difference between sealed classes and enums. When should you choose which?

Answer: An enum represents a fixed set of singleton instances where every constant shares the exact same state structure. A sealed class represents a fixed set of types / classes, where each subtype can have its own distinct fields, constructors, methods, and multiple independent instances. Use enums for simple fixed values (e.g. OrderStatus: PENDING, APPROVED); use sealed classes for rich domain models / Algebraic Data Types (e.g. PaymentMethod: CreditCard(card, cvv) vs Cash(amount)).
