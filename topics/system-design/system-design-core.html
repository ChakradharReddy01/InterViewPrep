System Design Masterclass — From Fundamentals to Real Products

A beginner-friendly but in-depth guide for backend engineering interviews. Learn why each concept exists, how the components work together, how to reason about trade-offs, and how to explain designs clearly in interviews.

Beginner-friendly explanationsDistributed systems14 real-world designsProduction failuresInterview scripts
Remember: There is no single “correct” architecture without requirements. Interviewers assess how you reason about scale, correctness, failure, cost, and trade-offs—not how many buzzwords you mention.

How to use this masterclass

Start with the fundamentals, learn what each infrastructure component contributes, then practice each design using the same interview method. Every design section includes a simple explanation, a request flow, data/storage choices, trade-offs, production failures, and an interview-ready summary.

Golden rule: System design is not a contest to name the most technologies. First define requirements and constraints, estimate load, design the simplest correct architecture, then evolve it around bottlenecks and failure modes.

A repeatable 45-minute interview framework

  1. Clarify requirements (5 min): functional scope, users, APIs, permissions, edge cases, and out-of-scope items.
  2. Non-functional goals (3 min): latency, availability, consistency, durability, security, and cost.
  3. Estimate scale (5 min): daily active users, requests/second, read-write ratio, storage growth, bandwidth, peak multiplier.
  4. Sketch APIs and data model (5 min): main endpoints, entities, keys, indexes, and invariants.
  5. High-level architecture (10 min): clients, gateway, services, database, cache, queues, object storage/CDN.
  6. Deep dive (10 min): choose the riskiest part—hot keys, consistency, fanout, payment correctness, scheduling, etc.
  7. Reliability and trade-offs (5 min): failure handling, monitoring, security, scaling limits, and what you would change at 10× scale.
REQUIREMENTS → SCALE ESTIMATES → API + DATA MODEL → HIGH-LEVEL DESIGN → BOTTLENECK DEEP DIVE → FAILURES + TRADE-OFFS → METRICS + EVOLUTION

Part I — System Design Fundamentals

These concepts help explain why an architecture is designed a certain way. Learn the meaning, the trade-off, and a concrete example rather than memorizing definitions only.

1. Scalability

Explain it simply

Scalability means handling more work by adding resources or improving how efficiently existing resources work. Think of a shop: open more checkout counters, or make each counter faster.

Understand it in depth

Vertical scaling (scale up) gives one machine more CPU/RAM; it is simple but has a hardware ceiling and may create a bigger failure point. Horizontal scaling (scale out) adds instances behind a load balancer; it improves capacity and resilience but requires stateless services or shared/distributed state.

How to apply it in a real system

Estimate demand first: requests per second, concurrent users, payload size, database reads/writes, peak-to-average ratio. Then load-test, find the bottleneck, scale that tier, and re-measure. Caching can reduce reads; partitioning can distribute data; queues can smooth bursts. Scaling the app does not help if one database remains the bottleneck.

Interview answer: “I start with workload estimates and measurements, identify the saturated resource, then choose vertical or horizontal scaling. I keep app instances stateless where possible, scale the bottleneck, and validate with load tests. I also check downstream limits so added instances do not overwhelm the database.”

2. Availability

Explain it simply

Availability is the fraction of time a system can successfully serve requests. A shop is available when customers can actually complete the intended purchase, not merely when the building has power.

Understand it in depth

Availability = successful time / total time. Roughly, 99.9% availability allows about 8 hours 46 minutes of downtime per year; 99.99% allows about 52 minutes. Redundancy helps only when failover works and shared dependencies are not single points of failure.

How to apply it in a real system

Use multiple instances/zones, health checks, load balancing, replicated data, tested failover, graceful degradation, and sensible timeouts. Define what counts as success in an SLI; a process being “up” while every request returns 500 is not useful availability.

Interview answer: “I define availability from the user’s successful outcome, set an SLO, remove single points of failure, and test zone/dependency failures. I balance redundancy against cost and consistency requirements.”

3. Reliability

Explain it simply

Reliability is the ability to keep doing the correct thing over time, including during faults. Availability asks “can I use it now?”; reliability also asks “does it behave correctly and recover predictably?”

Understand it in depth

A service can be available but unreliable if it occasionally charges a customer twice. Reliability includes correctness, durability, fault handling, recovery, and predictable behavior under stress.

How to apply it in a real system

Use idempotency, durable writes, bounded retries, timeouts, circuit breakers, backups, restore drills, monitoring, and failure testing. Prevent cascading failures and make operations observable.

Interview answer: “I distinguish uptime from correctness. For reliability I protect invariants, use durable storage and idempotent operations, contain failures, and test recovery—not just health endpoints.”

4. Latency

Explain it simply

Latency is how long one operation takes, usually measured from the caller’s perspective. It is the wait for one parcel to arrive.

Understand it in depth

Track p50, p95, and p99, not only the average. If 99 requests take 50 ms and one takes 3 seconds, the average can hide the poor tail experience. Sequential network calls add latency; parallel calls reduce wall-clock time but increase resource use.

How to apply it in a real system

Set an end-to-end deadline and propagate timeouts. Reduce chatty calls, optimize queries, cache safe reads, keep payloads small, use connection pools correctly, and inspect traces. Never “fix” latency by retrying every slow request without bounds.

Interview answer: “I use percentile latency and distributed traces to locate the slow segment. I set an end-to-end deadline, optimize the actual bottleneck, and verify p95/p99 under realistic load.”

5. Throughput

Explain it simply

Throughput is how much work completes per unit time: orders per second, MB/s, or messages per second. Latency is the time per request; throughput is the number completed.

Understand it in depth

A system may have high throughput but poor latency if it batches heavily. Throughput depends on concurrency, CPU, I/O, lock contention, database capacity, and workload mix. Little’s Law: in a stable system, average in-flight work L = arrival rate λ × average time W.

How to apply it in a real system

Measure completed successful work, not merely incoming requests. Use load tests, bounded concurrency, batching where appropriate, backpressure, efficient queries, and capacity planning. Avoid unbounded queues: they turn overload into very long waits and memory exhaustion.

Interview answer: “I measure sustainable successful throughput and latency together. I ramp load, find the saturation knee, then address CPU, database, locks, or network constraints while maintaining queue and latency limits.”

6. CAP Theorem

Explain it simply

CAP says that when a network partition prevents nodes from communicating, a distributed data system cannot guarantee both linearizable consistency and availability for every request.

Understand it in depth

C means a read sees the latest completed write according to a single-copy ordering (linearizability); A means every request to a non-failing node gets a response; P means the system tolerates network partitions. In real distributed systems partitions must be considered, so during a partition the design chooses which operations to reject/delay or allow with potentially stale/conflicting data.

How to apply it in a real system

A bank balance transfer may reject writes to preserve correctness; a social “like” counter may accept writes and reconcile later. CAP is specifically about behavior during partitions—not a general claim that every system simply picks two properties all the time.

Interview answer: “I first identify the consistency contract and partition behavior. For money or inventory invariants I may reject operations when quorum cannot be reached; for low-risk feeds I may accept writes and reconcile. The choice is per operation, not just per product.”

7. PACELC

Explain it simply

PACELC extends CAP: if there is a Partition (P), choose Availability or Consistency; Else (E), during normal operation choose Latency or Consistency.

Understand it in depth

A replicated database may normally wait for remote replicas to acknowledge a write, improving consistency but increasing latency. During a partition it may reject requests to preserve consistency or accept them with conflict risk to improve availability.

How to apply it in a real system

Ask how reads/writes behave both normally and during failures: quorum size, replica distance, stale-read tolerance, conflict resolution, and latency SLO. Avoid saying “database X is always CP/AP” without configuration and operation context.

Interview answer: “CAP tells me about partition trade-offs; PACELC also makes normal-operation latency-versus-consistency explicit. I choose based on each workflow’s correctness needs and latency budget.”

8. Consistency

Explain it simply

Consistency describes what a read is allowed to observe after writes. Imagine two people checking the same notebook: do they always see the latest entry, or might one see an older copy?

Understand it in depth

Strong/linearizable reads reflect the latest completed write; sequential consistency preserves a global order but not necessarily real-time order; causal consistency preserves cause-and-effect; eventual consistency means replicas converge if updates stop and communication resumes. Read-your-writes is a useful user-facing guarantee.

How to apply it in a real system

Choose the weakest guarantee that still preserves business rules. Account balances and unique reservations need strong coordination at the critical write boundary. Likes, view counts, and search indexes can often be eventually consistent. Document stale-read behavior in API contracts.

Interview answer: “I describe consistency in terms of observable guarantees, not vague labels. I identify the invariant, select the read/write guarantee, and explain the latency and availability cost.”

9. Eventual Consistency

Explain it simply

Eventual consistency means replicas may temporarily disagree, but if updates stop and the system can communicate, replicas eventually converge. It does not mean “data will be correct immediately.”

Understand it in depth

Example: an order is created in the order database, then an event updates the search index and analytics store a moment later. The order API can be correct while search briefly does not show the order.

How to apply it in a real system

Design for duplicate and out-of-order events, retries, idempotent consumers, versioning, reconciliation, lag monitoring, and user-visible pending states. Do not use eventual consistency where a stale result can violate a critical invariant, such as overselling the last item without a reservation mechanism.

Interview answer: “I use eventual consistency for derived views and workflows that tolerate a short delay. I make the delay observable, process events idempotently, and provide reconciliation and a clear user experience for pending updates.”

Part II — System Design Components

Components are tools with specific responsibilities. A strong design explains why each one exists, what it costs, and how the system behaves when it fails.

1. Load Balancer

Explain it simply

Distributes incoming traffic across healthy service instances, like a host directing guests to open counters.

How it works

Layer 4 balances TCP/UDP connections; Layer 7 understands HTTP and can route by host/path/header. Common algorithms: round robin, least connections, weighted routing, consistent hashing. Health checks remove unhealthy targets, but bad health checks can flap or mark a slow-but-recoverable service dead.

Production concerns and solutions

Use multiple instances across failure zones, configure connection/read timeouts, graceful draining for deployments, TLS policy, and meaningful health checks. Beware sticky sessions: they can create uneven load and complicate failover.

Interview answer: “The load balancer improves distribution and removes unhealthy targets, but it does not make a service scalable by itself. I also make instances stateless, set health checks/timeouts, and plan zone-level failure.”

2. API Gateway

Explain it simply

The public front door for APIs. It routes a request to the right backend and can apply authentication, quotas, TLS termination, request validation, and API version policies.

How it works

Mobile app → gateway → order service. It hides internal topology and can aggregate multiple backend calls, but aggregation can create latency and a central bottleneck. A gateway should not become the place where all business logic lives.

Production concerns and solutions

Deploy it redundantly, set per-route limits, propagate identity/correlation IDs, validate payload sizes, and monitor upstream latency/errors. Avoid chaining gateways and avoid retrying non-idempotent requests blindly.

Interview answer: “I put cross-cutting edge concerns at the gateway, business rules in domain services, and keep the gateway horizontally scalable with explicit timeout and rate-limit policies.”

3. Cache

Explain it simply

A cache stores reusable results close to the caller so repeated work is avoided. It is like keeping popular books at the front desk instead of fetching them from a warehouse every time.

How it works

Cache-aside: read cache; on miss read DB and populate cache. Write-through updates cache and DB through the cache layer; write-behind asynchronously persists changes and needs careful durability handling. TTL controls expiry, but does not guarantee freshness by itself.

Production concerns and solutions

Cache hot reads, not every value blindly. Plan invalidation, stale-data tolerance, stampede protection, TTL jitter, negative caching, size limits, and fallback behavior. A cache outage can overload the database, so use bulkheads and rate limits.

Interview answer: “I define what can be stale, use cache-aside for many read-heavy paths, select TTL/invalidation deliberately, and protect the database against cache misses or cache failure.”

4. Database

Explain it simply

The durable source of truth for structured state and business invariants. Pick it around access patterns, consistency, relationships, and operational needs—not fashion.

How it works

Relational databases are strong for transactions and relational queries; key-value/document stores can suit specific access patterns and horizontal scale; wide-column/time-series/search systems serve other workloads. Replication improves resilience/read scale; partitioning distributes data but complicates queries and transactions.

Production concerns and solutions

Design indexes from query plans, use connection pooling, bound transactions, backup and test restores, plan migrations, monitor replication lag and pool saturation, and understand isolation levels. Never treat replicas as automatically current.

Interview answer: “I start from invariants and query patterns, then choose the data model. I size pools, inspect execution plans, protect transactions, and test restore and failover.”

5. Message Queue

Explain it simply

A queue lets a producer hand work to a broker so a consumer can process it later. It separates the time when work is requested from the time it is completed.

How it works

Useful for email, image processing, and burst absorption. Delivery may be at-most-once or at-least-once depending on broker and acknowledgment design; duplicates are common enough that consumers should be idempotent. Queues differ from logs: a queue often models work distribution, while a log retains ordered events for replay.

Production concerns and solutions

Use bounded retries, dead-letter handling, visibility/ack timeouts, poison-message isolation, queue-depth and age alerts, and idempotency keys. A queue smooths bursts but does not create unlimited capacity; backlog age matters more than count alone.

Interview answer: “I use a queue for asynchronous work and load leveling. I define acknowledgment and retry semantics, make handlers idempotent, monitor oldest-message age, and design a DLQ replay process.”

6. Kafka

Explain it simply

Kafka is a distributed event log: topics are split into partitions, events are appended and retained, and consumers track offsets. It is suited to durable event streams and replay, not merely as a generic task queue.

How it works

Partitions provide parallelism and ordering within each partition, not globally across a topic. Consumer groups divide partitions among consumers. Retention or compaction determines how data remains available; replication protects against broker failure.

Production concerns and solutions

Choose partition keys carefully, monitor consumer lag, size retention/storage, use schemas, handle duplicates, and avoid assuming “exactly once” automatically covers external databases or payment APIs.

Interview answer: “I choose Kafka when multiple consumers need durable event history, replay, and high-throughput streams. I explain partition ordering, consumer groups, lag, schema evolution, and the end-to-end idempotency boundary.”

7. CDN

Explain it simply

A Content Delivery Network caches static or cacheable content near users at edge locations, reducing distance and origin load.

How it works

Browser → nearby edge cache → origin only on miss/expiry. Great for images, CSS, JavaScript, video segments, and downloads. Dynamic personalized content needs careful cache keys and privacy controls.

Production concerns and solutions

Set Cache-Control correctly, version immutable assets, purge carefully, protect origin from cache-miss storms, and never cache private responses under a shared key.

Interview answer: “I use a CDN for geographically distributed read-heavy content, version static assets, set explicit cache headers, and prevent personalized data from leaking through shared caches.”

8. Object Storage

Explain it simply

Stores files as objects addressed by keys, often with metadata, in highly durable distributed storage. Think of a huge managed warehouse for photos, videos, backups, and documents.

How it works

Application stores file bytes in object storage and stores metadata/ownership in a database. Clients can upload/download with short-lived signed URLs, avoiding routing large payloads through app servers. It is not generally a POSIX filesystem or a replacement for transactional relational data.

Production concerns and solutions

Validate file type/size, scan uploads, encrypt, enforce tenant-level authorization, use lifecycle policies, versioning, checksums, and backups/replication according to needs. Make upload completion and metadata creation recoverable.

Interview answer: “I keep large blobs in object storage and metadata in a database. I use signed URLs, least-privilege policies, checksums, malware scanning where needed, and lifecycle/retention controls.”

9. Search

Explain it simply

A search engine builds an index optimized for text relevance, filters, and faceted queries. It is usually a derived view, not the authoritative database.

How it works

Write business data to the source database, publish changes, and update a search index asynchronously. Inverted indexes map terms to documents. Search can be eventually consistent and results may briefly lag the source.

Production concerns and solutions

Handle reindexing, mapping/schema changes, duplicate/out-of-order events, deleted records, access-control filters, and index lag. Never rely on a search result alone for a critical final authorization or inventory decision.

Interview answer: “I use search for relevance and discovery, keep the source of truth elsewhere, update the index from reliable events, and re-check authorization and critical business conditions against authoritative data.”

10. Rate Limiter

Explain it simply

Controls how many requests a user, API key, IP, or tenant may make in a time window. It protects fairness and downstream capacity.

How it works

Token bucket allows bursts up to bucket capacity while limiting average rate; leaky bucket smooths output; fixed windows are simple but allow boundary bursts; sliding windows are more accurate but costlier. Distributed limits need shared state or partitioned quotas.

Production concerns and solutions

Return 429 with Retry-After when appropriate, define per-user and global limits, prevent spoofed IP identity, protect the limiter itself, and distinguish rate limiting from concurrency limiting. Fail-open versus fail-closed depends on risk.

Interview answer: “I choose an algorithm based on burst tolerance and precision, key quotas by authenticated identity, define distributed behavior, and return predictable 429 responses while protecting critical downstreams.”

Part III — End-to-end System Designs

For every design, say assumptions out loud, sketch the core path, choose the source of truth, then discuss the hardest correctness and scale problem.

1. Design: URL Shortener

1. Clarify the problem

Turn a long URL into a short code and redirect visitors quickly.

2. High-level architecture

Client / Mobile / Web | v Load Balancer / API Gateway | v Domain API / Application Service |--------------------| v v Durable Database Cache / Queue / Workers | | +------ Events -------+ | v Monitoring / Alerts

Request or event flow: Create: validate URL → generate unique code → store code-to-URL mapping → return short URL. Visit: GET /{code} → cache lookup → database lookup on miss → redirect (301/302 based on product needs).

3. Data model and storage

Mapping table: code (unique primary key), long_url, owner_id, created_at, expires_at, status. Cache popular codes with TTL. Analytics can be asynchronous.

4. Deep design decisions

Generate collision-resistant codes (random Base62 or ID + encoding), enforce a unique constraint, retry collisions, protect against abuse/phishing, define expiration and deletion, and decide whether analytics are best effort. Read traffic is often much larger than create traffic.

5. Failure modes and mitigations

Hot links can overload a single cache shard; a cache miss storm can overload the DB; a code collision can overwrite a mapping if uniqueness is not enforced. Use cache protection, DB uniqueness, rate limits, and asynchronous analytics.

6. How to explain it in an interview

“I separate the write path from the redirect read path. I use a unique code with a database uniqueness constraint, cache hot mappings, keep analytics asynchronous, and plan expiry, abuse protection, and hot-key behavior.”

Follow-up questions to prepare

  • What changes if traffic grows 10× or 100×?
  • What is the single point of failure, and how is it removed?
  • Which data must be strongly consistent, and what can be eventually consistent?
  • How do you handle retries, duplicate requests, timeouts, and partial failure?
  • What metrics and alerts tell you the design is unhealthy?

2. Design: Parking Lot

1. Clarify the problem

Model a parking facility that assigns a suitable available spot and tracks entry, exit, and payment.

2. High-level architecture

Client / Mobile / Web | v Load Balancer / API Gateway | v Domain API / Application Service |--------------------| v v Durable Database Cache / Queue / Workers | | +------ Events -------+ | v Monitoring / Alerts

Request or event flow: Vehicle enters → ticket/booking created → find compatible free spot → atomically reserve it → calculate fee at exit → collect payment → release spot.

3. Data model and storage

ParkingSpot(id, floor, type, status), Ticket(id, vehicle, spot, entry_time, exit_time), Payment. Keep spot assignment and state transition transactional.

4. Deep design decisions

Use a domain model: Vehicle, Spot, Floor, Ticket, Gate, PricingStrategy, Payment. Match vehicle size/type and accessibility rules. In concurrent entry, two gates must not reserve the same spot; use conditional update/locking or reservation tokens.

5. Failure modes and mitigations

Race condition assigns one spot twice; payment failure leaves ticket open; gate/network outage interrupts entry. Use atomic reservation, payment state machine, reconciliation, and manual/online fallback.

6. How to explain it in an interview

“I clarify requirements first—vehicle types, reservations, pricing, multiple lots, offline gates. I model spot state transitions and enforce single allocation atomically, then isolate payment and gate integrations.”

3. Design: Rate Limiter Design

1. Clarify the problem

Limit requests by identity and time while allowing a controlled burst.

2. High-level architecture

Client / Mobile / Web | v Load Balancer / API Gateway | v Domain API / Application Service |--------------------| v v Durable Database Cache / Queue / Workers | | +------ Events -------+ | v Monitoring / Alerts

Request or event flow: Request → identify tenant/API key → consult limiter state → allow and decrement token or reject with 429 → record metrics. A local limiter protects each instance; a distributed limiter enforces a shared quota.

3. Data model and storage

For token bucket store token count and last refill time per key; use atomic scripts/operations in shared storage when needed. Keep keys bounded and expire idle entries.

4. Deep design decisions

Token bucket is a strong general default: rate controls long-term average and capacity controls burst. Sliding log is accurate but memory-heavy; fixed window is cheap but has boundary bursts. Discuss clock behavior, multi-region quotas, and fail-open/fail-closed.

5. Failure modes and mitigations

Distributed counters race or shared store outage causes inconsistent limits. Use atomic updates, local emergency limits, explicit failure policy, and monitor rejection rate and limiter latency.

6. How to explain it in an interview

“I choose token bucket for burst-friendly quotas, key by authenticated tenant, use atomic shared updates for global limits, and define the degraded mode if the limiter store fails.”

4. Design: Notification System

1. Clarify the problem

Deliver email, SMS, push, or in-app notifications reliably without slowing the business request.

2. High-level architecture

Client / Mobile / Web | v Load Balancer / API Gateway | v Domain API / Application Service |--------------------| v v Durable Database Cache / Queue / Workers | | +------ Events -------+ | v Monitoring / Alerts

Request or event flow: Business event → notification request/outbox → queue → preference/template service → channel workers → provider → delivery status/retry/DLQ.

3. Data model and storage

Store notification ID, recipient, channel, template/version, status, attempt count, scheduled time, provider ID, idempotency key, and audit timestamps. Use an outbox to avoid losing events between DB commit and publish.

4. Deep design decisions

Separate transactional business success from best-effort delivery. Support user preferences, quiet hours, localization, priority, provider fallback, deduplication, retries with backoff, and rate limits per provider/recipient.

5. Failure modes and mitigations

Provider outage creates backlog; retry loops send duplicates; bad templates affect many users. Circuit-break providers, cap retries, DLQ poison items, canary templates, and alert on oldest message age.

6. How to explain it in an interview

“I make notification delivery asynchronous, use an outbox plus queue, model delivery as a state machine, and design for duplicates, provider outages, preferences, retries, and observability.”

5. Design: Chat System

1. Clarify the problem

Send messages between users or groups with low latency, durable history, and correct conversation membership.

2. High-level architecture

Client / Mobile / Web | v Load Balancer / API Gateway | v Domain API / Application Service |--------------------| v v Durable Database Cache / Queue / Workers | | +------ Events -------+ | v Monitoring / Alerts

Request or event flow: Client connects via WebSocket → gateway authenticates → message service validates membership → persist message and sequence → publish event → fan out to online devices → offline clients fetch history and unread state.

3. Data model and storage

Conversation, membership, message(conversation_id, sequence, sender, body, created_at), per-user read cursor, device/session presence. Partition by conversation ID to keep conversation ordering manageable.

4. Deep design decisions

Separate durable message history from ephemeral presence/typing. Use reconnect cursors, acknowledgments, deduplication IDs, push notifications for offline users, attachments in object storage, and encryption/privacy requirements.

5. Failure modes and mitigations

Reconnect causes duplicates or gaps; one huge group creates a hot partition; presence becomes stale. Use client message IDs, sequence/cursors, fanout strategies, TTL presence, and backpressure.

6. How to explain it in an interview

“I define ordering per conversation rather than globally, persist before acknowledging, use WebSockets for online delivery and cursors for recovery, and treat presence/typing as ephemeral.”

6. Design: Food Delivery

1. Clarify the problem

Coordinate customer order, restaurant acceptance/preparation, courier assignment, delivery tracking, and payment across independent actors.

2. High-level architecture

Client / Mobile / Web | v Load Balancer / API Gateway | v Domain API / Application Service |--------------------| v v Durable Database Cache / Queue / Workers | | +------ Events -------+ | v Monitoring / Alerts

Request or event flow: Browse restaurants/menu → create order → reserve/confirm payment according to policy → restaurant accepts → dispatch assigns courier → pickup → live tracking → delivered → settle/refund if needed.

3. Data model and storage

Separate Order, Restaurant/Menu, Dispatch, Payment, and Tracking models. Order state machine with durable events; geospatial index for nearby couriers/restaurants; event history for audit.

4. Deep design decisions

Use saga/workflow for long-running steps, idempotent commands, inventory/menu availability checks, ETA estimates, location sampling, and compensating actions such as refund/cancel. Payment timing is a business decision.

5. Failure modes and mitigations

Restaurant rejects after authorization; courier cancels; GPS goes stale; duplicate provider callback. Use explicit states, timeouts, re-dispatch, payment compensation, and callback idempotency.

6. How to explain it in an interview

“I model order fulfillment as a state machine and saga, keep payment and dispatch separate, use events for state changes, and design compensation for restaurant or courier failures.”

7. Design: E-commerce

1. Clarify the problem

Support catalog discovery, cart, checkout, inventory, orders, payments, shipping, and returns at scale.

2. High-level architecture

Client / Mobile / Web | v Load Balancer / API Gateway | v Domain API / Application Service |--------------------| v v Durable Database Cache / Queue / Workers | | +------ Events -------+ | v Monitoring / Alerts

Request or event flow: Browse → product/search → cart → checkout validates price and stock → reserve inventory → authorize payment → create order → confirm/ship asynchronously.

3. Data model and storage

Catalog/search index, cart store, order DB, inventory ledger/reservations, payment records, and object storage for product media. Each domain owns its writes; search/cache are derived views.

4. Deep design decisions

Prevent overselling with atomic inventory reservation; snapshot price/tax at checkout; use idempotency keys; handle payment webhooks; use saga/outbox; separate browse traffic from checkout capacity.

5. Failure modes and mitigations

Flash sale overwhelms DB; cache shows stale price; payment succeeds but order update fails. Use queueing/virtual waiting room, authoritative checkout validation, reservation, outbox, reconciliation, and autoscaling.

6. How to explain it in an interview

“I separate read-heavy catalog from correctness-critical checkout. I reserve inventory atomically, make payment operations idempotent, use an outbox/saga for cross-service flow, and reconcile asynchronous outcomes.”

8. Design: Payment System

1. Clarify the problem

Move money safely while handling retries, timeouts, provider callbacks, and reconciliation.

2. High-level architecture

Client / Mobile / Web | v Load Balancer / API Gateway | v Domain API / Application Service |--------------------| v v Durable Database Cache / Queue / Workers | | +------ Events -------+ | v Monitoring / Alerts

Request or event flow: Client sends payment with idempotency key → validate and persist intent → authorize/capture with provider → store provider reference → consume webhook idempotently → update state → reconcile against provider settlement.

3. Data model and storage

PaymentIntent/PaymentAttempt, idempotency key, amount/currency, state, provider reference, ledger entries, webhook inbox, reconciliation records. Ledger entries should be append-only and balanced where double-entry accounting applies.

4. Deep design decisions

Never assume timeout means payment failed; provider may have succeeded while response was lost. Model states (created, pending, authorized, captured, failed, refunded), verify signatures, use integer minor units/decimal-safe money, and audit every transition.

5. Failure modes and mitigations

Retry charges twice; out-of-order webhook overwrites final state; internal/provider ledger diverges. Use idempotency at every boundary, state-transition guards, webhook dedupe, and periodic reconciliation/manual review.

6. How to explain it in an interview

“I prioritize correctness over availability for money movement. I use idempotency keys, durable payment intents, explicit state transitions, signed webhook handling, append-only ledger/audit, and reconciliation.”

14. Design: Job Scheduler

1. Clarify the problem

Run tasks at a specified time or recurrence, with retries, concurrency limits, and recovery after scheduler failure.

2. High-level architecture

Client / Mobile / Web | v Load Balancer / API Gateway | v Domain API / Application Service |--------------------| v v Durable Database Cache / Queue / Workers | | +------ Events -------+ | v Monitoring / Alerts

Request or event flow: User creates job → validate schedule/time zone → scheduler claims due job → enqueue execution → worker acquires lease → executes with idempotency → records outcome and next run.

3. Data model and storage

Job definition, schedule/cron, timezone, next_run_at, status, lease owner/expiry, attempt count, execution history. Use DB row locks/leases or a durable scheduling service to coordinate replicas.

4. Deep design decisions

At-least-once execution is common; exactly-once side effects require idempotent task design. Handle daylight saving time, missed runs, overlapping runs, jitter, priorities, cancellation, and poison jobs. Separate schedule discovery from task execution.

5. Failure modes and mitigations

Two schedulers claim same job; worker crashes after side effect but before marking complete; clock/timezone bug causes duplicate/missed run. Use atomic claims, leases, idempotency keys, reconciliation, and explicit misfire policy.

6. How to explain it in an interview

“I separate schedule evaluation from worker execution, use durable due-job claims and expiring leases, assume retries can duplicate execution, and require idempotent side effects with explicit misfire/time-zone policies.”

Interview Q&A — core concepts

Practice answering aloud in 30–90 seconds. Then add an example and a trade-off.

How do you start a system design interview?

Clarify the use cases and constraints before choosing technologies. State assumptions, define measurable non-functional goals, estimate traffic/storage, and identify the critical invariants.

What is the difference between scalability and performance?

Performance describes how well the system responds now, often latency and throughput. Scalability describes how performance/capacity changes as load or resources grow.

When would you choose SQL over NoSQL?

Choose based on invariants, transactions, relationships, query patterns, and operational capabilities. SQL is often a strong default for transactional business data; NoSQL fits particular access patterns and scaling needs, not a blanket replacement.

Why use a cache if it can become stale?

Because some reads tolerate bounded staleness and cache hits reduce latency and origin load. Define freshness requirements, invalidation/TTL, and fallback behavior explicitly.

How do you prevent duplicate payments?

Use a stable idempotency key, persist a payment intent before provider calls, deduplicate callbacks, guard state transitions, and reconcile with the provider. A timeout does not prove the payment failed.

What does CAP actually mean?

When a network partition occurs, a distributed system cannot guarantee both linearizable consistency and a successful response for every request. The product must choose how operations behave during the partition.

Why is a queue not infinite scalability?

A queue buffers bursts but consumers still have finite throughput. If arrival rate exceeds processing rate for long enough, backlog and message age grow until storage or business deadlines are exceeded.

How do you design for failure?

Assume dependencies can time out, return errors, or partially succeed. Use deadlines, bounded retries with jitter, idempotency, circuit breakers, bulkheads, durable state, fallbacks, and tested recovery.

How do you explain a trade-off?

Name the options, the requirement that matters, the downside accepted, and how you mitigate it. Example: stronger consistency may add cross-region latency; if money correctness dominates, that latency may be acceptable.

How do you know a system is healthy?

Use user-oriented SLIs such as successful request rate, p95/p99 latency, freshness, queue age, and payment completion. Combine metrics with logs, traces, alerts, and actionable runbooks.

Strong answer structure

Definition → example → decision → trade-off → failure handling → metric. This structure shows that you understand both the concept and the operational consequences.
