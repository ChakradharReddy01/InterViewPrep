1. Entity

An entity is a Java object whose important state is stored in a database table. Think of it as a row that has an identity, such as customer id 42. Hibernate maps Java fields to table columns and translates entity operations into SQL.

Example scenario: A customer registration saves one `Customer`; Hibernate inserts a row and assigns the generated id.

Sample code

@Entity
@Table(name = "customers")
public class Customer {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 120)
    private String name;

    @Column(nullable = false, unique = true)
    private String email;

    protected Customer() { } // JPA needs a no-argument constructor

    public Customer(String name, String email) {
        this.name = name;
        this.email = email;
    }
    // getters/setters omitted
}
Thumb rule: `@Entity` makes the class persistent; `@Table` names the table; `@Id` defines identity. Keep a protected/public no-argument constructor, avoid final entity classes or persistent fields when proxying is required, and do not treat an entity as a request/response DTO.

Entity is useful when the use case requires the behavior described above, but always verify generated SQL and transaction boundaries rather than assuming an annotation guarantees a specific execution plan.

2. Persistence Context

The persistence context is the EntityManager’s working area: it tracks managed entity objects and their changes. Within one persistence context, one database identity normally maps to one Java object instance. It is not the same thing as the database itself.

Example scenario: A service loads an order, updates its status, and Hibernate tracks the change until flush/commit.

Sample code

Customer a = em.find(Customer.class, 42L);
Customer b = em.find(Customer.class, 42L);
System.out.println(a == b); // normally true in the same persistence context

// If a is managed, Hibernate can notice changes to it
// and synchronize them when the persistence context flushes.
a.setName("Updated name");
Thumb rule: Managed objects are tracked. Detached objects are no longer tracked by that context. `flush()` sends pending SQL; it does not necessarily commit the transaction. `clear()` detaches all managed entities.

3. Entity Lifecycle

Entities move between lifecycle states: transient/new, managed, detached, and removed. The state determines whether Hibernate tracks changes and whether an insert/update/delete may be issued.

Example scenario: A background job loads an entity and closes its transaction; later modifications to the detached object do not persist unless merged or reloaded.

Sample code

Customer c = new Customer("Mina", "mina@example.com"); // transient
em.persist(c);          // managed; insert scheduled
em.flush();             // SQL is synchronized now
em.detach(c);           // detached; changes no longer tracked
em.merge(c);            // copies state into a managed instance
em.remove(em.contains(c) ? c : em.merge(c)); // remove managed instance
Thumb rule: `merge()` returns the managed copy; the object passed to `merge()` does not magically become managed. `persist()` is for new entities. `remove()` expects a managed entity.

4. Repository

A Spring Data JPA repository is a convenient abstraction over common persistence operations. It reduces boilerplate while still generating SQL through the JPA provider.

Example scenario: A service can call `findByEmail` without writing the same EntityManager boilerplate in every method.

Sample code

public interface CustomerRepository extends JpaRepository<Customer, Long> {
    Optional<Customer> findByEmail(String email);
    List<Customer> findByNameContainingIgnoreCase(String fragment);
    boolean existsByEmail(String email);
}

@Service
class CustomerService {
    private final CustomerRepository customers;
    CustomerService(CustomerRepository customers) { this.customers = customers; }

    @Transactional
    public Long register(String name, String email) {
        return customers.save(new Customer(name, email)).getId();
    }
}
Thumb rule: Use repositories for standard CRUD and derived queries. Put transaction boundaries and business rules in the service layer. `save()` may call `persist()` or `merge()` depending on whether Spring Data considers the entity new.

5. EntityManager

EntityManager is the core JPA API for finding, persisting, removing, merging, querying, flushing, and controlling the persistence context. Spring Data repositories generally use it underneath.

Example scenario: Use EntityManager when a repository abstraction is insufficient—for example, building a dynamic query or controlling flush/clear in a batch.

Sample code

@PersistenceContext
private EntityManager em;

@Transactional
public Customer rename(Long id, String newName) {
    Customer customer = em.find(Customer.class, id);
    if (customer == null) throw new NoSuchElementException("Customer not found");
    customer.setName(newName);
    return customer; // dirty checking can issue UPDATE at flush/commit
}
Thumb rule: Use `find()` for primary-key lookup, `persist()` for new managed entities, `remove()` for deletion, `createQuery()` for JPQL, and `flush()` when SQL must be synchronized before continuing. Do not share one EntityManager across threads.

6. JPQL

JPQL queries the entity model, not raw table names. It uses entity class names and Java property names, then Hibernate translates it into SQL for the chosen database.

Example scenario: A portable query can work across PostgreSQL and MySQL because Hibernate adapts the generated SQL.

Sample code

@Query("select c from Customer c where lower(c.email) = lower(:email)")
Optional<Customer> findByEmailIgnoreCase(@Param("email") String email);

// JPQL constructor projection
@Query("select new com.example.CustomerSummary(c.id, c.name) " +
       "from Customer c where c.name like :prefix")
List<CustomerSummary> summaries(@Param("prefix") String prefix);
Thumb rule: Prefer parameters instead of string concatenation to prevent injection and handle escaping. JPQL uses `Customer` and `c.email`, not `customers` and `email` as SQL table/column names.

7. Native Query

A native query is SQL written for the actual database schema. Use it for database-specific features, advanced SQL, or a query that is hard to express in JPQL.

Example scenario: Use a database-specific full-text function when JPQL cannot express the desired operation cleanly.

Sample code

@Query(value = "select * from customers where email = :email", nativeQuery = true)
Optional<Customer> findNativeByEmail(@Param("email") String email);

// For read models, map selected columns to a projection/DTO
@Query(value = "select id, name from customers where name like :prefix%", nativeQuery = true)
List<Object[]> findNamesNative(@Param("prefix") String prefix);
Thumb rule: Native SQL is less database-portable and couples the code to schema details. Always bind values as parameters; never concatenate user input into SQL. Validate pagination, aliases, and result mappings carefully.

8. Relationships — the big picture

Relationships connect entities and map foreign keys or join tables. The owning side is the side that controls the database relationship mapping. In a bidirectional relationship, update both Java sides to keep the in-memory graph consistent.

Example scenario: When attaching an order to a customer, set `order.customer` as well as adding it to `customer.orders`.

Sample code

// In a bidirectional relationship, helper methods keep both sides aligned
public void addOrder(Order order) {
    orders.add(order);
    order.setCustomer(this); // owning side has the @ManyToOne foreign key
}
public void removeOrder(Order order) {
    orders.remove(order);
    order.setCustomer(null);
}
Thumb rule: The Java object graph and database foreign keys are related but not identical. `mappedBy` marks the inverse side. A common bug is updating only the inverse collection while never changing the owning side.

9. One-to-One

Each row is related to at most one row on the other side, such as a user and a profile. A unique foreign key usually enforces the one-to-one rule at the database level.

Example scenario: A profile row stores a unique `user_id`, so two profiles cannot belong to the same user.

Sample code

@Entity
class UserProfile {
    @Id @GeneratedValue
    private Long id;

    @OneToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id", nullable = false, unique = true)
    private User user;
}
Thumb rule: A database `UNIQUE` constraint matters: the Java annotation alone is not a substitute for schema constraints. Lazy one-to-one behavior can be provider/proxy dependent; verify generated SQL for your mapping.

10. One-to-Many

One parent has many children, such as one customer having many orders. In a typical relational schema, the foreign key is stored on the many side, so `@ManyToOne` usually owns the relationship.

Example scenario: Opening a customer detail page may show recent orders rather than loading every historical order.

Sample code

@Entity
class Customer {
    @Id @GeneratedValue private Long id;

    @OneToMany(mappedBy = "customer", cascade = CascadeType.PERSIST)
    private List<Order> orders = new ArrayList<>();

    public void addOrder(Order order) {
        orders.add(order);
        order.setCustomer(this);
    }
}
Thumb rule: Do not assume the parent collection is the owning side. Use helper methods to maintain both sides. Large collections often should not be loaded wholesale; query children by parent id with pagination.

11. Many-to-One

Many child rows refer to one parent row. This is the most common relationship shape and usually corresponds to a foreign-key column in the child table.

Example scenario: Many orders can reference the same customer through `orders.customer_id`.

Sample code

@Entity
class Order {
    @Id @GeneratedValue private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "customer_id", nullable = false)
    private Customer customer;
}
Thumb rule: `@ManyToOne` defaults to eager loading in JPA, so explicitly choosing `LAZY` is often a good performance default. Add a database foreign key and index when appropriate.

12. Many-to-Many

Many records on each side can relate to many on the other side, such as students and courses. A join table stores pairs of foreign keys.

Example scenario: A student can enroll in many courses, and each course can contain many students.

Sample code

@Entity
class Student {
    @Id @GeneratedValue private Long id;

    @ManyToMany
    @JoinTable(name = "student_courses",
      joinColumns = @JoinColumn(name = "student_id"),
      inverseJoinColumns = @JoinColumn(name = "course_id"))
    private Set<Course> courses = new HashSet<>();
}
Thumb rule: Use `Set` when duplicate links are not meaningful. If the relationship has attributes such as enrollment date, grade, or status, model the join table as its own entity (`Enrollment`) instead. Avoid cascade REMOVE across shared entities.

13. Lazy Loading

Lazy loading delays fetching a related entity or collection until code accesses it. This can reduce unnecessary data transfer, but it can also trigger extra queries or fail after the persistence context closes.

Example scenario: A list endpoint returns order summaries and does not fetch every customer’s full order history.

Sample code

@ManyToOne(fetch = FetchType.LAZY)
private Customer customer;

@OneToMany(mappedBy = "customer", fetch = FetchType.LAZY)
private List<Order> orders = new ArrayList<>();
Thumb rule: Lazy means “fetch when accessed,” not “never fetch.” Accessing a lazy association outside an open persistence context can cause `LazyInitializationException`. Design service queries around the data the use case actually needs.

14. Eager Loading

Eager loading asks JPA to fetch a relationship as part of loading the entity. It does not guarantee one SQL statement; a provider may issue secondary queries. Broad eager mappings can cause large result sets and unexpected query volume.

Example scenario: A report that always needs customer names can fetch that relationship explicitly rather than changing every endpoint’s default behavior.

Sample code

@ManyToOne(fetch = FetchType.EAGER) // legal, but use deliberately
private Customer customer;

// Often better: select the association for this specific use case
@EntityGraph(attributePaths = "customer")
List<Order> findByStatus(OrderStatus status);
Thumb rule: Avoid making every association eager as a quick fix for lazy-loading errors. Prefer use-case-specific fetch plans with entity graphs, fetch joins, or projections.

15. Cascade

Cascade propagates selected entity operations from a parent to related entities. Examples include persisting a new order line when saving an order. It is not the same as a database `ON DELETE CASCADE` constraint.

Example scenario: Saving a new order can persist its newly-created line items in the same unit of work.

Sample code

@OneToMany(mappedBy = "order", cascade = {
    CascadeType.PERSIST, CascadeType.MERGE
})
private List<OrderLine> lines = new ArrayList<>();
Thumb rule: Choose cascade types deliberately. `CascadeType.ALL` includes REMOVE and can delete related rows; that is dangerous for shared reference data. Cascade controls JPA operations, while database cascade rules are schema behavior.

16. orphanRemoval

With `orphanRemoval = true`, removing a privately-owned child from its parent relationship schedules deletion of that child. It is useful for value-like children that should not exist independently.

Example scenario: Deleting an item from a draft order removes the corresponding order-line row on flush.

Sample code

@OneToMany(mappedBy = "order", cascade = CascadeType.ALL,
           orphanRemoval = true)
private List<OrderLine> lines = new ArrayList<>();

public void removeLine(OrderLine line) {
    lines.remove(line);
    line.setOrder(null);
}
Thumb rule: Use only when the child lifecycle truly belongs to the parent. Do not use it for shared entities such as users, products, or tags. Removing a child from a collection is not equivalent to merely setting a foreign key to null.

17. Fetch Join

A fetch join loads an association in the same query as the root entity. It is a targeted way to avoid extra queries when the use case needs both parent and child data.

Example scenario: A page of order details loads each order and its customer without one customer query per order.

Sample code

@Query("select distinct o from Order o " +
       "join fetch o.customer " +
       "where o.status = :status")
List<Order> findWithCustomer(@Param("status") OrderStatus status);
Thumb rule: `distinct` can help avoid duplicate root entities when joining collections. Be careful paginating a collection fetch join: row multiplication can make pagination incorrect or force in-memory pagination. Fetch only the associations needed for this query.

18. N+1 Problem

N+1 means one query loads N parent rows, then each parent triggers another query for a relationship. A page of 100 orders may accidentally issue 101 or more queries.

Example scenario: An endpoint slows down as the number of returned orders grows because it runs one query per order’s customer.

Sample code

// Risky pattern if customer is lazily loaded for each order
List<Order> orders = orderRepository.findByStatus(status);
for (Order order : orders) {
    System.out.println(order.getCustomer().getName()); // may issue N queries
}

// Fix with a fetch join, EntityGraph, or DTO projection for this use case.
Thumb rule: Detect using SQL logs, Hibernate statistics, APM traces, and query-count tests. Fix the query plan rather than blindly changing every association to EAGER. Batch fetching may reduce round trips but is not always as efficient as a suitable join/projection.

19. Transaction

A transaction groups operations into a unit that should obey ACID properties. Spring’s `@Transactional` typically starts or joins a transaction around a proxied service method.

Example scenario: A transfer must not commit the debit while failing to credit the destination account.

Sample code

@Service
class TransferService {
    private final AccountRepository accounts;
    TransferService(AccountRepository accounts) { this.accounts = accounts; }

    @Transactional
    public void transfer(long fromId, long toId, BigDecimal amount) {
        Account from = accounts.findById(fromId).orElseThrow();
        Account to = accounts.findById(toId).orElseThrow();
        if (from.getBalance().compareTo(amount) < 0) throw new IllegalStateException("Insufficient funds");
        from.debit(amount);
        to.credit(amount);
    }
}
Thumb rule: Put the transaction around the business operation, not each individual repository call. By default, Spring rolls back on unchecked exceptions and `Error`, not all checked exceptions. Proxy-based transactions may not apply to self-invocation. Keep remote network calls out of long-running database transactions where possible.

20. Optimistic Locking

Optimistic locking detects concurrent updates by checking a version column. It is suitable when conflicts are relatively rare. One transaction succeeds; a stale concurrent update fails instead of silently overwriting newer data.

Example scenario: Two shoppers attempt to buy the last item. The second transaction detects that the version changed.

Sample code

@Entity
class Inventory {
    @Id private Long id;
    private int quantity;
    @Version
    private long version;
}

// If another transaction updates this row first, the stale update
// can fail with an optimistic-lock exception.
Thumb rule: `@Version` protects against lost updates; it does not automatically retry business logic safely. Handle conflicts by refreshing/re-reading and deciding whether to retry or return a conflict response.

21. Pessimistic Locking

Pessimistic locking asks the database to lock selected rows so competing transactions cannot modify them freely until the lock is released. It is useful for high-contention operations where a conflict must be serialized.

Example scenario: When many requests compete for a scarce inventory row, a row lock serializes reservations.

Sample code

@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select i from Inventory i where i.id = :id")
Optional<Inventory> findForUpdate(@Param("id") Long id);

@Transactional
public void reserve(long id) {
    Inventory inventory = repository.findForUpdate(id).orElseThrow();
    inventory.reserveOne();
}
Thumb rule: Locks can cause waiting, deadlocks, and reduced throughput. Keep transactions short, acquire locks in a consistent order, use timeouts where supported, and never assume a lock lasts beyond its transaction.

22. Dirty Checking

Dirty checking is Hibernate’s ability to detect changes to managed entities and generate SQL updates at flush/commit. You generally do not need to call `save()` for an already-managed entity inside a transaction.

Example scenario: A service loads a customer and changes one field; Hibernate writes the update automatically.

Sample code

@Transactional
public void changeEmail(long id, String email) {
    Customer customer = repository.findById(id).orElseThrow();
    customer.setEmail(email);
    // No explicit save() required for a managed entity.
    // Hibernate detects the change and issues UPDATE at flush/commit.
}
Thumb rule: Changes to detached objects are not tracked. Avoid modifying large numbers of managed entities without periodic flush/clear in batch jobs, or the persistence context can consume substantial memory.

23. First-Level Cache

The first-level cache is the persistence context itself. It is enabled by design and scoped to an EntityManager/session. Repeated lookups for the same id in the same context can reuse the managed object.

Example scenario: Within one transaction, reading the same customer twice often avoids a second database round trip.

Sample code

Customer first = em.find(Customer.class, 7L);  // database query if not already managed
Customer again = em.find(Customer.class, 7L);  // usually no second select in same context
Thumb rule: It is not a shared application-wide cache. Different transactions/persistence contexts may load different object instances and may observe different committed states. `clear()` evicts managed entities from the context.

24. Second-Level Cache

The second-level cache is an optional provider-level cache shared across persistence contexts, often across sessions in one application instance. It can reduce database reads for suitable entities or collections.

Example scenario: Country codes change rarely, so a configured second-level cache can reduce repeated reads.

Sample code

@Entity
@Cacheable
@org.hibernate.annotations.Cache(
    usage = org.hibernate.annotations.CacheConcurrencyStrategy.READ_WRITE)
class Country {
    @Id private String code;
    private String name;
}
Thumb rule: Enable and configure a cache provider explicitly; annotations alone do not guarantee it is active. Cache consistency, invalidation, multi-node behavior, and memory usage matter. Good candidates are mostly-read, slowly-changing reference data; avoid caching volatile data without a clear policy.

25. Specifications

Spring Data JPA Specifications let you build reusable, composable predicates for dynamic searches. They are useful when filters are optional and the number of combinations would make many repository methods impractical.

Example scenario: An admin search screen can combine optional name, email, and creation-date filters without dozens of methods.

Sample code

public static Specification<Customer> nameContains(String text) {
    return (root, query, cb) -> text == null ? null :
        cb.like(cb.lower(root.get("name")), "%" + text.toLowerCase() + "%");
}

public static Specification<Customer> emailIs(String email) {
    return (root, query, cb) -> email == null ? null : cb.equal(root.get("email"), email);
}

// Repository extends JpaSpecificationExecutor<Customer>
// repository.findAll(nameContains(name).and(emailIs(email)), pageable);
Thumb rule: Enable Spring Data JPA Specifications support through `JpaSpecificationExecutor`. Escape `%` and `_` if user input should be literal, validate sort fields, and watch query plans for unindexed filters.

26. Projections

A projection returns only the fields a use case needs rather than hydrating every entity and relationship. It can reduce data transfer, memory use, and accidental lazy-loading queries.

Example scenario: A customer list endpoint needs only id and name, not addresses, orders, and other associations.

Sample code

public interface CustomerNameView {
    Long getId();
    String getName();
}

public interface CustomerRepository extends JpaRepository<Customer, Long> {
    List<CustomerNameView> findByNameContainingIgnoreCase(String name);
}

public record CustomerSummary(Long id, String name) {}

@Query("select new com.example.CustomerSummary(c.id, c.name) from Customer c")
List<CustomerSummary> summaries();
Thumb rule: Use interface projections for simple field views and DTO/record projections for explicit read models. A projection is not automatically faster in every case—verify generated SQL, joins, and query plans. Avoid returning entities directly from public API controllers.

  1. Spring starts or joins the transaction around the service method.
  2. Repository/EntityManager loads entities; managed instances are tracked by the persistence context.
  3. Business logic changes managed state; dirty checking detects differences.
  4. At flush, Hibernate sends INSERT/UPDATE/DELETE SQL. Flush can occur before commit, including before certain queries.
  5. The database commits if the transaction completes successfully; otherwise rollback rules determine what is reverted.
Remember: `save()` is not the same as commit; `flush()` is not the same as commit; and changing a detached Java object does not automatically update the database.

Interview questions and answers

1. What is the difference between JPA and Hibernate?

JPA is the standard API/specification for ORM in Java. Hibernate is an implementation of that specification and adds provider-specific features. Spring Data JPA is a higher-level repository abstraction that commonly uses Hibernate underneath.

2. What is the persistence context?

It is the unit-of-work/identity-map scope that tracks managed entities, ensures one managed instance per database identity in that context, and enables dirty checking. It is usually associated with an EntityManager.

3. persist() versus merge()?

`persist()` makes a new entity managed. `merge()` copies state from the supplied object into a managed instance and returns that managed instance; the original object may remain detached.

4. What is dirty checking?

Hibernate compares managed entity state with its tracked snapshot and emits updates during flush when changes are detected. It usually removes the need to call save() again for an already-managed entity.

5. What is the N+1 problem and how do you fix it?

One query fetches N roots and then one additional query is triggered per root for an association. Diagnose query count and SQL, then use a fetch join, entity graph, DTO projection, or batch fetching as appropriate.

6. Lazy versus eager loading?

Lazy loading defers association retrieval until access; eager loading asks the provider to fetch it as part of loading the entity, but does not guarantee one SQL query. Prefer use-case-specific fetch plans over globally eager mappings.

7. Cascade versus orphanRemoval?

Cascade propagates entity operations such as persist/remove. `orphanRemoval` deletes a privately-owned child when it is removed from the parent relationship. They solve different lifecycle problems and must be chosen carefully.

8. Optimistic versus pessimistic locking?

Optimistic locking detects conflicting writes using a version field and is effective when conflicts are uncommon. Pessimistic locking acquires database locks to serialize access, but can increase waiting, deadlocks, and reduce throughput.

9. First-level versus second-level cache?

First-level cache is the persistence context and is always present for a given EntityManager. Second-level cache is optional, provider-managed, and shared across persistence contexts within the configured cache scope.

10. Why use projections?

They select only fields needed for a read use case, reducing entity hydration and unnecessary relationship loading. Verify generated SQL and use DTOs to avoid exposing persistence entities directly from APIs.

11. JPQL versus native SQL?

JPQL queries entities and Java properties and is generally more portable. Native SQL targets physical tables/columns and database-specific features but couples code more closely to schema and database dialect.

12. What should a strong answer include?

Definition, execution mechanism, code example, generated SQL/transaction effect, common failure mode, and trade-off. For performance topics, mention how you would observe and verify behavior rather than relying on annotations alone.
