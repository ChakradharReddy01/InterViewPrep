Module 4: Spring Boot Architecture, Production REST APIs & Enterprise Patterns

Spring Boot 3.x Enterprise REST Production Hardening ⏱️ 60 min deep dive Target Roles: SDE-2, SDE-3, Backend Tech Lead, Cloud Architect

1. Spring Boot Philosophy, Starters & Auto-Configuration

1.1 The Core Philosophy

Spring Boot was created to solve the massive XML configuration overhead, dependency version mismatches, and deployment friction of traditional Spring applications. It operates on Opinionated Defaults and Convention over Configuration:

  • Standalone Executable Fat JARs: Packages application bytecode, third-party libraries, and an embedded servlet container into a single deployable artifact executed via java -jar app.jar.
  • Starter POMs: Curated dependency bundles that aggregate cohesive libraries and provide compatible, pre-tested transitive versions managed by spring-boot-dependencies.

1.2 How Auto-Configuration Works Under the Hood

When you add a starter like spring-boot-starter-web, Spring Boot automatically configures Tomcat, DispatcherServlet, Jackson ObjectMapper, and validation validators.

  1. AutoConfiguration Discovery:
    • In Spring Boot 2.x: Loaded from META-INF/spring.factories.
    • In Spring Boot 3.x+: Loaded from META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports.
  2. Conditional Evaluation (@Conditional family): Auto-configuration classes evaluate conditions before loading beans:
    • @ConditionalOnClass(ObjectMapper.class): Loads only if Jackson is on the classpath.
    • @ConditionalOnMissingBean(DataSource.class): Provides a default DataSource only if the developer has not declared their own custom DataSource bean.
    • @ConditionalOnProperty(name = "feature.enabled", havingValue = "true"): Evaluates configuration flags.

1.3 Anatomy of @SpringBootApplication

@SpringBootApplication is a composite meta-annotation that bundles:

  • @SpringBootConfiguration: Specialization of @Configuration marking the class as a configuration source.
  • @EnableAutoConfiguration: Triggers the auto-configuration imports mechanism.
  • @ComponentScan: Automatically scans for @Component, @Service, @Repository, and @RestController within the current package and its sub-packages.

2.2 Type-Safe @ConfigurationProperties with Record Validation

Avoid scattering individual @Value("${prop}") annotations throughout business logic. Modern Spring Boot binds configuration trees directly into validated, immutable Records:

@Validated
public record PaymentGatewayProperties(

    int timeoutMs,

    @NotNull
    Duration retryInterval,

    List<String> supportedCurrencies
) {}

3. Embedded Servers, Production Actuator & Structured Logging

3.1 Embedded Server Tuning

Spring Boot defaults to Apache Tomcat, but can be switched to Undertow or Jetty. In high-concurrency microservices, configure connection queues and thread limits: 

server:
  tomcat:
    threads:
      max: 200           # Worker thread ceiling
      min-spare: 20      # Pre-warmed idle threads
    max-connections: 8192 # Max simultaneous TCP sockets
    accept-count: 100    # OS TCP listen queue length when all worker threads are busy
    connection-timeout: 20000

3.2 Spring Boot Actuator: Security & Endpoints

Actuator provides production monitoring endpoints (/health, /metrics, /beans, /env, /threaddump).

⚠️ Actuator Production Security Rule

Never expose sensitive endpoints publicly (include: "*")! Exposing /actuator/env or /actuator/heapdump can leak database passwords and security tokens. Only expose health and metrics publicly, and secure other endpoints behind OAuth2/admin role checks. 

management:
  endpoints:
    web:
      exposure:
        include: health, metrics, prometheus
  endpoint:
    health:
      show-details: when_authorized
      probes:
        enabled: true # Enables Kubernetes readiness & liveness probes!

3.3 Structured JSON Logging with MDC (Mapped Diagnostic Context)

In distributed microservices, tracing requests across systems requires correlating logs via a unique Trace ID injected into SLF4J's Mapped Diagnostic Context (MDC):

Trace ID Logging Filter using MDC Java 
@Component
public class CorrelationIdFilter extends OncePerRequestFilter {
    public static final String TRACE_ID = "traceId";

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain chain)
            throws ServletException, IOException {
        String traceId = request.getHeader("X-Correlation-Id");
        if (traceId == null || traceId.isBlank()) {
            traceId = UUID.randomUUID().toString();
        }
        MDC.put(TRACE_ID, traceId);
        response.setHeader("X-Correlation-Id", traceId);
        try {
            chain.doFilter(request, response);
        } finally {
            MDC.remove(TRACE_ID); // Prevent thread pool context pollution!
        }
    }
}

5. Global Exception Handling & RFC 7807 ProblemDetail

Spring Boot 3 implements the RFC 7807 Problem Details for HTTP APIs specification using ProblemDetail:

Enterprise GlobalExceptionHandler with RFC 7807 Java 
@RestControllerAdvice
public class GlobalExceptionHandler {

    // 1. Handle Bean Validation Failures (HTTP 400)
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ProblemDetail handleValidationException(MethodArgumentNotValidException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
            HttpStatus.BAD_REQUEST, "Validation failed for one or more fields"
        );
        problem.setTitle("Constraint Violation");
        
        Map<String, String> errors = new HashMap<>();
        ex.getBindingResult().getFieldErrors().forEach(error -> 
            errors.put(error.getField(), error.getDefaultMessage())
        );
        problem.setProperty("invalidFields", errors);
        problem.setProperty("timestamp", Instant.now());
        return problem;
    }

    // 2. Handle Custom Domain Exceptions (HTTP 404)
    @ExceptionHandler(ResourceNotFoundException.class)
    public ProblemDetail handleResourceNotFound(ResourceNotFoundException ex) {
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        problem.setTitle("Resource Not Found");
        problem.setProperty("timestamp", Instant.now());
        return problem;
    }

    // 3. Catch-all Internal Server Errors (HTTP 500)
    @ExceptionHandler(Exception.class)
    public ProblemDetail handleGenericException(Exception ex) {
        logger.error("Unhandled system error observed: ", ex);
        ProblemDetail problem = ProblemDetail.forStatusAndDetail(
            HttpStatus.INTERNAL_SERVER_ERROR, "An internal error occurred. Please quote incident reference."
        );
        problem.setTitle("Internal Server Error");
        problem.setProperty("traceId", MDC.get("traceId"));
        return problem;
    }
}

6. High-Performance Pagination, Sorting & Filtering

6.1 Page<T> vs. Slice<T>

A major performance pitfall in Spring Data JPA:

  • Page<T>: Computes total pages and total elements. To do this, Hibernate issues two queries: the data query (SELECT ... LIMIT 20) PLUS an expensive SELECT count(*) FROM orders. On tables with 10 million rows, count(*) triggers full index/table scans!
  • Slice<T> (Preferred for Infinite Scroll / Mobile): Only checks if a next slice exists by querying LIMIT 21 for a page size of 20. Zero count(*) queries! Saves massive database CPU.
Controller Pagination & Dynamic Sorting Java 
@GetMapping
public ResponseEntity<Slice<OrderResponse>> getOrders(
    @RequestParam(defaultValue = "0") int page,
    @RequestParam(defaultValue = "20") int size,
    @RequestParam(defaultValue = "createdAt,desc") String[] sort
) {
    Sort.Direction direction = sort[1].equalsIgnoreCase("asc") ? Sort.Direction.ASC : Sort.Direction.DESC;
    Pageable pageable = PageRequest.of(page, size, Sort.by(direction, sort[0]));
    
    Slice<OrderResponse> orders = orderService.fetchOrderSlice(pageable);
    return ResponseEntity.ok(orders);
}

7. API Versioning & Distributed Idempotency

7.1 API Versioning Strategies

  • URI Path Versioning (Most Popular): /api/v1/orders vs /api/v2/orders. Simple, clean caching, self-documenting.
  • HTTP Header Versioning: X-API-VERSION: 2. Keeps URIs clean.
  • Accept Header (Content Negotiation): Accept: application/vnd.company.v2+json. Adheres to strict REST HATEOAS standards.

7.2 Distributed Idempotency Pattern (Redis SET NX)

In distributed microservices, network timeouts cause clients to retry POST requests, which can trigger duplicate order creation and double-billing. An Idempotency Key guarantees safe retries:

Idempotent Order Creation via Redis SETNX Java 
@PostMapping
public ResponseEntity<OrderResponse> createOrder(
    @RequestHeader("X-Idempotency-Key") String idempotencyKey,
    @Valid @RequestBody CreateOrderRequest request
) {
    // 1. Atomic Redis SET key value NX EX 3600 (Set if Not Exists with 1-hour TTL)
    Boolean isFirstCall = redisTemplate.opsForValue().setIfAbsent(
        "idempotency:" + idempotencyKey, "PROCESSING", Duration.ofHours(1)
    );

    if (Boolean.FALSE.equals(isFirstCall)) {
        // Duplicate request detected! Either return cached response or HTTP 409 Conflict
        throw new DuplicateRequestException("Transaction with idempotency key is already processing");
    }

    try {
        OrderResponse response = orderService.processOrder(request);
        // Cache serialized response for identical subsequent calls:
        redisTemplate.opsForValue().set("idempotency:response:" + idempotencyKey, response, Duration.ofHours(1));
        return ResponseEntity.status(HttpStatus.CREATED).body(response);
    } catch (Exception ex) {
        redisTemplate.delete("idempotency:" + idempotencyKey); // Clear lock on failure
        throw ex;
    }
}

8. Custom Health Checks & Kubernetes Probes

In cloud-native Kubernetes environments, Actuator separates health into two separate operational probes:

  • Liveness Probe (/actuator/health/liveness): Tells K8s if the JVM is alive. If this fails (e.g. fatal deadlock), Kubernetes kills and restarts the container.
  • Readiness Probe (/actuator/health/readiness): Tells K8s if the application is ready to accept HTTP traffic. If this fails (e.g. database connection pool warming up), Kubernetes stops routing traffic to the pod without killing it.
Custom HealthIndicator for External Payment Gateway Java 
@Component
public class PaymentGatewayHealthIndicator implements HealthIndicator {
    private final PaymentClient paymentClient;

    public PaymentGatewayHealthIndicator(PaymentClient paymentClient) {
        this.paymentClient = paymentClient;
    }

    @Override
    public Health health() {
        try {
            boolean isUp = paymentClient.ping();
            if (isUp) {
                return Health.up().withDetail("gateway", "Operational").build();
            }
            return Health.down().withDetail("gateway", "Latency Degraded").build();
        } catch (Exception ex) {
            return Health.down(ex).withDetail("gateway", "Unreachable").build();
        }
    }
}

9. Real-Time Production Issues & Post-Mortems

🚨 Incident 1: Sensitive Database Credentials Leaked via Actuator /env Endpoint

Scenario: A security audit revealed that an e-commerce microservice exposed production PostgreSQL credentials, AWS access keys, and JWT signing secrets over the public internet at https://api.company.com/actuator/env.

🔍 Root Cause Analysis (RCA)

The application configured management.endpoints.web.exposure.include=* in application.yml for debugging purposes and forgot to restrict exposure in production. Spring Boot Actuator's default behavior exposed all configuration properties and system environment variables.

💡 Production Resolution
  • Configured minimal public exposure: management.endpoints.web.exposure.include=health,info,prometheus.
  • Enabled property masking for sensitive patterns: management.endpoint.env.keys-to-sanitize=password,secret,key,token.
  • Routed Actuator to an internal management port not exposed to external ingresses: management.server.port=8081.
🚨 Incident 2: Database CPU Spikes to 100% via Page count(*) Queries

Scenario: As an orders table grew to 15 million records, the admin dashboard's order search endpoint p99 latency spiked from 40ms to 8,500ms, driving PostgreSQL CPU to 100%.

🔍 Root Cause Analysis (RCA)

The query method returned a Page<Order>: Page<Order> findByStatus(OrderStatus status, Pageable pageable);. Every request generated two queries: SELECT ... LIMIT 20 (took 5ms) AND SELECT count(*) FROM orders WHERE status = 'COMPLETED'. The count(*) scanned 12 million index rows, locking database memory pages.

💡 Production Resolution

Switched the return type to Slice<Order>, which eliminates the count(*) query completely, reducing latency from 8,500ms back to 6ms!

10. Senior / Staff Technical Interview Q&A

🎯 Q1: What is the exact difference between @Controller and @RestController?

Answer: @Controller is the traditional Spring MVC annotation designed for returning HTML views (JSP, Thymeleaf). To return JSON from a @Controller method, you must explicitly annotate the method with @ResponseBody. @RestController is a convenience composite annotation combining @Controller and @ResponseBody at the class level; every method automatically serializes return values directly into the HTTP response body via configured HttpMessageConverter instances (such as Jackson).

🎯 Q2: How does Spring Boot resolve properties when defined in multiple sources?

Answer: Spring Boot uses a strict, deterministic property precedence order (highest to lowest):
1. Command Line Arguments (--server.port=9090)
2. JVM System Properties (-Dserver.port=9090)
3. OS Environment Variables (SERVER_PORT=9090)
4. Profile-specific configuration files outside packaged JAR (file:./config/application-prod.yml)
5. Profile-specific configuration files inside JAR (classpath:application-prod.yml)
6. Default application.yml inside packaged JAR.

🎯 Q3: Why is Keyset / Cursor Pagination superior to Offset Pagination for large datasets?

Answer: Offset pagination (OFFSET 1000000 LIMIT 20) forces the database engine to scan and discard 1,000,000 index rows before returning 20 rows, degrading at $O(N)$ time. Keyset pagination (Cursor pagination) uses an indexed predicate: WHERE id < last_seen_id ORDER BY id DESC LIMIT 20. The database performs an immediate $O(\log N)$ B-tree index seek to jump directly to the target record, maintaining constant-time sub-millisecond query performance regardless of how deep the user paginates.
