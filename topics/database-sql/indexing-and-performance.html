Module 7 (Part 4): Database Performance & Tuning

Understand how indexes work, choose composite and covering indexes, read execution plans, optimize SQL, size connection pools, and diagnose database deadlocks. Built around practical SQL, Spring Boot examples, and production root-cause analysis.

Suggested time: 60 minutes · Target: Java backend, database, and systems interviews

0. Learning Roadmap

  • Indexes reduce work, but every index costs storage and write overhead.
  • Execution plans reveal what the optimizer intends to do—and what actually happened when runtime analysis is enabled.
  • Optimization starts with evidence: latency, rows scanned, estimates, buffers, locks, and pool metrics.
  • Connection pools are a concurrency limit, not a magic throughput multiplier.
  • Deadlocks require both database-level retry handling and application-level prevention.
Performance rule: measure first, change one thing, and compare the same workload before and after.

1. Database Indexes

1.1 What is an index?

An index is an auxiliary data structure that helps the database locate rows without scanning the entire table. Without a suitable index, a lookup may require a sequential scan of many or all table pages. With a suitable B-tree index, the engine can often navigate to a small matching range efficiently.

-- Example table
CREATE TABLE customers (
  customer_id BIGINT PRIMARY KEY,
  email        VARCHAR(320) NOT NULL,
  country      VARCHAR(2),
  created_at   TIMESTAMP NOT NULL
);

-- Useful for exact email lookups (assuming the query and collation align)
CREATE INDEX idx_customers_email ON customers(email);

SELECT customer_id, email
FROM customers
WHERE email = 'alice@example.com';

An index is not guaranteed to be used. The optimizer may choose a table scan if many rows match, the table is small, statistics suggest the scan is cheaper, or the query expression cannot use the index.

1.2 Index benefits and costs

Benefits

  • Faster selective lookups
  • Efficient range scans and ordered retrieval
  • Can support joins, uniqueness, and covering access

Costs

  • Extra disk and memory use
  • Slower inserts, updates, and deletes
  • Maintenance, page splits, and write amplification
  • More choices for the optimizer to evaluate
Don't index every column. Index columns used by real, important predicates, joins, ordering, or uniqueness requirements. Confirm the index helps representative queries and does not impose unacceptable write costs.

1.3 Clustered and secondary indexes

In systems such as InnoDB, the primary-key clustered index leaf pages contain the row data, and secondary index entries include the primary key. Other databases organize heap and index storage differently. Avoid assuming that every RDBMS has exactly the same clustered-index model or exactly one physically clustered index.

2. B-Tree and B+ Tree Internals

Database indexes commonly use balanced multi-way search trees. B-tree-family structures keep the tree shallow by storing many keys per page, which matches page-oriented storage much better than a binary tree with only two children per node.

                 [ 40 | 80 ]          Root / internal page
                /    |     \\
          [10 | 25] [50 | 65] [90 | 110]  Internal pages
             |         |          |
       [10,15,20] <-> [40,50,60] <-> [80,90,100]  Leaf level
                         ordered leaf traversal

2.1 Why a B+ tree works well

  • High fan-out: many keys fit in each index page, keeping height low.
  • Balanced height: search, insert, and delete remain efficient as the index grows.
  • Leaf-level ordering: range scans can move through adjacent leaf pages instead of restarting at the root for every key.
  • Page-oriented design: minimizes page accesses compared with pointer-heavy binary trees in many database workloads.

Conceptually, point lookup is often described as \(O(\\log N)\), but real performance depends on page cache hits, row lookups, selectivity, I/O, and concurrency. A cached tree traversal is not the same cost as random physical disk I/O.

2.2 Point lookup vs range lookup

-- Point lookup
SELECT * FROM customers WHERE customer_id = 42;

-- Range lookup; ordered index may help
SELECT customer_id, created_at
FROM customers
WHERE created_at >= '2026-01-01'
  AND created_at <  '2026-02-01'
ORDER BY created_at;

3. Composite Index

A composite index contains more than one key column. Column order matters because the index is ordered lexicographically: first by the leading column, then by the next column within equal leading values, and so on.

CREATE INDEX idx_customers_location
ON customers(country, state, city);

-- Leading column: generally a good match
SELECT * FROM customers WHERE country = 'US';

-- Leading prefix: generally a good match
SELECT * FROM customers
WHERE country = 'US' AND state = 'CA';

-- Missing the leading column: usually cannot seek directly by this index
SELECT * FROM customers WHERE state = 'CA';

3.1 Leftmost-prefix intuition

PredicateLikely index utility for (country, state, city)
country = ?Strong match for leading key
country = ? AND state = ?Strong match for leading two keys
country = ? AND state = ? AND city = ?Matches all three keys
state = ?Usually cannot directly seek by state alone
country = ? AND city = ?Can use country prefix; city filtering may happen afterward

3.2 Equality, range, and ordering

For a query such as WHERE customer_id = ? AND status = ? ORDER BY created_at DESC, an index like (customer_id, status, created_at) may help filter and return rows in order. Equality columns often precede a range/order column, but the best order depends on selectivity, query patterns, sort direction support, and other queries sharing the index.

Design from real queries. The leftmost-prefix rule is a useful guide, not a promise that every predicate combination will be optimal. Check the actual execution plan and engine documentation.

4. Covering Index

A covering index contains all columns a specific query needs for filtering, joining, ordering, and output. The engine may then answer the query from the index without fetching the base table row. Some engines call this an index-only scan; visibility rules can still require additional checks.

-- PostgreSQL example: key columns plus included payload columns
CREATE INDEX idx_orders_customer_status
ON orders(customer_id, status)
INCLUDE (order_date, total_amount);

SELECT order_date, total_amount
FROM orders
WHERE customer_id = 1042
  AND status = 'COMPLETED';

Why it can help: fewer base-table lookups and less random I/O. Trade-off: wider indexes consume more space and increase write and cache costs. Don't include large text/blob fields indiscriminately.

Covering vs clustered index

ConceptWhat it means
Clustered indexDescribes the table's primary storage organization in engines that support this concept.
Covering indexAn index that contains everything required by one particular query; it may be a secondary index.

5. Query Plan and EXPLAIN

The query optimizer considers candidate access paths and chooses a plan based on statistics, estimated cardinalities, costs, and engine rules. An execution plan is a tree of operations such as scans, joins, sorts, and aggregates.

5.1 EXPLAIN vs EXPLAIN ANALYZE

  • EXPLAIN generally shows the estimated plan without executing the query.
  • EXPLAIN ANALYZE executes the statement and reports actual runtime measurements in engines that support it.
  • Options such as buffers, verbose output, and JSON output vary by database.
-- PostgreSQL syntax
EXPLAIN (ANALYZE, BUFFERS)
SELECT customer_id, SUM(total_amount)
FROM orders
WHERE order_date >= DATE '2026-01-01'
GROUP BY customer_id;
Caution: EXPLAIN ANALYZE runs the query. For UPDATE/DELETE or other statements with side effects, use a safe test environment or a deliberate transaction/rollback strategy; not every side effect can be undone by rollback.

5.2 What to inspect

Plan signalWhat it tells youNext question
Estimated rows vs actual rowsCardinality estimate qualityAre statistics stale or data distributions skewed?
Sequential/table scanReads many table pagesIs the table small, or does the query return a large fraction of rows?
Index scan + many row fetchesIndex found matches, but table lookups may be expensiveCould a covering index help? Is selectivity poor?
Sort / temporary spillOrdering or grouping may need extra workCould index ordering help? Is memory pressure involved?
Nested-loop join with huge inner loopsRepeated lookups may dominateAre join keys indexed and estimates accurate?

5.3 Estimated cost is not milliseconds

Optimizer cost units are usually internal relative estimates, not wall-clock milliseconds. Compare estimated and actual rows, loops, elapsed time, buffers, and the plan shape. A row-estimate mismatch by an order of magnitude is a useful clue, not a universal threshold proving stale statistics.

6. Query Optimization

6.1 SARGable predicates

A SARGable predicate allows the optimizer to use an index search argument effectively. Wrapping an indexed column in a function can prevent use of a normal index unless a matching expression/function-based index exists.

Potentially less index-friendlyAlternative to evaluate
WHERE YEAR(created_at) = 2026WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'
WHERE LOWER(email) = 'alice@example.com'Normalize stored values or create a matching functional index, depending on collation and requirements.
WHERE amount * 1.18 > 100Consider algebraically rewriting as amount > 100 / 1.18 if semantics and numeric precision remain correct.
LIKE '%smith'A leading wildcard often prevents ordinary B-tree prefix access; consider full-text/trigram or engine-specific indexing if needed.

6.2 Avoid SELECT *

Select only columns needed by the caller. This can reduce transferred data, memory, serialization, and table lookups, and may make a covering index possible. It is not automatically faster in every case, but it makes query intent explicit.

6.3 Deep pagination: OFFSET vs keyset

-- Deep OFFSET may scan/discard many rows
SELECT id, created_at FROM orders
ORDER BY id LIMIT 20 OFFSET 1000000;

-- Keyset pagination: requires stable ordered key and suitable index
SELECT id, created_at FROM orders
WHERE id > :last_seen_id
ORDER BY id
LIMIT 20;

Keyset pagination is often more efficient for deep pages and avoids some shifting-page problems. For a non-unique sort, use a deterministic tie-breaker such as (created_at, id) and encode both values in the cursor.

6.4 Practical optimization workflow

  1. Measure endpoint latency and database time; identify the expensive query.
  2. Capture representative parameters and run the plan safely.
  3. Compare estimated and actual rows, loops, I/O, sorting, and lock waits.
  4. Check predicates, join order, indexes, selected columns, and pagination.
  5. Change one thing at a time and retest with representative data and concurrency.
  6. Monitor after deployment; keep a rollback plan.

7. Database Connection Pool

Establishing a database connection can involve networking, authentication, TLS, and server-side session setup. A connection pool keeps a bounded set of reusable connections so requests borrow and return them rather than opening a new connection every time.

7.1 Pool lifecycle

HTTP request
    |
    v
Borrow connection from pool -- none available? wait up to timeout
    |
    v
Execute SQL / transaction
    |
    v
Commit or rollback; return connection
    |
    v
Pool can reuse it for another request

7.2 HikariCP configuration example

# Spring Boot application.yml — example values only
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      minimum-idle: 5
      connection-timeout: 30000
      idle-timeout: 600000
      max-lifetime: 1800000

These values are not universal recommendations. Align them with database capacity, application instance count, query duration, and infrastructure timeouts. If there are 8 app replicas and each can open 20 connections, the database may see up to about 160 connections from that service alone, plus other clients.

7.3 Pool sizing and the “more is better” trap

Too small a pool can cause requests to wait for connections; too large a pool can overload the database with concurrent work, increase contention, and waste resources. Start with a measured workload and database limits. A frequently cited rough sizing heuristic is (core_count × 2) + effective_spindle_count, but it is only a starting hypothesis—not a universal formula, especially for SSDs, cloud databases, and mixed workloads.

7.4 Metrics to monitor

  • Active, idle, and total connections
  • Connection acquisition wait and timeout count
  • Connection usage/transaction duration
  • Slow queries and lock waits
  • Database CPU, I/O, and active sessions
Pool exhaustion has multiple causes: a pool may be undersized, but slow queries, long transactions, connection leaks, or a database slowdown can all make connections stay borrowed too long. Increasing pool size without diagnosing the cause may worsen the incident.

7.5 Leak detection is a diagnostic aid

HikariCP leak detection can log a warning when a connection is held longer than a configured threshold. A warning does not prove a connection was permanently leaked; a legitimately long operation may trigger it. Use the stack trace to investigate and pair it with usage metrics.

8. Database Deadlocks

A deadlock occurs when transactions form a circular wait: each holds a lock another transaction needs. Many database engines detect the cycle, abort one transaction, and return an error to the application.

8.1 A two-row example

Transaction A                 Transaction B
-------------                 -------------
locks Account 1               locks Account 2
requests Account 2            requests Account 1
waits for B                   waits for A

A waits for B; B waits for A => circular wait / deadlock

8.2 Prevention: deterministic lock ordering

// Conceptual Java example: always lock IDs in ascending order
long first = Math.min(fromAccountId, toAccountId);
long second = Math.max(fromAccountId, toAccountId);

accountRepository.lockById(first);
accountRepository.lockById(second);

// Perform validated debit/credit in the same transaction.

Every code path that can lock the same resources should follow the same ordering convention. Consistent ordering reduces circular waits but does not eliminate every possible deadlock involving other tables, indexes, or implicit locks.

8.3 Diagnosis and recovery

  • Inspect database deadlock logs/reports and identify the exact statements and lock order.
  • Check indexes and query plans; broad scans can lock or touch more resources than expected.
  • Keep transactions short and avoid slow external API calls while holding locks.
  • Acquire shared resources in deterministic order.
  • Retry recognized deadlock/serialization failures with bounded retries and backoff.
Common examples (vendor-specific):
PostgreSQL deadlock_detected SQLSTATE: 40P01
MySQL InnoDB deadlock error number: 1213

Retry the complete transaction, not just the last SQL statement.
Ensure retrying cannot duplicate emails, payments, or other external side effects.
Important: a database can roll back the victim transaction, but it cannot automatically undo an external payment, email, or HTTP request your code already performed. Use an outbox/idempotency strategy when external side effects must align with committed state.

9. Production RCA Scenarios

Incident A: Login API suddenly becomes slow

Symptom: database CPU spikes after a code change to case-insensitive email lookup.

Root cause hypothesis: LOWER(email) no longer matches the normal index on email, so many requests scan the table.

Verify: inspect the query plan and rows read. Fix: normalize data/collation appropriately or create an expression index such as CREATE INDEX ... ON users (LOWER(email)) where supported; validate with the plan and workload.

Incident B: Checkout times out during reporting

Symptom: checkout requests fail to acquire a pool connection while long reports run.

Root cause hypothesis: reports borrow connections for a long time and starve latency-sensitive transactions.

Verify: active/idle pool metrics, acquisition wait, query duration, and transaction boundaries. Fix: optimize the report, limit concurrency, schedule it, or isolate reporting workload on a read replica/dedicated pool if the architecture and consistency needs allow.

Incident C: Transfer service sees intermittent deadlocks

Symptom: occasional deadlock exceptions during simultaneous transfers.

Root cause hypothesis: opposite-direction transfers lock accounts in opposite order.

Verify: deadlock report and statements involved. Fix: lock both accounts in deterministic order, keep the transaction short, and add bounded retry handling.

10. Interview Q&A

Q1. Why do databases use B+ trees?

They keep many keys per page and the tree shallow, making point lookups and range scans efficient for page-based storage.

Q2. What is the leftmost-prefix rule?

A composite index ordered by (A, B, C) generally supports searches beginning with A, then A+B, then A+B+C. It usually cannot directly seek efficiently by B alone because the index is primarily ordered by A.

Q3. What is a covering index?

An index containing all data needed by a particular query, potentially allowing an index-only access path and avoiding base-row fetches.

Q4. What is the difference between EXPLAIN and EXPLAIN ANALYZE?

EXPLAIN generally reports the estimated plan; EXPLAIN ANALYZE executes the query and adds actual runtime measurements in supporting engines.

Q5. Why might an index not be used?

The query may return many rows, the table may be small, statistics may mislead the optimizer, a function/cast/collation may prevent a matching index path, or the optimizer may estimate a scan is cheaper.

Q6. What is SARGability?

It describes predicates that can be used effectively as index search arguments. A function on an indexed column can interfere unless a matching functional index or equivalent strategy exists.

Q7. Why can increasing pool size reduce throughput?

More connections increase concurrent work against a finite database capacity and can worsen CPU, I/O, memory, and lock contention. Measure pool waits and database saturation before resizing.

Q8. What causes connection pool exhaustion?

Long queries, long transactions, leaked/unreturned connections, a pool that is too small, or database saturation. Diagnose acquisition wait and connection usage before changing the maximum size.

Q9. How do you prevent a transfer deadlock?

Lock account rows in a consistent global order, keep transactions short, inspect deadlock reports, and retry the complete transaction for recognized transient failures.

Q10. Should every slow query get another index?

No. Read the plan first. The cause may be poor selectivity, inaccurate estimates, excessive result size, an inefficient join, a sort, locks, or application-level connection contention. Each index also has write and storage costs.
