    Joins, Keys & Normalization: 1NF to BCNF

    A practical guide to relational joins, integrity constraints, functional dependencies, normalization, and denormalization—with SQL examples, common production failures, and interview-ready explanations.

    1. Relational joins: the core idea

    A join combines rows from two tables according to a join condition. Imagine customers is the left table and orders is the right table. The type of join determines whether non-matching rows are discarded or preserved.

    customers
+-------------+---------------+
| customer_id | customer_name |
+-------------+---------------+
| 1           | Alice         |
| 2           | Bob           |
| 3           | Charlie       |
+-------------+---------------+

orders
+----------+-------------+--------+
| order_id | customer_id | amount |
+----------+-------------+--------+
| 101      | 1           | 250    |
| 102      | 1           | 100    |
| 103      | 2           | 450    |
| 104      | NULL        | 75     |
+----------+-------------+--------+

    A customer may have many orders; an order may have no matching customer in this sample. The relationship and constraints matter more than the table names.

    First question before every join What should one output row represent? One customer? One order? One customer-order pair? Establish the intended “grain” before selecting join types or aggregating.

    2. INNER JOIN

    INNER JOIN returns only row pairs for which the join condition evaluates to TRUE. Non-matching customers and orders are excluded.

    SELECT c.customer_id, c.customer_name, o.order_id, o.amount
FROM customers c
INNER JOIN orders o
  ON o.customer_id = c.customer_id;

    Expected pairs: Alice–101, Alice–102, Bob–103. Charlie has no order, so no row is produced for Charlie. Order 104 has a NULL customer ID and does not match a customer.

    When to use it

    • Only records with a valid relationship belong in the result.
    • Joining orders to customers for a report of orders belonging to known customers.
    • Joining child rows to a parent when unmatched child rows should be excluded.
    Interview phrasing An inner join returns matching row combinations, not necessarily one row per entity. If one customer has five orders, that customer appears five times in a customer-to-order join.

    3. LEFT JOIN (LEFT OUTER JOIN)

    A left join returns every row from the left table. Matching right-side rows are attached; if no match exists, the right-side columns are filled with NULL. Multiple right matches still produce multiple output rows.

    SELECT c.customer_id, c.customer_name, o.order_id, o.amount
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.customer_id;

    Charlie appears once with NULL order columns. Alice appears twice because she has two matching orders.

    The ON versus WHERE trap

    -- Usually wrong if you must retain customers with no ACTIVE orders:
SELECT c.customer_id, c.customer_name, o.order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.status = 'ACTIVE';

-- Correct: preserve every customer; only match ACTIVE orders
SELECT c.customer_id, c.customer_name, o.order_id
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.customer_id
 AND o.status = 'ACTIVE';

    The first query filters after the join. A customer without an order has o.status = NULL; NULL = 'ACTIVE' is UNKNOWN, so the row is removed. The second puts the condition in the join predicate, preserving customers even when no active order matches.

    Important nuance A WHERE condition on the right table does not always turn a left join into an inner join. It does so when that condition rejects NULL-extended rows, such as o.status = 'ACTIVE'. Predicates like o.status IS NULL behave differently.

    4. RIGHT JOIN (RIGHT OUTER JOIN)

    A right join preserves all rows from the right table and fills left-side columns with NULL when no left match exists.

    SELECT c.customer_name, o.order_id, o.customer_id
FROM customers c
RIGHT JOIN orders o
  ON o.customer_id = c.customer_id;

    Every order remains in the output, including an order whose customer ID is NULL or has no matching customer. The customer columns are NULL for such an order.

    Readability tip: Many teams rewrite a right join as a left join by swapping table order. This keeps the preserved table visually on the left and can make complex queries easier to follow.

    5. FULL OUTER JOIN

    A full outer join preserves all rows from both sides: matched pairs appear together, and unmatched rows from either side appear with NULLs for the other table.

    SELECT c.customer_id, c.customer_name,
       o.order_id, o.customer_id AS order_customer_id
FROM customers c
FULL OUTER JOIN orders o
  ON o.customer_id = c.customer_id;

    Typical use case: reconciliation

    Suppose one system has customer records and another has imported customer records. A full join lets you find matching IDs and records that exist only on one side. Add explicit match-status logic to classify each result.

    SELECT
  COALESCE(a.external_id, b.external_id) AS external_id,
  CASE
    WHEN a.external_id IS NULL THEN 'ONLY_IN_B'
    WHEN b.external_id IS NULL THEN 'ONLY_IN_A'
    ELSE 'MATCHED'
  END AS reconciliation_status
FROM source_a a
FULL OUTER JOIN source_b b
  ON b.external_id = a.external_id;

    This example assumes external_id is non-NULL for real records. If it can be NULL, use a separate non-null key to classify matches correctly. MySQL does not support FULL OUTER JOIN directly; it can be emulated with a LEFT JOIN plus a right-side anti-match query using UNION ALL, with care to avoid duplicate matched rows.

    6. CROSS JOIN

    A cross join returns every possible combination of left and right rows. If the left side has M rows and the right side has N rows, the result contains M × N rows.

    SELECT s.size_name, c.color_name
FROM sizes s
CROSS JOIN colors c;

    If there are 4 sizes and 6 colors, the result has 24 combinations. This is useful for generating product variants, date/category grids, or test matrices.

    Production risk: accidental Cartesian product Omitting a join predicate can multiply millions of rows and exhaust CPU, memory, temporary storage, or network bandwidth. If row counts unexpectedly explode, inspect join predicates and cardinalities immediately.

    7. SELF JOIN

    A self join joins a table to itself. Give each reference a distinct alias so each role is clear. It is commonly used for adjacency relationships such as employee → manager or category → parent category.

    SELECT e.employee_id,
       e.employee_name AS employee_name,
       m.employee_name AS manager_name,
       e.salary AS employee_salary,
       m.salary AS manager_salary
FROM employees e
LEFT JOIN employees m
  ON m.employee_id = e.manager_id;

    A left join is appropriate if top-level employees have no manager but should remain in the output. Use an inner join if only employees with a matching manager are needed.

    Compare employee salary with manager salary

    SELECT e.employee_id, e.employee_name, e.salary,
       m.employee_name AS manager_name, m.salary AS manager_salary
FROM employees e
JOIN employees m ON m.employee_id = e.manager_id
WHERE e.salary > m.salary;

    A self join can compare only the direct relationship represented in each row. For all descendants in a multi-level hierarchy, a recursive CTE or database-specific hierarchy feature is usually more suitable.

    8. Join comparison and row-count intuition

    JoinPreserves unmatched left?Preserves unmatched right?Typical purpose
    INNERNoNoMatching pairs only
    LEFTYesNoAll left entities, optional right match
    RIGHTNoYesAll right entities, optional left match
    FULL OUTERYesYesReconciliation / preserve both sides
    CROSSNot a matching conceptNot a matching conceptAll combinations
    SELFDepends on chosen join typeDepends on chosen join typeRelationships within one table

    There is no universal rule that an inner join returns fewer rows than a left join when the join condition is many-to-many or duplicate keys exist. Learn the semantics and reason from key uniqueness and cardinality.

    9. Keys: primary, foreign, candidate, and related concepts

    Super key → candidate key → primary key

    SUPER KEY Any attribute set that uniquely identifies a row ↓ remove unnecessary attributes CANDIDATE KEY A minimal super key ↓ choose one candidate key PRIMARY KEY The candidate key selected as the table's main identifier Other candidate keys → alternate keys

    A key is about identifying rows and enforcing integrity, not just creating an index. A unique index may support a key constraint, but key semantics come from the declared constraints and data model.

    ConceptDefinitionExample
    Primary key (PK)The chosen candidate key. Must uniquely identify each row and cannot contain NULL.employees.employee_id
    Foreign key (FK)Column(s) in a child table constrained to reference a candidate/primary key in a parent table, subject to NULL rules.orders.customer_id → customers.customer_id
    Candidate keyA minimal set of attributes that uniquely identifies a row. A table can have several.employee_id and a genuinely unique work_email
    Super keyAny attribute set that uniquely identifies a row, including non-minimal sets.(employee_id, employee_name) if employee_id is unique
    Alternate keyA candidate key not selected as the primary key.work_email if employee_id is PK
    Composite keyA key made of two or more columns.PRIMARY KEY (order_id, product_id)
    Natural keyA key with domain/business meaning.A stable externally assigned product code
    Surrogate keyAn artificial identifier with no direct business meaning.Generated BIGINT or UUID

    Primary key example

    CREATE TABLE customers (
  customer_id BIGINT PRIMARY KEY,
  email VARCHAR(255) NOT NULL UNIQUE,
  customer_name VARCHAR(150) NOT NULL
);

    Here, customer_id is the declared primary key. The unique email constraint may represent an alternate candidate key only if the business rule truly guarantees one account per email and the database's NULL/collation semantics match that rule.

    Candidate key versus primary key

    Candidate keys are all minimal unique identifiers supported by the functional/business rules. The primary key is the one selected as the main identifier. A candidate key is minimal: if you can remove an attribute and still uniquely identify every row, the original set is a super key but not a candidate key.

    10. Foreign keys and referential integrity

    A foreign key prevents child rows from referring to a nonexistent parent key, subject to the database's NULL and constraint rules. It protects consistency even when data is written by multiple services or scripts.

    CREATE TABLE orders (
  order_id BIGINT PRIMARY KEY,
  customer_id BIGINT NOT NULL,
  order_date DATE NOT NULL,
  CONSTRAINT fk_orders_customer
    FOREIGN KEY (customer_id)
    REFERENCES customers(customer_id)
    ON DELETE RESTRICT
);

    Common referential actions

    • ON DELETE RESTRICT / NO ACTION: prevent deleting a parent while dependent rows exist; exact timing semantics vary by database and constraint configuration.
    • ON DELETE CASCADE: delete dependent child rows when the parent is deleted. Powerful but potentially destructive across large relationships.
    • ON DELETE SET NULL: clear child FK columns when the parent is deleted; those columns must allow NULL.
    Foreign key indexes A foreign key constraint does not universally guarantee an index on the referencing columns. PostgreSQL and many other systems commonly require you to create the child-side index when the workload needs it. MySQL/InnoDB generally creates a suitable index if one is missing. Verify the specific database behavior and workload.

    Indexing a child FK can make parent deletes/updates and joins more efficient, but it adds storage and write-maintenance cost. For a composite foreign key, consider an index whose leading columns match the common access pattern.

    11. Normalization and modification anomalies

    Normalization organizes relations to reduce avoidable redundancy and prevent update anomalies. It uses functional dependencies and keys to decide whether attributes belong together. It is not simply “make as many tables as possible.”

    The three classic anomalies

    Insertion anomaly

    You cannot store a fact independently without inventing an unrelated row. Example: cannot add a department until at least one employee is assigned if department data exists only in the employee table.

    Update anomaly

    The same fact is repeated in many rows. Updating only some copies leaves inconsistent values, such as different department names for employees in the same department.

    Deletion anomaly

    Deleting one fact unintentionally deletes another fact. Removing the last employee in a department could also erase the only stored record of that department.

    Design objective

    Store each independent fact in an appropriate place and connect relations with keys, preserving meaningful constraints.

    Before normalization

    EmployeeDepartment(emp_id, emp_name, dept_id, dept_name, dept_head)

emp_id | emp_name | dept_id | dept_name   | dept_head
101    | John     | D01     | Engineering | Sarah
102    | Jane     | D01     | Engineering | Sarah

    If dept_id → dept_name, dept_head, the department facts are repeated for each employee. A more appropriate design is:

    Employees(emp_id PK, emp_name, dept_id FK)
Departments(dept_id PK, dept_name, dept_head)

    Now department information is maintained once, and employees reference it by dept_id.

    12. First Normal Form (1NF)

    Core rule: Each attribute value in a relational row is represented as a single value from its domain; avoid repeating groups and packed lists that need to be queried as individual facts.

    Not a good relational design

    Employees(emp_id, name, phone_numbers)
101 | Alice | '555-0101, 555-0102'

    Searching for one phone number, enforcing uniqueness, and updating/removing one number becomes awkward when values are packed into a string.

    Normalize into separate phone rows

    Employees(emp_id PK, name)
EmployeePhones(
  emp_id FK REFERENCES Employees(emp_id),
  phone_number,
  PRIMARY KEY (emp_id, phone_number)
)

emp_id | phone_number
101    | 555-0101
101    | 555-0102

    Each phone is an individual row. Whether phone number itself is unique across all employees is a separate business rule and should be constrained only if appropriate.

    JSON and arrays nuance Real databases support JSON and array types. Their existence does not make every use invalid, but if elements are independent entities that need joins, constraints, indexing, or frequent updates, a separate relation is often the clearer relational model.

    13. Second Normal Form (2NF)

    A relation is in 2NF if it is in 1NF and every non-prime attribute is fully functionally dependent on every candidate key—there are no partial dependencies of non-key attributes on a proper subset of a candidate key. Partial dependencies are relevant when a candidate key is composite; a relation with only single-attribute candidate keys has no partial dependency of this kind.

    Example: order items

    OrderItems(order_id, product_id, quantity, product_name, unit_price)
Candidate key: (order_id, product_id)

(order_id, product_id) → quantity
product_id             → product_name, unit_price  -- partial dependency

    Product name and current product price depend on the product, not on the entire order/product key. Repeating them for every order line invites update anomalies.

    Decompose

    OrderItems(order_id, product_id, quantity)
  PK: (order_id, product_id)

Products(product_id, product_name, current_unit_price)
  PK: product_id

    Historical pricing caveat: If an invoice must preserve the price charged at purchase time, store a transaction snapshot such as OrderItems.unit_price_at_purchase. That value depends on the order line and is not redundant in the same way as the current catalog price.

    14. Third Normal Form (3NF)

    A relation is in 3NF if it is in 2NF and for every non-trivial functional dependency X → A, either X is a super key or A is a prime attribute (part of at least one candidate key). A common teaching shortcut is “remove transitive dependencies of non-key attributes,” but the formal definition matters for edge cases.

    Example: employee and department

    Employees(emp_id, emp_name, dept_id, dept_name, dept_budget)

Functional dependencies:
emp_id  → emp_name, dept_id
dept_id → dept_name, dept_budget

Therefore:
emp_id → dept_id → dept_name, dept_budget

    Department details depend on dept_id, not directly on the employee identity. Storing them for every employee repeats the same department fact.

    Decompose into 3NF-friendly relations

    Employees(emp_id PK, emp_name, dept_id FK)
Departments(dept_id PK, dept_name, dept_budget)

    Now a department budget can be updated once. A department can exist before it has employees, and deleting the last employee does not delete the department fact.

    15. Boyce–Codd Normal Form (BCNF)

    BCNF is stricter than 3NF. For every non-trivial functional dependency X → Y, X must be a super key. In plain language: every determinant must be a super key.

    Why 3NF may not be enough

    Consider a tutoring relation Tutoring(student_id, subject, professor) with these business rules:

    • A student can study a subject with one professor at a time: (student_id, subject) → professor.
    • Each professor teaches only one subject: professor → subject.

    Under these rules, candidate keys can be (student_id, subject) and (student_id, professor). subject is prime because it belongs to a candidate key. The dependency professor → subject has a determinant that is not a super key, but a prime attribute on the right, so it can satisfy 3NF while violating BCNF.

    Tutoring(student_id, subject, professor)
Functional dependencies:
(student_id, subject) → professor
professor → subject  -- BCNF violation if professor is not a super key

    BCNF decomposition

    ProfessorSubject(professor PK, subject)
StudentProfessor(student_id, professor, PK(student_id, professor))

    The professor-to-subject fact is now stored once. Validate the functional dependencies carefully: normalization examples depend on the exact business rules, and a decomposition should be checked for losslessness and whether the constraints can still be enforced.

    Interview nuance BCNF decomposition is lossless when performed correctly on a violating dependency, but it may not preserve every original functional dependency as a constraint within an individual decomposed table. 3NF synthesis is often discussed when dependency preservation is a priority.

    16. Normal forms: quick comparison

    FormMain conditionTypical issue it addresses
    1NFAtomic domain values; no repeating groups in the relational modelPacked lists and repeating attributes
    2NF1NF + no partial dependency of non-prime attributes on a proper subset of a candidate keyComposite-key partial dependency
    3NFFor every non-trivial FD X → A, X is a super key or A is primeMany transitive/non-key dependencies and anomalies
    BCNFFor every non-trivial FD X → Y, X is a super keyRemaining determinant anomalies permitted by 3NF
    1NF → 2NF → 3NF → BCNF Increasing constraint on functional dependencies (BCNF is stricter than 3NF; satisfying a stricter form satisfies the weaker forms under the same relational assumptions.)

    17. Normalization versus denormalization

    Denormalization deliberately introduces redundancy or precomputed data to optimize a known access pattern. It is an engineering trade-off, not automatically bad database design.

    DimensionNormalized designDenormalized design
    Primary goalConsistency, lower avoidable redundancy, manageable writesFaster or simpler reads for targeted workloads
    WritesOften update one authoritative factMay update several copies or derived values
    ReadsMay require joins and aggregationCan reduce joins or read precomputed results
    RisksOver-fragmentation can make read paths complexStale copies, write amplification, reconciliation complexity
    Common useTransactional OLTP coreReporting models, read models, materialized aggregates

    Controlled denormalization patterns

    • Historical snapshot: store the unit price and shipping address used on an order so a later catalog or address change does not rewrite history.
    • Precomputed aggregate: maintain a carefully updated order count or dashboard total rather than recomputing it on every request.
    • Read model: create a read-optimized projection for a high-traffic endpoint while preserving an authoritative normalized write model.
    • Materialized view: persist a query result and refresh it according to database support and freshness requirements.
    Denormalization requires a consistency plan For each duplicated value, define its source of truth, how it is updated, what happens on partial failure, whether updates are transactional, how stale data is tolerated, and how reconciliation detects drift.

    OLTP versus OLAP

    OLTP systems prioritize many concurrent, small, correct transactions. Normalized models often fit well. OLAP systems prioritize scans, aggregates, and analytical queries; dimensional or denormalized models can be effective. These are tendencies, not absolute rules—real systems often use both a normalized source and derived analytical/read models.

    18. Production scenarios and debugging

    Scenario A: parent delete is slow

    Symptom: deleting one customer takes seconds and causes request timeouts.

    Investigation: inspect the foreign-key relationships, child-row volume, delete cascade behavior, indexes on referencing columns, lock waits, and actual query plan. A child FK index may be essential for finding dependent rows efficiently.

    -- Example syntax; use your database's online-index options appropriately
CREATE INDEX idx_orders_customer_id ON orders(customer_id);

    Do not add an index blindly during an incident: index creation itself can lock, consume I/O, or affect replication depending on the engine and chosen command.

    Scenario B: report totals are inflated

    Symptom: revenue rises after joining order items and payment attempts.

    Likely cause: two one-to-many relationships multiply each other. Five item rows and three payment rows can produce 15 joined rows for one order.

    WITH item_totals AS (
  SELECT order_id, SUM(quantity * unit_price) AS item_total
  FROM order_items
  GROUP BY order_id
),
successful_payments AS (
  SELECT order_id, SUM(amount) AS paid_total
  FROM payments
  WHERE status = 'SUCCESS'
  GROUP BY order_id
)
SELECT o.order_id, i.item_total, p.paid_total
FROM orders o
LEFT JOIN item_totals i ON i.order_id = o.order_id
LEFT JOIN successful_payments p ON p.order_id = o.order_id;

    Confirm that each CTE returns at most one row per order before joining. Use realistic test data with multiple children on both sides.

    Scenario C: choose denormalization deliberately

    Symptom: a hot read endpoint needs many joins and misses its latency target.

    Response: measure the query and inspect indexes, cardinality estimates, and data-access patterns first. If joins remain the bottleneck, consider a targeted read model or materialized aggregate. Document freshness guarantees, backfill strategy, update propagation, and reconciliation.

    19. Interview Q&A

    Q1. INNER JOIN versus LEFT JOIN?

    INNER returns matching row pairs only. LEFT preserves every left-side row and adds NULLs for right-side columns when no match exists.

    Q2. Can a LEFT JOIN return more rows than the left table?

    Yes. If a left row matches multiple right rows, each matching pair is returned. Outer joins preserve unmatched rows; they do not enforce one-to-one cardinality.

    Q3. Why is a filter in ON different from a filter in WHERE?

    ON determines which right-side rows match. WHERE filters the completed joined rows. A WHERE condition that rejects NULL-extended rows can remove unmatched left rows.

    Q4. What is the difference between a candidate key and a primary key?

    A candidate key is any minimal unique identifier. One candidate key is selected as the primary key; other candidate keys are alternate keys.

    Q5. Does a foreign key automatically create an index?

    Not universally. Behavior depends on the database. Indexes on referencing columns often help joins and parent updates/deletes, but should be designed for the workload.

    Q6. What are insertion, update, and deletion anomalies?

    They are unintended consequences of storing multiple independent facts together: a fact cannot be inserted independently, repeated facts become inconsistent, or deleting one fact erases another.

    Q7. What does 2NF eliminate?

    Partial dependencies of non-prime attributes on a proper subset of a candidate key. The issue matters with composite candidate keys.

    Q8. What is the key difference between 3NF and BCNF?

    3NF permits a non-trivial dependency when the determinant is a super key or the dependent attribute is prime. BCNF requires every determinant of a non-trivial dependency to be a super key.

    Q9. Is denormalization always faster?

    No. It can reduce joins but increases storage, write amplification, and consistency complexity. Measure the workload and establish a reliable update strategy.

    Q10. What is a self join?

    A table is joined to another reference of itself using aliases. It is useful for parent-child relationships such as employees and managers.
