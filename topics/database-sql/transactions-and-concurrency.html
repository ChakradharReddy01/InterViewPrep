Module 7 (Part 3): Transactions, ACID & Isolation Levels

A practical masterclass on transaction guarantees, the four standard isolation levels, and the read anomalies they allow or prevent. Learn through timelines, SQL examples, engine behavior, production failure patterns, and interview-ready explanations.

Suggested time: 45–60 minutes · Target: Java backend, SQL, and software engineering interviews

0. Learning Roadmap

A transaction groups database operations into one logical unit. The central challenge is preserving correct results when operations fail or run concurrently.

First: correctness

  • Understand ACID
  • Know commit and rollback
  • Identify the invariant your transaction must preserve

Then: concurrency

  • Learn dirty, non-repeatable, and phantom reads
  • Compare isolation levels
  • Choose locking or retry strategies deliberately
Key mental model: ACID describes the guarantees a transaction should receive. Isolation level describes how concurrent transactions may observe and affect one another. The exact implementation depends on the database engine.

1. ACID Properties

ACID is the set of four commonly cited properties of reliable database transactions.

PropertyMeaningExampleTypical mechanisms
AtomicityAll operations in a transaction succeed together, or the transaction is rolled back.A bank transfer must debit one account and credit another—or do neither.Undo information, transaction logs, rollback/recovery.
ConsistencyA committed transaction preserves defined constraints and business invariants.Account balance cannot be negative if the rule is enforced.Constraints, keys, validation, correct transaction logic.
IsolationConcurrent transactions are controlled so their interleaving follows the chosen isolation guarantees.Two withdrawals must not both spend the same available funds.Locks, MVCC, serializable conflict detection.
DurabilityAfter a successful commit, changes survive the failures covered by the database's durability configuration.A confirmed payment remains recorded after a process restart.Write-ahead/redo logging, durable storage, flush policy, replication configuration.

1.1 A bank-transfer example

BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE account_id = 101 AND balance >= 100;

-- Application must verify that exactly one row was updated.

UPDATE accounts
SET balance = balance + 100
WHERE account_id = 202;

COMMIT;

If a required step fails, the application should roll back rather than commit a half-transfer. In real code, validate both accounts, check update counts, and handle errors. A database transaction does not automatically make incorrect business logic correct.

Consistency is not a magical repair service. The database can enforce declared constraints, but application-level invariants must be encoded and protected appropriately. If the transaction commits a logically invalid state that no constraint prevents, ACID does not infer the intended business rule.

1.2 Commit, rollback, and transaction boundaries

  • BEGIN / START TRANSACTION begins a transaction in engines that use these commands.
  • COMMIT makes the transaction's changes committed.
  • ROLLBACK abandons the transaction's uncommitted changes.
  • Autocommit behavior and nested-transaction support vary by database and framework. A nested Spring @Transactional method does not necessarily create a separate physical database transaction.
BEGIN;
UPDATE inventory SET quantity = quantity - 1 WHERE product_id = 42;
-- An error occurs before the order is successfully recorded.
ROLLBACK; -- Undo the inventory change too.

2. Isolation: What Problem Does It Solve?

Multiple requests can read and modify the same records at the same time. Without adequate concurrency control, the final result can depend on timing.

2.1 A lost-update race

Initial balance = 100

Transaction A reads 100       Transaction B reads 100
A calculates 100 + 50 = 150   B calculates 100 - 20 = 80
A writes 150                  B writes 80
A commits                    B commits

Final balance = 80
The +50 update was overwritten.

Merely wrapping read-then-write code in a transaction does not guarantee that every lost-update pattern is prevented at every isolation level. Use an atomic SQL update, a row lock, optimistic version checking, or stronger isolation as appropriate.

-- Atomic arithmetic; include a business-rule guard.
UPDATE wallet
SET balance = balance - 20
WHERE wallet_id = 7 AND balance >= 20;

-- Alternative: lock the row before reading and deciding.
BEGIN;
SELECT balance FROM wallet WHERE wallet_id = 7 FOR UPDATE;
-- Validate and update while holding the lock.
COMMIT;

2.2 Two broad implementation ideas

Lock-based concurrency

Transactions acquire locks to protect data. Locks can make conflicting operations wait; poor lock ordering can produce deadlocks.

MVCC (multi-version concurrency control)

The engine retains row versions or undo information so readers can see a consistent version without necessarily blocking writers. Details differ by engine and isolation level.

Important: “MVCC” does not mean “no locks” and does not guarantee serializable behavior by itself. Writes, explicit locking reads, and constraint checks can still block or conflict.

3. Dirty Read

A dirty read occurs when transaction B reads a change made by transaction A before A commits. If A rolls back, B has read a value that never became committed data.

Initial balance = 1000

A: BEGIN
A: UPDATE accounts SET balance = 500 WHERE id = 10; -- not committed
B: SELECT balance FROM accounts WHERE id = 10;      -- sees 500
A: ROLLBACK;                                        -- balance returns to 1000
B: makes a decision based on 500                    -- unsafe
Why it matters: a payment, inventory, or fraud decision based on uncommitted data can become invalid when the writer rolls back.

Standard behavior summary: READ UNCOMMITTED permits dirty reads in the SQL isolation model. READ COMMITTED, REPEATABLE READ, and SERIALIZABLE prevent them. Some engines implement READ UNCOMMITTED more strictly than the minimum standard; for example, PostgreSQL treats it as READ COMMITTED.

4. Non-Repeatable Read

A non-repeatable read happens when a transaction reads a row, another transaction commits an update or deletion of that row, and the first transaction reads that same row again and sees a different result.

Initial balance = 1000

A: BEGIN
A: SELECT balance FROM accounts WHERE id = 10; -- 1000
B: UPDATE accounts SET balance = 800 WHERE id = 10;
B: COMMIT;
A: SELECT balance FROM accounts WHERE id = 10; -- 800 at READ COMMITTED

READ COMMITTED prevents dirty reads but commonly takes a fresh committed view for each statement, so the second query can see B's committed update. REPEATABLE READ is designed to prevent a transaction from seeing a changed version of the same row on a repeated read, though exact snapshot and locking behavior is engine-specific.

Interview distinction: non-repeatable read is about a row already found; the row's values or existence changes between reads.

5. Phantom Read

A phantom read occurs when the same predicate query returns a different set of rows because another transaction inserts or deletes rows that satisfy that predicate and commits.

A: BEGIN
A: SELECT COUNT(*) FROM orders WHERE status = 'PENDING'; -- 5

B: INSERT INTO orders(id, status) VALUES (999, 'PENDING');
B: COMMIT;

A: SELECT COUNT(*) FROM orders WHERE status = 'PENDING'; -- may be 6

The issue is not necessarily a changed value on one existing row; it is a changed result set for the same condition.

Engine nuance: the SQL standard's isolation table allows phantoms at REPEATABLE READ, but implementations differ. MySQL InnoDB commonly prevents phantom results for ordinary consistent reads with its repeatable-read snapshot and uses next-key/gap locks for relevant locking operations. PostgreSQL's REPEATABLE READ provides a stable snapshot and prevents ordinary phantom reads, but can still allow serialization anomalies such as write skew. Do not assume every database's level name has identical behavior.

6. The Four Standard Isolation Levels

Think of the levels as increasingly strict control over which concurrent effects can become visible. Stronger isolation can reduce anomalies but may increase blocking, aborts, retries, and latency.

LevelDirty readNon-repeatable readPhantom readPractical interpretation
READ UNCOMMITTEDAllowed by standardPossiblePossibleWeakest isolation; dirty reads may be permitted, though engine implementations vary.
READ COMMITTEDPreventedPossiblePossibleEach statement sees committed data according to the engine's statement-level visibility rules.
REPEATABLE READPreventedPreventedStandard permits it; engine-dependent in practiceRepeated reads of existing rows are stable; snapshot and locking details matter.
SERIALIZABLEPreventedPreventedPrevented as a serializable outcomeTransactions behave as if run in some serial order; conflicts may block or abort a transaction that must be retried.

6.1 READ UNCOMMITTED

  • Weakest standard isolation level.
  • May expose uncommitted changes, making decisions based on data that can be rolled back.
  • Rarely appropriate for business-critical reads such as balances, inventory, or order state.

6.2 READ COMMITTED

  • Prevents dirty reads.
  • Two statements in one transaction can see different committed values.
  • Common default in PostgreSQL and Oracle; SQL Server commonly uses locking READ COMMITTED unless row-versioning options change read behavior. Check the database configuration rather than assuming.
-- PostgreSQL-style example
BEGIN TRANSACTION ISOLATION LEVEL READ COMMITTED;
SELECT balance FROM accounts WHERE id = 10;
-- another transaction commits an update
SELECT balance FROM accounts WHERE id = 10; -- may see the new value
COMMIT;

6.3 REPEATABLE READ

  • Prevents dirty and non-repeatable reads.
  • Phantom behavior and write-skew behavior vary by engine and implementation.
  • MySQL InnoDB commonly defaults to REPEATABLE READ; PostgreSQL's REPEATABLE READ uses snapshot isolation and can allow write skew.
-- PostgreSQL example
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 10;
-- another transaction commits an update
SELECT balance FROM accounts WHERE id = 10; -- same transaction snapshot
COMMIT;

6.4 SERIALIZABLE

  • Strongest standard isolation level.
  • Guarantees a result equivalent to some serial execution of concurrent transactions.
  • May use strict locking or serializable conflict detection. A transaction can fail with a serialization error and must be retried safely.
-- PostgreSQL-style example
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- read facts, check invariant, write changes
COMMIT;
-- Application must handle serialization failure by retrying
-- the complete transaction, with a bounded retry policy.
Production rule: choose isolation based on the invariant and access pattern, not by automatically selecting the strongest level for every query.

8. Database Engine Notes: MVCC, Locks, and Logs

8.1 MVCC snapshots

With multi-version concurrency control, a transaction can read a version that was visible at its snapshot rather than necessarily reading the newest physical row version. In a common model, READ COMMITTED uses a new visibility snapshot per statement, while REPEATABLE READ uses a transaction-level snapshot. This is a conceptual model; consult the chosen engine's documentation for exact semantics.

8.2 Write-ahead logging (WAL) and durability

  1. The transaction modifies data and the engine records the necessary log information.
  2. At commit, the database ensures the required commit log record is durably persisted according to its configuration.
  3. The database can acknowledge commit after the configured durability condition is met.
  4. Data pages can be written to their main table files later; recovery uses logs to restore a consistent state.
Do not oversimplify the physical sequence: redo/undo design, flush policies, replication acknowledgements, and synchronous-commit settings differ among engines. “COMMIT returned” means durability according to that database's configured guarantees.

8.3 Deadlocks and retries

A deadlock occurs when transactions wait on one another in a cycle. Databases typically detect a victim transaction and abort it. Applications should handle deadlock/serialization failures with bounded retries, and transactions should acquire locks in a consistent order where possible.

-- Keep transactions short.
-- Lock multiple rows in a consistent order (for example, ascending account_id).
-- Do not call slow external APIs while holding database locks.
-- Retry only recognized transient transaction failures.
-- Make retries safe: avoid duplicating external side effects.

9. Java / Spring Transaction Examples

9.1 Declarative transaction boundary

@Service
public class TransferService {
    private final AccountRepository accounts;

    public TransferService(AccountRepository accounts) {
        this.accounts = accounts;
    }

    @Transactional
    public void transfer(long fromId, long toId, BigDecimal amount) {
        Account from = accounts.findByIdForUpdate(fromId)
            .orElseThrow();
        Account to = accounts.findByIdForUpdate(toId)
            .orElseThrow();

        if (from.getBalance().compareTo(amount) < 0) {
            throw new InsufficientFundsException();
        }

        from.debit(amount);
        to.credit(amount);
        // On successful method completion, Spring normally commits.
        // A qualifying unchecked exception normally triggers rollback
        // by default; configure rollback rules for checked exceptions.
    }
}

Illustrative pseudocode: repository locking method and exception types must be implemented. Spring transaction behavior also depends on proxy boundaries, transaction manager, propagation, and rollback rules.

9.2 Setting isolation in Spring

@Transactional(isolation = Isolation.READ_COMMITTED)
public void processOrder() {
    // Database operations within this transaction
}
  • The isolation setting is applied when a new transaction is started; behavior with an existing transaction depends on propagation and transaction-manager settings.
  • Self-invocation within the same Spring bean may bypass proxy-based transaction interception.
  • Use the database's actual isolation semantics, not only the annotation name.

9.3 Optimistic locking with a version field

@Entity
public class Inventory {
    @Id
    private Long id;

    private int quantity;

    @Version
    private long version;
}

With JPA optimistic locking, the provider uses the version to detect conflicting updates. A transaction may fail with an optimistic-lock exception instead of silently overwriting a concurrent change. The application must decide whether to reject or retry the operation.

10. Production Scenarios and Root-Cause Analysis

Scenario A: Wallet balance loses an update

Symptom: balances are unexpectedly overwritten during concurrent cashback and payment requests.

Likely cause: both requests read the same old value, calculate in application memory, and write absolute values. READ COMMITTED alone does not prevent every lost-update implementation pattern.

Fix options: atomic arithmetic SQL with a balance guard, SELECT ... FOR UPDATE, optimistic version checks, or serializable isolation with retry. Add ledger-based reconciliation for money movement.

Scenario B: A rule is violated despite REPEATABLE READ

Symptom: two transactions each pass a check but together violate a cross-row invariant.

Example: at least one doctor must remain on call; two transactions each see two doctors on call and independently remove a different doctor from the on-call set.

Likely cause: snapshot isolation can permit write skew because the transactions write different rows.

Fix options: SERIALIZABLE with retry, explicit locking of a shared coordination row, or a schema/design that makes the invariant enforceable atomically.

Scenario C: Deadlocks or lock waits increase sharply

Symptom: API latency and deadlock exceptions rise under peak traffic.

Investigate: deadlock reports, lock wait graphs, transaction duration, query plans, missing indexes, and inconsistent row-lock ordering. For MySQL InnoDB REPEATABLE READ, range and gap/next-key locking may be relevant to locking reads and inserts.

Remediation: shorten transactions, index predicates, lock resources in a consistent order, use bounded retries, and consider READ COMMITTED only after validating the changed semantics and workload.

Avoid a blanket fix: lowering isolation can reduce some locking but may reintroduce anomalies. Reproduce the concurrency pattern and verify the business invariant before changing isolation.

11. Interview Questions and Strong Answers

Q1. What are ACID properties?

Atomicity makes the transaction all-or-nothing; consistency preserves defined constraints; isolation controls concurrent interactions; durability makes committed changes survive failures covered by the configured durability guarantees.

Q2. What is the difference between dirty, non-repeatable, and phantom reads?

Dirty read: reading uncommitted data. Non-repeatable read: rereading an existing row and seeing its committed value or existence change. Phantom read: rerunning a predicate query and getting a different set of matching rows.

Q3. Does READ COMMITTED prevent lost updates?

Not universally. It prevents dirty reads, but a read-calculate-write sequence can still overwrite another update. Use atomic SQL, row locks, optimistic versioning, or stronger isolation according to the workload.

Q4. Does REPEATABLE READ always prevent phantom reads?

No universal answer from the level name alone. The standard permits phantoms at REPEATABLE READ, while implementations differ: MySQL InnoDB and PostgreSQL have distinct snapshot and locking behavior.

Q5. Why can SERIALIZABLE transactions fail?

The engine may detect that concurrent execution cannot safely be equivalent to a serial order. It aborts one transaction so the application can retry the complete transaction.

Q6. What is MVCC?

Multi-version concurrency control maintains or reconstructs multiple row versions so transactions can read versions consistent with their visibility rules. It can reduce reader-writer blocking but does not eliminate all locks or conflicts.

Q7. What is write skew?

Concurrent transactions read overlapping state, then update disjoint rows. Both updates can succeed while their combined result violates a shared invariant. Serializable isolation or explicit coordination can prevent it.

Q8. How should an application handle deadlocks?

Keep transactions short, lock resources consistently, inspect deadlock reports and query plans, and retry recognized transient failures with a bounded policy. Ensure retries do not duplicate external side effects.

Q9. Is a Spring @Transactional annotation enough to guarantee correctness?

No. Correctness depends on transaction boundaries, proxy invocation, rollback rules, isolation, database behavior, locking, and business logic. A transaction groups operations; it does not automatically prevent all races.

Q10. When should you use pessimistic vs optimistic locking?

Pessimistic locking is useful when conflicts are likely and a resource must be protected during a decision. Optimistic locking is useful when conflicts are less common and the application can detect and handle concurrent changes.

13. Final Quick-Revision Sheet

  • Atomicity: all or nothing.
  • Consistency: preserve declared constraints and business invariants.
  • Isolation: govern concurrent visibility and conflicts.
  • Durability: committed data survives failures covered by configuration.
  • Dirty read: read uncommitted data.
  • Non-repeatable read: same row read again, changed value or existence.
  • Phantom read: same predicate query, changed matching row set.
  • READ UNCOMMITTED: weakest; dirty reads may be allowed.
  • READ COMMITTED: no dirty reads; repeated statements can see newer commits.
  • REPEATABLE READ: stable repeated row reads; phantom/write-skew semantics depend on engine.
  • SERIALIZABLE: equivalent to serial execution; handle aborts/retries.
  • Practical rule: encode invariants, keep transactions short, and choose concurrency controls intentionally.
