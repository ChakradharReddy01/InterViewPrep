Module 7 (Part 3): Database Transactions, ACID Internals, Isolation Levels & MVCC

Transactions MVCC & WAL Concurrency Anomalies & Locking ⏱️ 55 min deep dive Target Roles: SDE-2, SDE-3, Database & Backend Architect

1. ACID Under the Hood: Physical Engine Mechanics

In relational database management systems (RDBMS), a Transaction is a logical unit of work consisting of one or more SQL operations executed against the database. The engine guarantees the ACID contract not through magic, but through precise physical data structures:

ACID Pillar Architectural Guarantee Under-the-Hood Engine Mechanism
Atomicity
(All or Nothing)		 Either all modifications within the transaction are permanently applied, or all changes are rolled back with zero side effects. Undo Logs / Rollback Segments: Records before-images of modified data. If a rollback occurs (or crash happens), the engine replays undo records in reverse order to restore previous page states.
Consistency
(Invariant Preservation)		 Transactions take the database from one valid state satisfying all schemas, invariants, and constraints to another valid state. Enforced via primary keys, foreign key referential integrity, CHECK constraints, unique indexes, and application-level business invariants.
Isolation
(Concurrency Control)		 Concurrent transactions execute without stepping on each other's intermediate uncommitted states as if executed serially. Multi-Version Concurrency Control (MVCC), Snapshot Isolation, and Pessimistic Lock Managers (Two-Phase Locking / 2PL).
Durability
(Surviving Crashes)		 Once a transaction commits, its modifications are permanently recorded and survive power outages or operating system crashes. Write-Ahead Logging (WAL) & Redo Logs: Modifications are written sequentially to an append-only WAL on non-volatile disk and flushed via fsync() before dirty data pages are flushed from RAM to disk tablespaces. 
WAL (Write-Ahead Logging) Sequence during COMMIT:
1. Transaction executes UPDATE account SET balance = 900 WHERE id = 1;
2. Engine creates Redo/Undo log record in RAM log buffer.
3. Client issues COMMIT;
4. Engine writes log record to WAL file on disk and executes fsync().
5. Disk controller confirms WAL persist -> Server sends "COMMIT SUCCESS" to client!
6. Dirty page in RAM Buffer Pool (balance=900) is lazily flushed to database tablespace later (Checkpointer process).

2. The Concurrency Read Phenomena (Anomalies)

When multiple transactions read and write to the same rows concurrently without isolation, three classic ANSI SQL read phenomena can corrupt data:

2.1 Dirty Read

Definition: Transaction $T_1$ modifies a row but has not yet committed. Transaction $T_2$ reads the uncommitted row. If $T_1$ subsequently issues a ROLLBACK, $T_2$ has acted on "dirty" phantom data that never legally existed in the database. 

Timeline:
Tx 1: BEGIN;
Tx 1: UPDATE accounts SET balance = 500 WHERE id = 10; (Original was 1000)
Tx 2: BEGIN;
Tx 2: SELECT balance FROM accounts WHERE id = 10; ---> Reads 500! (DIRTY READ!)
Tx 1: ROLLBACK; (Balance reverts to 1000)
Tx 2: Dispatches money based on non-existent balance of 500!

2.2 Non-Repeatable Read (Fuzzy Read)

Definition: Transaction $T_1$ reads a row. Transaction $T_2$ modifies or deletes that row and commits. Transaction $T_1$ reads the exact same row again within the same transaction and discovers that its values have changed. 

Timeline:
Tx 1: BEGIN;
Tx 1: SELECT balance FROM accounts WHERE id = 10; ---> Reads 1000
Tx 2: BEGIN;
Tx 2: UPDATE accounts SET balance = 800 WHERE id = 10;
Tx 2: COMMIT;
Tx 1: SELECT balance FROM accounts WHERE id = 10; ---> Reads 800! (NON-REPEATABLE READ!)
Tx 1: Same query inside same transaction yielded different data for the same row!

2.3 Phantom Read

Definition: Transaction $T_1$ reads a set of rows satisfying a search predicate (e.g. range query WHERE age > 30). Transaction $T_2$ inserts new rows (or deletes rows) satisfying that predicate and commits. When $T_1$ re-executes the exact same range query, a new "phantom" row appears in the result set that was not present previously. 

Timeline:
Tx 1: BEGIN;
Tx 1: SELECT COUNT(*) FROM orders WHERE status = 'PENDING'; ---> Returns 5
Tx 2: BEGIN;
Tx 2: INSERT INTO orders (id, status) VALUES (999, 'PENDING');
Tx 2: COMMIT;
Tx 1: SELECT COUNT(*) FROM orders WHERE status = 'PENDING'; ---> Returns 6! (PHANTOM READ!)

2.4 Extended Anomalies: Lost Update & Write Skew

  • Lost Update: Two concurrent transactions read the same initial state (e.g. balance = 100). $T_1$ adds 50 and commits (150). $T_2$ subtracts 20 based on its old read (100 - 20 = 80) and commits. $T_1$'s update is completely overwritten and lost forever!
  • Write Skew (Snapshot Isolation Anomaly): Two concurrent transactions read overlapping data sets, make decisions based on an invariant, and write to disjoint rows. Example: A hospital rule states "At least 1 doctor must be on call". Both Doctor Alice and Doctor Bob are on call. Both simultaneously request leave. Under Repeatable Read/Snapshot Isolation, both see 2 active doctors, both approve their own leave, and the hospital is left with zero doctors on call!

3. The 4 ANSI SQL Isolation Levels

The ANSI/ISO SQL standard defines four transaction isolation levels based on which concurrency anomalies they prevent:

Isolation Level Dirty Read Non-Repeatable Read Phantom Read Lost Update Default Database Engines
READ UNCOMMITTED Allowed Allowed Allowed Allowed Rarely used. (Postgres treats it as Read Committed).
READ COMMITTED Prevented Allowed Allowed Possible PostgreSQL, Oracle, SQL Server.
REPEATABLE READ Prevented Prevented Prevented* Prevented MySQL InnoDB (prevents phantoms via Next-Key Locking).
SERIALIZABLE Prevented Prevented Prevented Prevented Strictest. Uses 2PL or SSI (Serializable Snapshot Isolation).
💡 Why does MySQL InnoDB prevent Phantom Reads in Repeatable Read?

Under the strict ANSI SQL standard, Repeatable Read is allowed to experience Phantom Reads. However, MySQL InnoDB's default implementation goes beyond the standard:

1. Consistent Non-Locking Reads (Plain SELECT): InnoDB reads from a single static MVCC Read View established at the beginning of the transaction. Any rows inserted by other transactions have transaction IDs greater than the snapshot and are invisible.

2. Locking Reads (SELECT FOR UPDATE / UPDATE): InnoDB utilizes Next-Key Locking (a combination of a record lock on the index record plus a gap lock on the gap before the index record). Gap locks physically block other transactions from inserting new rows into the scanned range!

4. MVCC (Multi-Version Concurrency Control) Internals

4.1 Why MVCC? "Readers Never Block Writers, Writers Never Block Readers"

In traditional locking databases (Two-Phase Locking / 2PL), a read query acquires a Shared Lock (S-Lock) on rows, blocking write queries from acquiring Exclusive Locks (X-Locks). High concurrency leads to massive lock contention.

MVCC solves this by storing multiple timestamped versions of each row. When a transaction updates a row, the engine does not overwrite the old row in-place; it creates a new version while preserving older versions for active concurrent readers: 

How PostgreSQL Implements MVCC (Tuple Header Fields):
Every row on disk contains hidden system columns:
- xmin: The transaction ID that inserted this row version.
- xmax: The transaction ID that deleted or updated this row version (0 if active).

Tuple Version Chain:
+----+---------+--------+--------+---------------------------------------+
| id | balance | xmin   | xmax   | Visibility Rule                       |
+----+---------+--------+--------+---------------------------------------+
|  1 |    1000 | Tx 100 | Tx 105 | Visible only to transactions < 105    |
|  1 |     900 | Tx 105 | Tx 110 | Visible to transactions between 105-110|
|  1 |     750 | Tx 110 | 0      | Currently active latest version!      |
+----+---------+--------+--------+---------------------------------------+

4.2 Read Committed vs Repeatable Read in MVCC

  • In Read Committed: The database engine creates a new Read View (Snapshot) at the start of every single SQL statement. If $T_2$ commits between statement 1 and statement 2 of $T_1$, statement 2 sees the new data (causing Non-Repeatable Reads).
  • In Repeatable Read: The database engine creates a single Read View at the start of the first read query in the transaction. All subsequent queries throughout the transaction read from that exact same immutable snapshot.

5. Real-World Production War Stories (RCA & Solutions)

🚨 Incident 1: $140,000 Lost Balance Anomaly in Read Committed via Race Condition

Environment: Peer-to-peer wallet transfer microservice running on PostgreSQL with Spring Boot default `@Transactional` (Read Committed).

The Failure: During a flash marketing promotion where users received concurrent cashback rewards and sent payments simultaneously, wallet balances became desynchronized, resulting in negative balances and an unexplained $140k accounting deficit.

Root Cause Analysis (RCA):

  • The transfer code executed a standard SELECT balance FROM wallet WHERE id = 10; followed by an in-memory Java calculation: int newBalance = oldBalance + cashback;, followed by UPDATE wallet SET balance = newBalance WHERE id = 10;.
  • Two concurrent transactions $T_1$ (cashback +$10) and $T_2$ (spend -$50) read the exact same balance of $100 simultaneously under Read Committed.
  • $T_1$ updated balance to $110 and committed. A millisecond later, $T_2$ blindly wrote balance = 50 (100 - 50) and committed, completely overwriting $T_1$'s cashback!

The Fix: Eliminate the Lost Update by avoiding in-memory arithmetic or using atomic database locks:

-- Solution A: Atomic In-Place SQL Update (No in-memory calculation)
UPDATE wallet SET balance = balance - 50 WHERE id = 10 AND balance >= 50;

-- Solution B: Pessimistic Locking inside Transaction
SELECT balance FROM wallet WHERE id = 10 FOR UPDATE; -- Acquires row-level exclusive lock
🚨 Incident 2: MySQL Deadlock Explosion via Gap Locks on Non-Unique Foreign Keys

Environment: High-throughput order placement system on MySQL 8.0 (InnoDB Repeatable Read).

The Failure: During peak load (3,000 orders/sec), API instances threw cascading CannotAcquireLockException: Deadlock found when trying to get lock; try restarting transaction. Throughput collapsed to zero.

Root Cause Analysis (RCA):

  • Under Repeatable Read, MySQL InnoDB uses Next-Key Locks (Record Lock + Gap Lock) for searches on non-unique secondary indexes.
  • Multiple threads simultaneously executed SELECT * FROM order_items WHERE order_id = ? FOR UPDATE; before inserting items.
  • Because order_id had a non-unique index, each thread acquired a Gap Lock on the phantom range surrounding the order ID.
  • When Thread A attempted to insert an item into the gap, it blocked waiting for Thread B's gap lock. Thread B simultaneously attempted to insert into the same gap, waiting for Thread A's gap lock → Mutual Deadlock!

The Fix: For high-throughput OLTP systems with heavy insert workloads, switch the transaction isolation level to READ COMMITTED (where gap locking is disabled for searches and row locks only are acquired), or enforce strict sequential resource ordering.

6. Senior & Staff Engineer Interview Q&A

Q1: What is the fundamental difference between a Non-Repeatable Read and a Phantom Read?

Answer:

  • Non-Repeatable Read: Concerns modifications or deletions of existing individual rows that were previously read. Prevented by locking the existing rows (shared read lock) or taking a row-level snapshot.
  • Phantom Read: Concerns new rows being inserted into a table that satisfy a search range predicate (e.g. WHERE department_id = 5). Row-level locks on existing records cannot prevent phantoms because the new row did not exist when locks were granted! Phantoms can only be prevented via predicate locking, Gap/Next-Key locking, or Snapshot Isolation.
Q2: Why does PostgreSQL require VACUUM while MySQL InnoDB does not?

Answer: This is a direct consequence of their differing MVCC architectures:

  • PostgreSQL: Stores all row versions (xmin, xmax) directly inside the main heap data table pages (append-only architecture). Old, dead row versions ("dead tuples") accumulate on disk. VACUUM is required to reclaim space occupied by dead tuples and freeze transaction IDs to prevent transaction ID wraparound.
  • MySQL InnoDB: Modifies rows in-place in the clustered index and writes old versions out to a separate Undo Log tablespace. Active readers reconstruct older views by traversing the undo rollback pointers (DB_ROLL_PTR). Once no active transaction requires the undo records, InnoDB's background Purge Threads automatically deallocate the undo space without bloating the main tablespace.
Q3: What is Write Skew, and why doesn't Repeatable Read prevent it?

Answer: Write Skew occurs in Snapshot Isolation / Repeatable Read when two concurrent transactions read overlapping data, verify a common constraint, but make disjoint updates that violate the constraint when committed together.

Under Repeatable Read, the engine only checks for conflicts when two transactions attempt to update the exact same row (first-committer-wins rule). In Write Skew, Transaction 1 updates Row A and Transaction 2 updates Row B. Because the write sets are disjoint, neither transaction experiences a row lock conflict. Both commit cleanly, but their combined result leaves the database in an invalid state. Write Skew can only be prevented using SERIALIZABLE isolation or explicit SELECT ... FOR UPDATE locks.
