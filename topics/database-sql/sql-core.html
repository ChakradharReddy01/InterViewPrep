Module 7 (Part 1): SQL Internals, Execution Order, Complex Joins & Window Functions

SQL Internals Cost-Based Optimizer Query Tuning & Post-Mortems ⏱️ 60 min deep dive Target Roles: SDE-2, SDE-3, Data Engineer & System Architect

1. The 10-Step Logical Query Processing Order

1.1 Syntactic Writing Order vs Logical Execution Order

Unlike imperative languages (Java, C++) which execute top-to-bottom, SQL is a declarative language. You specify what data you want, not how to retrieve it. A critical senior engineer requirement is understanding that the database engine parses and executes clauses in a fundamentally different sequence from how they are written:

Step Clause Engine Operation & Intermediate Virtual Table
1 FROM Identifies source tables, resolves aliases, performs Cartesian products for joins.
2 ON Evaluates join predicates against table rows.
3 JOIN Adds preserved outer rows (for LEFT, RIGHT, FULL OUTER joins).
4 WHERE Filters individual rows before aggregation. Cannot reference SELECT aliases or aggregate functions.
5 GROUP BY Collapses rows sharing identical key attributes into distinct bucket groups.
6 HAVING Filters collapsed groups using aggregate conditions (e.g. COUNT(*) > 5).
7 SELECT Evaluates expressions, computes column projections, assigns column aliases.
8 DISTINCT Eliminates duplicate projection rows using hashing or sorting algorithms.
9 ORDER BY Sorts final result set. Only step that can legally use SELECT aliases.
10 LIMIT / OFFSET Discards rows and caps result set cardinality before streaming to client.
⚠️ The "Alias Unknown in WHERE" Mystery

Why does SELECT salary * 12 AS annual_salary FROM emp WHERE annual_salary > 100000; fail with "column annual_salary does not exist"?

Because WHERE (Step 4) runs before SELECT (Step 7). The database has not yet evaluated the alias when filtering rows. However, ORDER BY annual_salary DESC succeeds because ORDER BY (Step 9) executes after SELECT.

2. Fundamental Clauses: Filtering, Grouping & Sorting

2.1 WHERE vs HAVING: Cardinality and Performance

  • WHERE: Filters individual records before rows enter memory for aggregation. Utilizes B-Tree indexes to prune row scans. Always filter row-level conditions in WHERE.
  • HAVING: Evaluated after all groups are constructed. Filters aggregated groups. Cannot utilize standard indexes on unaggregated columns without specialized grouped indexes.
-- BAD ARCHITECTURAL PRACTICE: Filtering row-level attributes inside HAVING
SELECT department_id, AVG(salary) AS avg_sal
FROM employees
GROUP BY department_id, is_active
HAVING is_active = TRUE AND AVG(salary) > 85000; -- Forces engine to aggregate inactive rows first!

-- OPTIMAL PRODUCTION QUERY:
SELECT department_id, AVG(salary) AS avg_sal
FROM employees
WHERE is_active = TRUE -- Prunes rows immediately using index on (is_active)
GROUP BY department_id
HAVING AVG(salary) > 85000; -- Only aggregates active rows

2.2 DISTINCT Internals: The Hidden Performance Tax

DISTINCT is not a simple flag; it triggers a heavy physical sort or hash operation:

  • Hash Aggregate: The engine allocates an in-memory hash table of all projected columns. If distinct values exceed allocated memory (work_mem in Postgres or tmp_table_size in MySQL), it spills to disk temporary files (I/O bottleneck).
  • Sort Aggregate: The engine executes an external merge sort across all rows to discard adjacent identical tuples.

2.3 Conditional Logic: CASE WHEN Expression

CASE is a scalar expression that returns a value. It evaluates sequentially from top to bottom and supports two forms:

  • Simple CASE: CASE status WHEN 'P' THEN 1 WHEN 'C' THEN 2 ELSE 0 END
  • Searched CASE: Supports boolean predicates and conditional aggregation (pivot queries):
-- Conditional Aggregation (Pivoting rows into columns without vendor-specific PIVOT syntax)
SELECT 
    DATE_TRUNC('month', order_date) AS order_month,
    COUNT(*) AS total_orders,
    SUM(CASE WHEN status = 'COMPLETED' THEN amount ELSE 0 END) AS completed_revenue,
    SUM(CASE WHEN status = 'REFUNDED'  THEN amount ELSE 0 END) AS refunded_loss,
    ROUND(100.0 * COUNT(CASE WHEN status = 'FAILED' THEN 1 END) / COUNT(*), 2) AS failure_rate_pct
FROM orders
WHERE order_date >= '2026-01-01'
GROUP BY DATE_TRUNC('month', order_date)
ORDER BY order_month ASC;

3. Relational Joins & Execution Engine Mechanics

3.1 Logical Join Types

[ INNER JOIN ]       Intersection: Only tuples matching predicates in both tables.
[ LEFT JOIN ]        Preserves ALL rows from Left table; NULLs for non-matching Right attributes.
[ RIGHT JOIN ]       Preserves ALL rows from Right table; NULLs for Left attributes.
[ FULL OUTER JOIN ]  Preserves all rows from both tables; NULLs wherever matching tuple is absent.
[ CROSS JOIN ]       Cartesian product (Size = M * N). Avoid unless generating coordinate matrices.
[ SELF JOIN ]        A table joined with itself (hierarchies, organizational trees, graph edges).

3.2 Under the Hood: Physical Join Algorithms

When a cost-based optimizer (CBO) plans a join, it translates logical joins into one of three physical algorithms based on statistics, cardinality, and available indexes:

Join Algorithm Algorithm Complexity Ideal Use Case Engine Vulnerability
Nested Loop Join $O(N \times \log M)$ with index, $O(N \times M)$ without Small outer table driving a large inner table indexed on join key. Missing index causes catastrophic $O(N \times M)$ CPU lockup.
Hash Join $O(N + M)$ Joining large datasets without suitable indexes on equijoins (=). Hash table size exceeds RAM, causing multi-batch disk spills. Only supports equijoins.
Merge Join (Sort-Merge) $O(N \log N + M \log M)$ or $O(N + M)$ if pre-sorted Both inputs already sorted on join keys via B-Tree clustered index. If data is unsorted, upfront sort cost overwhelms benefit. 
-- Self-Join for Organizational Hierarchy
SELECT 
    e.employee_id,
    e.first_name || ' ' || e.last_name AS employee_name,
    e.job_title,
    COALESCE(m.first_name || ' ' || m.last_name, 'TOP EXECUTIVE') AS manager_name
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.employee_id
ORDER BY m.employee_id NULLS FIRST;

4. Subqueries, CTEs, UNION & The Three-Valued Logic Trap

4.1 Subquery Types

  • Scalar Subquery: Returns exactly one row and one column. Can be placed anywhere a value is expected (SELECT list, WHERE comparison).
  • Multi-Row Subquery: Returns a column with multiple rows. Evaluated using IN, ANY, or ALL.
  • Correlated Subquery: The inner query references columns from the outer query. It evaluates once for every candidate row of the outer query unless unnested by the optimizer.

4.2 Common Table Expressions (CTE)

Defined using the WITH clause. CTEs enhance readability and enable Recursive Queries (e.g. bill-of-materials, folder trees, graph traversal): 

-- Recursive CTE: Traversing Management Hierarchy
WITH RECURSIVE OrgChart AS (
    -- Anchor member: Start at CEO (manager_id IS NULL)
    SELECT employee_id, first_name, manager_id, 1 AS depth_level
    FROM employees
    WHERE manager_id IS NULL

    UNION ALL

    -- Recursive member: Join with OrgChart anchor
    SELECT e.employee_id, e.first_name, e.manager_id, o.depth_level + 1
    FROM employees e
    INNER JOIN OrgChart o ON e.manager_id = o.employee_id
)
SELECT depth_level, LPAD(' ', (depth_level - 1) * 4) || first_name AS hierarchy
FROM OrgChart
ORDER BY depth_level, employee_id;

4.3 EXISTS vs IN: The Three-Valued Logic (NULL) Trap

In SQL, boolean logic is three-valued: TRUE, FALSE, and UNKNOWN (NULL).

⚠️ The Fatal NOT IN with NULL Disaster

Suppose table B has records: (1, 2, NULL). You execute: 

SELECT * FROM table_a WHERE id NOT IN (SELECT id FROM table_b);

This query expands to: WHERE id != 1 AND id != 2 AND id != NULL.
In SQL, id != NULL evaluates to UNKNOWN.
TRUE AND TRUE AND UNKNOWN evaluates to UNKNOWN.
Result: The query returns 0 rows! It silently fails to return any data at all!

The Enterprise Rule: Always use NOT EXISTS instead of NOT IN. EXISTS uses two-valued Boolean logic (either a matching row exists or it does not), completely immune to NULL values: 

SELECT a.*
FROM table_a a
WHERE NOT EXISTS (
    SELECT 1 FROM table_b b WHERE b.id = a.id
); -- Safe, index-optimized Anti-Semi-Join!

4.4 UNION vs UNION ALL

  • UNION ALL: Concatenates result sets directly into the output stream. $O(1)$ additional overhead, no buffering, minimal memory consumption.
  • UNION: Concatenates result sets and performs an exhaustive duplicate elimination pass via an in-memory hash table or disk sort. Has massive performance and CPU cost.
  • Best Practice: Never use UNION unless you specifically require mathematical set deduplication. Always default to UNION ALL.

5. Advanced Window Functions & Frame Specifications

5.1 Window Functions vs GROUP BY

While GROUP BY collapses multiple rows into a single summary tuple, a Window Function calculates an aggregate or ranking across a defined partition of rows while preserving every individual row's identity and detail. 

Syntax Anatomy:
FUNCTION(...) OVER (
    [PARTITION BY partition_col1, ...]
    [ORDER BY sort_col1 [ASC|DESC], ...]
    [ROWS | RANGE BETWEEN frame_start AND frame_end]
)

5.2 Ranking Functions Compared: ROW_NUMBER vs RANK vs DENSE_RANK

When rows share identical values for the ordering column (ties):

  • ROW_NUMBER(): Assigns a strict sequential integer (1, 2, 3, 4, 5) without regard for ties (arbitrary tie-breaker).
  • RANK(): Assigns identical rank to ties, but skips subsequent positions (e.g. 1, 2, 2, 4, 5).
  • DENSE_RANK(): Assigns identical rank to ties, but never skips subsequent ranks (e.g. 1, 2, 2, 3, 4).
-- Finding the Top 3 Highest Earners in Each Department (Staff Interview Classic)
WITH RankedEmployees AS (
    SELECT 
        department_id,
        employee_id,
        salary,
        DENSE_RANK() OVER (
            PARTITION BY department_id 
            ORDER BY salary DESC
        ) AS salary_rank
    FROM employees
)
SELECT department_id, employee_id, salary, salary_rank
FROM RankedEmployees
WHERE salary_rank <= 3
ORDER BY department_id, salary_rank;

5.3 Value & Navigation Functions: LAG, LEAD, FIRST_VALUE

-- Month-Over-Month (MoM) Growth Analysis
SELECT 
    order_month,
    revenue,
    LAG(revenue, 1) OVER (ORDER BY order_month) AS prev_month_revenue,
    ROUND(
        100.0 * (revenue - LAG(revenue, 1) OVER (ORDER BY order_month)) / 
        NULLIF(LAG(revenue, 1) OVER (ORDER BY order_month), 0), 2
    ) AS mom_growth_pct
FROM monthly_sales;

5.4 The Window Frame: ROWS vs RANGE

The frame clause dictates which subset of rows within the partition are included in the computation:

  • ROWS BETWEEN 2 PRECEDING AND CURRENT ROW: Physical count of rows.
  • RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW: Logical value offset based on duplicate values in the ORDER BY column. Warning: Default in SQL standard when ORDER BY is provided, often causing unexpected duplicate aggregations on ties!
-- 7-Day Moving Average of Daily Transaction Volume
SELECT 
    txn_date,
    daily_amount,
    AVG(daily_amount) OVER (
        ORDER BY txn_date
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ) AS moving_avg_7d,
    SUM(daily_amount) OVER (
        PARTITION BY DATE_TRUNC('year', txn_date)
        ORDER BY txn_date
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS ytd_running_total
FROM daily_revenue_ledger;

6. Real-World Production War Stories (RCA & Fixes)

🚨 Incident 1: 300GB Temporary Disk Spill via DISTINCT Masking a Cartesian Join

Environment: E-commerce financial reconciliation microservice running nightly against a PostgreSQL RDS cluster.

The Failure: The nightly ledger query, which normally finished in 45 seconds, began taking 4 hours and crashed with: ERROR: could not write to hash-join temporary file: No space left on device (300GB spilled).

Root Cause Analysis (RCA):

  • A junior engineer noticed duplicate order rows appearing in a report and added SELECT DISTINCT o.order_id, o.amount, p.status ... as a quick fix.
  • Underneath, the join was: FROM orders o LEFT JOIN order_items oi ON o.id = oi.order_id LEFT JOIN payments p ON o.id = p.order_id.
  • An order with 10 order items and 5 payment retry attempts produced $10 \times 5 = 50$ Cartesian product rows per order!
  • Across 5 million daily orders, the query generated 250 million rows. The DISTINCT clause attempted to deduplicate 250 million rows using an in-memory hash table, exhausted work_mem (64MB), and continuously spilled 300GB of intermediate runs to disk.

The Fix: Eliminate the Cartesian fanout by pre-aggregating payments and order items in separate CTEs or subqueries before joining:

WITH AggPayments AS (
    SELECT order_id, SUM(amount) AS total_paid
    FROM payments
    WHERE status = 'SUCCESS'
    GROUP BY order_id
),
AggItems AS (
    SELECT order_id, COUNT(*) AS item_count, SUM(price) AS items_total
    FROM order_items
    GROUP BY order_id
)
SELECT o.id, o.total_amount, p.total_paid, i.item_count
FROM orders o
LEFT JOIN AggPayments p ON o.id = p.order_id
LEFT JOIN AggItems i ON o.id = i.order_id; -- Perfect 1:1 join without DISTINCT!
🚨 Incident 2: 100% Database CPU Lockup via Correlated Scalar Subquery

Environment: Logistics tracking platform with 20 million shipment updates.

The Failure: Shipment search API latency degraded from 30ms to 45 seconds during morning dispatch, pushing database CPU to 100%.

Root Cause Analysis (RCA):

  • The API query retrieved the latest status for each shipment using a correlated subquery in the SELECT clause: 
    SELECT s.id, s.tracking_number,
    (SELECT status FROM shipment_events e 
     WHERE e.shipment_id = s.id 
     ORDER BY event_time DESC LIMIT 1) AS current_status
FROM shipments s WHERE s.created_at >= CURRENT_DATE;
  • For 50,000 shipments created that day, the database engine executed 50,000 individual index lookups and sort operations against shipment_events ($O(N \times \log M)$ overhead).

The Fix: Rewrite using a window function (ROW_NUMBER()) or PostgreSQL's DISTINCT ON to fetch all latest events in a single scan:

WITH RankedEvents AS (
    SELECT shipment_id, status,
           ROW_NUMBER() OVER (PARTITION BY shipment_id ORDER BY event_time DESC) as rn
    FROM shipment_events
)
SELECT s.id, s.tracking_number, e.status AS current_status
FROM shipments s
LEFT JOIN RankedEvents e ON s.id = e.shipment_id AND e.rn = 1
WHERE s.created_at >= CURRENT_DATE; -- Single pass hash join! CPU dropped from 100% to 4%.

7. Senior & Staff Engineer Interview Q&A

Q1: What is the fundamental execution and memory difference between UNION and UNION ALL?

Answer:

  • UNION ALL: An append-only operation. The database takes the row streams from both queries and streams them directly to the client without buffering or sorting. Execution complexity is $O(N + M)$ with $O(1)$ memory.
  • UNION: Implies mathematical set union with deduplication. The engine must buffer all rows into memory and execute either a Hash Aggregate (building an in-memory hash table of all projected fields) or a Sort Unique (external sort). Execution complexity is $O((N+M) \log(N+M))$. If the dataset exceeds available memory, it triggers severe disk I/O spills.
Q2: Why is SELECT COUNT(*) different from SELECT COUNT(column_name)?

Answer:

  • COUNT(*): Counts the total number of rows in the table or group. It does not inspect column values and does not care about NULLs. The database optimizer can satisfy COUNT(*) using the smallest available index (e.g. an integer primary key or narrow secondary index B-Tree).
  • COUNT(col): Counts only rows where col IS NOT NULL. The engine is forced to read the specific column data and evaluate each row for nullability.
Q3: How does the Cost-Based Optimizer (CBO) decide between a Nested Loop, Hash Join, and Merge Join?

Answer: The CBO calculates the estimated I/O and CPU cost of each strategy using table statistics (pg_statistic / histogram buckets):

  1. Nested Loop: Chosen when the driving (outer) table is very small (after WHERE filtering) and the inner table has an index on the join key. Cost $\approx C_{outer} + N_{outer} \times C_{inner\_lookup}$.
  2. Hash Join: Chosen for large tables where neither table is sorted and join condition is an equijoin (=). The smaller table is hashed into RAM, and the larger table probes the hash table. Cost $\approx C_{build\_hash} + C_{probe}$.
  3. Merge Join: Chosen when both inputs are already sorted on the join key (e.g. from an existing B-tree index or preceding ORDER BY) or when performing non-equijoins with inequalities. It scans both streams in lockstep without memory-intensive hashing.
Q4: What is the difference between ROW_NUMBER(), RANK(), and DENSE_RANK()?

Answer: Given values [100, 100, 80, 70]:

  • ROW_NUMBER(): Yields 1, 2, 3, 4 (arbitrary ordering for ties).
  • RANK(): Yields 1, 1, 3, 4 (ties share rank 1; rank 2 is skipped).
  • DENSE_RANK(): Yields 1, 1, 2, 3 (ties share rank 1; subsequent ranks are consecutive without gaps).
