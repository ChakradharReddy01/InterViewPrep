    SQL Masterclass: From SELECT to Window Functions

    A practical, interview-focused reference for writing correct SQL, understanding how clauses relate, avoiding common data bugs, and reasoning about query performance. Examples use broadly familiar SQL; functions such as date arithmetic, pagination, and string concatenation vary by database.

    1. Start with the right mental model

    SQL is declarative: describe the result you need, and the database optimizer chooses a physical execution plan. The order in which clauses are written is not the same as the logical order in which their results are formed.

    FROM / JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → OFFSET / FETCH / LIMIT

    This is a teaching model, not a promise about the engine's physical execution sequence. The optimizer may reorder operations while preserving query semantics.

    Why a SELECT alias often fails in WHERESELECT salary * 12 AS annual_salary FROM employees WHERE annual_salary > 100000; usually fails because WHERE is logically evaluated before the SELECT list creates that alias. Repeat the expression or put it in a derived table/CTE. ORDER BY annual_salary is commonly allowed.

    Example schema used throughout

    employees(
  employee_id INT PRIMARY KEY,
  employee_name VARCHAR(100),
  department_id INT,
  manager_id INT NULL,
  salary DECIMAL(12,2),
  status VARCHAR(20),
  hire_date DATE
)

departments(department_id INT PRIMARY KEY, department_name VARCHAR(100))
orders(order_id INT PRIMARY KEY, customer_id INT, order_date DATE,
       status VARCHAR(20), amount DECIMAL(12,2))
payments(payment_id INT PRIMARY KEY, order_id INT, amount DECIMAL(12,2), status VARCHAR(20))

    Assume the sample columns exist and contain realistic data. Add a stable unique tie-breaker to ORDER BY whenever deterministic ordering matters.

    2. SELECT — choose the columns and expressions

    SELECT defines the output projection: columns, expressions, calculations, aliases, and aggregate/window expressions. It does not itself guarantee row order.

    SELECT employee_id,
       employee_name,
       salary,
       salary * 12 AS annual_salary
FROM employees;

    Useful patterns

    • Explicit columns: prefer naming columns over SELECT * in application queries. It reduces accidental data exposure and avoids breaking clients when schemas change.
    • Aliases: use readable names, usually without spaces, such as annual_salary.
    • Expressions: arithmetic, string functions, date functions, and CASE can shape output.
    • NULL handling: use COALESCE(value, fallback) when a fallback is semantically correct. Do not turn unknown values into zero automatically unless that is the business rule.
    Backend practice Use parameterized SQL for user-supplied values (for example, JDBC PreparedStatement). Never concatenate untrusted input into SQL text.

    COUNT(*) versus COUNT(column)

    SELECT COUNT(*) AS all_rows,
       COUNT(manager_id) AS rows_with_manager
FROM employees;

    COUNT(*) counts rows; COUNT(manager_id) counts only rows where manager_id is not NULL. Aggregate behavior around NULL is a frequent interview topic.

    3. WHERE — filter individual rows

    WHERE keeps rows whose predicate evaluates to TRUE. FALSE and UNKNOWN (often caused by NULL) are both filtered out.

    SELECT employee_id, employee_name, salary
FROM employees
WHERE status = 'ACTIVE'
  AND salary >= 70000
  AND hire_date >= DATE '2024-01-01';

    Operators you should know

    OperatorPurposeExample
    INMatch any value in a list/subquerydepartment_id IN (10, 20)
    BETWEENInclusive rangesalary BETWEEN 50000 AND 80000
    LIKEPattern match; % many chars, _ one charemployee_name LIKE 'A%'
    IS NULLTest missing/unknown valuemanager_id IS NULL
    EXISTSTest whether a related row existsCovered in its own section
    NULL is not an ordinary valuecolumn = NULL and column != NULL do not work as intended. Use IS NULL / IS NOT NULL. SQL predicates can evaluate to TRUE, FALSE, or UNKNOWN.

    Index-aware filtering

    • A predicate like WHERE customer_id = ? can often use an index on customer_id.
    • Wrapping an indexed column in a function, such as WHERE LOWER(email) = ?, may prevent a normal index from being used unless a matching functional index or computed column exists.
    • A leading wildcard such as LIKE '%phone' commonly cannot use a standard B-tree index for a prefix seek.
    • Use correct date boundaries. For timestamps, a half-open range (created_at >= start AND created_at < next_start) is often safer than trying to include the last instant of a day.

    4. GROUP BY — aggregate rows into groups

    GROUP BY partitions input rows by the specified key(s) and produces one output row per group. Every selected expression must generally be grouped, aggregated, or accepted by the database through a functional-dependency rule.

    SELECT department_id,
       COUNT(*) AS employee_count,
       AVG(salary) AS average_salary,
       MAX(salary) AS highest_salary
FROM employees
WHERE status = 'ACTIVE'
GROUP BY department_id;

    Aggregate functions

    FunctionMeaningNULL behavior
    COUNT(*)Number of rowsCounts every row
    COUNT(expr)Number of non-NULL expression valuesSkips NULLs
    SUM(expr)TotalSkips NULLs; empty/all-NULL input often yields NULL
    AVG(expr)Arithmetic averageSkips NULLs
    MIN / MAXSmallest / largest non-NULL valueSkips NULLs

    Multiple grouping keys

    SELECT department_id, status, COUNT(*) AS employee_count
FROM employees
GROUP BY department_id, status;

    This yields a group for each distinct department/status combination. It does not mean “group by either column.”

    Join fan-out can corrupt aggregatesIf one order has 3 order-item rows and 2 payment-attempt rows, joining both child tables directly can produce 3 × 2 = 6 rows for that order. Summing item and payment amounts after the join may overcount. Aggregate each child to one row per order first, then join the aggregates.

    5. HAVING — filter groups after aggregation

    HAVING filters groups after grouping/aggregation. Use WHERE for row-level filters and HAVING for aggregate conditions.

    SELECT department_id, AVG(salary) AS avg_salary
FROM employees
WHERE status = 'ACTIVE'          -- filter rows first
GROUP BY department_id
HAVING AVG(salary) > 80000        -- filter completed groups
ORDER BY avg_salary DESC;

    WHERE

    • Evaluated before grouping in the logical model.
    • Filters individual records.
    • Can reduce rows entering aggregation.

    HAVING

    • Evaluated after groups are formed.
    • Filters aggregate results/groups.
    • Can use expressions like COUNT(*) and AVG(salary).

    Common trap: using HAVING status = 'ACTIVE' when status is a row-level condition and grouping only by department is invalid or ambiguous in many databases. Filter it in WHERE.

    6. ORDER BY — define result order

    Relational tables have no guaranteed order unless the query specifies ORDER BY. Use ASC (default in many systems) or DESC.

    SELECT employee_id, employee_name, salary
FROM employees
ORDER BY salary DESC, employee_id ASC;
    • Multiple keys break ties: salary descending, then employee ID ascending.
    • NULL sort position differs across database systems; use explicit syntax when portability or business meaning matters.
    • Pagination without a deterministic order can duplicate or skip records across requests.
    • Large OFFSET values can be expensive because the engine may still scan/discard earlier rows. Keyset pagination can be better for deep pages.
    -- Keyset pagination example: next page after the last seen (salary, employee_id)
SELECT employee_id, employee_name, salary
FROM employees
WHERE salary < :last_salary
   OR (salary = :last_salary AND employee_id > :last_employee_id)
ORDER BY salary DESC, employee_id ASC
FETCH FIRST 20 ROWS ONLY;

    The exact parameter syntax and row-limit clause depend on the database. Ensure the continuation predicate exactly matches the sort direction and tie-breaker.

    7. DISTINCT — remove duplicate output rows

    DISTINCT deduplicates the selected row shape, not an arbitrary single column unless only that column is selected.

    SELECT DISTINCT department_id
FROM employees;

-- Distinct pairs, not distinct employee IDs:
SELECT DISTINCT department_id, status
FROM employees;

    Deduplication may require hashing or sorting and can consume memory or spill to disk for large inputs. The exact plan is engine-dependent.

    Do not use DISTINCT to hide a bad joinIf a query returns duplicates because two one-to-many relationships multiply rows, adding DISTINCT may increase work while hiding the data-model issue. First inspect join cardinality and the intended grain (one row per what?). Pre-aggregate child tables or use EXISTS when only existence matters.

    8. CASE — conditional expressions

    CASE returns a value; it is not a control-flow statement that changes the query's overall structure. The first matching branch is chosen.

    SELECT employee_id,
       salary,
       CASE
         WHEN salary >= 120000 THEN 'HIGH'
         WHEN salary >= 80000  THEN 'MID'
         WHEN salary IS NULL   THEN 'UNKNOWN'
         ELSE 'STANDARD'
       END AS salary_band
FROM employees;

    Simple versus searched CASE

    -- Simple CASE: equality comparisons against one expression
CASE status
  WHEN 'PAID' THEN 'Closed'
  WHEN 'PENDING' THEN 'In progress'
  ELSE 'Other'
END

-- Searched CASE: independent Boolean predicates
CASE
  WHEN amount >= 1000 AND status = 'PAID' THEN 'Large paid order'
  WHEN status = 'PAID' THEN 'Paid order'
  ELSE 'Not paid'
END

    Conditional aggregation

    SELECT customer_id,
       COUNT(*) AS total_orders,
       SUM(CASE WHEN status = 'COMPLETED' THEN amount ELSE 0 END) AS completed_amount,
       SUM(CASE WHEN status = 'REFUNDED' THEN amount ELSE 0 END) AS refunded_amount,
       SUM(CASE WHEN status = 'FAILED' THEN 1 ELSE 0 END) AS failed_orders
FROM orders
GROUP BY customer_id;

    Conditional aggregation is useful for dashboards, financial summaries, and pivot-like reports. Keep output types compatible across branches and explicitly consider NULL behavior.

    9. JOIN — combine related tables

    A join combines rows based on a predicate. Before writing a join, identify the expected output grain and cardinality: one-to-one, one-to-many, or many-to-many.

    JoinResultTypical use
    INNER JOINOnly matching row pairsOrders with an existing customer
    LEFT JOINEvery left row; unmatched right columns become NULLAll customers, including those with no orders
    RIGHT JOINEvery right row; unmatched left columns become NULLOften rewritten as LEFT JOIN for readability
    FULL OUTER JOINAll rows from both sides, matched where possibleReconciliation between two systems
    CROSS JOINEvery left/right combinationIntentional combinations; beware M × N rows
    Self joinA table joined to itselfEmployee-to-manager relationships
    -- INNER JOIN: only orders with matching customers
SELECT o.order_id, o.order_date, c.customer_name
FROM orders o
INNER JOIN customers c ON c.customer_id = o.customer_id;

-- LEFT JOIN: keep every customer, even with no orders
SELECT c.customer_id, c.customer_name, o.order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id;

    The LEFT JOIN + WHERE trap

    -- Often unintentionally behaves like an INNER JOIN:
SELECT c.customer_id, o.order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.status = 'COMPLETED';

-- Keep customers without completed orders:
SELECT c.customer_id, o.order_id
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.customer_id
 AND o.status = 'COMPLETED';

    The first query filters out NULL-extended rows because o.status = 'COMPLETED' is UNKNOWN when no order exists. Put a right-side matching restriction in ON when unmatched left rows must remain.

    Join algorithm intuition

    • Nested-loop join: iterate one input and look up matches in the other; effective for small outer inputs and indexed lookups.
    • Hash join: build a hash table from one input and probe it with the other; often useful for large equijoins.
    • Merge join: walk sorted inputs in key order; useful when inputs are already sorted or sorting is worthwhile.

    These are physical plan strategies selected by the optimizer, not SQL syntax you normally choose directly. Check the actual execution plan and table statistics before assuming a specific algorithm.

    Prevent accidental row multiplication

    -- Safer pattern: aggregate each one-to-many child to one row per order
WITH payment_totals AS (
  SELECT order_id, SUM(amount) AS paid_total
  FROM payments
  WHERE status = 'SUCCESS'
  GROUP BY order_id
)
SELECT o.order_id, o.amount, p.paid_total
FROM orders o
LEFT JOIN payment_totals p ON p.order_id = o.order_id;

    10. Subqueries — query inside a query

    A subquery may appear in SELECT, FROM, or a predicate. Its type depends on what it returns and whether it references the outer query.

    TypeWhat it returnsExample use
    ScalarOne value (one row, one column)Compare salary with company average
    Single/multi-rowOne or more valuesIN, ANY, ALL
    Derived tableRows used as a table in FROMAggregate then join
    CorrelatedReferences outer-query columnsPer-customer existence or comparison
    -- Scalar subquery
SELECT employee_id, employee_name, salary
FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);

-- IN subquery
SELECT employee_id, employee_name
FROM employees
WHERE department_id IN (
  SELECT department_id FROM departments
  WHERE department_name IN ('Engineering', 'Data')
);

-- Derived table
SELECT d.department_id, d.avg_salary
FROM (
  SELECT department_id, AVG(salary) AS avg_salary
  FROM employees
  GROUP BY department_id
) d
WHERE d.avg_salary > 80000;

    Correlated subquery

    SELECT e.employee_id, e.employee_name
FROM employees e
WHERE e.salary > (
  SELECT AVG(e2.salary)
  FROM employees e2
  WHERE e2.department_id = e.department_id
);

    The inner query refers to e.department_id. The optimizer may decorrelate or transform it; do not assume it literally performs a full independent scan for every outer row. Validate with the execution plan and representative data volumes.

    11. CTE — Common Table Expressions

    A CTE gives a named result to a query using WITH. It helps structure multi-step logic, reuse a query expression within a statement, and express recursion. CTEs are primarily a readability and composition tool; they are not guaranteed to be materialized or faster.

    WITH department_stats AS (
  SELECT department_id, AVG(salary) AS avg_salary, COUNT(*) AS headcount
  FROM employees
  WHERE status = 'ACTIVE'
  GROUP BY department_id
)
SELECT department_id, avg_salary, headcount
FROM department_stats
WHERE avg_salary > 80000
ORDER BY avg_salary DESC;

    Multiple CTEs for clear stages

    WITH successful_payments AS (
  SELECT order_id, SUM(amount) AS paid_amount
  FROM payments
  WHERE status = 'SUCCESS'
  GROUP BY order_id
),
order_reconciliation AS (
  SELECT o.order_id, o.amount AS order_amount,
         COALESCE(p.paid_amount, 0) AS paid_amount
  FROM orders o
  LEFT JOIN successful_payments p ON p.order_id = o.order_id
)
SELECT *,
       order_amount - paid_amount AS outstanding_amount
FROM order_reconciliation
WHERE order_amount <> paid_amount;

    Recursive CTE

    -- PostgreSQL-style syntax; recursive CTE support/syntax varies by database.
WITH RECURSIVE org_chart AS (
  -- Anchor: top-level employees
  SELECT employee_id, employee_name, manager_id, 1 AS depth
  FROM employees
  WHERE manager_id IS NULL

  UNION ALL

  -- Recursive member: direct reports of rows already found
  SELECT e.employee_id, e.employee_name, e.manager_id, o.depth + 1
  FROM employees e
  JOIN org_chart o ON e.manager_id = o.employee_id
)
SELECT employee_id, employee_name, manager_id, depth
FROM org_chart
ORDER BY depth, employee_id;
    Recursive query safety A cycle in hierarchy data can make recursion repeat indefinitely unless the database has a recursion limit or the query explicitly detects cycles. Production code should define a termination condition and understand the vendor's recursion safeguards.

    12. UNION and UNION ALL

    Set operators combine compatible result sets vertically. Each branch must return the same number of columns in compatible types; column names typically come from the first query.

    SELECT email FROM active_customers
UNION
SELECT email FROM archived_customers;

SELECT email FROM active_customers
UNION ALL
SELECT email FROM archived_customers;

    UNION

    Combines results and removes duplicate rows across the combined result. Deduplication can require sorting or hashing and additional memory/work.

    UNION ALL

    Combines results without removing duplicates. Usually less work and preserves duplicates from each input and across inputs.

    Use UNION ALL when duplicates are meaningful or impossible by design. Use UNION only when duplicate elimination is part of the requirement—not as a generic fix for a faulty join.

    -- ORDER BY generally applies to the combined result and goes at the end
SELECT employee_id AS id, employee_name AS display_name FROM employees
UNION ALL
SELECT contractor_id, contractor_name FROM contractors
ORDER BY display_name;

    13. EXISTS — test whether matching rows exist

    EXISTS is TRUE if its subquery returns at least one row. The projected expression is irrelevant to existence, so SELECT 1 is a conventional style.

    -- Customers with at least one order
SELECT c.customer_id, c.customer_name
FROM customers c
WHERE EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.customer_id = c.customer_id
);

-- Customers with no orders
SELECT c.customer_id, c.customer_name
FROM customers c
WHERE NOT EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.customer_id = c.customer_id
);

    Databases often transform EXISTS into a semi-join and NOT EXISTS into an anti-semi-join. This is a useful mental model, not a guarantee of a specific physical plan.

    NOT IN and NULL

    -- Risky if the subquery can return NULL
SELECT a.id
FROM table_a a
WHERE a.id NOT IN (SELECT b.id FROM table_b b);

-- Usually safer for "there is no matching row"
SELECT a.id
FROM table_a a
WHERE NOT EXISTS (
  SELECT 1 FROM table_b b WHERE b.id = a.id
);
    NULL trapIf the NOT IN subquery contains a NULL, comparisons can become UNKNOWN and unexpectedly reject every otherwise-unmatched row. NOT EXISTS avoids that particular trap. If outer IDs may themselves be NULL, define explicitly whether those rows should be included.

    14. Window functions — calculate across related rows without collapsing them

    A window function computes a value over a set of rows related to the current row. Unlike GROUP BY, it keeps the detail rows in the result.

    FUNCTION(expression) OVER (
  [PARTITION BY grouping_columns]
  [ORDER BY ordering_columns]
  [ROWS | RANGE frame_clause]
)
    • PARTITION BY divides rows into independent groups for the function.
    • ORDER BY defines order within a partition for ranking, navigation, and running calculations.
    • The frame defines which rows around/up to the current row contribute to frame-sensitive functions.

    GROUP BY versus window function

    -- One row per department
SELECT department_id, AVG(salary) AS dept_avg
FROM employees
GROUP BY department_id;

-- Every employee row plus its department average
SELECT employee_id, department_id, salary,
       AVG(salary) OVER (PARTITION BY department_id) AS dept_avg
FROM employees;

    Ranking: ROW_NUMBER, RANK, DENSE_RANK

    SalaryROW_NUMBERRANKDENSE_RANK
    100111
    100211
    80332
    70443
    • ROW_NUMBER() assigns a unique sequence number. Add a tie-breaker if the exact row order matters.
    • RANK() gives ties the same rank and leaves gaps after ties.
    • DENSE_RANK() gives ties the same rank without gaps.
    -- Top 3 distinct salary levels per department (ties included)
WITH ranked AS (
  SELECT employee_id, department_id, salary,
         DENSE_RANK() OVER (
           PARTITION BY department_id
           ORDER BY salary DESC
         ) AS salary_rank
  FROM employees
)
SELECT employee_id, department_id, salary, salary_rank
FROM ranked
WHERE salary_rank <= 3
ORDER BY department_id, salary_rank, employee_id;

    For exactly up to three employees per department, use ROW_NUMBER() and a deterministic tie-breaker. For the top three salary ranks with ties, use DENSE_RANK() or RANK() according to the desired gap semantics.

    LAG and LEAD

    SELECT order_month, revenue,
       LAG(revenue) OVER (ORDER BY order_month) AS previous_month_revenue,
       LEAD(revenue) OVER (ORDER BY order_month) AS next_month_revenue
FROM monthly_sales;

    LAG reads a preceding row and LEAD a following row in the window order. They are useful for month-over-month comparisons, change detection, and event sequences. They do not automatically create missing calendar dates.

    Running totals and moving averages

    SELECT txn_date, daily_amount,
       SUM(daily_amount) OVER (
         ORDER BY txn_date
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total,
       AVG(daily_amount) OVER (
         ORDER BY txn_date
         ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
       ) AS trailing_7_rows_avg
FROM daily_revenue;
    ROWS is not necessarily seven calendar daysROWS BETWEEN 6 PRECEDING AND CURRENT ROW means seven rows when available. If some dates are missing, that is not necessarily a seven-calendar-day window. Join to a calendar/date spine first if the business definition requires calendar days.

    ROWS versus RANGE

    FrameMeaningWatch out for
    ROWSPhysical row positions relative to the current rowOrdering ties can be nondeterministic unless ordering is unique
    RANGELogical range of ordering values; peers with equal sort values may be included togetherDefault frames differ by function/database; ties can change running results

    For a predictable row-by-row running total, specify the frame and a unique ordering key where appropriate.

    Window-function execution gotcha

    In many SQL dialects, window functions are not allowed directly in WHERE because they are computed later in the logical query model. Use a CTE or derived table to rank first, then filter the rank in the outer query.

    15. High-value interview query patterns

    Second-highest distinct salary

    SELECT MAX(salary) AS second_highest_salary
FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);

    This returns NULL if there is no second distinct non-NULL salary. To return employee rows at the second-highest salary level, use DENSE_RANK().

    Find duplicate email values

    SELECT email, COUNT(*) AS occurrences
FROM users
GROUP BY email
HAVING COUNT(*) > 1;

    Latest event per entity

    WITH ranked_events AS (
  SELECT event_id, entity_id, event_time, status,
         ROW_NUMBER() OVER (
           PARTITION BY entity_id
           ORDER BY event_time DESC, event_id DESC
         ) AS rn
  FROM events
)
SELECT event_id, entity_id, event_time, status
FROM ranked_events
WHERE rn = 1;

    Adding event_id DESC resolves ties when multiple events share a timestamp. If there is no unique tie-breaker, “latest” may not be deterministic.

    Customers who have never ordered

    SELECT c.customer_id, c.customer_name
FROM customers c
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id
);

    Conditional counts without separate queries

    SELECT department_id,
       SUM(CASE WHEN status = 'ACTIVE' THEN 1 ELSE 0 END) AS active_count,
       SUM(CASE WHEN status = 'INACTIVE' THEN 1 ELSE 0 END) AS inactive_count
FROM employees
GROUP BY department_id;

    16. Production performance and debugging checklist

    1. Check correctness first: define one output row per what? Confirm join cardinality and NULL behavior before tuning.
    2. Inspect the execution plan: use EXPLAIN and, where safe, the database's actual-plan facility. Estimated versus actual row counts can expose bad statistics or cardinality assumptions.
    3. Filter early when semantically valid: row-level predicates belong in WHERE; this may reduce work before aggregation.
    4. Index for access patterns: consider join keys, selective filters, and ordering together. Composite index column order matters; avoid adding indexes blindly because writes and storage also cost more.
    5. Avoid unnecessary deduplication: DISTINCT and UNION can require extra sorting/hashing. Fix fan-out at the source.
    6. Watch correlated work: correlated subqueries can be excellent or expensive depending on indexes, optimizer rewrites, and outer-row count. Measure instead of assuming.
    7. Limit result size intentionally: do not fetch thousands of unused columns/rows into a Java service. Use pagination and select only needed columns.
    8. Parameterize application queries: improves safety against SQL injection and can support plan reuse depending on driver/database.
    9. Validate with realistic data: small development tables can hide expensive scans, skew, sort spills, and poor estimates.
    10. Observe runtime behavior: track latency percentiles, rows read/returned, lock waits, temp-file spills, CPU, and connection-pool pressure.
    Common production incident: duplicate financial totals A report joins orders, order_items, and payments; multiple items and multiple payment attempts multiply each other. SUM(order.amount) becomes inflated. Reproduce with a tiny dataset, calculate expected cardinalities, aggregate each child independently, and compare row counts before/after each join. Never trust a plausible-looking total without checking the grain.

    17. Interview Q&A — concise answers with reasoning

    Q1. WHERE vs HAVING?

    WHERE filters input rows before grouping; HAVING filters groups after aggregation. Put row-level predicates in WHERE when semantics permit.

    Q2. GROUP BY vs window functions?

    GROUP BY collapses rows to one row per group. Window functions calculate over a related set while retaining individual rows.

    Q3. UNION vs UNION ALL?

    UNION removes duplicates across the combined result and may require extra work; UNION ALL keeps duplicates and is generally cheaper.

    Q4. Why can LEFT JOIN behave like INNER JOIN?

    A WHERE predicate on the nullable right side rejects NULL-extended rows. Move the right-side match restriction into ON when unmatched left rows must remain.

    Q5. Why is NOT IN dangerous with NULL?

    A NULL in the subquery can make the comparison UNKNOWN, so rows are unexpectedly excluded. NOT EXISTS is often safer for anti-matching.

    Q6. Are CTEs always materialized?

    No. Behavior depends on the database and query. The optimizer may inline, materialize, or otherwise transform them.

    Q7. Is a correlated subquery always slow?

    No. Optimizers can decorrelate it, and indexed lookups can be efficient. Check plans and real row counts.

    Q8. ROW_NUMBER vs RANK vs DENSE_RANK?

    ROW_NUMBER gives unique sequence numbers; RANK shares ranks for ties and leaves gaps; DENSE_RANK shares ranks without gaps.

    Q9. Why is SELECT DISTINCT not a reliable join fix?

    It may hide a many-to-many fan-out and adds deduplication cost. Fix the join or aggregate each child relation to the intended grain.

    Q10. Does ORDER BY guarantee stable pagination?

    Only when ordering is deterministic, typically with a unique tie-breaker. Without it, rows with equal sort keys can shift between pages.

    Q11. Can window functions be filtered in WHERE?

    Usually not at the same query level. Compute the window value in a CTE/derived table, then filter in the outer query.

    Q12. Does an index always make a query faster?

    No. Low-selectivity predicates, small tables, write overhead, storage, and optimizer cost estimates matter. Measure the plan.
