1. Monolith

Definition

A monolithic application is built and deployed as one application unit. It can still contain well-separated modules; “monolith” describes the deployment/runtime unit, not necessarily poor code organization.

WEB / MOBILE CLIENT | v +-----------------------------+ | E-COMMERCE APPLICATION | |-----------------------------| | Order Module | | Payment Module | | Inventory Module | | Customer Module | +-----------------------------+ | v SHARED DATABASE One application deployment (JAR/WAR)

How it works in Java

@Service
public class OrderService {
    private final InventoryService inventory;
    private final PaymentService payment;
    private final OrderRepository orders;

    public OrderService(InventoryService inventory,
                        PaymentService payment,
                        OrderRepository orders) {
        this.inventory = inventory;
        this.payment = payment;
        this.orders = orders;
    }

    @Transactional
    public Order placeOrder(OrderRequest request) {
        inventory.reserve(request);
        payment.charge(request);
        return orders.save(Order.from(request));
    }
}

These calls may be in-process method calls. Database changes can share a local transaction if they use the same transaction manager and resource. A database rollback does not automatically reverse an external payment-provider charge.

Advantages

  • Simple development, deployment, debugging, and local testing.
  • Low-overhead in-process calls.
  • Local database transactions can be straightforward.
  • Fewer runtime infrastructure components.
  • Often ideal for an early product or a small team.

Disadvantages

  • Releasing one capability may require deploying the whole application.
  • Scaling one high-load module can mean scaling all modules.
  • Poor internal boundaries cause tight coupling.
  • A process-wide memory leak or resource exhaustion can affect all capabilities.
  • Build and test times may grow with the codebase.
Practical example: if recommendations need 10 times more CPU than checkout, scaling the entire monolith wastes resources. A modular monolith can still be the right choice until independent scaling or deployment is worth the added distributed complexity.

When to choose it

Choose a monolith when the domain and team are small, release coordination is manageable, and a distributed architecture would add more operational cost than value. Keep modules cohesive and enforce dependency rules so future extraction remains possible.

2. Microservices

Definition

Microservices architecture organizes a system as independently deployable services, each responsible for a cohesive business capability and exposing explicit contracts.

Clients | v API GATEWAY |-------------------|------------------| v v v Order Service Payment Service Inventory Service | | | Order DB Payment DB Inventory DB | +---- events / API calls / workflows ----+

Core characteristics

  • Business-oriented: boundaries follow capabilities, not just technical layers.
  • Independent deployment: services can release independently when contracts remain compatible.
  • Data ownership: each service controls its persistence model and invariants.
  • Explicit communication: HTTP, gRPC, or messaging crosses process boundaries.
  • Independent scaling: scale a service according to its own demand.
  • Failure isolation: possible only with appropriate timeouts, resource limits, and recovery design.
DimensionMonolithMicroservices
CallsOften in-processOften network-based
DeploymentUsually one unitMultiple units
TransactionsOften simpler within one DBLocal transactions plus distributed coordination
ScalingOften whole applicationPer service
OperationsFewer componentsDiscovery, security, tracing, deployment, and reliability controls

Challenges and when to choose

Microservices add network latency, partial failure, contract versioning, distributed data consistency, and operational overhead. They fit organizations with independently evolving capabilities, distinct scaling profiles, autonomous teams, and mature delivery/monitoring practices. Do not split an application merely because the architecture is fashionable.

3. Service Boundaries

Definition

A service boundary defines which business responsibilities, data, invariants, and decisions belong to a service and which interactions must cross a contract.

Bad: technical-layer split

UI Service | Business Service | Database Service

A simple request may need many network hops, and business behavior is scattered.

Better: business capabilities

Order Service Payment Service Inventory Service Shipping Service

Each service owns cohesive rules and data for its business capability.

How to identify boundaries

  • Does the capability have distinct business rules and invariants?
  • Does it change for different reasons from neighboring capabilities?
  • Can it own a meaningful data model?
  • Does it need a different scaling, security, or availability profile?
  • Can a team develop and deploy it without constant coordination?
  • Will separation reduce coupling more than it increases network coordination?

Common mistakes

  • Too large: one “business service” owns orders, inventory, billing, shipping, and notifications.
  • Too small: every table or CRUD entity becomes a service.
  • Shared rules: different services independently implement pricing or tax logic and diverge.
  • Excessive synchronous calls: requests wait through a long chain of dependencies.
Rule: optimize for business cohesion, data ownership, and manageable interactions—not for the number of services.

4. Bounded Context

Definition (Domain-Driven Design)

A bounded context is an explicit boundary within which a domain model and its terminology have a consistent meaning. A concept such as “Customer” can mean different things in different business contexts.

Identity Context

Customer

User ID, credentials, MFA settings

Billing Context

Customer

Billing account, tax details, payment provider ID

Shipping Context

Customer

Recipient, delivery address, delivery instructions

Ubiquitous language

Developers, product owners, and domain experts use terms consistently inside the context. In payments, “authorize,” “capture,” and “refund” have precise meanings. Another context may use the same word differently; the context makes the intended meaning clear.

Relationship to microservices

A bounded context is a domain-model boundary; a microservice is a deployment/runtime boundary. They often align, but are not identical. A context can live in a modular monolith, and a poorly designed service can contain several tangled contexts.

Interview point: DDD informs service decomposition; it does not mean “one service per database table” or mechanically “one service per entity.”

5. API Gateway

Definition and purpose

An API Gateway is an entry point that receives external requests and routes them to backend services. It prevents clients from needing to know every internal service address and can centralize edge concerns.

Web / Mobile / Partner Clients | v +------------------------------------------+ | API GATEWAY | | Routing | TLS | Auth policies | Limits | | Correlation context | Request controls | +-------------------+----------------------+ | +---------+----------+ v v v Orders Payments Catalog

Responsibilities

  • Route by path, host, or configured predicates.
  • Terminate TLS and manage certificates.
  • Validate tokens and enforce edge authorization policies.
  • Apply rate limits, request-size limits, and selected traffic controls.
  • Propagate trace context and correlation IDs.
  • Log request metadata and publish metrics.
  • Optionally aggregate or transform responses where justified.

Spring Cloud Gateway example

spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: http://order-service:8081
          predicates:
            - Path=/api/orders/**
        - id: catalog-service
          uri: http://catalog-service:8082
          predicates:
            - Path=/api/products/**

This shows static destinations. A production deployment may use service-discovery-aware route URIs supported by its Spring Cloud configuration.

BFF (Backend for Frontend)

A Backend for Frontend is a client-specific backend or gateway: for example, a mobile BFF can return compact payloads, while a web BFF aggregates data for a rich page. A BFF is useful when client needs genuinely differ, not mandatory for every system.

Pitfalls: putting all business logic in the gateway, trusting arbitrary client identity headers, allowing unbounded request bodies, or assuming the gateway replaces authorization checks inside sensitive services.

6. Service Discovery

Problem

Instances can restart, scale, move, or receive new IP addresses. Hardcoded instance addresses become stale. Service discovery provides a way to locate eligible service instances dynamically.

Client-side discovery

Caller | query registry v Registry → instance list | Client-side load balancer | Chosen instance

The caller obtains instance addresses and selects one using a load-balancing strategy.

Server-side discovery

Caller | Stable service DNS name | Proxy / platform routing | Healthy endpoint

A platform or proxy resolves the service name and routes to an eligible endpoint.

Concepts to distinguish

  • Registration: an instance declares its presence.
  • Heartbeat/lease: indicates continuing participation.
  • Readiness: indicates whether the instance should receive traffic.
  • Load balancing: selects among eligible instances.
  • Deregistration: removes an instance from service.

Registration is not proof that an instance is ready. Discovery, health checks, endpoint propagation, and load balancing must work together.

When to use which

Eureka is common in Spring Cloud systems using client-side discovery. Kubernetes offers DNS-based service naming and endpoint management inside the cluster. Choose based on deployment platform, existing infrastructure, and operational requirements.

7. Eureka

Definition

Netflix Eureka is a service registry. Spring Cloud Netflix integrates Eureka with Spring Boot applications for registration and discovery.

+------------------+ | Eureka Server | | Service Registry | +--------+---------+ ^ register / heartbeat / \\ v v Order Service Payment Service | discovery-aware client | selected service instance

Minimal server setup

@SpringBootApplication
@EnableEurekaServer
public class DiscoveryApplication {
    public static void main(String[] args) {
        SpringApplication.run(
            DiscoveryApplication.class, args
        );
    }
}

Client configuration example

spring:
  application:
    name: order-service
  cloud:
    discovery:
      enabled: true

eureka:
  client:
    service-url:
      defaultZone: http://localhost:8761/eureka/

The appropriate Eureka client dependency must be included. The server commonly uses port 8761, but this is configurable. Align Spring Boot and Spring Cloud versions using a compatible release train.

Heartbeats and self-preservation

Clients periodically renew leases. When renewals stop, the registry may eventually evict an instance. Eureka self-preservation can reduce mass eviction when heartbeat traffic unexpectedly drops, because the cause might be a network partition rather than mass instance failure. This can also leave stale entries temporarily registered.

Eureka vs Kubernetes DNS

EurekaKubernetes service discovery
Registry used by discovery-aware clientsStable service names with cluster networking and endpoint management
Needs registry operation and client integrationUses Kubernetes DNS, Services, and endpoint routing
Registry and client cache behavior matterReadiness probes and endpoint propagation still matter
Production note: do not assume a registered Eureka instance is healthy or that Kubernetes DNS alone guarantees application readiness. Use appropriate probes, timeouts, and connection-failure handling.

8. Config Server

Definition

Spring Cloud Config Server centralizes externalized configuration so applications can obtain settings by application name, profile, and label/version. A Git repository is a common backend.

Git Configuration Repository application.yml / order-service.yml | v Spring Cloud Config Server / \\ v v Order Service Payment Service

Typical client setup

spring:
  application:
    name: order-service
  config:
    import: optional:configserver:http://localhost:8888

This style is used by modern Spring Boot / Spring Cloud Config setups. Exact configuration depends on the compatible version train.

Dynamic refresh

Spring Cloud supports refresh mechanisms, including @RefreshScope for supported beans, refresh endpoints, and Spring Cloud Bus for broadcasting refresh events through a supported message broker. Centralized configuration does not mean every property updates live automatically; some properties require bean recreation or a restart.

Security and production

  • Do not commit plaintext credentials or private keys to an exposed repository.
  • Protect Config Server with authentication, TLS, and network controls.
  • Use an appropriate secrets manager for sensitive values.
  • Version, review, and roll back configuration changes.
  • Plan startup behavior when Config Server is unavailable.
  • Roll out risky changes gradually and monitor their effects.

9. Database per Service

Definition

Each service owns its data and persistence rules. Other services access that data through published APIs, events, or intentionally maintained projections—not direct access to the owning service's private tables.

Order Service

Orders and order state

PostgreSQL

Catalog Service

Products and descriptions

PostgreSQL / MongoDB

Payment Service

Payment attempts and statuses

PostgreSQL

Session Service

Session/cache data

Redis

Example: reading product data for an order

The Order Service can call the Catalog API, consume catalog events into a local read projection, or save a purchase-time product snapshot. Saving the purchase-time unit price is often essential: changing the catalog price later must not rewrite the historical order amount.

Advantages

  • Independent schema evolution and access control.
  • Clear business-data ownership.
  • Service-specific scaling and persistence technology.
  • Reduced cross-team coupling.

Challenges

  • Cross-service joins are no longer ordinary local SQL joins.
  • Cross-service reports may need a warehouse or read model.
  • Distributed workflows may need a Saga.
  • Copied data requires synchronization, versioning, and reconciliation.
  • Backups and migrations become multi-store operational tasks.
Important distinction: database per service means independent ownership and access boundaries, not necessarily a separate physical database server for every service.

10. Shared Database

Definition

A shared database architecture lets multiple services read or modify the same database or private business tables.

Order Service ------\\ +---- Shared PostgreSQL Payment Service ----/ Inventory Service --/

Why it can be risky

  • One service cannot safely change a schema without coordinating with other consumers.
  • Services can bypass the owning service's business validations.
  • Database permissions and ownership become unclear.
  • A heavy query from one service can affect others.
  • Independent deployments become harder.

Is sharing physical infrastructure always wrong?

No. Multiple services may use the same database cluster while having separate schemas/databases, restricted credentials, and clear data ownership. The main risk is shared ownership of private business tables and direct cross-service writes.

During migration, a shared database may be a practical stepping stone. Over time, reduce cross-service table access and move toward API/event-based integration where justified.

11. Saga Pattern

Definition

A Saga coordinates a business workflow as a sequence of local transactions. If a later step fails, compensating transactions counteract earlier business actions where possible. It is a strategy for multi-service workflows, not a single atomic ACID transaction.

Successful checkout

T1: Create Pending Order | v T2: Reserve Inventory | v T3: Authorize Payment | v T4: Confirm Order

Payment failure and compensation

Create order SUCCESS Reserve inventory SUCCESS Authorize payment FAILURE | v Release reservation Cancel / mark order failed | v Persist final Saga state

A compensation is a new business operation, not a database rollback across services. A captured payment may require a refund; it cannot necessarily be erased from payment history.

Choreography vs orchestration

AspectChoreographyOrchestration
CoordinationServices react to domain eventsExplicit coordinator sends commands and tracks state
Good fitShort, straightforward workflowsComplex or long-running workflows
StrengthLooser central couplingWorkflow visibility and explicit recovery logic
RiskHard-to-follow event chains and cyclesCoordinator complexity and over-centralized business logic

Production requirements

  • Durable workflow state and recoverable transitions.
  • Idempotent commands and consumers.
  • Timeouts, bounded retries, and late-event handling.
  • Explicit compensation rules.
  • Monitoring, reconciliation, and manual recovery for exceptional failures.
Do not assume compensation always succeeds. Persist failed compensations, retry safely, alert operators, and provide a repair workflow.

12. CQRS — Command Query Responsibility Segregation

Definition

CQRS separates the model that changes state from the model used to read state. It does not inherently require two databases, microservices, or Event Sourcing.

Write / command side

Command | Validate invariants | Write model | Local transaction

Read / query side

Query | Read model / projection | Optimized response

Example

An order-management system can update a normalized relational model while serving order history from a denormalized read model containing customer name, order status, item summaries, and totals.

Benefits

  • Independent read/write optimization and scaling.
  • Simpler queries for complex screens.
  • Clear separation of commands and queries.

Challenges

  • Duplicate representations and synchronization logic.
  • Eventual consistency if projections update asynchronously.
  • Additional infrastructure and rebuild procedures.
  • More complexity than ordinary CRUD for simple domains.
Interview distinction: CQRS is about separate command/query models; separate HTTP GET and POST endpoints alone do not establish a meaningful CQRS architecture.

13. Event Sourcing

Definition

Event Sourcing stores the sequence of meaningful state-changing events as the authoritative history, instead of storing only the latest state.

OrderCreated → initial order ItemAdded → revised contents PaymentAuthorized → payment authorized OrderShipped → shipping state updated | v Replay events / use snapshot | v Reconstructed current state

Worked example

AccountOpened(1000)
MoneyDeposited(500)
MoneyWithdrawn(200)

// Reconstructed balance = 1000 + 500 - 200 = 1300

Events should represent immutable facts. Correcting state generally means appending another event, rather than silently rewriting history. Snapshots and projections avoid replaying the full stream for every query.

Benefits

  • Detailed business history and audit trail.
  • Ability to rebuild projections.
  • Temporal analysis of business decisions.
  • Explicit record of how state changed.

Challenges

  • Event schema evolution and versioning.
  • Replay performance and snapshot management.
  • Duplicate/out-of-order event handling.
  • Privacy, retention, and deletion requirements.
  • Operational complexity and eventual consistency of projections.

CQRS vs Event Sourcing

CQRSEvent Sourcing
Separates write and read models.Stores state changes as an event history.
Can use ordinary database tables.Uses an event store or durable event stream as source of truth.
Does not require event history.Can be combined with CQRS, but they are distinct concepts.

14. Strangler Fig Pattern

Definition

The Strangler Fig pattern incrementally replaces selected legacy capabilities while the existing monolith continues to serve the remaining functionality. It avoids a risky all-at-once rewrite.

Client Traffic | v +----------------------+ | Gateway / Router | +----------+-----------+ | +------+------+ | | v v Legacy Monolith New Service remaining paths migrated paths | | +------ gradual migration | retire old path

Migration steps

  1. Identify a capability with a clear boundary.
  2. Establish baseline tests, metrics, and behavior.
  3. Define compatible API/event contracts.
  4. Extract the capability and its data ownership.
  5. Route a controlled slice of traffic to the new service.
  6. Validate errors, latency, business behavior, and data consistency.
  7. Increase traffic gradually and monitor.
  8. Retire the old implementation once consumers have migrated.

Challenges

  • Duplicate business logic during transition.
  • Dual writes and data synchronization.
  • Backward compatibility and routing mistakes.
  • Two active implementations lingering indefinitely.
Best practice: plan how the old path will be retired, not just how the new service will be created.

15. Circuit Breaker

Problem

A slow downstream dependency can exhaust upstream threads, connections, and memory. A circuit breaker observes call outcomes and temporarily stops calls when failure thresholds indicate that a dependency is unhealthy.

CLOSED calls are allowed | failure threshold v OPEN fail fast / block calls | wait duration v HALF-OPEN limited trial calls / \\ success failure | | v v CLOSED OPEN

Resilience4j example

@CircuitBreaker(
    name = "paymentService",
    fallbackMethod = "paymentFallback"
)
public PaymentResponse charge(PaymentRequest request) {
    return paymentClient.charge(request);
}

public PaymentResponse paymentFallback(
        PaymentRequest request, Throwable ex) {
    // Do not claim payment succeeded.
    throw new PaymentUnavailableException(
        "Payment outcome unavailable", ex
    );
}

What it does and does not do

  • OPEN temporarily prevents repeated calls to a failing dependency.
  • HALF-OPEN probes whether recovery has occurred.
  • It does not itself impose a network timeout.
  • It does not isolate all resource usage by itself.
  • It does not make an uncertain payment outcome safe to abandon.

Use a fallback only when it preserves the business contract. For optional recommendations, cached data may be suitable. For payment, a durable pending state and reconciliation may be safer.

16. Retry

Definition

Retry repeats an operation after a failure judged transient. It is useful for short-lived network errors or temporary overload, but can worsen an incident if unbounded or applied to non-idempotent operations.

Exponential backoff and jitter

Attempt 1 → transient failure → short wait Attempt 2 → transient failure → longer wait Attempt 3 → failure → stop / recovery queue Delay = min(cap, base × 2^attempt) + jitter

Jitter randomizes retry timing to prevent clients from retrying in synchronized bursts. Use bounded attempts, an overall deadline, and a retry budget.

Retry candidates

  • Temporary connection errors.
  • Selected 502, 503, or 504 responses.
  • 429 responses when retry timing is respected.
  • Transient database or broker failures.

Usually do not retry blindly

  • Invalid input, authentication, or authorization failures.
  • Business validation errors such as insufficient funds.
  • Permanent not-found conditions.
  • Non-idempotent external operations without a safe deduplication strategy.
Payment example: a request may time out after the provider has charged the card. Retrying with a new operation key can charge twice. Reuse the provider-supported idempotency key and reconcile uncertain results.

17. Timeout

Definition

A timeout bounds how long a caller waits for an operation. Without explicit timeouts, blocked remote calls may hold threads, connections, and memory indefinitely.

Timeout typePurpose
Connection timeoutLimits the time to establish a connection.
Read/response timeoutLimits waiting for response data according to client semantics.
Overall deadlineBounds the complete operation, including downstream calls.
Database query timeoutBounds query execution/waiting.
Message-processing timeout/leaseControls or detects stalled processing according to broker semantics.

Deadline propagation example

Overall request budget: 800 ms Gateway → Order Service: remaining 500 ms Order → Inventory: remaining 250 ms Order → Payment: remaining 200 ms

The values are illustrative. Downstream operations must not each consume the entire original deadline. Leave time for local processing and response delivery.

Production advice

  • Set explicit HTTP-client, database, and broker timeouts.
  • Align timeouts with service objectives and the overall request deadline.
  • Leave time for fallback and error handling.
  • A timeout is not proof the remote operation failed.
Critical distinction: a timed-out payment may still complete remotely. Timeout means the caller did not receive a timely response, not that no side effect happened.

18. Bulkhead

Definition

The bulkhead pattern isolates resource consumption so one slow dependency cannot consume all capacity needed by unrelated operations.

Checkout / Payment

Illustrative 60 slots

Recommendations

Illustrative 25 slots

Notifications

Illustrative 15 slots

Types

  • Thread-pool bulkhead: separate execution pool for dependency work. Helps isolate blocking calls but adds thread and queue overhead.
  • Semaphore bulkhead: caps concurrent executions using permits; lightweight but does not create a separate pool.

Design guidance

Configure concurrency limits and queue capacity deliberately. Oversized queues can delay failures and consume memory. Isolate the resources that actually saturate: threads, connections, CPU, memory, or downstream quotas. A bulkhead complements—not replaces—timeouts and circuit breakers.

19. Rate Limiting

Definition

Rate limiting restricts the number of requests a client, tenant, API key, or system can make over a time interval or quota.

Common algorithms

AlgorithmBehaviorTrade-off
Fixed windowCounts within fixed time windowsSimple; bursts can occur at window boundaries.
Sliding windowTracks/estimates usage over a moving intervalSmoother limits, more implementation cost.
Token bucketTokens replenish over time; requests consume tokensAllows controlled bursts.
Leaky bucketShapes traffic toward a controlled output rateUseful for smoothing traffic.

Token bucket example

Imagine capacity of 100 tokens with replenishment of 10 tokens per second. Each request costs one token. Requests can burst while tokens are available; excess requests are rejected or delayed until capacity returns. These values are illustrative.

Distributed rate limiting

If ten replicas each enforce 100 requests/minute locally, the combined allowance may be roughly 1,000 requests/minute. A global tenant quota needs a coordinated counter or gateway/platform mechanism with explicit consistency and failure semantics.

HTTP 429 Too Many Requests is commonly used for excess traffic; a Retry-After header may tell clients when to retry. Rate limiting protects APIs, login endpoints, expensive reports, and multi-tenant fairness.

20. Idempotency

Definition

An operation is idempotent when repeating it with the same intended input produces the same relevant final effect as performing it once. Setting a status to CANCELLED may be idempotent; charging a card is not inherently idempotent.

Client → Payment Service: charge ₹2,000 Provider charges card Response is lost Client retries Without idempotency → possible duplicate charge With same idempotency key → return existing operation/result

Idempotency-key strategy

POST /payments
Idempotency-Key: order-123-payment-attempt-1
  1. Enforce a unique key in the correct customer/operation scope.
  2. Associate the key with a request hash or equivalent input identity.
  3. Reject conflicting reuse of the same key.
  4. Persist operation state and result.
  5. Handle concurrent requests with the same key.
  6. Define retention/expiration behavior.
  7. Use provider-supported idempotency where available.

Idempotent event consumers

CREATE TABLE processed_events (
    event_id VARCHAR(100) PRIMARY KEY,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

Insert the event ID and apply the local business update in the same transaction. If the unique key already exists, skip the duplicate effect, following the consumer's acknowledgment and error-handling design.

Limit: a database deduplication table does not make an external email, payment, or HTTP side effect atomic. Coordinate those effects with their own idempotency support or reconciliation.

21. Distributed Transactions

Definition

A distributed transaction coordinates changes across multiple transactional resources. For example, an order database, payment database, and inventory database may all participate in one business workflow.

Order Database Payment Database Inventory Database | | | +--------------------+---------------------+ one business workflow

Two-phase commit (2PC)

  1. Prepare: a coordinator asks participants to prepare and retain the resources needed to commit.
  2. Commit/abort: the coordinator directs participants to finish or roll back.
Coordinator → Order DB: PREPARE Coordinator → Payment DB: PREPARE Order DB → Coordinator: YES Payment DB → Coordinator: YES Coordinator → participants: COMMIT

Trade-offs of 2PC

  • Prepared participants may retain locks or state while waiting.
  • Coordinator failures and network partitions complicate recovery.
  • Coordination increases latency.
  • External payment providers and many messaging integrations do not participate in a common XA transaction.
  • Long-running business workflows are poor candidates for holding distributed transactional resources.

2PC's behavior depends on its protocol and deployment; it is not accurate to summarize every distributed transaction as universally “choosing CP” in all senses of CAP.

Practical alternatives

  • Use one local transaction when changes belong to one service/resource.
  • Use a Saga for multi-step workflows with compensations.
  • Use a transactional outbox to atomically store local changes and a pending event.
  • Use idempotent consumers, durable messaging, and reconciliation.
  • Use distributed transactions only when their guarantees justify infrastructure and availability costs.

22. Transactional Outbox Pattern

Problem: dual writes

Saving an order and publishing an event are two separate operations. If the database write succeeds but Kafka publication fails, downstream services never learn about the order. If an event is published before the database transaction rolls back, consumers can observe a fact that was not committed.

Solution

Order Service | | one local ACID transaction v +-------------------------------+ | Local Database | | orders table | | outbox_events table | +---------------+---------------+ | polling / transaction log CDC | v Outbox Publisher | v Kafka | v Consumers

Example schema

CREATE TABLE outbox_events (
    event_id UUID PRIMARY KEY,
    aggregate_id UUID NOT NULL,
    event_type VARCHAR(100) NOT NULL,
    payload JSONB NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    published_at TIMESTAMPTZ
);

Spring service example

@Transactional
public void createOrder(Order order) {
    orderRepository.save(order);

    OutboxEvent event = OutboxEvent.orderCreated(
        order.getId(),
        order.getCustomerId()
    );

    outboxRepository.save(event);
}

An independent publisher sends unpublished rows to Kafka. It may use polling or change-data capture (CDC), for example with Debezium, depending on the architecture.

Guarantees and limitations

  • The business row and outbox record commit or roll back together in the same local transaction.
  • The publisher can retry after failures.
  • A crash after publishing but before marking the event published can cause duplicate publication.
  • Consumers therefore need idempotency; the outbox does not automatically guarantee exactly-once end-to-end business processing.
  • Define event ordering, retry, poison-event handling, monitoring, and outbox cleanup.

23. Distributed Tracing

Purpose

Distributed tracing connects individual operations belonging to one end-to-end request. It helps locate latency, errors, and unexpected dependency paths across services.

Trace: checkout request └── API Gateway span └── Order Service span ├── Inventory HTTP span ├── SQL query span └── Payment Service span └── Payment DB span

Core terms

  • Trace ID: identifies the complete trace.
  • Span ID: identifies one operation.
  • Parent span: links a child operation to its caller.
  • Trace context: carries identifiers and propagation metadata between services.
  • MDC: logging context used by SLF4J-compatible logging to add identifiers to log lines.

W3C Trace Context example

traceparent: 00-<trace-id>-<parent-span-id>-01

This is a format illustration; the placeholders are not actual IDs. Java services commonly use OpenTelemetry or Micrometer Tracing with a backend such as Jaeger, Grafana Tempo, or a commercial APM.

How to debug with a trace

  • Find the slowest spans and downstream waits.
  • Inspect retries, database queries, and connection-pool delays.
  • Compare traces with service-level latency and saturation metrics.
  • Use correlated logs for detailed error messages.

Sampling helps control cost. Propagate context across HTTP, messaging, and asynchronous boundaries. Do not place secrets or sensitive personal data in span attributes.

24. Correlation ID

Definition

A correlation ID associates logs, messages, and operations with a common business request or workflow. It is particularly useful for support investigations that span multiple services.

Correlation ID: checkout-abc123 Gateway → checkout-abc123 Order Service → checkout-abc123 Inventory → checkout-abc123 Payment → checkout-abc123

Correlation ID vs Trace ID

Correlation IDTrace ID
Application/business identifier for related activityIdentifier for one distributed trace
May span multiple requests, jobs, or tracesTypically identifies a single traced execution
Application-defined semanticsTracing-system propagation semantics

One order workflow can span several HTTP requests, message consumers, and scheduled jobs. It may have multiple trace IDs but share one business correlation ID.

Java logging example

try {
    MDC.put("correlationId", correlationId);
    log.info("Processing order {}", orderId);
} finally {
    MDC.remove("correlationId");
}

Configure the logging pattern to include the MDC value. Thread-local MDC does not automatically propagate through every asynchronous executor; use supported context propagation or instrumentation.

Security: never treat a client-provided correlation ID as identity or authorization. Validate its format and length, and generate a server-controlled ID when appropriate.

25. Health Checks

Why health checks matter

A process can be running while unable to serve requests. Health checks help orchestrators and monitoring systems distinguish application liveness, readiness, and startup state.

Liveness

Is the process alive and progressing, or stuck and potentially in need of restart?

Readiness

Can this instance accept requests now? It may be alive but still initializing.

Startup

Has initialization completed? Useful for applications with long startup periods.

Spring Boot Actuator endpoints

GET /actuator/health
GET /actuator/health/liveness
GET /actuator/health/readiness

Endpoint availability depends on Actuator dependencies and health-probe configuration.

Kubernetes example

livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 15
  periodSeconds: 10

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 5

Timings are illustrative; tune them to application startup and response characteristics.

Common mistakes

  • Making liveness fail whenever any downstream dependency is unavailable, triggering restart storms.
  • Allowing traffic before the application is ready.
  • Making every probe execute expensive deep checks against many dependencies.
  • Returning healthy unconditionally when critical operations cannot work.

Separate liveness, readiness, startup, and dependency-health semantics. Use probes to improve recovery rather than amplify an outage.

26. Service-to-Service Communication

Synchronous communication

HTTP/REST and gRPC are common request-response approaches. The caller generally waits for the response before continuing.

Order Service | | synchronous HTTP / gRPC v Payment Service | | response v Order Service continues

Benefits: immediate response and straightforward request/response contracts. Costs: network latency, downstream failure propagation, and latency multiplication through call chains.

Asynchronous communication

Kafka, RabbitMQ, and other messaging systems let a producer publish a message without waiting for a consumer to finish processing it.

Order Service | v Message Broker / Topic | v Payment Consumer | v Local transaction / result event

Benefits: temporal decoupling, buffering, and natural support for event-driven workflows. Costs: eventual consistency, duplicates, ordering concerns, and more complex debugging/recovery.

Choosing an approach

RequirementTypical fit
Read a price needed immediatelySynchronous query or local read model
Send a confirmation after order creationAsynchronous event
Reserve stock as part of checkoutSynchronous response or asynchronous Saga, based on business needs
Update analytics projectionsAsynchronous events
Long-running approval processDurable asynchronous workflow/orchestration
Important: asynchronous messaging does not automatically provide correctness. Define delivery semantics, idempotency, event ordering where required, observability, dead-letter handling, and recovery.

End-to-End Example: Checkout Architecture

1. Client sends checkout request | v 2. API Gateway authenticates and rate-limits | v 3. Order Service creates PENDING order | v 4. Local transaction writes order + outbox event | v 5. Outbox publisher publishes event to Kafka | +-----+------+ v v Inventory Payment reserve stock authorize payment | | +------+- ----+ v 6. Saga records progress and handles failures | v 7. Order status is updated; projections/notifications follow Throughout: timeouts, retries, circuit breakers, bulkheads, idempotency, trace context, correlation IDs, metrics and probes.

State and consistency

A real implementation must define its business states and recovery behavior. The customer may see PENDING while payment is being confirmed. A successful message publication is not proof that payment or inventory processing has completed. Only the workflow's validated state should determine whether an order is confirmed.

Production Failure Scenarios

Scenario 1 — Payment times out

Problem: The provider might have charged the card even though the response never arrived.

Response: Use explicit timeouts, durable payment-attempt state, a stable provider idempotency key, and reconciliation. Do not mark payment successful just because the request was sent, or failed solely because the caller timed out.

Scenario 2 — Kafka delivers duplicate events

Problem: Inventory reserves stock twice for one order.

Response: Use stable event IDs, atomically persist deduplication state with the local business change, and acknowledge messages according to durability requirements.

Scenario 3 — Recommendations become slow

Problem: Optional recommendation calls consume all Order Service threads.

Response: Use timeouts, circuit breakers, bulkheads, and cached optional data. Preserve capacity for critical checkout operations.

Scenario 4 — Inventory reserved, payment failed

Problem: Stock remains reserved for an unsuccessful order.

Response: Use a durable Saga, idempotent compensation, retries for failed release, and operator alerts for unresolved compensation.

Scenario 5 — Database schema changes

Problem: A consumer still expects the old field.

Response: Use expand-and-contract: add the new representation compatibly, migrate consumers, observe usage, then remove the old field only after it is safe.

Senior Java Backend Interview Q&A

1. Why choose a modular monolith instead of microservices?

A modular monolith reduces deployment and distributed-systems overhead while preserving business boundaries. Microservices are justified when independent deployment, scaling, ownership, or fault isolation benefits outweigh operational costs.

2. How do you maintain consistency across services without a global transaction?

Use local ACID transactions, Saga coordination, explicit business states, idempotent operations, durable messaging, and compensating actions. Reconciliation handles exceptional states that automated recovery cannot resolve.

3. How does the transactional outbox solve dual writes?

The business change and outbox event record commit in the same local transaction. A publisher later sends the event. Consumers still need idempotency because publication can be duplicated.

4. CQRS vs Event Sourcing?

CQRS separates command and query models. Event Sourcing persists state transitions as an event history. They can be combined but are separate concepts; neither should be introduced without a business need.

5. How do timeout, retry, circuit breaker, and bulkhead work together?

Timeout bounds waiting, retry handles eligible transient errors, circuit breaker stops repeated calls to an unhealthy dependency, and bulkhead isolates resource consumption. Retry must respect deadlines and idempotency.

6. How do you debug a slow checkout across six services?

Use tracing to find slow spans, metrics to identify saturation and latency trends, and correlated structured logs for detailed events. Inspect downstream waits, retries, connection pools, and database queries.

7. Why is a shared database risky?

Direct shared-table access couples schemas, business rules, permissions, and release schedules. Independent ownership avoids this coupling, although services may still share physical database infrastructure.

8. Correlation ID vs Trace ID?

A correlation ID groups activity for a business request or workflow. A trace ID identifies a distributed trace. One business workflow may span several traces.

9. What happens when Eureka self-preservation activates?

Eureka can avoid evicting too many instances after a sudden drop in heartbeat traffic, protecting against a network partition being mistaken for mass failure. The trade-off is that stale entries can remain, so client failure handling and health monitoring matter.

10. Why is a timeout not proof that a payment failed?

The request may have reached the provider and completed while its response was delayed or lost. The caller must preserve an uncertain state, query/reconcile the operation, and retry only with safe idempotency semantics.

11. What is the difference between liveness and readiness?

Liveness indicates whether a process should continue running or be restarted. Readiness indicates whether it should receive traffic. A temporarily unavailable downstream dependency should not automatically make every instance fail liveness.

12. Does Kafka guarantee exactly-once business processing?

Broker-level transactional or exactly-once features can provide specific guarantees within defined boundaries, but they do not automatically make arbitrary external side effects exactly once. Consumers still need correct transaction boundaries, idempotency, and recovery design.
