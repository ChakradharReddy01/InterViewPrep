1. Authentication

Plain-English explanation

Authentication answers “Who are you?” It verifies a claimed identity, such as a username/password, passkey, certificate, or identity-provider login. In Spring Security, authentication is represented by an Authentication object whose principal identifies the user and whose authorities describe granted permissions.

Explain it like I am a kid: Think of a school guard checking that you really are the student named on your card. A successful login proves identity; it does not automatically mean you can enter every room.

How it fits into a Spring Security application

Understand the identity proof and the trust boundary before choosing the authentication mechanism.

Thumb rules — remember these

  • Use a trusted identity store, generic login errors, throttling, MFA for sensitive accounts, secure password storage, and audit events. Never log passwords, access tokens, or refresh tokens.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

I separate identity verification from permissions. The client presents credentials, the server validates them, and successful authentication creates an authenticated principal for later authorization decisions.

2. Authorization

Plain-English explanation

Authorization decides whether an already identified principal may perform a particular action on a particular resource. It should be enforced server-side for every protected request, including object-level ownership checks.

Explain it like I am a kid: A school guard knows who you are, then checks whether your card lets you enter the science lab.

How it fits into a Spring Security application

Make the permission decision as close as practical to the protected operation.

Thumb rules — remember these

  • Default-deny, least privilege, check ownership as well as roles, and avoid trusting user IDs or roles sent in request bodies. A role check alone can still expose another user’s record.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

Authentication establishes who the caller is; authorization evaluates what that caller may do. I enforce authorization at request and, where appropriate, service/method and domain-resource levels.

3. Security Filter Chain

Plain-English explanation

Spring Security’s FilterChainProxy selects a matching SecurityFilterChain and runs its ordered servlet filters before the controller. Filters can load context, handle CORS/CSRF, authenticate credentials, translate exceptions, and authorize requests. Order and matcher configuration matter.

Explain it like I am a kid: Before a parcel reaches the right room, it passes several checkpoints in a fixed order.

How it fits into a Spring Security application

Treat configuration order and request matching as security-critical behavior.

Thumb rules — remember these

  • Prefer the modern SecurityFilterChain bean configuration. Define explicit matchers and a final catch-all chain. Multiple chains are selected by matcher order; a request usually runs one matching chain, not every chain. Avoid casually adding custom filters at the wrong position.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

A request enters the servlet container, then Spring Security’s filter chain. Authentication filters establish the principal; authorization filters check access; only an allowed request proceeds to MVC/controller handling.

4. SecurityContext

Plain-English explanation

SecurityContext holds the current Authentication. SecurityContextHolder exposes it to application code, commonly through a thread-local strategy during a servlet request. Spring Security’s filters manage loading, clearing, and persistence according to the configured setup.

Explain it like I am a kid: It is the temporary badge information available to the people handling one request.

How it fits into a Spring Security application

Read the established security context rather than trusting identity fields supplied by the caller.

Thumb rules — remember these

  • Do not assume thread-local context automatically follows work into @Async, executors, or message consumers. Use appropriate context-propagation mechanisms or pass identity/claims explicitly. Clear context to prevent leakage between reused threads.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

After authentication, the Authentication is stored in the SecurityContext. Application code can inspect the principal and authorities, but should not manually create a trusted authenticated identity from unverified input.

5. UserDetails

Plain-English explanation

UserDetails is Spring Security’s core representation of a user for username/password authentication. It exposes username, encoded password, authorities, and account-state flags. UserDetailsService loads it by username; it is not itself the database entity or a general OAuth user model.

Explain it like I am a kid: It is a small profile card the security system reads to verify a login and learn the user’s permissions.

How it fits into a Spring Security application

Load only the information required by the authentication mechanism and map permissions intentionally.

Thumb rules — remember these

  • Return authorities deliberately, avoid exposing password hashes in APIs, and distinguish disabled, locked, expired, and credential-expired states. A custom UserDetailsService typically throws UsernameNotFoundException when no user exists.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

I keep persistence entities separate from the security-facing UserDetails model when that improves boundaries, and connect UserDetailsService to AuthenticationProvider/DaoAuthenticationProvider.

6. Password Encoding

Plain-English explanation

Passwords should be stored as salted, computationally expensive one-way hashes, never plaintext or reversible encryption. PasswordEncoder encodes a raw password at registration and verifies a candidate during login with matches(raw, encoded).

Explain it like I am a kid: Keep a scrambled, hard-to-reverse fingerprint—not the actual key—in the database.

How it fits into a Spring Security application

Use a one-way adaptive hash and the PasswordEncoder contract.

Thumb rules — remember these

  • Use an adaptive password hashing algorithm, tune its work factor to your server, rehash after successful login when parameters become outdated, and never compare encoded strings directly because salts make hashes differ.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

Registration uses encode; login uses matches. I use Spring’s PasswordEncoder abstraction so the algorithm can evolve without changing business code.

7. BCrypt

Plain-English explanation

BCrypt is a widely used adaptive password hashing algorithm. Its cost factor controls computational work; a random salt is included in the encoded result. Spring Security provides BCryptPasswordEncoder. The appropriate cost depends on latency and hardware and should be benchmarked.

Explain it like I am a kid: It deliberately makes each password check slow enough to make mass guessing expensive.

How it fits into a Spring Security application

Benchmark the cost under realistic login traffic and monitor authentication failures.

Thumb rules — remember these

  • BCrypt is not encryption and cannot be decrypted. Set a cost that is secure but acceptable under real login load; protect login endpoints against brute force. Consider Argon2 where operationally supported and suitable.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

I use BCryptPasswordEncoder or a suitable modern adaptive encoder, call matches for verification, benchmark the work factor, and combine it with rate limiting and breached-password controls.

8. JWT

Plain-English explanation

JSON Web Token is a token format, often a signed compact set of claims. A signed JWT commonly has header.payload.signature. Signing lets a verifier detect tampering; it does not hide the payload. Validate signature, allowed algorithm, issuer, audience, expiry, not-before, and relevant claims.

Explain it like I am a kid: It is like a tamper-evident ticket carrying a few facts. Anyone holding it may be able to read those facts, so do not put secrets inside.

How it fits into a Spring Security application

Use a maintained library to validate the token rather than writing JWT cryptography yourself.

Thumb rules — remember these

  • Base64url is encoding, not encryption. Reject algorithm confusion, validate key rotation, keep claims minimal, use TLS, and plan revocation/compromise response. Do not trust decoded claims until signature and claims are validated.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

A JWT is a format, not an authentication strategy by itself. For APIs I validate its signature and required claims through a trusted resource-server configuration rather than manually decoding it.

9. Access Token

Plain-English explanation

An access token authorizes calls to a resource server and is usually short-lived. It may be an opaque token or a JWT. The API validates it according to the issuer’s protocol and policy, then checks scopes/authorities and resource permissions.

Explain it like I am a kid: It is a short-term entry pass for specific services.

How it fits into a Spring Security application

Send the token only to the intended resource server over TLS.

Thumb rules — remember these

  • Keep expiry short enough to limit exposure but practical for clients. Send over HTTPS in the Authorization: Bearer header; avoid URLs and logs. A bearer token can be used by whoever steals it.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

I treat access tokens as credentials. The resource server validates them and applies authorization; the frontend should not assume possession means every endpoint is allowed.

10. Refresh Token

Plain-English explanation

A refresh token is used with the authorization server to obtain new access tokens without asking the user to sign in again. It should be protected more strongly than an access token, stored only where appropriate, rotated where supported, and revoked on logout or suspicious reuse.

Explain it like I am a kid: The short-term pass expires; a protected renewal slip lets you request another pass.

How it fits into a Spring Security application

Keep renewal credentials out of ordinary API calls and protect them as long-lived secrets.

Thumb rules — remember these

  • Do not send refresh tokens to resource APIs. Use rotation and reuse detection, bind to client/session where supported, secure storage, expiration, and server-side revocation. Browser storage choices depend on the threat model; HttpOnly Secure cookies need CSRF consideration.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

Access tokens are presented to APIs; refresh tokens are presented to the authorization server. I use rotation/revocation and treat refresh-token theft as a session compromise.

11. Role-Based Access Control

Plain-English explanation

RBAC grants permissions through roles such as USER, SUPPORT, or ADMIN. In Spring Security, authorities can be checked in request rules or method security. By convention hasRole("ADMIN") checks for ROLE_ADMIN, while hasAuthority checks the exact authority string.

Explain it like I am a kid: A role is a bundle of permissions, like “librarian” or “teacher.”

How it fits into a Spring Security application

Translate business roles into narrowly scoped authorities.

Thumb rules — remember these

  • Avoid a single giant ADMIN role. Keep least privilege, define role naming consistently, and add ownership/tenant checks for data access. Roles are not a substitute for business-level authorization.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

I map users to roles and roles to authorities, use request rules for coarse access and method/domain checks for sensitive operations, and test both allowed and denied cases.

12. OAuth 2.0

Plain-English explanation

OAuth 2.0 is an authorization framework that lets a client obtain limited access to resources with delegated authorization. It defines roles such as resource owner, client, authorization server, and resource server. It is not, by itself, a user-authentication protocol.

Explain it like I am a kid: You let an app access only the specific things you approve, without giving that app your main password.

How it fits into a Spring Security application

Choose the OAuth grant based on client type and use case.

Thumb rules — remember these

  • Use Authorization Code with PKCE for interactive public clients. Avoid the implicit and resource-owner-password grants for new designs. Validate redirect URIs, state, scopes, and token handling; use client credentials for service-to-service when appropriate.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

OAuth2 answers how delegated access is granted. If I need to know who the user is, I pair the appropriate flow with OpenID Connect rather than assuming OAuth access tokens are login identity assertions.

13. OpenID Connect (OIDC)

Plain-English explanation

OIDC adds an identity layer on top of OAuth 2.0. It defines the ID Token and standard identity claims, plus discovery and user-info conventions. An ID token is for the client to learn about the authentication event; an access token is for calling APIs.

Explain it like I am a kid: OAuth gives permission to use a service; OIDC adds a standardized identity card about the signed-in user.

How it fits into a Spring Security application

Use the ID token for identity and the access token for API access.

Thumb rules — remember these

  • Validate ID token issuer, audience, signature, expiry, nonce when used, and flow-specific requirements. Do not send an ID token to an API as though it were an access token.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

For “Sign in with …” I use OIDC. The client validates the ID token under protocol rules, while APIs validate access tokens intended for them.

14. CORS

Plain-English explanation

Cross-Origin Resource Sharing is a browser-enforced policy that controls whether frontend JavaScript from one origin may read a response from another origin. The server expresses allowed origins, methods, headers, and credential behavior. CORS is not authentication and does not stop non-browser clients.

Explain it like I am a kid: A website asks another website whether scripts from its address may read the response.

How it fits into a Spring Security application

Configure allowed browser origins separately from access-control rules.

Thumb rules — remember these

  • Use specific trusted origins. Credentialed requests cannot use wildcard origin. Handle OPTIONS preflight and allow only necessary methods/headers. CORS does not replace authorization, CSRF defenses, or TLS.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

CORS controls browser cross-origin access. I configure it intentionally for known frontend origins and still secure every endpoint independently.

15. CSRF

Plain-English explanation

Cross-Site Request Forgery tricks a browser into sending an unwanted authenticated request to a site where the victim has a session or other automatically attached credentials. CSRF defenses include synchronizer tokens, cookie settings such as SameSite, origin checks where appropriate, and avoiding unsafe state changes on GET.

Explain it like I am a kid: A bad website tricks your browser into using the login badge it already carries.

How it fits into a Spring Security application

Protect state-changing requests when browsers automatically attach credentials.

Thumb rules — remember these

  • CSRF is especially relevant to cookie/session authentication. Stateless bearer tokens manually added by JavaScript have a different exposure profile, but token storage and browser behavior matter. Do not blindly disable CSRF without understanding credential transport and endpoints.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

I first identify how credentials are sent. Cookie-based browser sessions generally need CSRF protection for state-changing requests; CORS alone is not a CSRF defense.

16. Session Management

Plain-English explanation

In session-based authentication, the server tracks authenticated state and the browser typically carries a session identifier cookie. Session controls include creation, expiration, renewal, logout invalidation, fixation prevention, cookie flags, and concurrent-session policy. Distributed apps may need shared session storage.

Explain it like I am a kid: The browser keeps a numbered claim ticket; the server uses it to find the login session.

How it fits into a Spring Security application

Treat the session identifier as a secret and manage its full lifecycle.

Thumb rules — remember these

  • Use Secure, HttpOnly and suitable SameSite cookie attributes, rotate session ID after login/privilege change, expire idle and absolute sessions, invalidate on logout, and protect distributed session stores. Never put session IDs in URLs.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

I choose sessions when server-managed browser login is useful, protect the cookie and lifecycle, and account for horizontal scaling with a shared session store when required.

17. Method Security

Plain-English explanation

Method security applies authorization at Spring bean method invocation, for example with @EnableMethodSecurity and annotations such as @PreAuthorize, @PostAuthorize, @Secured, or @RolesAllowed where supported/configured. It is useful for service-layer and domain-sensitive checks.

Explain it like I am a kid: A locked front door is not enough; each important room can also check your badge.

How it fits into a Spring Security application

Place sensitive checks in a service method as well as appropriate HTTP rules.

Thumb rules — remember these

  • Ensure calls pass through Spring proxies; self-invocation can bypass proxy-based advice. Prefer explicit expressions, test method authorization, and avoid relying only on controller annotations for critical business rules.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

I use HTTP rules for endpoint-level access and method security for sensitive operations. I understand proxy boundaries and keep object ownership checks close to the data/business operation.

18. API Security

Plain-English explanation

API security combines transport protection, identity, authorization, input validation, abuse prevention, secret management, safe errors, logging, dependency hygiene, and operational response. Threats include broken object-level authorization, token theft, injection, replay, brute force, overexposure, and denial of service.

Explain it like I am a kid: The whole building needs secure doors, visitor checks, cameras, and rules—not just one lock at the entrance.

How it fits into a Spring Security application

Combine controls because no single security feature blocks every attack.

Thumb rules — remember these

  • Use HTTPS, least privilege, request validation, rate limits, quotas, timeouts, safe CORS/CSRF policy, secret rotation, security headers where applicable, audit logs without secrets, dependency updates, and negative security tests.
  • Use least privilege and fail closed when a required security check cannot be completed.
  • Write tests for both permitted and forbidden requests; a successful happy path is not enough.

Interview answer (30–60 seconds)

I use defense in depth: authenticate, authorize each resource/action, validate inputs, limit abuse, protect secrets and transport, observe suspicious behavior, and test failure paths.

Common mistakes and production thumb rules

1. Treating CORS as API security

CORS is a browser rule. A script or command-line client can still call the API, so every endpoint still needs authentication and authorization.

2. Assuming JWT payload is secret

Signed JWT claims are generally readable. Never place passwords, secrets, or unnecessary personal data in claims.

3. Checking role but not record ownership

A user role such as USER does not prove the requested order belongs to that user. Enforce tenant and object-level access checks.

4. Disabling CSRF without analyzing cookies

If browsers automatically attach session cookies or other credentials, state-changing endpoints may remain vulnerable. Choose controls based on the actual credential transport.

5. Storing passwords with plain SHA-256

Fast general-purpose hashes are unsuitable for password storage. Use an adaptive password encoder designed to make guessing expensive.

6. Logging secrets for debugging

Do not log passwords, bearer tokens, refresh tokens, session IDs, or authorization headers. Log safe identifiers and security outcomes instead.

7. Relying only on controller annotations

Service methods may be called from schedulers, message listeners, or other controllers. Put critical authorization close to the protected operation and test all entry paths.

Interview thumb rule: Explain the threat first, the control second, and the trade-off third. For example: “Cookie sessions are convenient for browser apps, but because the browser attaches cookies automatically, I include CSRF protection and secure cookie attributes.”

Interview questions and answers

Try answering each question aloud before opening the answer. Use a simple structure: definition → how it works → trade-off → production safeguard.

Authentication vs authorization?

Authentication verifies identity; authorization decides whether that identity may perform an action on a resource. A valid login does not imply access to every record.

What happens in the Spring Security filter chain?

A request is matched to a SecurityFilterChain and processed by ordered filters. Depending on configuration, filters load context, apply CORS/CSRF, authenticate, translate exceptions, and authorize before the request reaches the controller.

Why use PasswordEncoder.matches instead of comparing hashes?

Password hashes use salts and adaptive algorithms, so encoding the same raw password again may produce a different string. matches verifies the candidate against the stored encoded representation.

Is a JWT encrypted?

Not necessarily. A typical signed JWT is readable by whoever has it; the signature detects tampering but does not conceal claims. Validate signature and claims before trusting it.

Access token vs refresh token?

Access tokens are presented to resource APIs and are usually short-lived. Refresh tokens are presented to the authorization server to obtain new access tokens and need stronger storage, rotation, and revocation controls.

OAuth2 vs OIDC?

OAuth2 is for delegated authorization. OIDC adds standardized user authentication and identity claims, including an ID token.

CORS vs CSRF?

CORS governs whether browser JavaScript can read cross-origin responses. CSRF concerns unwanted authenticated requests caused by credentials the browser attaches automatically. They solve different problems.

When can CSRF protection be disabled?

Only after evaluating the actual credential transport and endpoint behavior. Cookie/session authentication usually needs CSRF protection for state-changing requests; do not disable it merely because an API is stateless or uses JSON.

hasRole vs hasAuthority?

hasRole("ADMIN") conventionally checks for ROLE_ADMIN; hasAuthority("invoice:read") checks the exact authority. Use a consistent naming scheme.

Why method security if URL security exists?

URL rules protect request paths, while method security protects service operations that may be called from multiple entry points. Critical checks should also enforce resource ownership and business constraints.

Can SecurityContext be relied on in @Async?

Not automatically in every setup. Thread-local context does not inherently propagate to arbitrary executor threads or message consumers. Configure supported context propagation or pass necessary identity explicitly.

How would you secure a production API?

Use TLS, trusted authentication, strict authorization including object ownership, validation, rate limits, safe token/session handling, secrets management, secure error/log practices, monitoring, dependency updates, and negative security tests.
