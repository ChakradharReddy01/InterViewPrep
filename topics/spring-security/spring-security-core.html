1. Authentication vs Authorization & The Core Security Model

1.1 Authentication vs Authorization

Enterprise security fundamentally bifurcates into two distinct operations:

  • Authentication (AuthN): "Who are you?" The process of verifying the claimed identity of a principal using supplied credentials (password, bearer token, client certificate, TOTP MFA). Result: an authenticated Authentication object with isAuthenticated() == true.
  • Authorization (AuthZ): "What are you permitted to do?" The process of evaluating whether an authenticated identity possesses the necessary rights (authorities, roles, scopes, attributes) to access a specific URI, method, or domain object.

1.2 Under the Hood: The Spring Security Authentication Subsystem

Authentication in Spring Security is handled by a chain of collaborating components. When an unauthenticated request arrives, it flows through: 

[ Incoming HTTP Request ]
          |
          v
[ DelegatingFilterProxy ] (Servlet Filter Bridge in web.xml / Spring context)
          |
          v
[ FilterChainProxy ] (Spring bean managing SecurityFilterChains)
          |
          v
[ SecurityFilterChain ] (Ordered list of ~15-30 Security Filters)
          |
          +---> [ Authentication Filter ] (e.g., JwtAuthenticationFilter / UsernamePasswordAuthFilter)
                     |
                     | Extracts credentials -> Creates unauthenticated AuthenticationToken
                     v
             [ AuthenticationManager ] (Interface: authenticate(Authentication))
                     |
                     v
             [ ProviderManager ] (Default implementation of AuthenticationManager)
                     |
                     +---> Iterates over List<AuthenticationProvider>
                     |        |
                     |        +--> DaoAuthenticationProvider (checks DB / UserDetailsService)
                     |        +--> JwtAuthenticationProvider (verifies RSA/HMAC signature)
                     |        +--> LdapAuthenticationProvider / OAuth2AuthenticationProvider
                     v
             [ UserDetailsService ] (Queries DB / Cache -> returns UserDetails)
                     |
             [ PasswordEncoder ] (BCrypt / Argon2 matches raw password with hash)
                     |
                     v
    [ Authenticated Authentication Object ] (Principal + GrantedAuthorities)
                     |
                     v
    [ SecurityContextHolder ] (Stored in ThreadLocal for request duration)

1.3 The Core Interfaces

  • Authentication: Represents the token for an authentication request or for an authenticated principal. Key methods: getPrincipal() (user entity/DTO), getCredentials() (cleared after authentication), getAuthorities() (collection of GrantedAuthority), and isAuthenticated().
  • SecurityContext: Holds the currently authenticated Authentication object. Associated with the current thread of execution.
  • SecurityContextHolder: Provides static access to the current SecurityContext.
  • AuthenticationManager & ProviderManager: The primary API for authentication. ProviderManager delegates to a list of configured AuthenticationProvider instances. If one provider successfully authenticates, it returns a fully populated Authentication object; if none can authenticate, it throws AuthenticationException.

2. The Security Filter Chain & DelegatingFilterProxy

2.1 How Spring Bridges Servlet Filters into the Spring Context

The standard Java Servlet specification does not know about the Spring IoC container. To allow Spring beans to intercept HTTP requests as standard Servlet Filters, Spring Security introduces DelegatingFilterProxy:

  • DelegatingFilterProxy: A standard Servlet filter registered with the servlet container (Tomcat/Jetty). It looks up a Spring bean named springSecurityFilterChain inside the ApplicationContext and delegates every incoming request to it.
  • FilterChainProxy: The Spring bean implementing Filter. It contains one or more SecurityFilterChain instances matched by RequestMatcher (e.g., one chain for /api/** and another for /actuator/**).

2.2 The Canonical Filter Ordering (Spring Security 6.x)

Order matters critically. If a filter executes out of order (such as checking authorization before extracting a JWT), requests fail unpredictably. Below is the standard runtime sequence:

Order Filter Name Responsibility
1 ChannelProcessingFilter Enforces HTTPS / SSL redirection if configured.
2 CorsFilter Handles preflight HTTP OPTIONS requests and attaches CORS response headers before security checks run.
3 SecurityContextHolderFilter Loads existing SecurityContext from repository (replaces legacy SecurityContextPersistenceFilter in Spring Security 6).
4 HeaderWriterFilter Attaches secure headers: X-Content-Type-Options: nosniff, X-Frame-Options: DENY, HSTS.
5 CsrfFilter Generates and validates Synchronizer CSRF tokens for mutating requests (POST, PUT, DELETE).
6 LogoutFilter Handles /logout requests, clears SecurityContext and invalidates sessions.
7 UsernamePasswordAuthenticationFilter Intercepts form-login POST submissions (e.g. /login) and initiates authentication.
8 Custom JwtAuthenticationFilter Intercepts Authorization: Bearer <token>, validates cryptographic signature, sets SecurityContext.
9 BearerTokenAuthenticationFilter / OAuth2LoginAuthenticationFilter OAuth2 resource server / OIDC login interceptors.
10 ExceptionTranslationFilter Catches downstream AuthenticationException (triggers AuthenticationEntryPoint 401) and AccessDeniedException (triggers AccessDeniedHandler 403).
11 AuthorizationFilter Final gatekeeper (replaces legacy FilterSecurityInterceptor). Evaluates URI authorization rules against authenticated authorities.

2.3 Modern Spring Security 6.x Configuration (Lambda DSL)

In Spring Security 6.x (Spring Boot 3.x), WebSecurityConfigurerAdapter is completely removed. Configuration is expressed as a @Bean SecurityFilterChain using the lambda DSL: 

@Configuration
@EnableWebSecurity
@EnableMethodSecurity(prePostEnabled = true) // Enables @PreAuthorize, @PostAuthorize
public class SecurityConfiguration {

    private final JwtAuthenticationFilter jwtAuthFilter;
    private final AuthenticationProvider authenticationProvider;
    private final CustomAuthenticationEntryPoint authEntryPoint;
    private final CustomAccessDeniedHandler accessDeniedHandler;

    public SecurityConfiguration(JwtAuthenticationFilter jwtAuthFilter,
                                 AuthenticationProvider authenticationProvider,
                                 CustomAuthenticationEntryPoint authEntryPoint,
                                 CustomAccessDeniedHandler accessDeniedHandler) {
        this.jwtAuthFilter = jwtAuthFilter;
        this.authenticationProvider = authenticationProvider;
        this.authEntryPoint = authEntryPoint;
        this.accessDeniedHandler = accessDeniedHandler;
    }

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        return http
            // 1. CORS enabled with custom configuration
            .cors(Customizer.withDefaults())
            // 2. CSRF disabled for stateless REST APIs using JWT
            .csrf(AbstractHttpConfigurer::disable)
            // 3. Stateless Session Management (No HttpSession stored on server)
            .sessionManagement(session -> 
                session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            // 4. Exception Handling for 401 and 403
            .exceptionHandling(exceptions -> exceptions
                .authenticationEntryPoint(authEntryPoint)
                .accessDeniedHandler(accessDeniedHandler)
            )
            // 5. URL Authorization rules
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/v1/auth/**", "/actuator/health", "/v3/api-docs/**").permitAll()
                .requestMatchers(HttpMethod.GET, "/api/v1/products/**").permitAll()
                .requestMatchers("/api/v1/admin/**").hasRole("ADMIN")
                .requestMatchers("/api/v1/orders/**").hasAnyRole("USER", "ADMIN")
                .anyRequest().authenticated()
            )
            // 6. Pluggable AuthenticationProvider
            .authenticationProvider(authenticationProvider)
            // 7. Insert JWT filter before UsernamePasswordAuthenticationFilter
            .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class)
            .build();
    }
}

3. SecurityContext & ThreadLocal Storage Strategies

3.1 How SecurityContextHolder Works Under the Hood

By default, SecurityContextHolder uses a ThreadLocal strategy to store the SecurityContext. When a Tomcat worker thread picks up an HTTP request, the security filter populates the thread's local map: 

// Retrieving current authenticated principal anywhere in the call stack
Authentication authentication = SecurityContextHolder.getContext().getAuthentication();
if (authentication != null && authentication.isAuthenticated()) {
    String username = authentication.getName();
    Collection<? extends GrantedAuthority> authorities = authentication.getAuthorities();
    CustomUserDetails userDetails = (CustomUserDetails) authentication.getPrincipal();
}

3.2 The Three Storage Modes

Configured via system property spring.security.strategy or SecurityContextHolder.setStrategyName(...):

  • MODE_THREADLOCAL (Default): The security context is bound exclusively to the executing thread. Thread pool reuse requires explicit clearing at request termination by SecurityContextHolderFilter.
  • MODE_INHERITABLETHREADLOCAL: Spawns an InheritableThreadLocal. Child threads spawned directly by the parent thread inherit the security context. Warning: Dangerous in pooled worker environments (e.g. ForkJoinPool or ExecutorService) because threads are reused across distinct requests, leading to context bleeding.
  • MODE_GLOBAL: A single JVM-wide SecurityContext. Used strictly for standalone desktop Swing/JavaFX applications.
⚠️ The Async Thread Pool Pitfall (@Async & CompletableFuture)

When a method annotated with @Async or executed via CompletableFuture.supplyAsync() runs, it executes on a separate worker thread from an executor pool. By default, SecurityContextHolder.getContext().getAuthentication() on that thread returns null!

The Enterprise Fix: Wrap your task executor in Spring's DelegatingSecurityContextAsyncTaskExecutor: 

@Bean(name = "applicationTaskExecutor")
public AsyncTaskExecutor applicationTaskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.setCorePoolSize(10);
    executor.setMaxPoolSize(50);
    executor.setThreadNamePrefix("async-sec-");
    executor.initialize();
    // Automatically propagates parent SecurityContext to worker thread and cleans it up
    return new DelegatingSecurityContextAsyncTaskExecutor(executor);
}

4. UserDetails, UserDetailsService & Password Encoding (BCrypt)

4.1 UserDetails & UserDetailsService Contract

Spring Security decouples your database ORM schema from framework security through the UserDetails and UserDetailsService interfaces: 

@Service
public class JpaUserDetailsService implements UserDetailsService {

    private final UserRepository userRepository;

    public JpaUserDetailsService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    @Override
    @Transactional(readOnly = true)
    public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {
        User user = userRepository.findByEmail(username)
            .orElseThrow(() -> new UsernameNotFoundException("User not found with email: " + username));

        return new SecurityUser(user);
    }
}

// UserDetails adapter wrapping domain entity
public class SecurityUser implements UserDetails {

    private final User user;

    public SecurityUser(User user) {
        this.user = user;
    }

    @Override
    public Collection<? extends GrantedAuthority> getAuthorities() {
        return user.getRoles().stream()
            .map(role -> new SimpleGrantedAuthority("ROLE_" + role.getName()))
            .collect(Collectors.toSet());
    }

    @Override public String getPassword() { return user.getPasswordHash(); }
    @Override public String getUsername() { return user.getEmail(); }
    @Override public boolean isAccountNonExpired() { return true; }
    @Override public boolean isAccountNonLocked() { return !user.isLocked(); }
    @Override public boolean isCredentialsNonExpired() { return true; }
    @Override public boolean isEnabled() { return user.isActive(); }
}

4.2 Password Encoding: The Mathematics of BCrypt

Plain SHA-256 or MD5 hashes are fatally insecure for passwords because modern GPUs can compute over 100 billion SHA-256 hashes per second, rendering rainbow tables and brute force trivially fast.

BCrypt is an adaptive, slow hashing algorithm based on the Blowfish cipher. It incorporates:

  • A cryptographically random 128-bit Salt: Prevents precomputed rainbow table attacks. Each hash has a unique salt embedded in it.
  • Adaptive Work Factor (Cost): Expressed as $2^{\text{cost}}$ iterations. A cost of 10 means $2^{10} = 1024$ rounds. A cost of 12 means $2^{12} = 4096$ rounds (4x slower).
  • Time-Constant Comparison: matches(raw, hash) executes in constant time to prevent side-channel timing attacks.
BCrypt Hash Anatomy:
$2a$12$e8kGv0jZ5L4xY3v2b1a9u.OqX8H5VnLp7k2J1s4F7d0Q3g6h9k2Lm
\__/ \/ \____________________/\____________________________/
 |    |           |                         |
 |    |           +- 22 char 128-bit Salt   +- 31 char Blowfish Hash
 |    +- Cost Factor (12 = 4096 rounds)
 +- Algorithm Identifier ($2a, $2b, $2y)
@Bean
public PasswordEncoder passwordEncoder() {
    // Work factor 12 is optimal for enterprise servers (targets ~200-300ms per verification)
    return new BCryptPasswordEncoder(12);
}

5. JWT Architecture, Access Tokens & Refresh Token Rotation

5.1 Anatomy of a JSON Web Token (RFC 7519)

A JWT consists of three base64url-encoded components separated by dots (.): 

[ Header (Base64Url) ] . [ Payload (Claims) ] . [ Cryptographic Signature ]

Header:    {"alg": "HS256", "typ": "JWT"}
Payload:   {"sub": "user_8912", "roles": ["ROLE_ADMIN"], "iat": 1700000000, "exp": 1700000900}
Signature: HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), secretKey)

5.2 Symmetric (HMAC-SHA256) vs Asymmetric (RSA/ECDSA) Signing

  • Symmetric (HS256/HS512): A single shared secret key is used both by the Auth service to sign the token and by downstream microservices to verify it. Risk: Any microservice with the secret can forge valid tokens.
  • Asymmetric (RS256/ES256): The Auth Server signs the JWT using a Private Key. All downstream resource servers verify the signature using the Auth Server's Public Key (exposed via JWKS endpoint: /.well-known/jwks.json). Public keys can be shared freely with zero forgery risk.

5.3 The Dual-Token Pattern: Access Token + Refresh Token Rotation

Stateless JWTs cannot be revoked natively until they expire. If an attacker steals a 24-hour token, they have full access for 24 hours.

The Enterprise Solution:

  1. Access Token: Short-lived (5 to 15 minutes), kept in memory (JS variable), stateless verification by microservices.
  2. Refresh Token: Long-lived (7 to 30 days), stored in an HttpOnly, Secure, SameSite=Strict cookie or Redis database.
  3. Automatic Token Rotation: Every time a refresh token is used to issue a new access token, the old refresh token is invalidated and a brand new refresh token is issued. If a revoked refresh token is presented, all tokens belonging to that user family are immediately purged (Breach Detection).
@Component
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    private final JwtTokenService jwtTokenService;
    private final UserDetailsService userDetailsService;
    private final HandlerExceptionResolver handlerExceptionResolver;

    public JwtAuthenticationFilter(JwtTokenService jwtTokenService,
                                   UserDetailsService userDetailsService,
                                   @Qualifier("handlerExceptionResolver") HandlerExceptionResolver handlerExceptionResolver) {
        this.jwtTokenService = jwtTokenService;
        this.userDetailsService = userDetailsService;
        this.handlerExceptionResolver = handlerExceptionResolver;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {
        final String authHeader = request.getHeader(HttpHeaders.AUTHORIZATION);

        // 1. Guard against non-Bearer requests
        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            filterChain.doFilter(request, response);
            return;
        }

        try {
            final String jwt = authHeader.substring(7);
            final String userEmail = jwtTokenService.extractUsername(jwt);

            // 2. Authenticate if username valid and SecurityContext is unauthenticated
            if (userEmail != null && SecurityContextHolder.getContext().getAuthentication() == null) {
                UserDetails userDetails = this.userDetailsService.loadUserByUsername(userEmail);

                if (jwtTokenService.isTokenValid(jwt, userDetails)) {
                    UsernamePasswordAuthenticationToken authToken = new UsernamePasswordAuthenticationToken(
                        userDetails,
                        null,
                        userDetails.getAuthorities()
                    );
                    authToken.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));
                    // 3. Set authenticated state into ThreadLocal SecurityContext
                    SecurityContextHolder.getContext().setAuthentication(authToken);
                }
            }
            filterChain.doFilter(request, response);
        } catch (Exception ex) {
            // Forward JWT expiry or signature errors directly to RestControllerAdvice
            handlerExceptionResolver.resolveException(request, response, null, ex);
        }
    }
}

6. Role-Based Access Control (RBAC) & Method Security

6.1 hasRole() vs hasAuthority()

A classic senior interview question:

  • hasAuthority("PRIVILEGE_NAME"): Checks the exact string inside GrantedAuthority.getAuthority() with no modification. Example: hasAuthority("READ_PRIVILEGES").
  • hasRole("ROLE_NAME"): Automatically prefixes the parameter with ROLE_. Example: calling hasRole("ADMIN") searches for authority ROLE_ADMIN. If your database authority is ADMIN without the prefix, hasRole("ADMIN") evaluates to false!

6.2 Method-Level Security: @PreAuthorize & SpEL Expressions

Enabled via @EnableMethodSecurity(prePostEnabled = true). Operates using Spring AOP method interceptors (dynamic proxying) to evaluate authorization logic before or after business methods: 

@Service
public class OrderService {

    // 1. Role check
    @PreAuthorize("hasRole('ADMIN')")
    public void cancelAnyOrder(Long orderId) { /* ... */ }

    // 2. Ownership check: evaluate method argument against authenticated principal
    @PreAuthorize("hasRole('ADMIN') or #userId == authentication.principal.id")
    public OrderResponse getOrderForUser(Long userId, Long orderId) {
        return orderRepository.findByUserIdAndOrderId(userId, orderId);
    }

    // 3. Post-execution filtering: Inspect returned object before client receives it
    @PostAuthorize("returnObject.ownerUsername == authentication.name")
    public Order getOrderDetails(Long orderId) {
        return orderRepository.findById(orderId).orElseThrow();
    }

    // 4. In-flight collection filtering: Remove unauthorized items from list argument
    @PreFilter("filterObject.companyId == authentication.principal.companyId")
    public void bulkUpdateOrders(List<OrderUpdateDto> orders) {
        // Only orders matching user's company survive the filter
    }
}

7. OAuth2 & OpenID Connect (OIDC) Architecture

7.1 OAuth2 vs OpenID Connect

  • OAuth 2.0 (RFC 6749): An authorization framework that delegates access to third-party applications without sharing passwords. It issues Access Tokens. It does not standardize user identity.
  • OpenID Connect (OIDC): An identity layer built on top of OAuth 2.0. In addition to an Access Token, it returns an ID Token (always a signed JWT) containing verified user identity claims (email, name, sub).

7.2 The 4 OAuth2 Roles

  1. Resource Owner: The end user who owns the data.
  2. Client: The application (e.g. React SPA, mobile app, backend service) requesting access.
  3. Authorization Server: Issues tokens upon user authentication (e.g., Keycloak, Okta, Auth0, Google Identity).
  4. Resource Server: The protected API (e.g., your Spring Boot microservices) validating tokens and serving resources.

7.3 Authorization Code Flow with PKCE (Proof Key for Code Exchange)

The industry standard for all clients (SPAs, mobile, and web apps): 

[ Browser / Client ]       [ Authorization Server ]        [ Spring Boot API ]
        |                              |                            |
        | 1. Generate code_verifier    |                            |
        |    and code_challenge (SHA256)                            |
        | 2. GET /authorize?           |                            |
        |    code_challenge=xyz...     |                            |
        +----------------------------->|                            |
        |   (User logs in & consents)  |                            |
        | 3. Redirect back with 'code' |                            |
        |<-----------------------------+                            |
        |                              |                            |
        | 4. POST /oauth/token         |                            |
        |    (code + code_verifier)    |                            |
        +----------------------------->|                            |
        |   (Auth Server verifies hash)|                            |

8. CORS & CSRF Under-the-Hood Mechanics

8.1 Cross-Origin Resource Sharing (CORS)

CORS is an enforcement mechanism implemented by web browsers, not servers, according to the Same-Origin Policy (protocol, domain, and port must match).

  • Preflight Request (HTTP OPTIONS): Sent by browsers prior to "non-simple" requests (custom headers like Authorization, or methods like PUT, DELETE, PATCH).
  • Mandatory Response Headers:
    • Access-Control-Allow-Origin: https://app.company.com (Never use * in production when credentials are sent!)
    • Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
    • Access-Control-Allow-Headers: Authorization, Content-Type, X-Correlation-ID
    • Access-Control-Allow-Credentials: true (Allows browser to include cookies/auth tokens)
@Bean
public CorsConfigurationSource corsConfigurationSource() {
    CorsConfiguration configuration = new CorsConfiguration();
    configuration.setAllowedOrigins(List.of("https://app.company.com", "https://admin.company.com"));
    configuration.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
    configuration.setAllowedHeaders(List.of("Authorization", "Content-Type", "X-Requested-With", "X-Trace-Id"));
    configuration.setAllowCredentials(true);
    configuration.setMaxAge(3600L); // Cache preflight response for 1 hour

    UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
    source.registerCorsConfiguration("/**", configuration);
    return source;
}

8.2 Cross-Site Request Forgery (CSRF)

CSRF exploits the browser's automatic inclusion of session cookies with every cross-site request: 

User logs into bank.com (Session cookie stored in browser)
  |
User visits malicious.com in another tab
  |
malicious.com triggers: <form action="https://bank.com/transfer" method="POST">
  |
Browser automatically attaches bank.com session cookie!
  |
bank.com executes transfer unless protected by CSRF token!
💡 Why disable CSRF for Stateless JWT APIs?

When an API is completely stateless (SessionCreationPolicy.STATELESS) and clients store JWT tokens in memory or JavaScript variables, passing them via the Authorization: Bearer <token> header:

Browsers NEVER automatically attach custom HTTP headers to cross-site requests! A malicious site cannot force a victim's browser to send a custom Authorization: Bearer header. Therefore, CSRF protection is mathematically redundant and safely disabled (csrf(AbstractHttpConfigurer::disable)).

Crucial Caveat: If your application stores JWTs in automatic browser cookies without SameSite=Strict, you MUST still enable CSRF protection!

9. Session Management & Session Fixation Protection

9.1 Session Creation Policies

  • STATELESS: Spring Security will never create or use an HttpSession. Ideal for REST microservices and JWT authentication.
  • IF_REQUIRED (Default): Creates an HttpSession only if authentication requires one (e.g., standard web UI).
  • ALWAYS: Always creates an HttpSession if one does not exist.
  • NEVER: Spring Security will never create an HttpSession, but will use one if it already exists.

9.2 Session Fixation Defense

Session Fixation Attack: An attacker obtains a valid session ID from a site, tricks a victim into authenticating using that session ID, and then hijacks the authenticated session.

Spring's Defense: sessionManagement().sessionFixation().migrateSession() (default). Upon successful login, Spring immediately invalidates the old session ID, creates a brand new session ID, and migrates all existing session attributes over.

9.3 Concurrent Session Control

http.sessionManagement(session -> session
    .maximumSessions(1) // Allows only 1 active session per user account
    .maxSessionsPreventsLogin(true) // Second login attempt rejected (or false to boot first session)
    .sessionRegistry(sessionRegistry())
);

10. Zero-Trust API Defense & Security Headers

10.1 Defense-in-Depth Best Practices

  1. Enforce Mutual TLS (mTLS): Zero Trust inside Kubernetes clusters. Envoy/Istio service meshes authenticate service-to-service communication via X.509 certificates.
  2. Rate Limiting & Throttling: Guard against brute force credential stuffing on /api/v1/auth/login using Redis Token Bucket (Bucket4j).
  3. Sanitize Error Payloads: Never return stack traces, DB vendor errors, or class names to the client (RFC 7807 ProblemDetail).
  4. Principle of Least Privilege: Microservices should only request and receive minimal OAuth2 scopes (e.g. read:orders instead of wildcard).

10.2 Mandatory Security Headers

http.headers(headers -> headers
    .contentSecurityPolicy(csp -> csp.policyDirectives("default-src 'self'"))
    .frameOptions(HeadersConfigurer.FrameOptionsConfig::deny)
    .xssProtection(HeadersConfigurer.XXssConfig::disable) // Deprecated in modern browsers, replaced by CSP
    .httpStrictTransportSecurity(hsts -> hsts
        .includeSubDomains(true)
        .maxAgeInSeconds(31536000))
);

11. Real-World Production War Stories (RCA & Fixes)

🚨 Incident 1: Cross-Origin Preflight (OPTIONS) 401 Outage in Production

Environment: React Single Page App + Spring Boot 3.2 Gateway & Microservices.

The Failure: After deploying a security upgrade, all frontend cross-origin POST and PUT requests failed immediately with 401 Unauthorized or 403 Forbidden. GET requests mysteriously worked.

Root Cause Analysis (RCA):

  • The frontend added a custom header: Authorization: Bearer .... The browser automatically sent an HTTP OPTIONS preflight request before every mutating request.
  • Per W3C specs, browsers never send credentials (Authorization header) with preflight OPTIONS requests.
  • The Spring Security filter chain was configured with .anyRequest().authenticated(), but CORS was either declared in a separate MVC WebMvcConfigurer or ordered after the Spring Security filter chain.
  • Spring Security intercepted the unauthenticated OPTIONS request and promptly rejected it with 401 Unauthorized before the CORS filter could ever evaluate it!

The Fix: Integrate CORS directly inside the SecurityFilterChain bean and register CorsConfigurationSource:

// Inside SecurityFilterChain definition:
http
    .cors(Customizer.withDefaults()) // Uses corsConfigurationSource bean FIRST
    .authorizeHttpRequests(auth -> auth
        .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll() // Explicit permit for preflights
        .anyRequest().authenticated()
    );
🚨 Incident 2: 100% CPU Spike & Thread Starvation via Over-Tuned BCrypt Cost Factor

Environment: High-traffic e-commerce login service under a Black Friday surge.

The Failure: As traffic increased to 1,500 req/sec, all Kubernetes pods spiked to 100% CPU utilization. Response times jumped from 80ms to over 25 seconds, triggering cascading gateway 504 timeouts and pod crash-loops.

Root Cause Analysis (RCA):

  • A security engineer had changed the BCrypt strength to new BCryptPasswordEncoder(15) to comply with a paranoid compliance checklist.
  • BCrypt cost is logarithmic: $2^{15} = 32,768$ rounds. On production server CPUs, a single password verification took ~1.4 seconds of dedicated CPU core execution.
  • With Tomcat configured for 200 worker threads, 200 concurrent login requests consumed 100% of the node's CPU cores for 1.4 seconds continuously. Subsequent requests queued indefinitely, exhausting thread pools and starving health-check probes.

The Fix: Lower the work factor to 10 or 12 (which takes ~80-150ms per verification) and deploy a Redis-based rate-limiter in front of /api/v1/auth/login to cap brute-force attempts without starving the JVM.

🚨 Incident 3: Critical SecurityContext Leakage Across Async Threads

Environment: SaaS Banking platform processing asynchronous financial reconciliations.

The Failure: Audit logs revealed that user reports generated via @Async methods intermittently exposed financial data belonging to completely different corporate tenants!

Root Cause Analysis (RCA):

  • The developers switched the strategy to SecurityContextHolder.MODE_INHERITABLETHREADLOCAL thinking it would solve context sharing with @Async tasks.
  • The application utilized a pooled ThreadPoolTaskExecutor. In pooled thread pools, threads are never destroyed; they are returned to the pool and reused for subsequent tasks from different HTTP requests!
  • InheritableThreadLocal copies the context only upon thread creation. When a pooled thread finished Task A (User Alice) and was later assigned Task B (User Bob), it retained Alice's old security context, causing Bob's task to execute under Alice's identity!

The Fix: Revert strategy to standard MODE_THREADLOCAL and wrap executors with DelegatingSecurityContextAsyncTaskExecutor, ensuring context is propagated per-task and purged upon task completion:

@Bean
public Executor taskExecutor() {
    ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
    executor.initialize();
    return new DelegatingSecurityContextAsyncTaskExecutor(executor);
}

12. Senior & Staff Engineer Interview Q&A

Q1: How does Spring Security 6.x differ from Spring Security 5.x architecture?

Answer: Key architectural shifts in version 6 (Spring Boot 3.x):

  1. Removal of WebSecurityConfigurerAdapter: All configuration is now component-based using @Bean SecurityFilterChain and lambda DSL.
  2. Deprecation of antMatchers() and authorizeRequests(): Replaced by authorizeHttpRequests() and requestMatchers(), which provides unified matching across MVC patterns, regex, and DispatcherServlet paths.
  3. Replacement of SecurityContextPersistenceFilter: Replaced by SecurityContextHolderFilter, which changes context saving from implicit auto-save on request exit to explicit saving via SecurityContextRepository.
  4. Removal of legacy FilterSecurityInterceptor: Replaced by the more performant AuthorizationFilter.
  5. Modern Method Security: @EnableGlobalMethodSecurity is deprecated in favor of @EnableMethodSecurity.
Q2: How do you invalidate or revoke a stateless JWT before its expiration timestamp?

Answer: Because JWT verification is cryptographic and decoupled from database lookups, native revoking is an architectural trade-off. Common solutions in production:

  • Token Blacklisting with Redis (TTL): When a user logs out, store the JWT ID (jti claim) in Redis with a TTL equal to the token's remaining lifespan. The JwtAuthenticationFilter checks Redis (O(1) memory lookup). If present, reject with 401.
  • Short-lived Access Tokens (5-10 min) + Revocable Refresh Tokens: Accept that access tokens expire quickly. Invalidate only the refresh token in the database/Redis, preventing token renewals upon logout or credential reset.
  • Token Versioning (Generation Counter): Store a token_version integer on the user entity and include it in the JWT payload. Incrementing the user's version in the DB immediately invalidates all tokens signed with older versions.
Q3: Why should passwords never be compared using String.equals()?

Answer: String.equals() compares strings character-by-character from left to right and returns false as soon as a mismatch is detected (short-circuit evaluation).

An attacker can measure microsecond differences in server response latency (a Side-Channel Timing Attack) to deduce how many initial characters of the password or hash were correct. Passwords and cryptographic digests must always be verified using constant-time comparison algorithms (e.g. MessageDigest.isEqual() or BCrypt.checkpw()), which always examine every byte regardless of where the mismatch occurs.

Q4: What is the difference between OAuth2 Scopes and Spring Security Roles?

Answer:

  • Roles (RBAC): Define what an identity/user is allowed to do within the system based on their job function (e.g., ROLE_ADMIN can delete accounts).
  • OAuth2 Scopes: Define the boundaries of permissions delegated to a third-party client application. A user might be an ADMIN, but when authorising a mobile app with scope read:profile, the app is only granted read access. The resulting permission is the intersection of user privileges and granted scopes.
